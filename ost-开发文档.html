01 一句话摘要

天枢已拥有 dsh 的两块地基(工具目录插件系统 + provider 接缝),缺的是中间胶水—— 一个对齐 Cordis 的极简 ctx(约 200 行,零新依赖)、一套带否决语义的事件扩展点、一份装配清单。

03 dsh 的底牌: Cordis 是什么设计

Cordis 是 dsh 底下真正干活的插件框架(官称 Meta-Framework of Spatiotemporal Composability,配套论文 arXiv 2608.25512)。 它的全部主张可缩成 五个想法——不是"依赖注入容器",而是:

插件组合 = 可回卷的效果;上下文 = 一棵服务组成的时间树。

① 插件 = 实现 Service 的东西

一个函数(可选 inject/apply(ctx))或一个 Service 子类,交给 Cordis 挂载。没有魔法、没有基类。

export default {
  inject: ['llm', 'tools'],      // ③ 等它们存在才 activate
  apply(ctx) {                   // ② 从 ctx 认领/挂服务、事件
    ...
  }
}

② Context = 服务的仓库

服务认领稳定的 ctx.<key>(ctx.tools、ctx.llm…)。别人靠 key 找服务,不靠 import。换 provider = 往 ctx.llm 挂新 adapter,消费者无感知。

ctx.tools.register(tool)   // 我提供
ctx.inject(['tools'])      // 我需要
// 不 import,只按 key 协作

③ 依赖用 inject 声明,不手工排序

命名所需服务的插件等到服务就位才激活。装配顺序由依赖推导,替代"boot 文件里手工排先后"。这是天枢 app.ts 手排 sweep 顺序的对立面。

inject: ['sessions', 'systemPrompt', 'tools']

④ 类型化事件 + 5 种分派模式

事件名经 TS declaration merging 声明,类型即契约。按语义选分派模式:

模式await顺序返回值语义
emit否注册序无旁路通知
waterfall否注册序有中间件,可短路
parallel是并行无扇出
serial是注册序有链式决策
bail否首决即停有单一决策

⑤ 注册都是可回卷的效果(reversible effects)

一切注册走 ctx.effect() / ctx.on(),返回 disposer;插件卸载/热重载时逆序自动回卷。这就是 dsh 能 HMR、插件树能安全重建的前提——注册不是"往全局 Map 塞",而是"付出一段可撤回的影响"。

const dispose = ctx.effect(() => {
  ctx.tools.register(myTool)          // 产生注册
  const off = ctx.on('agent/pre-step', guard)   // 挂监听
  return () => { off(); /* 逆序回卷 */ }
})

waterfall —— 最关键的机制

ctx.waterfall 就是 around-middleware:listener 收到 (...args, next),不调 next() 即否决(短路),调则携带改写后的值委托下游。策略、审批、提示注入都是挂上去的 listener,而不是循环里的 if/else。

ctx.on('agent/pre-step', (args, next) => {
  if (!approved(args.message)) return   // 否决,短路
  args.message = rewrite(args.message)  // 改写
  next(args)                            // 委托下一家
})

在 dsh 里,连 agent loop 本身都是插件:core/agent-loop → ctx.agentLoop。整个包只有它含真实循环逻辑,其余全是"抽象服务 + 扩展点上的插件"。换 loop = 换个提供 ctx.agentLoop 的插件。

04 天枢目标架构

装配层:从"焊线机器"变"读清单的装配器"

boot
├─ 创建根 ctx(Container)
├─ mount 各插件 { inject: [...], apply(ctx) }
│    // 依赖推导加载顺序 —— 不再手工排 sweep
├─ 启动顺序按依赖拓扑,停止顺序逆序回卷
└─ 路由由 createRouter(ctx) 工厂生成,依赖显式注入

可视化 · 目标架构插件树

读图:上方 boot 装配层 读清单组装而非焊线;中间 root context 是一棵全局服务树(绿=已成形 / 黄=缺皮 / 红=缺);scope() 派生每会话 session / agent context,插件挂上互不干扰——这正是《现状》里 app.ts / outer.ts / loop 三处焊线被拆开后的样子。

天枢版 ctx 契约(约 200 行,零新依赖)

  • register/get/has — 服务仓库,靠 key 不靠 import
  • mount({inject, apply}) — 等依赖就位再激活
  • effect(on) → disposer — 可逆效果,卸载逆序回卷
  • on/emit/waterfall/serial/bail — 5 种分派(先落 emit/waterfall,serial 预留)
  • scope() — 从父 ctx 派生,继承服务、隔离事件
  • start/stop — 按依赖序启动 / 逆序停止

关键取舍

  • 不引入 Cordis 本体自研约 200 行 ctx,接口对齐,保留白盒替换点。
  • serial/bail/parallel 进契约但实现留空(YAGNI),防后续改签名。
  • 转换用兼容壳旧 setXxxRuntime 保留至本层结束再删。

08 迁移期不变式("don't make it worse")

1
Model-visible means logged —— 写入模型上下文的任何新内容,必须先有 durable 事件 + 落库,不准只写内存。
2
禁新全局单例 —— setXxxRuntime 模式不再新增,新服务一律过 ctx。
3
禁在 app.ts 内联新 sweep —— 启动逻辑一律走 LifecyclePlugin。
4
路由禁新增模块级 const router —— 一律 createRouter(ctx)。
5
任一注册必带 disposer —— ctx.on/effect 都返回回卷函数,禁止"只塞 Map 不提供卸载"。
6
每层一个 PR + 全绿 + 可单独 revert —— 不允许跨层大爆炸提交。

10 dsh 成熟度对标:谁更成熟就照搬谁

决策仍是不嵌入 dsh 运行时;但对个别子系统,若 dsh 的实现明显更成熟,按「移植契约词汇、实现长在天枢自己的存储上」吸收(dsh 为 MIT,可照搬代码再改造成天枢 SQLite 版)。本表是成熟度基线 + A 组移植契约,供各层验收对照;它不推翻五层 strangler,而是升级其中两块 seam。

① 会话模型 → event-sourced log

  • 契约:会话 = 仅追加类型化事件日志;Model-visible means logged 从条文变结构保证。
  • 落点:run_events 已半成形,目标把 messages/sessions 收敛为「写事件 → 派生表」。
  • 边界:数据模型层改动,独立成步,配 Layer 3 storage seam;只事件化不斩旧表。

② Compaction → dsh 形状 seam

  • 词汇:compaction/start|summary|end 锁包围「测长→选区→摘要→落面」,最后 end;崩溃 = 无 end 的孤儿锁。
  • 落点:run.before-compact 扩展为这套词汇 + 触发词(升级 Layer 4)。
  • 验收:全程可重放可审计;孤儿锁由 Layer 2 LifecyclePlugin 回收。

③ 工具执行管线 → policy 监听

  • 形状:tools.pre-execute / post-execute 两个 waterfall 点;审批/只读判定从 if/else 变 listener(升级 Layer 4)。
  • 落点:即 RFC §5 扩展点表落地。
  • 验收:审批与执行解耦;策略挂载可逆(disposer);新增策略不碰 loop。

④ LLM 适配器 → 中立流契约

  • 契约:带 block 边界的类型化流(文本/推理/tool-call 显式块)+ finish 终块携带稳定错误码与 Retry-After;provider 声明 retryPolicy,执行器独立。
  • 落点:llm/client.ts 的 LLMChunk 块化;format 兑现或删除;字符串判 429 收敛为错误码;disjoint 记账。
  • 验收:新增供应商不再手改单函数;google preset baseUrl 恢复可连通;错误告别字符串匹配。

11 前端工作台化:插件即窗口

前端从「页面」升级为「工作台」——每个持久信息面 = 一个独立的窗(Pane),默认停泊在主容器,可拉出独立窗口、可自由换位;新增一个插件 = 新增一个插件窗口。参照物是 VSCode / Obsidian 的副窗口停泊模式(dsh 是单窗口插件应用,此模式天枢自研)。

核心模型:Pane = 单元,Layout = 数据,窗口 = 一种挂载方式。

布局是一份可序列化的 JSON(主窗内嵌网格 + 同窗悬浮 + 独立窗),存进 /api/preferences(沿用 theme/iconpack 的按文件持久化)。红利:uiStore 的 sidebarOpen / rightPanelOpen / filePanelOpen 三开关直接消失——面板开合 = 布局里有没有该 pane 节点。

前端的 app.ts 现状装配点

12 服务商适配器对标:目录与问题清单

复核结论:RFC §10 原判 providers 为「B · 相当,不动」,本次深调研推翻——天枢的 provider 层不是「适配器集合」,而是「目录 + 单一 openai 兼容 wire」;dsh 的 packages/llm/* 构型显著更成熟,提级为 A 组「契约对齐」(见 RFC §9.2-④ / §11)。
