插件组件模型（定稿）

概念定义关系
插件 Plugin可安装/卸载单元，含服务层 + 一组 UI 组件一对多
服务层总是运行，headless，贡献 Tool / prompt / 事件 / schema，无 UI随插件启停
组件 Component插件提供的可装配 UI 单元，可多实例属插件
装配用户自建窗口，把组件加入窗口（拖拽 或 点击加入）用户决定
要点：
  • 组件多实例是硬需求——同插件同组件可同时放入多个窗口各一实例。
  • 不放 ≠ 关闭——组件未放入任何窗口时 UI 不显示，但插件服务层照常运行（Tool/prompt/事件在位）。
  • 无「能力位」抽象——附件插件就是贡献自己的附件按钮组件，与官方按钮无隐式冲突，纯用户选放。
  • 无 UI 插件——组件清单为空，仅改变后端服务能力。

安装 / 停用 / 卸载 语义

操作服务层组件层数据
安装启动，Tool/prompt/事件/schema 在位组件出现在侧栏，可装配无
停用停止，能力移除所有实例从窗口移除保留（重启用原位恢复）
卸载停止，能力移除所有实例从窗口移除保留但不可见（重装恢复）
依赖缺失不启动，标记「依赖未满足」组件不可装配—
停用 ≠ 卸载：停用是临时，数据与装配关系都保留，重启用原位恢复；卸载是彻底移除，数据保留但不可见（对齐 capability-design 的「数据保留，只是不可见」）。

⑥ 客户端技术选型 · Tauri（推荐）

推荐 Tauri，理由

维度TauriElectron
打包体积3~10MB80~200MB
Vue3+Vite官方支持支持
原生多窗口WebviewWindowBrowserWindow
插件权限控制主动式白名单手动配置
跨窗口通信emit/listen 事件总线（与 Core 总线相似）ipcMain
学习成本需会 Rust（壳层很薄）纯 JS
关键判断：Tauri 只做「壳」（开窗口/浮窗/托盘/快捷键），业务全在 Node Core，因此文件/AI/深度原生操作都不经 Tauri，Rust 生态浅不构成瓶颈。

三层架构分层（职责分离）

┌─ Tauri（Rust 壳）──────────────────────────────┐
│  开主窗口 · 原生浮窗(可拖出主窗口) · 托盘 · 快捷键 │
│  打开 localhost:5173 (Vue 前端)                 │
│  ❌ 不做文件 / 不做 AI / 不做业务               │
└──────────────────┬─────────────────────────────┘
                   │ HTTP / SSE (127.0.0.1:1420)
┌──────────────────▼─────────────────────────────┐
│  Node Core（龙骨 · 一切业务）                   │
│  文件系统 · 命令执行 · 会话 · 记忆 · MCP        │
│  插件装配 · 凭证 · 事件总线                     │
└───────┬──────────────────────────┬─────────────┘
        │                          │ HTTP (OpenAI 兼容)
┌───────▼──────────┐   ┌───────────▼─────────────┐
│ 远程 LLM 服务商   │   │ 本地推理引擎(可选)       │
│ deepseek/openai  │   │ Ollama / llama.cpp      │
└──────────────────┘   └─────────────────────────┘
  • 文件深度操作不构成 Tauri 瓶颈——AI agent 的文件操作（read_file / exec / MCP / 附件）全在 Node Core 做，Tauri 壳不碰文件。
  • 本地 AI 推理引擎由 Core 统一控制——走 HTTP（OpenAI 兼容）或 child_process，Tauri 不碰推理；本地/远程 LLM 都做成统一 provider（P4 的 Registry 一份即可）。
  • 前端壳发起命令 → Core 处理 → SSE 回事件，Tauri 不接触业务数据。

⑦ 关键决策对照

场景行为
用户新建窗口空白 Panel，可自由布局
用户把组件拖入/加入窗口该组件 UI 显示；插件服务本就在跑
用户不放某个组件UI 不显示，但 Tool/prompt/事件/服务照常运行
组件多实例同组件可放多个窗口各一实例（如两个「发送」按钮在不同窗口）
官方附件 vs 三方附件无隐式冲突，纯用户选放；可并存或只用一个
无 UI 插件只装服务，不产生任何组件，用户看不到界面
卸载插件该插件所有组件实例从窗口移除 + 服务停止 + Tool/prompt 消失

⑧ 组件实例数据模型（草案）

// 插件
interface Plugin {
  id: string                 // 'plugin.chat' | 'plugin.attachment'
  name: string
  components: ComponentDef[] // 该插件贡献的组件定义
  onActivate?: (ctx) => void // 服务层启动（headless 引擎）
}

// 组件定义（可多实例）
interface ComponentDef {
  id: string                 // 'comp.chat-attach' | 'comp.attach-button'
  title: string              // '附件按钮'
  component: () => Promise<{default: Component}>
}

// 窗口里的一个组件实例
interface ComponentInstance {
  instId: string             // 实例 id（多实例区分）
  componentId: string        // 指向 ComponentDef.id
  panelId: string            // 所属窗口
  rect: {left,top,width,height,zIndex}  // movable-box 几何
}

// 布局真源：panel → instances
Panel.params = {
  instances: ComponentInstance[],   // 取代当前 widgets: string[]
  layout: Record
}
当前实现 `widgets/registry.ts` 是「全局单例 + import.meta.glob 自动发现」；按此模型需演进为「插件贡献多组件 + 实例化」，布局从 `widgets: string[]` 演进为 `instances: ComponentInstance[]`。
