0与天枢的形态差异：为什么不能照抄

天枢的角色管理界面（CharactersPage.tsx + 1109 行的 CharacterDetailPage.tsx） 是成熟的 master–detail，本次形态骨架照搬：左列表 / 右详情 / 详情内 Tab / 双栏绑定 / 自动保存。 但字段集、Tab 划分与纪律必须按 OST 重做 —— 天枢的角色是一个「有人格有记忆有皮肤有帮手的完整实体」， OST 的角色是一组引用。照抄字段会造出一堆无处落地的存储。

维度天枢 CharacterOST Character为什么
本质一个完整实体：人格 + 记忆 + 皮肤 + 动画 + 帮手 + 审批偏好 一组绑定：prompt · skills[] · tools[] · provider/model/thinking · params 「绑引用不绑实现」。角色存技能包、工具代码、沙箱路径，就是把抽象层次写错了
存储后端 characterStore + 一堆子表（memory / skin / revisions / assets） 一个文件 userData/plugin/agents/characters.json，owner 是 agent 服务 UI 不拥有数据。视图只订阅 agent.state，不读文件、不发 GET
分组groups[]，影响记忆共享范围与知识库绑定，左栏按组折叠 没有这个字段。左栏改为「搜索 + 状态筛选」 天枢的分组承载真实语义。OST 没有这些概念，保留一个只用来折叠列表的字段是纯装饰， 而装饰性存储会被用户当成语义
审批 / 权限default_strategy（Ask Risky / Ask All / Auto）+ helpers 审批链 没有这个字段。审批在 tools 插件的 approvals.json Core 不该知道有哪些工具、更不该知道哪些危险。角色层再放一份审批口径，用户改角色就会以为绕过了审批
记忆memory.md + 记忆浏览器 + 审计日志三个子 Tab 没有这个字段。会话历史是 session 服务的职责（append-only 不可变） 会话层与角色层是两个 bounded context。角色可变的部分只有「这一轮装什么」
视觉 / 皮肤skinId + 6 个动作槽 + 裁剪器 + 预览弹窗 没有。只留一个 32px 的 emoji 标记，用于列表识别 characters.json 里不该出现二进制与路径。列表识别用 emoji 足够
帮手helpers[]，可递归委派没有 委派是 loop 的编排能力，不是角色档案里的一条引用
生效时机自动保存，立即生效 自动保存，但下一轮才生效，且不追溯历史会话 prompt 每轮重算（历史里的 system 一律丢弃）。 改提示词对已有会话立刻生效 —— 既是特性也是意外来源，所以界面必须写明，见 §2
独有— 装配预览 Tab：p0/p5/p10/p30 四层 + 工具交集 + 预算条 + 悬空引用 天枢完全没有这个视图，而它恰好是 OST 角色界面唯一能回答 「我改的这些到底会不会被模型看到」的地方。见 §5
三条不变量，界面上必须处处可见，不能只写在文档里：
① 角色存引用，技能与工具归服务。本插件的 dist/server/ 里不许出现 tool.execute 的执行实现 —— 它只能出现在 service.json 的 publishes 里（发命令，不是执行）。所以本视图没有「上传工具」「编辑工具代码」入口， 绑定列表只从 tools.state / skills.state 取。
② 缺失是合法的。绑一个未注册的工具 → 忽略并标一条悬空引用，不报错；一个技能都没绑 → 空集，合法； 没选角色 → p5 层为空，回落裸会话，不是错误。
③ 顺序抖动会让 prompt 缓存全部失效。所以装配预览里工具的展示顺序必须就是 serviceId → name，界面顺序 = 模型看到的顺序。

2Tab 角色：只有三样东西属于「角色自己」

RoleIdentityTab 失焦即发 patch（合并式）。改 prompt 不追溯历史会话

七个决定

决定为什么
没有「删除」以外的破坏性操作 唯一能删掉一个角色的动作就是删除。而删除是立刻生效的（下一轮 p5 层变空，回落裸会话）， 所以删除要二次确认，确认框里要写明后果：不会追溯已有会话。
没有 enabled 开关 天枢有停用开关，OST 不需要：不选这个角色就是不用它。 输入框那个下拉本来就是每轮选的。再给一个开关等于多一个与下拉冲突的状态源 ——「下拉里选了它，但它被停用了怎么办」是经典的自相矛盾
id 创建后不可改 id 出现在 prompt.fragment.registered 的片段 id （role:<characterId>）里。改它 = 注销一条片段 + 注册一条新的。 天枢允许改 id 并自动重命名，代价是每次改名都要 navigate 刷新； OST 这里直接把它做成创建后只读，并说明原因
prompt 是 textarea 而不是富文本，且标注字节数 预算闸门按字节算（默认 8 KB / 20 条），超了整块丢弃 + warn，不许静默截断。 一个不告诉你字节数的编辑器，用户写到 20 KB 才发现「提示词不见了」
「下一轮生效」写成常驻提示，不是 toast 这是文档明确要求的文案。它是永久属性，不是一次操作的结果 —— 用 toast 意味着没改东西时这句话消失，而恰恰是「没改东西的时侯生效方式最需要解释」
emoji 标记可选，只有 32px characters.json 里只存一个短字符串。给上传位就是给路径，二进制不进用户数据档案
描述字段可以有也可以没有 天枢的 description 用于列表副标题与选择器 tooltip。 OST 把它降级为可选的「给自己看的备注」，不进装配 —— 界面上要写清它不进模型
为什么 prompt 不叫「系统提示词」。它只是四层里的 p5 角色层。 p0 身份层是 loop 内置常量、恒在不可卸；p10 是技能索引；p30~90 是各服务自愿 publish 的能力层。 所以编辑器标题写的是 「人格提示词 → p5 角色层」，旁边一个 role:<id> 的片段 id 预览。 叫「系统提示词」会让用户以为改它能替换掉整个 system message —— 而实际上 p0 恒在，他删不掉。

3Tab 绑定：技能选择器 + 工具选择器

天枢把「工具」「技能」做成两个独立 Tab，OST 合成一个 —— 因为从用户视角它们是同一个问题的两半： 这一轮它能碰到什么。

RoleBindingsTab 左 已绑定 / 右 可绑定。悬空引用红框虚线、灰显但不隐藏

技能与工具的十处不对称

维度工具 tools[]技能 skills[]
取值 string[]，且允许 "*" = 全部已注册 string[]，没有 "*"
界面表达 顶部一个 seg 开关：绑定全部已注册 / 显式挑选。 选「全部」时右侧列表整体降为只读预览 没有这个开关 —— 一个角色通常只需要 1~2 个技能，全绑没有意义
未注册 忽略 + 标一条悬空引用，不报错同左
来源标签 必显 serviceId（tools/fs-tools…）， 因为排序键就是它 必显 ownerPluginId：用户自建 或 chat-workbench 这样的具体插件。 技能没有 category 字段 —— 分组维度只有 owner，因为它的运维含义是 「卸掉哪个插件会带走哪些技能」，而分类没有这个含义 （见 ../skill_manager/技能管理-组件Demo.html §2）
本机可用性 无对应物（工具只有「注册 / 未注册」） 要有这一态，且不能省：技能多一个机器级开关 skill.enabled（skills.json）。 于是 本轮索引 = 本机可用 ∩ 角色绑定， 与工具目录 union(registered) ∩ role.tools 同一条式子。 绑上一个本机不可用的技能 → 绑定保留、不生效， 必须显式标注（本机不可用 + 「本轮生效 N」）， 不能静默成功也不能静默失败
风险徽章 必显（read / write / net / proc）。它决定这一轮会弹几次审批窗 无
名字是否可编辑 不可，只能从列表里挑 可：底部一个 chip 输入框，回车直接加一个技能名。 因为技能可能来自任何插件甚至没装 —— 允许手写名字，悬空引用照常标
自动托管项 managedBy:'auto' 的（如 skill_manager） 由技能列表状态决定注入，不进角色绑定，在两侧都灰掉 —
进不进 system 文本 不进。工具进的是 API 的 tools 参数（前缀缓存友好） 进：技能索引是 p10 一条片段，一行一个「name + 什么时候该用它」
排序 serviceId → name，界面顺序即模型顺序 与模型无关，按名字排即可
两个开关的分工，跨插件看才完整。
本视图不设 enabled（§2 那条决定）：不选这个角色就是不用它。
机器级那个在 widget.skills，列头叫「本机可用」不叫「启用」—— 否则它和这里的「绑定」听着像同一件事，而它们是 AND 不是覆盖。
那一侧存在的原因是预算闸门：p10 索引片段 8 KB / 20 条，超了整块丢弃； 而角色绑定是分散的，所有角色的并集照样能撑爆它，只有机器级开关能保证这个不变量。
所以两边合起来正好两个开关，缺一个都不成立。而 AND 必须在服务端成立： 装配器先 agent.resolve 拿角色，再拿 skills.list{characterId} 取过滤后的清单， skill_manager 的可读范围就是那份清单 —— 看得见的就一定读得到。
悬空引用灰显但不隐藏，是这个 Tab 最重要的一条。 灰色 = 不参与这一轮；隐藏 = 用户以为是自己配错了，然后跑去重装插件。 而实际情况常常是正常的：用户把某个可选插件卸了，角色少一点能力而已。
每条悬空引用旁边都写清是谁没提供它（mcp 插件未安装 / skills 插件未安装），而不是只标一个红框 —— 用户要知道该装什么，或者这条绑定可以直接删掉。
已绑定区与可绑定区的比例是 1:1，不是天枢的「窄列表 + 宽详情」。 天枢的工具行有长描述，OST 的工具只有一行名字 + 来源 + 风险， 一行能装下 2~3 个。双栏等宽换来了「一屏看到全部可用能力」—— 而这正是配绑定时唯一需要横向对照的信息。

4Tab 模型偏好：一个回落链，不是四个字段

RoleModelTab 每个下拉都带 src 徽章；链上高亮当前实际生效的那一环
这一 Tab 存在的唯一理由，是把回落链画出来。 resolve(provider ?? 角色偏好 ?? preferences.json ?? env → 硬编码) —— 角色偏好排第三。也就是说：用户这一轮在 composer 上手选了模型，角色的模型偏好就被覆盖了。
天枢的界面里没有这个问题（角色就是唯一的模型选择源）。如果 OST 照抄天枢那四个独立下拉，用户会理所当然地以为 「我给这个角色设的模型永远生效」。所以：每个下拉都要标 角色偏好 这个来源， 链上当前真正命中的那一环高亮，并且有一行文字说明 「这一轮在输入框手选模型会临时覆盖它」。
字段来源缺省界面
providerllm 服务的已注册 provider id省略 = 不覆盖 下拉，选项来自 llm.provider.registered；首项 （不覆盖）
model模型目录 id省略 = 不覆盖 下拉，选项按 provider 分组（optgroup）
thinkingoff/low/medium/high省略 = 不覆盖 五段 seg（含首段「不覆盖」），不是下拉 —— 只有五个值，下拉框里全是废话
params透传给 provider 的采样参数省略 = 不覆盖 键值对编辑器，只暴露白名单键（temperature / max_tokens / top_p）。其余键手工加会被拒绝并给出原因
没有「恢复默认」按钮，只有一个「全部不覆盖」。 天枢的运行策略用 4 个「空 = 继承」的空输入框表达继承，代价是用户看不出空着的那个到底继承了什么。 OST 的做法是让下拉首项就是 （不覆盖），并在旁边实时显示 「实际会用：deepseek-chat（来自 models 偏好）」。空是一个被命名的状态，不是一个空单元格。

5Tab 装配预览：这个角色下一轮会被装成什么

OST 角色界面与天枢最大的新增块。天枢的角色页没有任何地方能回答 「我绑的这 4 个工具，最后真的进了模型看得见的目录吗」。在 OST 里这个问题有确定答案，而答案完全可以算出来 —— 所以必须算给用户看。

RoleAssemblyPreview 切角色实时重算 · 纯前端模拟，真实实现走 agent.resolve

为什么是这个形状

它逐字对应第 ④ 步的装配代码：

prompt = composePrompt([
  { id:"identity",       priority:0  },   // chat-workbench/loop 内置，恒在
  { id:"role:reviewer",  priority:5  },   // agents/agent   服务 publish  ← 本页配置的那一条
  { id:"skill-index",    priority:10 },   // skills/skills  服务 publish
  { id:"reliability",    priority:30 }    // reliability/llm-retry 服务 publish
])
// 排序：priority → 发布者 id → 片段 id（字典序）
tools = union(tool.registered) ∩ role.tools      // 4 / 6
// 预算闸门：8 KB / 20 条，超了整块丢弃 + warn（不许静默截断）
界面元素对应的代码事实
四行表格：p / 层名 / 发布者 / 字节 排序键 priority → 发布者 id → 片段 id。 发布者 id 必须显示 —— 它是排序键第二段，而用户判断「这块能不能删」靠的正是「谁 publish 的」
p0 行没有删除按钮，且标注「恒在不可卸」 身份层是 loop 内置常量。给一个点了没反应的控件，比不给更糟 —— 它同时教会用户「这个界面不可信」
p5 行高亮 这一行就是当前编辑的角色。切角色时它跟着换名字，用户能直接看到「哦，我改的是这一块」
被预算丢弃的行 → 划掉 + 标 DROPPED 「超了整块丢弃 + warn（不许静默截断）」。划掉而不是隐藏 —— 隐藏等于用户不知道自己的提示词根本没生效，而那会导致他去调 temperature 去救一个根本不存在的问题
工具 chip：绿 = 策略免审，琥珀 = 需审批，红虚线划掉 = 悬空引用 绿/琥珀来自 tools.state 的 risk 与 policy 判定 （risk=read → auto；write/net/proc → ask）。 红虚线来自本角色绑了但未注册的工具
底部 tools = 注册并集(6) ∩ 角色绑定(4) · 排序 serviceId → name · 不过 Core 把整条算式连同中间结果一起印出来。「不过 Core」四个字是刻意保留的 —— 它提醒用户这个界面显示的东西一个字节也没有经过 Core， 所以 Core 的事件流里看不到这些内容（排障时会去找错地方）
装配摘要是纯前端推导，不是一个命令的返回值。 真实实现里 agent.resolve 是两跳（总线不提供返回值）， 而这个预览要失焦即出，所以它按同一套规则在客户端算： 角色绑定 ∩ 已注册工具 + 四层片段字节数求和。
不一致的风险写在界面上：如果注册表与 agent.state 不同源， 预览可能与真实装配有出入 —— 所以底部那行写的是「按当前注册表推导」， 而不是「这就是本轮的真实提示词」。这个措辞不能省。

6Tab 事件：这个角色在总线上说了什么

照搬工具管理面板的「事件」Tab 做法。绑定是运行期才解析的（插件可以随时装卸）， 出了问题「界面看着对但模型没拿到」只能靠这里定位。

RoleEventsTab 只读。所有行都是真 topic，紫色 = 总线事件，蓝色 = 本页发出的命令
topic什么时候出现在这个列表里
agent.state 服务启动时重播整份（这是下拉数据的来源）；每次 agent.state.set 落盘后再重播一次。 「重播整份」是这个 topic 的全部语义 —— 订阅方永远拿到全量，不需要增量合并逻辑
prompt.fragment.registered 服务启动时为每个有 prompt 的角色注册一条（id: "role:<characterId>", priority: 5）。没有 prompt 的角色不注册 —— 它的 p5 层就是空的
prompt.fragment.unregistered 角色被删，或 prompt 被改成空串
agent.state.set （去向） 本页每次编辑发的那一条。带 requestId，日志里标 → 以示方向
agent.resolve / .result （非本页发出） 由 loop 在第 ④ 步发出，不经过本视图。列出来是为了让用户知道 「绑定什么时候被真正读了一次」—— 只在每轮的第 ④ 步，不在保存时
「保存时解析一次」是错的。绑定是每轮第 ④ 步现解析的： 用户装了插件、启用了 MCP，目录可能在这几秒里变了，所以装配必须每轮重做。
这个事件 Tab 的价值就在这里：它让「保存了」与「被读过了」这两件事在界面上分开。 天枢的界面里这两者是同一件事（保存即生效），OST 里差一轮。

7composer 侧角色下拉（ComposerRolePicker）

第二个组件。住在 chat-workbench 的 widget.chat-composer，与 widget.agents 零通信 —— 它也订阅 agent.state， 选的 characterId 随 loop.run 的 payload 走。

ComposerRolePicker 点「🎭 代码评审员」打开菜单；没装 agents 插件时整个下拉消失

用 composer 上方那组按钮切换「装了 agents」「没装 agents」「运行中」三种状态。

没装 agents 插件时，这个下拉要消失。 不能留一个空的，也不能留一个写死的「默认」—— 那是在对用户说谎： 界面上有个能点的角色，但它背后没有服务。而这恰恰是最容易漏的一处归属问题： 角色的存在性由 agents · agent 服务注册， 而输入框是 chat-workbench 的界面，它需要跨插件读到角色的存在。
正确通路是总线事件（agent.state，owner 每次变更重播整份）， 不是文件。所以下拉的渲染条件是：收到过至少一条 agent.state 且 characters 非空。 还没收到 ≠ 不存在 —— 这两种情况用同一个「消失」渲染，但日志里能区分。
决定为什么
下拉在输入框上方那一行，与模型下拉、思考强度并排 三者都是「这一轮用哪个」。它们的字段地位完全一样： loop.run{ text, characterId, model, thinking }。 分散到别处会暗示角色比模型更重要，而它并不
每个字段标签右侧带一个 src 徽章 角色 · agent.state / 模型 · models.prefs.state / 思考强度 · 本地值。来源可见是这套架构的基本要求 —— 用户看到一个下拉就该知道它会不会消失
选项里带一行摘要（工具数 / 技能数） 用户挑角色的实际依据就是「它能不能干这件事」，也就是绑了什么。一行 4 工具 · 1 技能 比进管理页快得多
「裸会话」作为一个真实的角色存在 而不是「不选角色」。因为「不选」在 loop.run 里是 characterId 缺失，而文档要求角色不存在 = p5 层为空，不是错误。 把它做成一个可选项，界面状态与协议状态就一一对应了
切换角色不清空输入框，也不改已发消息 「下一轮生效」。已发出的消息里那一轮用的是哪个角色，已经写在历史里了
运行中（loop.state.changed = running）下拉置灰但可见 与模型下拉同样的处理。置灰而不是隐藏 —— 隐藏会让用户以为它坏了
没有「在管理页打开」按钮 那是 widget.agents 的事。两个 iframe 之间的通信为零， 唯一的联系是 Core 的插件注册表。给一个跨 iframe 的跳转按钮等于开一条本设计明令禁止的通路

e4 是最容易被做错的一格。天枢的角色管理器允许「角色什么技能都没绑、提示词为空」—— 它照样是一个完整角色。而在 OST 里，prompt 为空 = 这个角色对模型而言不存在： 它没有身份、没有能力，区别只在输入框里有个人类可读的标签。 所以界面必须把这件事说出来，而且要说得平静（信息条，不是警告）—— 因为「裸会话」是一个合法的、常用配置（文档的回落行为就是往它落）。
反过来：提示词为空但绑了工具是完全正常的， 界面不应暗示用户「你这个角色没填提示词所以是坏的」—— 那只是一份默认配方。

10外观：角色只存引用，皮肤是用户数据

§0 那张表里「视觉 / 皮肤」那一行写的是「没有」 —— 但那只是描述 characters.json 今天的样子，不是一条设计结论。 这一节把那个问题摊开：皮肤该不该有、有的话归谁、落在界面的哪一格。 服务与协议设计在 ../skin_manager/皮肤管理插件设计.html。

先纠正一个前提：天枢现在不是「皮肤归到角色」，它已经拆了。 CharactersPage.tsx 顶部是 角色 / 皮肤 两个 Tab； CharacterDetailPage 的「视觉与动画」Tab 里装的是 CharacterSkinBinder —— 它只做绑定，一行上传代码都没有。 原来那套 CharacterVisualEditor.tsx（上传 / 裁剪 / 预览弹窗）还在仓库里， 但没有任何地方 import 它，是死代码。
改造记录在 天枢 dev/docs/skin-decouple-plan.md，§一原话： 「把角色主观定义与『视觉/动画』解耦：角色绑定皮肤，皮肤是一组可复用的视觉组合」， §五.4 进一步确认「皮肤可被多个角色复用」。 所以要决策的不是「抄不抄天枢改造前」，而是「抄不抄它改造后」。

10.1 三条路线，三份 characters.json

A · 折进角色（天枢改造前）

{ "id": "reviewer", "prompt": "…", "tools": ["read_file"], "portrait": "assets/reviewer/p.png", "motions": { "idle": "assets/r/i.mp4", "working": "assets/r/w.mp4" } }

破坏 角色档案从「纯引用」变成「引用 + 资产路径」。 踩 §2 那张「这个角色不存什么」的表最后一行（沙箱路径）。

B · 独立实体 + 只存引用 推荐

{ "id": "reviewer", "prompt": "…", "tools": ["read_file"], "skinId": "miku" } ── 另一个插件的目录 ── skin/miku/ portrait · avatar idle · working

合法 skinId 与 tools:["read_file"] 同类 —— 都是引用。 皮肤可复用，agents 的产物里不会出现任何资产代码。

C · 按约定推导，不存字段

{ "id": "reviewer", "prompt": "…", "tools": ["read_file"] } （没有 skinId） ── 约定 ── skin/ 找 skin/<characterId>/ 有就用，没有就空

将就 characters.json 一个字段都不用加， 但隐式约定 = 路径耦合：用户没法表达「这个角色用别处那套皮肤」。 这是天枢 §五.3 的 fallback 规则，作为兜底合理，作为唯一机制太弱。

A 踩的不是审美问题，是一条已经写死的不变量。 OST 的 §11 第一条是「写只限自己」，AgentLoop 教程 §9.3 那条更直接： 角色 → 只存引用，永远不持有路径。 折进角色意味着 agents 服务要能写资产文件， 于是 agent.state.set{patch} 这个「合并角色字段」的语义 要长出第二类操作（写文件），而它是一个 HTTP 命令，不是进程内调用。
更麻烦的是做不出来：见 10.2。

10.2 B 落点的硬阻塞在 Core 的字节层，而它只需要一条路由

下面五条都是在仓库里核对过的事实，不是推演：

10.3 角色页里的落点：绑定 Tab 底部一行，不是身份 Tab 一个字段

下面这段可以点。它是「外观」这一行在 §3 绑定 Tab 底部应有的三种形态 —— 形态由 skin.state 决定，不由界面决定：

RoleBindingsTab · 底部三段 ← 绑定 Tab 的最后一张卡 发 agent.state.set{ patch:{ "<charId>.skinId": … } }

切上面的按钮看七种形态。「绑着但停用」与「悬空引用」的区别， 以及最后两种（悬空 / 无法校验）的区别，都是这一节最要紧的两条： 前者是「皮肤在但用户关了它」，恢复动作是启用； 后者是「一份清单都没拿到」，不能说是哪个插件没提供。 但两种情况下解绑按钮都必须在。

已确认		 收到了 skin.state，而清单里没有这个 id 红框虚线 + 标提供方（skins 插件，说得出因为清单收到了）+ 一键解绑。不报错、不阻止保存 —— 缺一层外观只是「少一点东西」， 而角色仍然完全可用。
最常见的成因是用户自己在 skins 面板删掉了那张脸， 而skins 插件不会替这里清引用（§10.6）
无法校验
未确认		 没收到 skin.state（skins 插件未安装） 幽灵选择器 + 「skins 插件未安装，skinId 仍在 characters.json 里」。 界面上不能说是谁没提供 —— 它一份清单都没拿到，说出来就是猜。 但解绑仍然要给：校验不了 ≠ 清不掉，恢复成本必须是一个点击
「绑着但停用」和「悬空引用」不能合并成同一个灰态。 一个是皮肤在、用户主动关了它（恢复 = 启用）， 一个是皮肤已经不在清单里（恢复 = 装回来，或解绑）。 两者都只让会话退回纯文字气泡，看起来一样 —— 而这正是要区分的理由：用户的下一步动作不一样。
最后两行（悬空 / 无法校验）也是两条不同的诊断。 工具侧的悬空引用（§3）遵守同一条区分： 能说出「mcp 插件未安装」与只能说出「无法确认」， 用户的下一步动作不一样 —— 前者是「装回来或删掉那条绑定」，后者是「先看插件装没装」。 合并成一行的话，两种情况都只剩下一句含混的「绑定无效」。
为什么放在绑定 Tab 而不是身份 Tab。身份 Tab（§2）装的是「角色自己」—— 名字、提示词、人格。而 skinId 是指向另一个插件的引用， 和 tools[] / skills[] 同类。 放进身份 Tab 会让它看起来像角色的固有属性，而它可以被卸掉、可以被别的插件提供。
同一条理由让它不参与 §5 的装配预览：皮肤不进 prompt、不进 tools 参数， 它一个字节也不进模型。装配摘要里加一行「外观：不影响本轮装配」是诚实的做法， 而默默不提会让用户去找「为什么这段提示词算不出字节数」。

10.4 两个必须先处理的坑

坑 1 · --motion-* 令牌已经被占用了，含义完全不同。 ../chat-workbench/对话工作台-会话列表重设计.html 刚引入：
--motion-idle:#8a95a1; --motion-thinking:#d29922; --motion-listening:#0f8a8a; --motion-working:#2f6feb;
那是「一行会话正在干什么」的状态色。皮肤动画也叫 idle / thinking / working / speaking / error， 两套语义会在同一份 CSS 里撞名 —— 而「idle」在两处都出现，是最容易撞的一个。

处置：皮肤侧一律用 --skin-motion-* 前缀， 并且不要把这套令牌放进 sdk/ui/src/tokens.css —— 它是某个具体视图的状态色，不是组件库真值。
坑 2 · OST 目前没有任何渲染器，皮肤没有落点。 ChatTimelineView 只有 msg--agent 气泡， 没有 stage / portrait 这条通路。天枢的 CharacterRenderer 有 portrait / avatar / stage 三种 mode 加一条 <video>→<img> 回退链，OST 一个都没有。

所以真实成本不在管理界面，在渲染侧要先有落点 —— 否则建了一套皮肤管理，界面上没地方显示。 这也是为什么 skin 那一稿要自带 SkinRenderer： 先有一个能播的组件，再谈让谁用它。

第三条（顺带）：contentTypeFor 的 MIME 表没有 mp4 / webm， 会回落成 application/octet-stream，<video> 放不出来。 动画 webp / gif 在 <img> 里就能播， 所以 v1 只支持静态图 + 动画 webp/gif 的话，那条新路由一行都不用改 —— MIME 表是共用的，动它会影响到别的插件，而没有必要。

10.5 待决清单

#问题选项建议
1皮肤归角色还是独立实体？ ① 折进角色 ② 独立实体 + 只存 skinId ③ 按约定推导 ②。① 让 characters.json 持有路径（违反已写死的不变量）， 且在今天的 Core 通路上做不出来；③ 只适合当兜底规则，不适合当唯一机制

② 的代价是 §10.2 那条：皮肤管理界面只能是只读的， 于是「外观」这一行的下拉里只有发版时定下的那几张。
① 需要 Core 新增一条伺服 userData 的路由，而它没有让 Core 理解任何插件内容 —— 它仍然只做「查白名单 + 搬字节」，只是根目录换了一个
3允许用户自定义皮肤吗？ ① 允许（运行期上传）② 不允许，用户自己装 skins 插件 ①。② 的问题不是技术，是产品形态： 「我想让这个角色用我自己的图」是这件事最核心的用户动作， 而 ② 让它变成「先写一个插件、发一版、等升级」—— 那是把用户的一次点击变成一次发版请求。
① 在选定 2 的①之后没有新增架构代价： 写入走服务握手里已有的可写 dataDir， 不需要 Core 参与；读走新增的那条路由。 剩下的是 UI 工作量与四条约束（格式 / 大小 / 新 assetId / 失败要说清哪一步）， 不是架构问题

5一个角色能绑几个皮肤？ ① 恰好一个 ② 多个 + 按场景挑 ①。「多个 + 按场景挑」会立刻要求「这一轮用哪个」， 于是外观也变成 loop.run 的一个字段 —— 而外观一个字节也不进模型， 让它占数据通路的字段是不划算的
6资产文件名的缓存策略？ ① 全部 no-cache ② 用内容寻址的 assetId，换图即换 URL ②。用户换一张图 = 服务生成一个新的 assetId = 新 URL —— 「浏览器还在显示旧图」结构上不会发生，不需要版本号、查询参数或任何缓存失效技巧。
代价要说清：它匹配不上 plugin-ui.ts 的 immutable 判据 （/-[0-9a-zA-Z_-]{6,}\.[a-z0-9]+$ 要求哈希段前带 -）， 所以实际走的是 no-cache —— avatar 是 32px 无所谓， 立绘和 motion 是要看流量的（skin 稿 §6 已把这个列为待决）
7本界面要不要「管理皮肤」入口？ ① 不给，只显示绑定与状态 ② 给一个「打开 skins 面板」按钮 ①。② 要一条尚不存在的宿主能力（Dockview 开指定面板）， 而直接跨 iframe 调另一个插件的函数会毁掉「零跨插件通信」这条性质。
写清「被哪些角色引用、缺哪个动作」已经够用 —— 而「创建一个新皮肤」在它自己的面板里，不需要从角色页跳过去
如果现在什么都不做，最省事的做法是什么都不加：characters.json 里既没有 skinId，界面上也没有「外观」这一行 —— 缺失是合法的，而一个永远显示「未绑定」的行比没有这行更糟： 它会让用户去找「为什么我装不上皮肤」。
真要留位置，就在绑定 Tab 底部加一行，而不是先造一个空 Tab。

10.6 两边各管各的：一份数据一个 owner

选定 §10.5 的 ①① 之后，这件事最容易被搞混的就是 「谁写谁」。下面这张表是 widget.skins 与 widget.agents 的职责边界 —— 它俩是两个插件，通信为零：

数据owner谁写另一个插件能做什么
userData/plugin/skins/skins.json
皮肤清单		 skin 服务 widget.skins 发 skin.set widget.agents 一个字都不写； 它只是读 skin.state 来填那个下拉
userData/plugin/skins/<skinId>/
立绘 / 动作字节		 skin 服务 同上（上传 / 删目录） 只能经 GET /plugins/skins/data/* 读， 不能写 —— 那里没有 PUT（§10.2）
characters.json 的 skinId agents 服务 widget.agents 发 agent.state.set skin 服务一个字都不写； 它删除皮肤前只读 agent.state 来核对引用
最后一行是唯一一处「跨插件读」，而它必须留在读这一侧。 删除一道皮肤要确认「没有角色在用」，而那份数据在 agents 的 agent.state 里 —— 所以 skin 服务订阅它、 只读不写。
反过来不成立：如果 agents 要在皮肤被删时「顺手清掉角色的 skinId」，那就要求 agents 写 skins 插件的清单， 或者要求 skins 命令 agents 去改角色 —— 两者都破了 §11「写只限自己」。
所以处置是让引用悬空：删掉皮肤后角色的 skinId 仍指向一个不存在的 id，界面显示「已确认悬空」并给一键解绑。
这不是妥协，是本设计里 missing 是合法的 那条不变式的直接应用。 角色档案里存的是一个引用，引用失效不该让「谁负责删」变成一个跨插件协商问题。
反过来的一次删除拦截（同一份数据，另一个方向）也一样是读。 skin 服务在处理 skin.set{removed} 时 拿 agent.state 核对，有引用就拒绝并回 blockedBy，一个字都不改。
而「核对不到」不等于「没人用」：那份 agent.state 可能根本没来（agents 插件没装 / 服务挂了）。 所以删除要带一个显式的 confirmUnreferenced， 并把这件事写在删除确认框里 —— 用户看到的是「我确认了没人用」，而不是「系统说没人用」。
样式全部取自 sdk/ui/src/tokens.css 的真名（--color-* / --space-* / --radius-*），所以这份 demo 与真正组件库同源； 交互是手写的，用来说明行为，不是产物代码。
