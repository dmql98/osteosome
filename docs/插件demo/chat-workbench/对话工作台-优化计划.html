这份计划是什么。chat-workbench 插件（三个服务 + 三个视图）的可执行优化清单。 形态设计在同目录的 对话工作台-会话列表重设计.html —— 那份说长什么样，这份说按什么顺序改、改哪几行、怎么验收。

三条硬约束，贯穿每一项：

  1. 协议契约一字不改。三视图边界、curId 走 sessionStorage 跨 iframe 共享、 loop.* 的事件形状。只加字段与命令，不改语义。
  2. 会话服务是唯一写者。并发防护靠单进程串行，不引入跨进程锁。
  3. 不假装不存在的字段。凡是需要新字段才成立的形态，要么排进 P2，要么这一版就别放那个按钮。

下面每一条结论都带证据：文件路径 + 行号，或本机实测输出。拿不准的写进 §10 的待决问题。

1.1 存储：不是 SQLite，是 JSON 文件

<userData>/plugin/chat-workbench/sessions/ ├─ index.json ← SessionMeta[] 列表视图唯一来源 ├─ s_<16hex>.json ← { meta, messages } 单会话全文 └─ *.json.tmp ← 写入期间的临时文件

store.ts:69 INDEX_FILE='index.json'　·　 store.ts:112 join(this.dir, id + '.json')　·　 store.ts:86 this.dir = join(dataDir,'sessions')　·　 manager.ts:188 dataDirOf() → shared/src/paths.ts:36 pluginDataDir()

操作复杂度做什么代价
session.list零磁盘 I/O 返回构造函数里 loadIndex() 读进的内存数组（store.ts:88, 180） 零 stat、零目录扫描。这是现存储的优点，升级时不许丢掉
message.appendO(M + N) push 后 writeSession() 全量重写会话文件（:257） ＋ syncIndex() 全量重写索引（:258 → :266） 长会话的主要死因。实测见 §6.1：平均 20 KB 的消息、5000 条时， 一次 append 写 96 MB / 耗时 399 ms
session.renameO(M) 改一个 title，重写全部消息（:206） 改个标题 = 再来一次全量写。JSONL 也解决不了，要 SQLite
session.getO(M) 传输 整个 messages 数组进 session.get.result 走 SSE 长会话的第二个死法：40 MB 的数组要序列化、走 SSE、在前端 parse，三处都摊不掉
（内存）无界 store.cache 是个无上限 Map（store.ts:82） 打开过的会话永远常驻内存，一个 40 MB 的会话就是常驻 40 MB RAM，没有淘汰
session.deleteO(N) 先 writeIndex()（:217）再 rmSync()（:218） 顺序反了：中间崩了留孤儿文件，而 store.ts 里没有 readdirSync，那文件永远看不见
session.clearO(N) 逐个 unlink，deletedCount 取自索引长度（:223-232） 索引损坏期间丢掉的会话既不会被删也不会被计数
实测规模：userData\plugin\chat-workbench\sessions\ 当前 3 个会话， 最多 4 条消息，index.json 0.46 KB。 但这个数字不能用来论证「整写可接受」 —— 它只说明还没人用过。 判断阈值要看的是 §6.1 的 B/C 两组，不是当前这 3 个会话。

SessionListView.vue 130 行，<Card title="会话"> + 三个工具条按钮 + 一个 <List>。没有搜索、没有分组、没有 pin 开关、没有键盘、没有预览行。 七个断层见 重设计 Demo §0。这里只记两个与存储无关的结论：

P0-0 为什么是唯一的阻塞项

时间桶分组、跨桶重排、手动排序的持久化，全都建立在「客户端知道每条会话最新的 updatedAt」之上。而现在：store.ts:256 已经把 meta.updatedAt 改成消息时间，index.ts:72-77 却不发 session.updated。 于是客户端的 SessionMeta.updatedAt 只在 create/rename 时更新 —— 分组会停在错误位置且不自愈。

接缝已经在了。ui/state/session.ts:140 已经订阅 session.updated， :143 会重排列表。所以 P0-0 是服务端加一个 publish，不是加一条通道。

P0-14 的两条硬规矩

① 绝对不要为了画一个点去临时订阅新 topic。ui/state/session.ts:183 记着这个坑： sse.subscribe() 遇到之前没订阅过的 topic 会触发 reconnect() —— 旧 EventSource 已关、新的还没 open，中间窗口里发出的命令没有回音。 session 级 motion 表必须由 run.ts 已有的 7 个永久订阅（:117 / :132 / :143 / :174 / :186 / :202 / :211）投影出来。
② 只在 ① 这个视图里算。三个 iframe 各算一份 = 内存与 CPU ×3，而只有侧栏需要它。 按 view id 分流，不是无条件生效。

4P1 · 存储正确性与止血

六项，不换存储、不改数据格式。P1-1~5 是正确性，P1-6 是性能止血。 全部只动 store.ts，与 P0 无依赖可并行。

P1 顺手带走的一个性能项

D5 说 index.ts:47 那次 store.list() 在每条命令前无条件执行，唯一用途是给 session.clear 逐个发 session.deleted。 改法：把快照挪进 topic === 'session.clear' 分支， 或让 store 暴露 ids() 返回 Set（省掉 N 个对象拷贝）。 这不是性能优化，是删掉一笔别的命令白付的钱。

P1-1~5 全做完，append 仍是 O(M)。它们修的是数据可能静默丢失这件事。 只有 P1-6 是性能止血 —— 它把 append 从 O(M) 变 O(1)，是当前规模下唯一能立刻消掉 §6.1 那张表里全部成本的改动。别把两者混为一谈。

6.2 三个结论

  1. 瓶颈是单会话文件，不是索引。看 D 组：20000 个会话、索引 2.7 MB， 每次 append 仍只要 16.9 ms —— 索引是一次性顺序写。 而 B 组只要 13 个会话、单会话 5000 条，append 就要 45.8 ms。 长会话是主要矛盾，会话多是次要的。上一版把两者并列，是错的。
  2. C 组是最坏情况，也是最可能的情况。Message.toolCalls[].arguments 会原样存工具入参 —— write / edit 的入参包含整份文件内容。 加上 S4 单独存的 reasoning（思维链动辄数千字）， 一条消息 20 KB 不是极端假设。这一组里 200 条消息就已经 3.9 MB。 而 ost 的主用途就是带工具调用的 Agent Loop —— 长会话是常态，不是边缘情况。
  3. 真正的断点比「占用太大」更早、更硬。上面只算了磁盘写。还有三处同量级甚至更糟：
    • session.get.result 把整个 messages 数组塞进 SSE （session.ts:169 → shared/src/events.ts 的 SessionFile）。 40 MB 的数组要序列化、走 SSE、在前端 JSON.parse，三处都摊不掉。
    • store.cache 是无界 Map（store.ts:82）。 打开过的会话永远留在内存里，一个 40 MB 的会话就是常驻 40 MB RAM，没有淘汰、没有上限。
    • rename 重写全部消息（store.ts:206）。 在长会话上改个标题 = 再来一次全量写。
所以「JSON 占用太大」这个说法要更精确一点。问题不是磁盘占用 —— 96 MB 磁盘不贵。 问题是每追加一条消息就要重写这 96 MB，以及打开会话时要把这 96 MB 走一遍 SSE。 前者把 append 从 O(1) 变成 O(M)，后者让长会话根本打不开。 换 SQLite 同时解决这两件（append 是一条 INSERT；get 可以按游标取）—— 这才是它该换的理由。

6.3 「SQLite 是踩过的坑」—— 坑是 better-sqlite3，不是 SQLite

这条要澄清，因为它直接决定用哪个 SQLite。ost 仓库从未用过 SQLite （git log --diff-filter=A 全历史零个 sqlite / .db 文件； 文档里每次提到 SQLite 都是推迟到 P8：P1a L24 / P3 L16,28,244 / 阶段追踪 L137,253）。 所以「踩过」指的是天枢。它那份 963 行的迁移指南把原因写得很清楚：

天枢 docs/跨平台客户端与Node-SQLite迁移开发指南.md L18 用 node:sqlite 替代 better-sqlite3，消除额外的 SQLite 原生插件和 ABI 风险。 L41 Node 24 已无官方 Windows x86 运行时；Electron 43 是最后一个提供 x86 预编译产物的系列。 L212 Phase 2 完成后，运行时只能存在 node:sqlite。不得保留： L214 · better-sqlite3（dependencies / devDependencies / optionalDependencies 任一） L215 · @types/better-sqlite3 L216 · 动态 import('better-sqlite3') L217 · 「node:sqlite 失败就回退 better-sqlite3」的双驱动逻辑 L218 · 针对 better_sqlite3.node 的 ABI 检查 / 复制 / 打包 / 下载代码 L55 保留 SQLite 文件格式，只替换 Node 驱动。不得迁移到远程数据库。
结论：坑是「原生模块 + ABI + 跨平台打包」，不是「SQLite」。 逃法就是 L12 给的那句：用 Node 内置的 node:sqlite。 它是 Node 自带的，零原生依赖、零 ABI、零 .node 文件， 打包时不需要为它做任何跨平台编译 —— 也就是把天枢那个坑整个绕开，而不是重蹈覆辙。 本机 Node 24.14 实测可用（仅一条 ExperimentalWarning）。
写成红线：services/session/package.json 里永远不出现 better-sqlite3。

✅ P1-6 会话文件 <id>.json → <id>.jsonl： 首行 meta，其余每行一条 message；appendMessage 改 appendFileSync append 从 O(M) 变 O(1)。这是当前成本最低的止血点 —— 一条消息平均 20 KB 时，它把 399 ms 降到一次追加 无 高：读时两种格式都兼容，旧 .json 首次打开时迁移

反过来，如果现在直接硬上 node:sqlite，要么引入 better-sqlite3（重蹈天枢的坑）， 要么在运行时没锁的状态下让一部分用户 require 就炸。

10决策记录与待决

ID决策理由推翻它需要什么
DR-1（已修订）换存储：P3 已触发，按 P1-6 → P3-0 → P3-1 三步走 上一版判「不触发」建立在 300 B/条的假设上。§6.1 实测：平均 2 KB 时 1000 条就是 2 MB / 11 ms， 平均 20 KB 时 5000 条是 96 MB / 399 ms，且 get 全量走 SSE。 而 ost 的主用途就是带工具调用的长会话 几乎推翻不了。要推翻需要拿出 ost 真实会话的消息大小分布，且证明 P95 远低于 2 KB
DR-2只用 Node 内置 node:sqlite，永不 better-sqlite3 天枢为摆脱 better-sqlite3 的原生模块 / ABI / 跨平台打包问题写了 963 行迁移指南（§6.3）。 node:sqlite 零原生依赖，是同一件事的正确答案 永不。这是红线
DR-3node:sqlite 上线前必须先有 Node 版本约束 lib.rs:295 + start-client.cmd:116 说明 Node 来自用户 PATH，仓库无任何版本约束（§6.4）。 node:sqlite 需要 Node ≥ 22.5 除非产品决定内嵌一个 Node 运行时并强制使用 —— 那其实就是 P3-0 的一种形态
DR-4先 JSONL（P1-6），不一步跳到 SQLite node:sqlite 今天还上不了（DR-3），而 O(M) 重写是当前就在流血的问题。 JSONL 20 行、零依赖、可回退，且它的输出就是 P3-1 迁移脚本的输入 若 P3-0 提前做完，可跳过 P1-6 直接上 SQLite
DR-5分组键用时间桶，不引入 workspace SessionMeta 没有该字段；时间桶零成本且解决真实痛点 用户开始按项目找会话；届时 bucketOf() 是唯一改动点
DR-6置顶/归档不改 updatedAt 抄天枢 update() 的 touchKeys 规则。 操作分类 ≠ 操作活动时间 几乎没有。它是 P0-7 分桶正确性的前提
DR-7未读存 sessionStorage，不用 localStorage localStorage 跨窗口，两个窗口会互相清对方未读（天枢现状即如此） 要做跨窗口/跨端未读 → 那是服务端 read receipt，属另一个量级
DR-8会话级 motion 只在 ① 里算 三个 iframe 各算一份 = 资源 ×3，而只有侧栏需要 ② 或 ③ 也开始需要跨会话状态
DR-9P1-1~5 只算「正确性」，P1-6 才算「性能」 混为一谈会让 §6.7 的阈值失真，也会让人以为上了 P1 就解决了长会话（其实 get/cache 两条还在，R9） 不要
