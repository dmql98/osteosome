为什么现在做：AgentLoop 教程第 ⑩ 步写死了「tool.execute 转发给注册了这个 name 的那个服务」—— 那条路由依据是一张注册并集的表，而这张表今天还不存在（今天只有 loop 进程内的一个数组）。 审批（第 ⑬⑭ 格）与 MCP 都压在同一个缺口上，拆一次补齐三处。
Core 一行不改。新增的 13 个 topic（6 事件 + 7 命令）全部先进 shared/src/events.ts 的 EventMap / CommandMap， Core 的校验逻辑就是查表，表变宽它自动覆盖。

1定位：这个插件管什么，不管什么

它管（4 件）

  • 审批闸门：写 / 网络 / 进程类工具逐次问用户；策略落 userData/plugin/tools/approvals.json。
  • 目录的可视化与试调：widget.tools 列出运行期成形的工具目录，带来源服务、风险等级、参数 schema，并支持手工试调。
  • 策略默认值：用户在这里把某个工具标成 auto，就等于替角色省掉一类弹窗。
  • 一份对照清单：模型的目录 = 注册并集 ∩ 角色绑定；这个视图是那件事唯一能被人看懂的地方。

它不管（4 件）

  • 不持有工具实现：目录来自各服务 publish 的 tool.registered，这个插件只是订阅方之一。
  • 不做路由：tool.execute 是 loop 按注册并集直接发给执行者的，tools 服务不在数据通路上。
  • 不存会话：审批请求与结果都带 requestId（= toolCallId），一次性，不落盘。
  • 不改 Core：Core 不该知道有哪些工具、也不该知道审批过没有。
为什么审批闸门是「一个服务」而不是「一个 listener」： 审批弹窗要送到界面 → 界面回一条命令 → 执行者才知道能不能跑。这条回路天然跨进程， 而工具执行者又不一定都在本插件里（未来的 MCP 在别的插件）。所以闸门必须是一个独立进程， 并且它不认识工具——它只按 risk 与策略文件判断，把执行请求原样转交。 它是「不知道工具清单也能工作」的：所以卸载某个工具插件，闸门照常工作。

第 2 跳是本设计与「闸门转发」方案的分水岭：审批是执行者向上问，不是 loop 向下绕。
如果让闸门做转发（loop → 闸门 → 执行者），总线上会同时存在两个 tool.execute 的订阅者，而转发意味着发第二条 —— 执行者收到两次、跑两次；要避免它，loop 就必须知道「这个 name 该绕还是直达」， 那条知识只存在于用户的策略文件里，于是 loop 手里多了一条会长的规则。
倒过来（执行者自己问、总线按 topic 投递）之后：loop 一行审批代码都没有， 闸门不认识任何工具、也不转发，只回答「这一次允许吗」， 手工试调与模型调用走同一条链路。零新增 topic，零路由分支。
多个闸门怎么办。谁订阅 tool.approval.requested 谁就答； 多答的那几条由幂等兜住 —— 第一个 tool.approval.resolved{T} 生效，之后的按 「pending 里查不到就丢弃」这条既有纪律处理（§7）。这与「同一 name 两个服务都注册工具」的处理是同一条纪律。

三条必须一起满足的契约纪律

  1. 重播整份而不是发增量。订阅方可能晚于发布方启动（管理视图永远晚）。同 llm.provider.reannounce。
  2. 缺失是合法的。不带工具的插件完全正常；订阅失败要忽略，不能让装饰性内容打死主链路。
  3. 顺序必须确定。目录排序键 = serviceId → name。抖动会让 prompt 缓存全失效， 症状是「同样的对话 token 费用翻了十倍」且零报错。
严禁把 source 用作业务字段。 EventBase.source 是总线级保留字：ServiceManager 会把每条服务消息权威盖章成 serviceId。 需要表达「工具属于哪个服务」时用 serviceId 字段（同 llm.models.list.result 用 catalog 的教训）。

所以「MCP 是动态的」这件事在协议层看不出来 —— 这正是关键。 loop、闸门、界面对 MCP 与对 read 一视同仁：都只是一条 tool.execute 与一条 tool.registered。 差异被完全关在 mcp-tools/src/ 里。§5.5 那三条要求是这个插件里唯一因为某类工具特殊而多出来的规矩。
两条容易看成「写错」的地方，它们是刻意的：
  • tools 服务 publish tool.execute：它不拥有任何工具， publish 只是为了手工试调能用同一张目录表派发（§4.2-④）。发布一个 topic 不等于拥有它。
  • fs-tools publish tool.approval.requested：审批是执行者向上问， 不是别人替它问。这让 loop 完全不必知道「这个工具要不要审批」—— 那条知识在用户的策略文件里，而用户的数据不该变成 loop 的代码。

4.2 tools 服务：四段职责

段做什么关键决定
① 目录镜像订阅 tool.registered / tool.unregistered，维护内存里的 ToolRecord[]，任何变更后 publish tools.state 整份。 ToolRecord = spec + serviceId + risk + enabled + policy。enabled 是本地开关，默认 true。
它维护这份目录只是为了界面与试调派发；权威副本在 loop 那边，两份各用各的（总线事件的性质，见教程 §2 推论三）。
② 审批闸门订阅 tool.approval.requested → 查策略 → 答 tool.approval.resolved{approved}。ask 时先把请求留给界面。 按 risk 兜底：策略里没有这个 name 时，read → auto、write/net/proc → ask。
它不认识工具、也不转发执行——只回答「这一次允许吗」。
③ 策略 ownertools.set 合并式写 approvals.json；写完 publish tools.state。接受 remember（勾「以后都允许」）。 JSON 原子写（临时文件 + rename）。合并不覆盖——两个视图各改一条不会互相清空。
④ 手工试调tools.invoke{name, arguments} → 查自己的目录副本 → 发 tool.execute{requestId=T合成} → 等 tool.execute.result{T} → 回 tools.invoke.result。 试调走的是和模型完全相同的链路：所以它也会被审批——一个 proc 类工具在这里点一下， 等于真的执行了它。这不是缺陷，是「只有一条路径」的直接后果（见 §14 待决 4）。

4.3 审批状态机（tools 服务内，挂在 T 上）

// pending: Map<toolCallId, { name, risk, arguments, sessionId, timer }>

// ── 入口：执行者问「这一次允许吗」 ──────────────────────────────
tool.approval.requested{T,name,risk,arguments}
  ├─ policy=auto → answer(T, true)                 // 立刻回，不进 pending
  ├─ policy=deny → answer(T, false, '用户已禁用该工具')
  └─ policy=ask  → pending.set(T, …)                // 挂起，等人；定时器同时起
                    └ 定时器到期 → answer(T, false, '审批超时（未响应）')
                                                    // 超时按拒绝，不是按允许

// ── 出口：一条 topic，执行者与界面都能发 ──────────────────────
tool.approval.resolved{T, approved, reason?, remember?}
  ├─ 找不到 pending[T] → 静默丢弃 + logger.info      // 幂等 & 孤儿（§7）
  ├─ approved → remember ? patchPolicy(name,'auto') : 无
  └─ denied   → 无（reason 已在 payload 里，执行者把它写进结果）

// 执行者收到 resolved{T,approved} 后才真正动手；approved=false 时
// 它产 tool.execute.result{ok:false, content:'用户拒绝了这次工具调用'}
// ——与「执行失败」同一条通路，让模型自我纠正。
「失败也要产结果」是这一层的硬纪律。 被拒绝、超时、禁用三种情况都最终落到 tool.execute.result{ok:false}， 因为 loop 只认这一个 topic —— 它不区分「执行失败」与「不许执行」。 静默丢弃的等价物就是「模型一直转圈」。

risk默认可升到 auto？理由
readauto是路径锁在自己 tool-root 内，只读，不出网
writeask是，但新装工具第一次仍问会改用户文件；「装上就等于有写权限」不该由插件单方面决定

5.2 为什么是 6 个执行者，而不是 1 个

切分依据说明
沙箱根不同fs-tools 的根是它自己的 tool-root；shell-tools 的「根」是约束清单（允许命令 / 禁止模式）；web-tools 没有根，只有出网与否；mcp-tools 的边界是子进程。四者的沙箱不是同一个概念，硬塞进一个进程就得让 loop 或闸门学会区分。
故障域不同bash 会起子进程（超时、杀进程、非零退出码、Windows 编码探测）；MCP 会拉起外部 server（它自己崩/它自己挂）；read 都不会。放一起意味着一次 bash 卡死或某个 MCP server 崩了会带走在跑的读取。
目录生命周期不同五个静态执行者的目录在启动时一次成型；mcp-tools 的目录随连接增删（§5.5）。合并成一个进程就得分两套注册逻辑，而它们只是「什么时候重发一份注册」的区别 —— 不值得合并。
审批节奏不同shell/web/mcp 是「每次问」；fs 的读是「不问」，写是「每次问」；skills/misc 是「不问」。闸门按 risk 决定，而 risk 在这一层已经知道了。
不切开的代价一个进程崩 → 13 个静态工具同时消失 → loop 的目录塌大半 → 模型症状是「有的工具能调有的不能」，而进程状态只显示 degraded。更糟的是 MCP：server 连不上不该让 read 也跟着没了。

把两者分开，就是本设计对我自己原稿那个「靠自律」的修法。 原稿说「risk:'read' 是承诺，承诺错了就绕过闸门」。现在这条承诺不再只靠自觉： constraintFields 是声明（要照抄进 shared/，不能自己改）， 规则引擎在 shared/ 里只有一份，四个执行者共用； 而「这个工具只做只读」这件事本身由闸门按 risk 复核， 执行者谎报 risk:'read' 去执行写操作，闸门看不到 —— 但 write 工具自己就会触发 constraintFields 里的 bytes-max 与审批， 而 constraints.json 里没有它的任何条目时按空清单 = 全禁处理。

  | 'glob-allow' | 'glob-deny'      // 路径白/黑名单（前缀 glob）
  | 'bytes-max'                      // "1MB" / "512KB" / 裸字节数
  | 'exact-allow' | 'substring-deny' // 命令：首 token 精确 / 子串拒绝
  | 'readonly-query' | 'max-number'
export function validateConstraints( fields: ConstraintField[], // 工具声明的（来自 tools.json） values: Record<string, unknown>, // 角色/机器给的 args: Record<string, unknown>, // 模型这次传的 ): string | null // null = 通过；否则是人话原因，直接当 ok:false 回填
为什么放 shared 而不是闸门。约束校验必须发生在动手之前，也就是执行者进程里； 放进闸门就变成「先执行再检查」，那是顺序颠倒。而四个执行者各写一份的实现必然漂移 ——「edit 的路径检查比 read 宽」这种差异零报错，只在某天越界时才显形。
工具不能自己改规则表：一个插件声明 validateRule:'glob-allow' 却给出 allowed_paths: ['**']，等于自己解除限制。所以引擎侧要有一条硬规则： ** 与 * 单独出现时视为无效声明并 fail fast， 且「全放行」只能由用户在界面上显式打勾 —— 跟「risk:'read' 不能由插件自称」是同一条纪律。

5.5 MCP：目录是运行时生成的，所以它有三个别处没有的要求

mcp-tools 是本插件里唯一不读 tools.json 的执行者。 它的目录来自 MCP 协议的 tools/list，于是「注册」变成了一个连接态问题。

① 目录随连接增删，不是启动时一次

连接事件动作
某个 server 连上tools/list → 逐个转 ToolSpec（risk:'proc'）→ 整份 publish tool.registered
某个 server 断开 / 超时tool.unregistered{serviceId:'mcp-tools'} 整份重发（含剩下的 server）
连接重试成功再整份发一次 —— 所以必须幂等，否则目录里出现重影
整个 mcp-tools 被 kill -9Core 发 service.failed → loop 与闸门按 serviceId 清目录（§7-③）

② 命名：平铺 + 服务端自带前缀可能冲突

平铺的两个代价，都要显式处理：
① 模型看到的是一个混在一起的目录 —— 这是优点（天枢这么做是对的： 模型不必知道「MCP 工具」这个概念），但界面上必须按来源分组，否则用户以为那是内置工具。
② 一个 server 返回 create_issue，与内置工具同名 → 本设计的 fail-fast 规则会拒绝注册并在界面标 ⚠。这正是期望行为： 宁可少一个工具，也不要让「模型调的到底是哪个」变成猜谜。
③ __ 的切分：天枢用 name.match(/^mcp__(.+?)__(.+)$/)（非贪婪）， 本设计照抄并加一条测试：server 名含 __ 时必须仍能路由到正确 server。

③ 审批：MCP 是最需要逐次确认的一族，而它恒为 proc

risk:'proc' 不是默认值，是这一族的性质。 MCP server 是用户机器上的子进程，「它要干什么」由那个程序决定，不由我们的 schema 决定 —— 而我们连它会干什么都不知道（tools/list 只给 name/description/inputSchema）。 所以：
  • 不做静态放行：MCP 工具永远逐次审批，不允许「按 server 批量信任」。
  • 描述进弹窗：审批卡片把 server 的 description 原文与全部入参显示出来 —— 用户能判断的只有这些，所以必须给他（天枢的 UI 没做这一层，它只显示命令与入参）。
  • 「以后都允许」要二次确认：见 §4.4 的表 —— proc 档升到 auto 不是一次点击。

关于「每个执行者各写一遍 risk:'read' 判定」这条自律要求，§5.3 给了它一个机制化的落点。 原文写的顾虑仍然成立（执行者自称 read 就绕过了闸门），但现在多了两道独立的闸： ① 约束由 constraintFields 声明 + shared 里唯一一份引擎强制， 工具改不了规则表；② shell-tools/web-tools 干脆不提供任何 read 工具 —— 它们的全部工具都是 proc/net，没有「只读快路径」这个分支可走。 所以真正需要自审判定的只剩 fs-tools 与 misc-tools 两个服务。

// loop 进程内：等一个 toolCallId 的结果，带硬超时
const pendingTools = new Map<string, { a: string; timer: NodeJS.Timeout }>()

function dispatchTool(a: string, sessionId: string, call: ToolCall): void {
  const serviceId = registry.get(call.name)      // 查表，不是规则
  if (!serviceId) {
    if (pendingTools.has(call.id)) return        // 同一 T 不重复派发
    finishTool(a, sessionId, call, { ok:false, content:'不在本轮目录内的工具：'+call.name,
      summary:'未注册 '+call.name })            // ← 必须是失败，不是静默
    return
  }
  service.publish('tool.execute', { requestId: call.id, sessionId, name: call.name, arguments: call.arguments })
  pendingTools.set(call.id, { a, timer: setTimeout(() => {
      finishTool(a, sessionId, call, { ok:false, content:`工具 ${call.name} 超时（${TIMEOUT_MS}ms 无响应）`,
        summary:`${call.name} 超时` })
  }, TIMEOUT_MS) })
}

service.subscribe('tool.execute.result', (p) => {
  const hit = pendingTools.get(String(p.requestId))
  if (!hit) return                               // 孤儿结果：静默丢弃，不补发
  clearTimeout(hit.timer); pendingTools.delete(String(p.requestId))
  finishTool(hit.a, …, call, { ok: p.ok, content: p.content, summary: p.summary })
})
为什么按 toolCallId 一对一配对是「免费」的。 模型返回的工具调用块 id 天然就是一次执行请求的 id，所以不需要任何额外关联表 —— 这就是教程 §7 那句「T₁ T₂ 同时用作 tool.execute 的 requestId」。 所以审批弹窗天然知道自己等的是哪一次，而 Core 不需要参与这个关联。

7三个必须一起解决的新问题

第 ⑩ 步引入了本轮唯一真正的新协议（跨进程执行 + 审批），它带来的三个问题必须在同一批解决，否则只是把问题挪到了别处。

问题触发不处理会看到什么处置落在哪
① 超时执行者崩溃 / 卡死；或在审批上挂住（闸门或界面没回） 用户看到「模型一直转圈」，无错误、无提示 硬超时 → 产生一次失败结果（ok:false + 人话原因）回填给模型 loop（执行超时）· 执行者（审批超时）· 闸门（无人应答超时）—— 三处各管自己那一段
② 孤儿结果审批期间用户按了停止；或这轮已结束而结果才到；或多个闸门都答了 界面上出现一个「幽灵工具块」，挂在已结束的轮次下面；或工具莫名跑了两遍 静默丢弃，不许补发。判据：结果到达时 A 已释放 / 轮次不匹配 / pending 里查不到 loop（pendingTools）· 执行者（pendingApprovals）· 闸门（pending）—— 同一个判据，三处各判一次
③ 残留注册执行者被 强杀（崩溃 / 插件被替换），来不及发注销事件 「工具偶尔失灵，重启一次就好了」——间歇性、无报错、没人想到去查注册表 订阅 Core 已发布的 service.failed / service.stopped，按 serviceId 清目录 loop + tools（两边都要清）
第 ② 条在新结构下多了一层含义。 「多个闸门都答了同一 T」如果不幂等，就是工具执行两次 —— 而对 proc 类那等于跑了两遍命令。 所以 pending 的 delete 必须发生在 answer 之前，而 answer 本身还要再查一次。 这一条比「孤儿丢弃」更严：它防的不是显示错乱，是副作用重复。
第 ③ 条最容易被漏，因为本地测试走的永远是优雅停机。 必须有 kill -9 集成测试：起 fs-tools → 记下目录里有 read_file → kill -9 它 → 断言 N 秒内 tools.state 不再含这个 serviceId 的条目、且 loop 下发给模型的目录少了这一项。
这条与 provider 那次崩溃事故同源：Core 早已发布 service.failed，只是没人订阅。
顺带说明：这是 Core 少数「主动产出语义」的地方（它知道进程死了）， 但它仍然不判断「这意味着哪个工具没了」 —— 那是订阅方的事。 Core 依然只做「查白名单 · 搬字节 · 记生命周期」。

为什么「沙箱边界随执行者走」是这三件事的自然解法

今天 loop 用自己插件的 dataDir 算只读沙箱根，理由是它同时也是文件工具的宿主。 一旦工具分散到多个插件，loop 若还要裁定边界，就得知道每种工具的边界规则 —— 那是一条必然会长歪的耦合：某个执行者改了规则，loop 不知道，于是它给出的判定是过时的。

正确形态是「谁执行谁负责」：执行者有 dataDir 和 plugins.readFile，自己算自己的根； loop 只需要知道「这个 toolCall 该发给谁」，而那是从注册并集里查出来的一份数据，不是一条规则。

如果只记四句

① 能力住在服务里，不住在插件清单里。装一个 tools 插件就是多起 6 个进程，它们 publish 自己的那份， 下一轮 loop 的装配器就多认得它一点；卸掉就是模型不再假装拥有那些能力。这个效果不来自任何目录规则。
② loop 手里只剩一张表。「这个 toolCall 该发给谁」是查出来的数据，不是一条规则； 于是沙箱边界随执行者走，loop 不再持有任何路径常量。
③ 审批是逐次的，因为出网能力属于插件而不属于 Core。 弹窗问的是「现在要不要让这条通路真的被用掉」，不是在问 Core 能不能代理 —— 它根本没这个能力。 MCP 是这一条的极端情形：我们不知道那个 server 会做什么（tools/list 只给 name/description/schema）， 所以它永远逐次审批，连「按 server 批量信任」都不提供。
④ 试调必须过审批。管理界面与运行时同一条纪律，否则 widget.tools 就是审批系统的一个后门。
⑤ 约束与审批是两道闸，不是一道。约束（角色/机器给的允许清单）直接失败不问人； 审批（用户的一次点头）才放行副作用。工具谎报 risk 绕过后者，前者仍在 —— 这条是从天枢「dangerous 两值 + constraintFields 声明」里拆出来的。
