① widget.tools（本插件唯一的视图，5 个 Tab）—— 管「这台机器上有什么能力」： 目录 · 审批 · 试调 · MCP · 事件。数据全部来自 tools.state，只订阅事件、不发请求。
② ApprovalPanel（对话流里的一个内联块，住在 chat-workbench 的 widget.chat-timeline）—— 管「这一次允许吗」。三个按钮对应天枢的 reject / once / always，但作用域要印在按钮上（天枢没做这层）。
两者共享 name / requestId(=toolCallId) / risk 三个 id，所以同一个面板能被两个视图复用 —— 时间线按 sessionId === curId 渲染它，管理面板按 sessionId === 'tools-console' 渲染它。零跨组件通信。

与天枢最大的形态差异：审批从「浮层对话框」改成「内联块」。 天枢是 .approval-overlay + ApprovalDialog.tsx（居中浮层）， 工具块是另一条消息（ToolCall.tsx）。两者一分离，浮层一关， 界面上就看不出这一轮是被谁批准的 —— 而「谁批准的」是用户事后唯一会想查的事。 合并成一个内联块之后，批准记录跟着工具块一直留在时间线上。

面板本体。5 个 Tab 共用一份 tools.state，切 Tab 不重新取数、不重新订阅。

widget.tools index.html#catalog 订阅 tools.state · 发 tools.set / tools.invoke / tools.mcp.*

560px 模拟 dockview 里一个中等面板的真实高度。窄于 900px 时目录表要退化成卡片列表（见 §11）。

Tab回答为什么在这章节
目录模型现在能看到哪些工具？谁提供的？风险多大？开了吗？ 唯一能一眼看出「这台机器有什么」的地方§2
审批我放过哪些工具？以后还问吗？ 与目录分开：一个是「有什么」，一个是「我授权到哪」§4
试调这个工具在当前机器上真的能用吗？ 没有它，用户只能靠模型试错来发现问题§5
MCP接了哪些外部 server？连上了吗？各带哪些工具？ server 是配置，与「有什么工具」不是一回事§6
事件这个插件到底在总线上说了什么？ 能力目录运行期才成形，排障只能看这里点上面的 Tab
头部那三个数字是刻意加的：总工具数 / 需审批数 / 未启用数。 「需审批」这个数直接告诉用户模型每轮会弹几次窗 —— 而这个数在天枢的界面里完全看不出来 （它只有一张静态卡片列表，没有任何与风险/审批相关的呈现）。

2管理面板 · 目录表（按来源分组）

ToolCatalogView 点开关就地改 enabled；点「详情」开抽屉（下一节）；悬空引用 / 同名冲突灰显但不隐藏

九个决定，都写在表里了

决定为什么
按来源分组，不按名字排序 用户的问题是「MCP 那批怎么没连上」，不是「a 开头有哪些」。名字排序对这个问题零帮助； 分组还顺带回答了「哪个插件挂了会带走哪些工具」。
组内按 name 排序这一条是给模型的：tool.registered 的顺序必须 serviceId → name 稳定，否则 prompt 缓存全失效。 界面顺序与它一致，用户看到的就是模型看到的。
名称等宽字体 + 描述省略名称是模型调用的标识符，用户要能一字不差核对； 描述长了不影响判断（抽屉里有全文）。
风险徽章紧挨名称扫一行就知道「这行要不要点审批」，不用横向对齐看某列。
策略列显示「按默认」而非留空空单元格会被读成「没设置」； 而 6 个只读工具就是按 risk 默认的。
managedBy:'auto' 的行禁用开关 skill_manager 由技能列表决定。给个点了不生效的开关比没有更糟 —— 它同时教会用户「这个界面不可信」。
悬空引用 / 同名冲突灰显但不隐藏灰 = 不参与这一轮；隐藏 = 用户以为是自己配错了。
「无约束声明」打警示该工具没有第二道闸，审批是唯一一道。对 proc / net 类尤其显眼。
没有「删除工具」按钮本插件不拥有工具实现，删它等于卸插件。给一个按钮等于骗用户。只有「停用」，而停用是可逆的。

3管理面板 · 详情抽屉（含约束编辑器）

点目录任意一行的「详情」。抽屉里除了看参数，还要能就地改约束 —— 因为约束是本插件的第二道闸。

ToolDetailDrawer 右滑出 · 四段：说明 / 参数 / 约束 / 策略
约束编辑器是抽屉里最重要的部分，因为它是不弹窗的那道闸。 每个 constraintField 渲染成一个卡片：标题 + 规则名 + 值 chip + 输入框。
规则名（glob-allow / bytes-max）必须显示。 只放一个「允许路径」输入框是不够的：用户需要知道自己填的东西怎么被解释 —— glob-allow 是前缀匹配（src/** 匹配 src/a/b.ts， 而 ** 只在末尾有意义）。不解释的话，填个 ** 会「意外全放行」。
三处刻意不提供的能力：
① 没有「允许所有路径」开关。要放行全部只能显式填 **， 而引擎拒绝单独出现的 */**（fail fast）—— 所以这件事在界面上也做不出来。恢复成本由「常用值」快捷 chip 承担。
② 没有「继承角色设置」。约束是「机器级 + 角色级」两层，这个编辑器改的是机器级； 角色级在 widget.agents。在这里显示角色级会让人以为改这里能改角色。
③ risk 不可改（界面上是只读徽章）。它是执行者声明的事实，不是用户能调的口径 —— 否则「把 bash 标成 read」就绕过了审批。

4管理面板 · 审批策略

与目录分开一个 Tab。目录回答「有什么」，审批回答「我授权到哪」，混在一张表里两个问题互相干扰。

ApprovalPolicyTab 只列需要决策的行 · 点三档就地生效 · 「恢复询问」= 删掉那条覆盖

三档与两个刻度

档效果默认谁能设成它
ask每次执行都问write / net / proc用户
auto直接放行read 只有用户；proc 档还要二次确认
deny产失败结果，模型自我纠正无用户
「恢复询问」放在「变更」列而不是工具名旁边。 它的语义是撤销一次改动，不是操作这个工具。放在名字旁边会让人以为它跟另外两档是平级三选一 —— 而它其实是「回到第 1 档」的快捷方式。
这张表默认很短（只列非 read 或已覆盖的），这不是「界面漏了」—— 表格下面那行小字专门说了这件事。
三档不是「让模型自己学」。它们是闸门的判定输入，写进 approvals.json； 闸门不认识工具，只按 name 查这一条。所以「我把策略调松了但工具不生效」是不可能的状态 —— 目录里 enabled=false 的工具根本不会进这一轮的目录，压根到不了闸门。

5管理面板 · 手工试调（会触发同一个权限面板）

ToolRunner 切到不同 risk 的工具看审批面板是否出现
这是整个面板里最容易被「优化掉」的一处，所以要写明。 试调必须触发审批：tools.invoke 发一条合成 toolCallId，之后完全走同一条链路 —— 执行者自审 → 闸门 → 审批面板 → 执行。
给试调开后门（管理界面里不审批），那么 widget.tools 就成了审批系统的一个后门： 点一下 bash 就等于执行了任意命令。一个只有一条执行路径的系统才不会被绕过去。
「参数（JSON）」旁的参数表直接由 constraintFields 的同源 schema 生成， 给出示例 JSON 作为起点 —— 但它不是校验器。用户不该先查 schema 再手写。

6管理面板 · MCP 服务

McpServerPanel 形态照天枢 McpView 的卡片，但删掉了「检测本机」入口、env 改掩码

与天枢 McpView 的三处不同

天枢有本设计为什么
检测本机 MCP（扫 opencode / Claude / Cursor 配置）不做 读别的应用的配置目录 = 越界。OST 的 plugins.readFile 只能读自己插件目录， 这条纪律不该为导入方便而破。要导入就手贴 JSON —— 那是有意识的一次动作。
导入 JSON保留 粘贴配置是用户主动给数据，与扫别人目录性质不同。
卡片把 env 明文列出（K=V 原样） 掩码，悬停/点击才临时显示 MCP 的 env 里就是 GITHUB_TOKEN 这类东西。 天枢那条是 UI 便利，但明文铺在卡片上会进截图、进录屏、进 bug 报告。 形态照搬凭证插件已有的做法：GITHUB_TOKEN=ghp_••••7f2a。
「删除」要终止子进程，不只是从列表里划掉。 天枢的 handleDelete 只删配置。本设计要求同时杀掉那个 server 进程 —— 否则「删了」只是 UI 上的删除，进程还在跑，那才是真正的暴露面。所以删除需要二次确认，文案要写明会终止进程。

7权限面板 · 形态与三档选择

对话流里的一个内联块，不是浮层。三个按钮对应天枢的 reject / once / always， 但作用域印在按钮上。

ApprovalPanel 换工具看不同 risk 的文案 · 切状态按钮看流转 · 点面板上的按钮真的能走完

七行文案，每行都不能省

行示例省掉会怎样
① 工具名 + riskbash proc用户不知道在批什么
② 为什么需要问「这个工具会拉起一个子进程，也就是任意代码执行」 只能凭工具名猜。尤其 MCP 必须有：我们不知道那个 server 会做什么
③ 完整入参{"command":"pnpm test"}批一个没看过的命令 = 没批
④ toolCallIdT=call_8f2c1d出问题后无法定位是哪一次（排障的唯一线索）
⑤ 超时「60s 后按拒绝处理」用户不知道放着不管会怎样
⑥ 作用域「仅 bash」 「允许本机此工具」听起来像全局开关，必须写明范围
⑦ 结算后的结果「已允许 · 已记住」 不点任何东西就不知道卡在哪 —— 而它就在挡着模型
「始终允许」这个按钮名要改。 天枢的 always 在界面上叫「始终允许」，而它的实际作用域是 本机 + 这一个工具名。这个措辞差得很远 —— 用户以为买了永久通行证， 结果换个角色（约束更严）它又被拦。本设计改成把作用域印在按钮上： 拒绝 / 允许一次 / 允许本机此工具。 按钮变长了，但它不再骗人。
不设「记住我的选择」复选框，而是让「允许本机此工具」成为一个独立档位。 天枢是「仅本次 / 始终允许」两按钮、无复选框，于是「这次允许但别记」没有路径。 三档并列之后每个选项都不需要解释，而两档 + 复选框需要用户自己想清楚组合。

8权限面板 · proc 档的二次确认

ApprovalPanel · 需要二次确认时 只有 proc 档升到「本机此工具」会走这一步；切到 MCP 那条能看到 server 说明
为什么只有 proc 需要二次确认。 net 也会把数据发出去，但它至少有 URL 与请求体可看，且用户通常知道自己在查什么； proc 是任意代码执行 —— allowed_commands 里哪怕有一条 npm，npm run 背后的东西也是不可预见的。
这不是不信任用户，而是不信任「remember」这个动作本身：用户可能只是手滑点了「允许本机此工具」， 而这一点的后果是此后每次都自动放行，他自己都不会再看。
MCP 的卡片比 bash 还要多一段：server 的 description 原文。 tools/list 只给 name/description/inputSchema， 而用户能判断的全部依据就是这几行 —— 不给他的话，这次审批就是在盲批。

9权限面板 · 结算后的工具块

批完之后，同一个块原地变成结果，而不是消失或换一条新消息。这是与天枢浮层方案最大的差别。

一条完整时间线上的五种块 点头部展开/折叠 · 注意成功块底部那行「依据：本机策略」
终态头部点开看到什么时候
执行中名称 · 实时秒数 · 折叠箭头参数（结果还没有） 照天枢 LiveDuration：从卡片创建时刻起算
成功✓ 名称 · 后端结算的耗时参数 + 结果 + 「依据」行常规成功
失败✗ 名称 · 耗时参数 + 人话原因 执行报错 / 路径越界 / 约束层拒绝 / 被拒绝 / 审批超时
幽灵块灰 · 名称 · 「本轮已结束」不展开，只有一行说明 结果到达时 A 已释放。不补发、不消失
被拒绝与执行失败合并成同一种呈现，是刻意的。 loop 不区分这两者（同一个 tool.execute.result{ok:false}）， 对用户的区别只在原因那行字：「用户拒绝了这次工具调用」vs「命令包含禁止模式」。
但审批记录要留在块里：折叠状态下头部要能看到「已允许 · 已记住」。 这是事后唯一能查「谁批准的」的地方 —— 天枢的浮层方案给不了这个。
成功的块也保留「谁批的」。 Demo 里那条 bash 走的是「允许本机此工具」，块底部会留一行 依据：本机策略（2026-10-06 用户批准）。 这样用户在长会话里扫一眼就知道哪些动作是自动放行的 —— 极其有用。

10权限面板 · 四种边界情形

这四条是实现时最容易漏、且都不会报错的。

边界情形 点四个按钮逐一触发
情形界面必须显示为什么不显示就是 bug
① 审批中用户按了停止该块变成「本轮已结束」，审批面板消失，不产生任何结果块 不消失的话，一个永远等不到人的面板会永久挡在时间线上； 而补发一个「已取消」的工具结果，会让模型以为「取消」是一种工具行为
② 审批超时块变成失败，原因写「审批超时（未响应）」 「一直转圈」是这个系统最容易出的症状。静默的等价物就是转圈
③ 工具已卸载但结果才到幽灵块（灰、不展开） 挂在已结束的轮次下面，用户会以为工具「偶尔失灵，重启一次就好了」
④ 刷新页面时正在审批面板重新出现，T 不变，倒计时从原剩余继续 pending 在闸门进程里且经总线重播，所以刷新后界面重订事件就能看到在途请求
④ 是天枢方案的一个真实缺陷。 它的 approvalRegistry 把 pending 挂在进程内 Map，key 是 (sessionId, toolCallId)，注释写「不靠 stream 闭包所以重连还能答」—— 方向是对的，但 Map 在 agent 进程里，所以重连要靠前端另外去问「有没有在途审批」。 本设计把 Map 放进独立的闸门服务，pending 状态本身就经总线重播 —— 不需要任何补偿逻辑。

窄面板退化

面板窄于 900px 时目录表的 6 列会挤成一团。两种做法： ① CSS @container 查询（dockview 面板宽度可用）→ 表格换卡片列表； ② 用 Table 的 cell:* 具名插槽把风险徽章挪到名称下面。
建议 ①：表格在这个面板里是主形态，退化成卡片就失去了「扫一眼对齐比较」的价值。 本 Demo 未实现窄屏退化（stage 宽度固定），实现时补。
