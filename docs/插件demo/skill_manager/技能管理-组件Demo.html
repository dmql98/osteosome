① 列表单位不是「技能包 + 子技能两层」，而是一个技能一行 —— 因为 OST 的子技能不是独立条目，是同一个 SKILL.md 里的分节，靠 skill_manager 懒激活；

③ 面板从 4 个 Tab 收到 2 个：技能库 + 统计。砍掉的那三个去哪了，见 §5；
④ 没有「导出 / 同步到云端」—— OST 的技能不跨机搬运；
⑤ 启停开关是真的（skill.enabled.set），与工具目录里那行 managedBy:'auto' 的 skill_manager 是两件事，别混。

0两个消费者：界面管「装了什么」，工具管「读了什么」

组件住在哪数据源回答写什么
SkillCatalogView + 统计 Tab skills 插件（widget.skills） skills.state（owner 每次变更重播整份） 「这台机器上有哪些技能、它们现在是启用还是停用、我这份描述模型读不读得懂」 skills.list · skill.enabled.set · skill.package.write
skill_manager 工具 skills 插件的 skills 服务（不是 UI） 同上 + 会话激活表 「现在该读哪一份技能正文」 会话激活表（进程内，不上总线）
为什么这两件事不能合并成一个组件。它们的时间尺度不一样： 界面管的是跨会话的「装没装 / 开不开」，工具管的是本轮的「读不读」。
合并的代价很具体：界面上会出现一个「本轮已激活」的列表，而它是每轮都会变的 —— 用户盯着它会以为「模型没读就是没装好」，于是去改描述，改了三轮，最后发现问题在别处。 所以拆成两个 Tab：一个跨会话（技能库），一个本轮（会话）。
与天枢最大的一处形态差异：列表不再是「分类 → 卡片墙」。 天枢 SkillView 按 category 分组、卡片上显示 「名称 / id / v版本 / N 个子技能 / 绑定角色」。这套信息密度对天枢成立，因为它的技能包是独立目录（有 skill-package.json）。
OST 的技能是 SKILL.md 一个文件 + frontmatter，没有 category 字段； 而「谁提供的」（ownerPluginId）是唯一真实存在的分组维度 —— 它的运维含义是「卸掉哪个插件会带走哪些技能」，而 category 没有这个含义。

1面板 · 总览

面板本体。两个 Tab，共用一份 skills.state，切 Tab 不重新取数、不重新订阅。 被砍掉的另外三个 Tab 去哪了，写在 §5。

widget.skills index.html#library 订阅 skills.state · 发 skill.enabled.set / skill.package.write

520px 模拟 dockview 里一个中等面板的真实高度。窄于 900px 时表退化成卡片列表（见 §9）。

Tab回答为什么是它章节
技能库有哪些技能？谁提供的？开了吗？正文谁能读？ 唯一需要一份全量列表的地方 —— 也是唯一能停用 / 改描述的地方§2
统计我装的这些技能，有几个模型真的会用？ 唯一能把一份列表变成一个决定的地方。渐进披露让「装了没用过」是静默的， 界面上不给它一个数，用户就只能靠猜§4
头部那四个数字各自对应一个失败模式，不是装饰：
技能数 —— 零的时候 skill_manager 根本不注册（§6）。
本机可用数 —— 关掉「可用」的技能不进索引片段，所以它不占模型上下文，但仍在目录里可见、角色绑定也保留。
从没被读过 —— 这一栏是红灯，且只在「本机可用 + 装了够久 + 调用 0 次」时才亮； 新装的技能不算（见 §4）。
索引字节 —— 索引片段是 priority 10 的一整块，预算 8 KB / 20 条； 超了整块丢弃 + 每条一条 warn，不是截断。所以这个数字要一直看得见。
两个 Tab 是这份设计里最费口舌的部分。 工具管理面板有 5 个 Tab，因为工具要管 4 类东西（内置 / MCP / 审批 / 试调）； 技能只有一件东西 —— 一堆 SKILL.md。 Tab 的数量应该等于「不同的用户问题」的数量，而不是等于「能做的操作」的数量。 能做的操作（改描述、停用、设 preload）都在技能库这一屏里就地完成，不需要各自的 Tab。

2技能库 · 表（按 owner 分组）

SkillCatalogView 点开关就地改 enabled；点「详情」开抽屉；同名冲突 / 悬空绑定 / 来源插件未运行都灰显但不隐藏

两个开关：一个「本机可用」，一个「角色绑定」，合成是 AND

这是整个面板最容易设计错的一处，所以先说清楚：本视图的开关不叫「启用」。

本机可用（本视图的开关） 角色绑定（在 widget.agents 选）
回答什么这台机器有没有这个能力 这个角色要不要这个能力
粒度机器级 · 一份（skills.json） 角色级 · 每个角色一份（characters.json · skills[]）
存在的原因 预算闸门。索引片段是 p10 的一整块，8 KB / 20 条，超了整块丢弃； 而角色绑定是分散的，所有角色的并集照样能撑爆它。只有机器级开关能保证这个不变量。 外加「这台机器上不要有这个能力」这种诉求，与谁用无关 不同角色用不同技能 —— 这是最常见的情况，不该由一个全局开关去表达
合成 本轮索引 = 本机可用 ∩ 角色绑定。与工具目录同一条式子 （tools = union(registered) ∩ role.tools）。
关掉它会怎样 角色绑定保留（与「卸载不回溯历史」同一条纪律），重开即恢复； 但那 N 个角色本轮拿不到它 只是从这个角色的候选里去掉
为什么角色侧不给开关，只给「选择」。 角色插件自己的判断是对的：不选这个角色就是不用它。再加一个 enabled 只会制造「下拉里选了它，但它被停用了怎么办」这种自相矛盾。
所以两边各留一半，合起来正好两个开关，缺一个都不成立： 只有角色侧 → 撑爆索引预算时无计可施；只有机器侧 → 所有角色被迫用同一批技能。
AND 必须在服务端成立，不能靠界面约定。 如果 skills.state 里那份技能清单不分角色， 而 skill_manager.read 又按角色绑定拒绝，那么每一轮都会出现： 模型在索引里看见了一个技能，去读，被拒 —— 而拒绝的原因用户完全看不到。
所以索引片段不能是静态 publish 的一份：它是随角色解析一起算出来的。 做法是给已有的 skills.list 加一个可选字段 （skills.list{characterId}，只加字段不改语义）， loop 先 agent.resolve 拿到角色，再按角色要清单。 skills 服务仍然是唯一持有技能目录的人，零新 topic。
界面上唯一需要做对的一件事：把「有效」显示出来。 「绑了 2 个 · 有效 0 个」这一格是 AND 的唯一出口。 没有它，用户只能自己在脑子里做交集 —— 而人做交集会出错， 出错后的症状是「我明明绑了它，模型就是不用」。

十一个决定，都写在表里了

决定为什么
按 owner 分组（用户自建 / 插件自带 + 具体插件） 用户的问题是「卸掉 chat-workbench 会带走什么」，不是「web 开头的有哪些」。 group 就是卸载影响面，所以它必须是最外层结构。
组内按 name 排序 这一条是给模型的：skills.state 与索引片段的顺序必须 ownerPluginId → name 稳定，否则 prompt 缓存全失效。 界面顺序与它一致，用户看到的就是模型看到的。
名称等宽字体 + 描述单行省略 name 是模型调用的标识符，用户要能一字不差核对； description 长不影响扫表（抽屉与编辑器里有全文）。
描述后面只跟一个徽章，且只在有问题时出现 渐进披露让 description 成为契约，所以要有一个信号；但信号只在可改的那一条上出现 （没有触发条件 / 过短），其余问题各归各屏（脚本 → 抽屉、冲突 → 抽屉、预算 → 底部预算条）。
没有「体检通过」绿标 —— 大部分行是绿的，绿标就只是噪声。
「索引 B」列显示字节数而不是条数 预算卡在字节上（8 KB），也卡在条数上（20）。两个都超了才有事， 先看到字节，因为它先到。
停用的行不隐藏，只降透明度 隐藏 = 用户以为「我装过这个技能」。停用是可逆，所以留在原地。
同名冲突标 ⚠ 且说明是哪两个 owner 撞了 fail fast 的另一半在界面上：被拒的那个不覆盖生效的那个。 只标「冲突」不写来源，用户会去错的那个插件里改。
来源插件未运行的行标残留快照 技能目录是运行期成形的：插件停了，它 publish 过的那一份就该 skill.unregistered 消失。行还在，说明这条链路有问题， 所以要显眼而不是灰掉。
列头叫「本机可用」不叫「启用」 中文里「启用」和角色侧的「绑定」听起来是同一件事，而它们是 AND 不是覆盖。 叫「可用」才说得清：它管的是这台机器上有没有，不是「让不生效」。 （对比：工具目录里 skill_manager 那行的开关是禁用的 —— 它由技能列表决定，我们这行的开关是真的。）
加一列「角色」，显示 绑了 N · 有效 M AND 的唯一出口。没有它，用户只能自己做交集； 而「我明明绑了它，模型就是不用」这个症状没有任何线索可查。
没有「删除技能」按钮 删除是不可逆的，而技能正文可能正被历史消息引用着（append-only，不改）。 本视图只提供停用；真要删，去删那个目录。
头部只有 「导入目录…」，没有「新建技能」 技能的事实来源是磁盘上的目录：一个没有 frontmatter 的空目录没有 name， 也就没法被索引、被角色引用。所以「新建」只能表现为「指一个目录过来」， 给一个从零开始的新建表单等于让人先填一堆再生成目录。

3技能库 · 详情抽屉

点任意一行的「详情」。抽屉里最重要的不是看正文，而是看清这个技能从哪来、正文谁能读、卸载会发生什么。

SkillDetailDrawer 四段：概览 · 结构 · 绑定角色 · 停用影响　｜　子技能与目录结构合成一段
为什么是四段而不是五段。 「子技能」与「目录结构」讲的是同一件事 —— 这个技能由哪些文件组成、哪几块能被单独激活。 拆成两段的后果是用户要在一个抽屉里上下滚动才能把它们对上，而它们本来就是一张表的行。 合成一段之后，preload 开关就落在它描述的那一行上，不需要先解释「preload 是什么」再让人去找开关。
插件自带技能的正文，本插件读不到 —— 这不是缺陷，是 readFile 边界直接推出来的。 plugins.readFile 只限自己插件目录，所以 skills 服务从不读别的插件的 SKILL.md；那份正文是那个插件自己的服务读完再 publish skill.registered 交上来的。
于是抽屉里对插件技能显示的是「来源：chat-workbench · 正文由它提供」加一条灰字， 正文区替换成 frontmatter 摘要。给一个读不出内容的区域配一个「展开全文」按钮， 等于教用户这个界面不可信。
「卸载影响」这一段是刻意放进去的，因为 OST 的第 4 条硬边界是 「卸载不回溯历史」：历史里那条 role:'tool' 的技能正文还在（append-only）。
用户点「停用」之前必须知道三件事：① 索引片段里这一行会消失；② 历史消息里的正文不会被删； ③ 角色绑定保留，下次装回来即恢复。所以这一段在按钮上方，不是折叠区。

4统计 · 哪些技能真的被读了

面板只保留两个 Tab。第二个既不是「体检」也不是「事件」，而是这一个 —— 它是唯一能回答「我装了它，模型到底用上了吗」的界面。

SkillUsageTab 数据来自 skills.state.usage —— skills 服务数自己执行的那次 tool 调用 · 只读

为什么是「统计」而不是「事件」

事件流统计
回答的问题「这个插件在总线上说了什么」 「我装的这些技能，有几个模型真的会用」
谁需要它写插件的人（排障） 用插件的人（决定停用谁、谁的描述要改）
已有归属吗 有 —— 工作台的「事件流」视图，按 serviceId=skills 过滤即可。 在这里再抄一份是重复，而重复的日志会让人以为它是权威来源 没有 —— 别处都不提供这个数
数据从哪来总线（人人可订阅） skills 服务数自己的 tool.execute.result，落 usage.json，聚合后搭 skills.state 的车（不新增 topic）
统计不需要新协议。计数的数据源是 skills 服务自己执行的 skill_manager.activate —— 它收到结果时就知道了：不需要 Core 参与、 不需要别的服务配合，也不需要新的 topic。
聚合值挂在 skills.state 的 usage 字段上， 和技能列表一起重播整份。于是这一屏与技能库表永远一致， 不会出现「列表说有 6 个技能、统计说 5 个」这种需要人去对账的状态。
「0 次调用」不能直接等于「描述写坏了」。 昨天刚装的技能调用 0 次完全正常。所以这张表里必须有「已装 N 天」， 而且只有本机可用 + 装了够久 + 调用 0 次这一组才被判成问题，其余如实显示、不下结论。
这条比任何图表都重要：图表会让人把噪声当信号，而「装了 40 天 · 调用 0 次」 是可以直接下结论的证据。
刻意不做的事。
① 不按模型 / 按会话下钻。那是日志的活，而且从来没人靠它改过描述。
② 不做趋势折线。技能调用是稀疏事件（一个技能一周被读 0～3 次）， 折线画出来是锯齿噪声，读的人只会记住「好像在涨」。
③ 不做「推荐停用」。停用是用户的决定；界面只把候选挑出来并给停用按钮。

5砍掉的三个 Tab：体检 / 会话 / 事件

它们不是被删掉的功能，是被移到了它们唯一该在的地方。写清楚，否则实现时会顺手加回来。

原 Tab去哪了为什么留在原地是错的
体检 拆开：可改的那条检查并进技能库表的徽章与编辑器的实时提示； 不可改的几条并进它们各自发生的那一屏 —— 脚本 → 抽屉的文件列表； 冲突 → 抽屉与库表；悬空绑定 → 抽屉的「绑定角色」段；预算 → 库表底部的预算条 它把四种不同性质的事混进一个列表：两种改描述就行，两种根本不是用户能改的（预算、卸载）。 用户扫过 12 行红字，不会知道先做哪一件 —— 而这一屏真正有用的其实只有一件事：description 有没有触发条件。 它应该在改它的地方响，而不是单开一屏等用户想起来去看。
会话 激活记录 → 对话时间线里的工具块（loop 本来就把每次 skill_manager 调用渲染成块了）+ 抽屉里一行 「本轮 N 个 · B 字节」摘要；preload 开关 → 抽屉的子技能列表（本来就在那儿） 它是同一份数据的第二个位置。用户想知道「刚才那轮模型读了什么」，看时间线就行； 在管理面板里再列一遍只造成两种误读：① 以为那是模型这轮的全部能力； ② 以为它比时间线更权威。
更大的代价是它暗示了「激活」是人的动作 —— 激活是模型每轮自己的决定， 面板一提供这个按钮，用户就会开始替模型选技能，而下一轮模型又会按自己的判断重来。
事件 工作台的事件流视图（按 serviceId=skills 过滤） 见 §4 的表：它有归属。插件视图里再抄一份事件日志， 是把开发者视图混进用户视图；而且抄的那份没有 Core 的重播语义 —— 刷新即空，用户会以为「没事件 = 没发生过」。
「砍掉一个 Tab」的代价必须说出来：排障时少了一个就地看事件的地方， 「刚才那个技能到底被读了没有」要多跳一步。这是真的损失。
所以它成立的前提是替代品真的存在：工作台事件流必须已经支持按 serviceId 过滤。 如果没有，这一屏就得留着 —— 砍它的依据是「有更好的地方」，不是「看起来更干净」。
剩下的两个 Tab 为什么站得住。 技能库回答「这台机器上有什么技能、开了吗、正文谁能读」—— 只有它需要一份全量列表。 统计回答「哪些白装了」—— 只有它能把一份列表变成一个决定。 这两件事之间，没有第三个问题值得一张 Tab。

6skill_manager 的披露面：工具那一侧

技能是被这个工具披露给模型的：模型看到的全部技能信息 = 索引片段里的一行 + 它自己调 skill_manager 拿到的正文。所以界面必须与工具同源。

① 七个 action 分别落在界面的哪一处

action参数返回什么给模型界面上对应的地方
list_packages— name / description / 子技能清单（无正文） 技能库表的数据源；抽屉「概览」段展示同一份
describe_packagepackage_id frontmatter 全字段 + 子技能数组抽屉「概览」段（字段逐字对应）
list_childrenpackage_id 子技能 id / name / description / preload抽屉「结构」段的开关就是 preload
activatepackage_id · skill_id 子技能正文 + 磁盘目录 + <dataDir> 绝对路径 对话时间线里的工具块（loop 本来就在渲染）+ 抽屉「概览」末尾一行「本轮 N 个 · B 字节」摘要
deactivatepackage_id · skill_id 是否真的移除了 同上 —— 管理面板里没有这个按钮（§5：撤销模型刚做的事不该在设置面板里）
list_active— 本会话已激活清单抽屉「概览」末尾那一行摘要（只显示计数与字节）
readskill_name 或 package_id[/skill_id] 正文（不计入激活上限） 不显示 —— 正文不进界面，它是给模型的
这一栏是「界面与工具同源」的验收方式。 把每个 action 的返回字段逐一对到界面的某一处，就会发现只有 activate / deactivate / list_active 三项在界面里没有一一对应 —— 它们落在时间线与一行摘要上。
这个「对不齐」本身是结论：模型的工作过程不搬家到管理界面里。 界面显示的是配置与后果，模型的动作留在它发生的地方。
刻意没有的三个 action：create_package / update / delete。 写盘只能从界面走（§7）。理由和天枢一样，但理由要写全：
① 模型直接改盘 = 技能内容变成模型的输出，而 description 是契约（§4）—— 模型会为了「让技能被读到」去改自己的触发条件，那是自我授权。
② 写盘没有第二道闸：工具管理里审批是唯一的无约束兜底，而技能包写入会改到别的会话正在读的文件。
③ 用户无法回答「这个技能是我写的还是它自己改的」。
所以 OST 的分工是：模型只读，界面可写。界面上那个编辑器是唯一的写入口。

「索引片段按角色过滤」与「工具目录按角色取交集」必须是同一件事， 否则模型会看见一个自己读不了的技能。
工具那条好办：工具进的是 API 的 tools 参数，loop 在装配时取交集就行。 技能索引是一个文本片段，所以过滤必须发生在片段被组装之前 —— 一份不分角色的索引片段，配上一个按角色拒绝的 skill_manager.read， 每轮都会产生「模型看见 → 去读 → 被拒」，而拒绝理由用户看不到。
所以：skills.list 加一个可选的 characterId （只加字段，不改语义、不加 topic）， loop 先 agent.resolve 拿角色，再按角色要清单。 技能目录仍然只有 skills 服务持有，skill_manager 的可读范围 就是那份过滤后的清单 —— 看得见的就一定读得到。
第三行是本设计新增的一条，也是最容易实现错的一条。 「停用全部技能」与「卸载全部技能」在实现上是两个完全不同的状态： 前者目录还在，skill_manager 仍注册（它还有 list_packages 可调，只是返回空列表）， 后者才触发注销。所以启用开关不能直接连带工具注册态 —— 否则「停用一个技能」就会让模型的工具目录少一项，而用户只是关了一个东西。

7编辑器 · SKILL.md 是唯一要写的东西

整个技能只有一个文件：SKILL.md（frontmatter + 正文）。编辑器就是它的一个表单化外壳。

SkillEditor 改 description → 左下角实时体检；保存 = 一次 skill.package.write + 重新注册 · 下一轮生效
保存的语义必须写在按钮旁边：「下一轮生效」。 prompt 每轮重算，历史里的 system 一律丢弃 —— 所以改完立刻生效，不会追溯已有会话里的任何一轮。这既是特性也是意外来源， 不写清楚用户会以为「我改了怎么刚才那轮还是老样子」。
（同一个性质在角色提示词上也成立，见 ../chat-workbench/智能体角色-组件Demo.html。）
正文编辑区刻意不做富文本 / 不做 Markdown 预览。 技能正文是给模型读的，不是给人排版的。做预览会诱导用户去「美化」， 而美化对模型毫无收益、对字节数只有损失。
scripts/ 区域只读且带删除线：P6 阶段审批位没落地，执行位必须显示为不可用 —— 否则「文件在目录里」会被读成「它能跑」。
编辑插件自带技能要显式拒绝。 它们住在别的插件目录里，本插件既读不到也写不到（plugins.readFile 的边界， 见 §3）。所以对这类技能只提供「查看 frontmatter 摘要」+ 一句人话原因， 不提供「去那个插件改」的超链接 —— 我们连它在哪都不知道。

点天枢 devOST 本设计
分组维度category（finance / mysticism …）， 且 categoryLabels 硬编码后已过期，9 个分类里 5 个显示英文 slug owner（用户自建 / 插件自带 + 具体插件）。分类不存在，就不硬造一个
