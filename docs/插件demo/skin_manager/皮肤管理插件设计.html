一句话：给「角色长什么样」这件事一个主人 —— 而那个主人是用户。
资产进 userData/plugin/skins/，由 skin 服务独占读写。 「我想让这个角色长什么样」是用户的选择，与 tools/approvals.json（用户的授权决定）、 models/preferences.json（用户的接入决定）同一类。 所以界面可写：上传 / 裁剪 / 停用 / 删除都有落点。
代价是明摆着的，全部写在这里（判据始终是同一句：这是用户的决定还是产品的一部分？）：
① Core 要加一条路由。今天 GET /plugins/<id>/ui/* 只伺服 dist/ui，而 plugins.readFile 是 utf8 / 2 MiB / 只限自己插件目录 —— 送不了二进制。需要新增 GET /plugins/<id>/data/*（§6 逐条核对）。 它仍然只是一条路由：Core 继续只做「穿越检查 + MIME + 缓存头 + 搬字节」， 不解析内容。
② 要回答两个真源的冲突。skins.json 是持久文件， 而内置皮随插件升级而增删改 —— 不做合并的话，新内置皮永远不会出现、 下线的内置皮会永远赖着。合并规则是 shared/src/skin.ts 的 mergeCatalog，三条规则见 §6。
③ 卸载不删数据，照 approvals.json 的先例：数据保留、 只是不再可用，重装即恢复。代价是界面要能回答「这些旧资产占着多少磁盘」。
④ 路径校验变成运行期的事。资产路径不再由构建保证，必须每次写都验（第一道闸）， 外加 Core 路由侧的穿越检查（第二道闸）。两道不是重复，理由见 skin.ts 头部。
角色侧仍然只多一个字段：characters.json 里加 skinId?: string，与 tools:["read_file"] 同级。 本插件一个字都不写那个文件 —— owner 是 agents 服务， 界面由 widget.agents 写。
配套：角色界面的落点见 ../character_manager/智能体角色-组件Demo.html §10。

1定位：这个插件管什么，不管什么

它管（3 件）

  • 皮肤目录的唯一真相源：skins.json 经 skin.list 收集、经 skin.state 重播整份。
  • 一个可复用的渲染组件：SkinRenderer（三个 mode + 四级回退链）， 谁要用谁 import —— 它随 dist/ui/ 一起伺服，别的插件视图 用 <img src> 直接引，不需要它跑起来。
  • 一份可预览、可编辑的清单：widget.skins 列出有哪些皮肤、 各自带几个动作、被哪些角色引用，并提供新建 / 上传 / 改名 / 停用 / 删除。
    它拥有 userData/plugin/skins/ —— 卸载插件不清这里，重装即恢复。

它不管（5 件）

  • 不管角色：skinId 写在 agents 的 characters.json 里，owner 是 agent 服务。 本插件一个字都不写那个文件。
  • 不管会话与消息：皮肤不进 loop.run 的任何字段， 不进 prompt、不进 tools 参数。一个字节也不发给模型。
  • 不管装配：它不参与第 ④ 步的四层提示词合成。装配摘要里那行 「外观：不影响本轮装配」是诚实而不是遗漏。
  • 不管审批：皮肤没有任何执行体，不产生副作用，不需要闸门。
  • 不拥有用户数据：userData/plugin/skins/ 不存在（§11）。
为什么「不管角色」这条要写在最前面。 因为最容易被想到的形态是「在角色管理里加个『上传立绘』按钮」—— 天枢改造前就是那样的（CharacterVisualEditor.tsx），而那份文件现在 没有任何地方 import 它，是死代码。改造记录在 天枢 dev/docs/skin-decouple-plan.md，§一原话： 「把角色主观定义与『视觉/动画』解耦：角色绑定皮肤，皮肤是一组可复用的视觉组合」。
本设计沿着它继续往下走了一步：连 skinId 之外的一切都不进角色档案。

2地基决定：资产是用户数据，Core 加一条路由

这一节单独拎出来，因为其余所有设计都由它派生。三条路线对照，标出本文采用的那条：

A · 资产进 userData 本文采用

userData/plugin/skins/ ├── skins.json owner: skin 服务 └── miku/ ├── portrait.png └── idle.webp …
  • 用户可上传 / 裁剪 / 停用 / 删除
  • 需要 Core 加一条路由（§6）
  • 卸载保留数据，重装即恢复

B · 资产进 dist/ui

plugins/skins/ ├── catalog.json → 构建复制 └── assets/… → 构建复制 落 dist/ui/
  • 照 models/catalog.json 的先例
  • Core 零改动 —— 而这就是它唯一的优点
  • 界面只能只读：用户传不进自己的图
  • 改一张脸 = 等我们发一次版

C · 资产走总线 base64

skin.asset.get{ id } → base64 + 33% 膨胀 → 撞 2 MiB / 帧大小
  • 技术上能写出来
  • 一段 8 MB 立绘走不通
  • 违背「工具目录进 API 参数而非文本」
选 A 的理由：它是「用户的数据」，不是「产品的内容」。 判据只有一句，与 tools/approvals.json、 models/preferences.json 完全同一条： 这是用户的决定还是产品的一部分？
「我想让这个角色长什么样」显然是用户的决定。所以它进 userData， 卸载时保留，重装即恢复 —— 用户装插件是为了用它，不是为了每次升级都重新画一遍脸。
B 形态（资产随插件走）适合的是产品自带的那几张脸，它有个真先例 （models 的 12 家厂商预设）。但它是只读的： 用户改不了任何一张，而「改一张脸要等一次发版」正是它唯一做不到的那件事。
「Core 零改动」在 B 形态下是优点，在 A 形态下只是达标线。 凡是用户能改的东西，宿主都得提供一条取它的路 —— 否则「能改」这件事无法兑现。 Core 欠的那一条是「按目录伺服用户数据」，不是「理解皮肤」， 而这与它已经在做的 dist/ui/ 伺服是同一件事，只是目录不同（§6）。
所以本文取 A，并且把内置皮也放进同一份 skins.json —— 用 builtin 字段区分两类，而不是分成两个存储位置。 理由见 §6 的合并规则：分成两处就要回答「同名怎么办」， 而那正是第二个真源的起点。
A 要给 Core 加的那条能力，是「搬字节」而不是「理解内容」。 Core 现在的职责是两句话：查白名单、搬字节（外加记 service.* 生命周期）。 GET /plugins/<id>/data/* 听起来也是搬字节， 它要求 Core 知道的只是「这个插件的数据目录在哪」 —— 而那个锚点已经存在：shared/src/paths.ts 的 pluginDataDir(dataDir, pluginId)， 握手里发给每个服务的 dataDir 就是它。
Core 仍然不知道什么是 portrait、什么是 skinId、什么是 license。 那些全在 skins.json 里，是内容，由服务与 UI 各自解析。 这就是「不解释 payload」那条纪律没有被破坏的意思。

A 形态的五条直接推论

推论为什么必然界面上的样子
有上传 / 裁剪 / 删除 运行期有可写的目录（userData/plugin/skins/）， 服务握手里就有它的路径 widget.skins 是编辑器：目录 + 上传 + 裁剪 + 动作预览。 与 tools 插件形态一致，区别只在数据住哪（§8）
有「停用」开关 enabled 落 skins.json，与「删除」分开 停用 = 渲染侧不看它，资产保留、随时开回来。 不要把停用做成删除的软化版 —— 按错一次丢图是比多点一次更贵的事
删除要问「有没有角色在用」 删了之后那些角色的 skinId 会变悬空 skin.set{ removed:true, confirmUnreferenced }。 服务拿 agent.state 核对，被引用就拒绝并列出引用者。 而 confirmUnreferenced 必填，因为那份数据可能没到（§4）
卸载插件 = 数据保留 照 approvals.json 的先例：用户的决定不该被卸载悄悄清掉 重装即恢复用户的皮肤。代价是界面要能回答 「userData/plugin/skins/ 占着多少磁盘」，§11
要回答内置皮与用户皮的关系 skins.json 是持久文件，而内置皮随插件版本变化 mergeCatalog：内置以代码为准、用户皮以数据为准、 孤儿内置皮留痕并给删除按钮（§6）

3拓扑：谁在哪个进程，一条皮肤解析经过谁

下面是本插件落地后的进程图。核心观察只有一处： 资产从 Core 到浏览器的这一跳，是一条早就存在的静态路由，本插件只是把自己的文件放进它的目录。

HTTP（过 Core）：伺服 UI / 收命令 / 发事件 / 取资产 总线（过 Core）：命令与事件都走这条 文件（进程内，不过 Core）：服务读自己插件目录 外部（不过 Core） 进程内调用（不过 Core）
第 ④ 跳是本设计全部的巧思所在，而且它是白捡的。 <img src="/plugins/skins/ui/assets/miku/portrait.png"> 只是一次同源静态 GET。 而 plugin-ui.ts 开头那段「同源，而不是再开一个端口」的论证 （同源才有 postMessage / localStorage / BroadcastChannel，多一个源就多一处 CSRF 面） 正好让这件事不需要任何跨插件通信。
于是：widget.chat-timeline（chat-workbench 的 iframe）能画 skins 插件的皮肤， 而两个插件之间一条消息都没有，Core 也不需要知道「谁在画谁」。 这与「插件 iframe 之间彼此零通信」那条纪律完全一致 —— 它不是被绕过的，是被用上的。

4协议：4 个新 topic（2 事件 + 2 命令）

这是 tools 插件（13 个）与 skills（skill.registered）的同一个模式， 规模小得多 —— 因为皮肤没有执行体、不产生副作用、不需要审批。

'skin.list'            { }                                  // 收集方上线时问一次
'skin.set'             { requestId, patch: SkinSetPatch }   // 合并式改元数据 / 停用 / 删除

// ── shared/src/events.ts · EventMap 新增 2 行 ──
'skin.state'           { skins: SkinBrief[] }               // owner 重播整份
'skin.set.result'      SkinSetResult                        // ok / blockedBy / reason
已落地：以上四条与 SkinBrief / SkinSetPatch / SkinSetResult 见 shared/src/skin.ts 与 shared/src/events.ts（M1 已完成，65 个单测）。

skin.set 为什么长这样

三种操作（改元数据 / 停用 / 删除）形状不同，因为它们的失败模式完全不同 —— 混在一个 patch 里，调用方就得自己判断哪个字段组合合法：

操作形状典型失败
改元数据id + patch{name?, license?, enabled?} id 不存在
停用id + enabled: false 被角色引用中
删除id + removed: true + confirmUnreferenced: true 被角色引用中；不可逆（资产目录一起删）
「停用」与「删除」必须分开，不能合成一个 enabled。 前者让渲染侧不再用它、资产保留、随时开回来；后者连 assets/ 一起删、 不可逆。把两者并成一个布尔，用户按错一次就永久丢图 —— 而「按错」的成本只是多点一次界面。
为什么删除要用户点两次确认（confirmUnreferenced 必填）： 服务会拿 agent.state 里活着的角色核对有没有人在用。 但那份数据可能没到（agents 服务刚起、或已被卸载）， 那时候服务无法确认。所以「我确认没人用」这句话要由更有资格的人（用户）说。
推论：blockedBy: [] 有两个含义（真的没人用 / 不知道有没有人用）， 界面上不能把它当成「确认无人引用」的证明 —— SkinSetResult 的注释里写了这一条。

皮肤清单的 schema

// userData/plugin/skins/skins.json  —— owner: skin 服务，持久文件
{
  "version": 1,
  "skins": [
    {
      "id": "default",              // 全局唯一；会变成一个目录名，所以不许含分隔符
      "name": "默认",
      "builtin": true,              // 内置（随插件版本走） vs 用户自建
      "enabled": true,              // 停用 = 渲染侧不看它，资产保留
      "license": "MIT",
      "assets": {
        // 存「记录」而不是路径 —— 见下面的说明
        "portrait": { "assetId": "a1b2c3d4", "bytes": 482103, "mtime": 1735689600000, "ext": "png" },
        "avatar":   { "assetId": "e5f6a7b8", "bytes":  12044, "mtime": 1735689600000, "ext": "png" }
      },
      "motions": {
        "idle":     { "assetId": "0a1b2c3d", "bytes": 88422, "mtime": 1735689600000, "ext": "webp" },
        "thinking": { "assetId": "1b2c3d4e", "bytes": 91233, "mtime": 1735689600000, "ext": "webp" }
        // … 另外四个，或整个 motions 省略（静态皮肤也是合法皮肤）
      }
    }
  ]
}
为什么资产存「记录」而不是路径。 写 "portrait": "assets/default/portrait.png"（手写相对路径）有两个问题：
① 改名 = 改 JSON：用户在界面上换一张图，服务得去改 skins.json 的字符串， 而那个文件正被别的逻辑读写，两处改同一个文件容易撞。
② 缓存没法失效：文件被替换但名字没变，浏览器继续用缓存里的旧图 —— 用户换了图却显示没变。
所以存三件事：内容寻址的 assetId（换内容就换 id）、 bytes（配额与上传前预检）、mtime（变更检测）。 真实路径由服务按 assets/<assetId>.<ext> 拼出来 （skinAssetFileName()，路径规则只有这一处知道）。
⚠️ bytes 是上传真值，不是真相。真值由服务读文件时 stat 得到；这个字段只用于配额与前端展示。
动作名刻意收窄到 6 个，照抄天枢 SkinVisualEditor 暴露的那 6 个 （idle / thinking / working / speaking / success / error）。 天枢的 motion 枚举其实有 16 个（blink / breathe / listening / toolCalling / happy / touched / wave / walk / jump / sleep…），但编辑器只给 6 个。
本文取 6 个，因为渲染侧要能自己决定播哪个： 一个只有 idle 与否的渲染器，遇到 blink 就必须回退， 而回退策略又是一笔界面复杂度。少而够用，比多而半吊子好。 多出来的动作在 skins.json 里合法但不被引用，界面上标「未被使用」而不是报错。

SkinBrief —— 事件里到底带什么

这是 AgentLoop 教程里唯一一个没有定义过的类型（§2 那张表只写了 { characters: CharacterBrief[] }，CharacterBrief 全文未出现）。 本节顺手把它定下来，因为两个插件都要用：

字段类型说明
idstring引用它的那把钥匙。缺失即悬空。 过 assertSafeSkinId —— 它会变成一个目录名（§8 第 2b 条）
namestring人类可读名
builtinboolean内置 / 我自建的。界面上必须能区分 —— 它决定了升级会不会覆盖它（内置以 fresh 为准，用户皮以数据为准，§6）。 缺省视为 true（迁移期旧清单都没有这个字段）
enabledboolean停用开关。与「删除」是两件事： false 只是渲染侧不再选它（可逆），资产保留。 缺省视为 true。
停用不改任何角色的 skinId —— 角色侧会显示成「绑着但不可用」，恢复动作是「启用」而不是「解绑」
assets{ portrait?, avatar? } 每条是一个 SkinAsset：文件 id（内容寻址）+ 字节数 + mtime + 扩展名， 不带 URL。真实路径由服务按 assets/<assetId>.<ext> 拼出， 浏览器经 /plugins/skins/data/… 取（§6）—— 路径规则只有服务一处知道，不进数据文件
motionsRecord<Motion, SkinAsset> 同上。可以为空（一套静态皮肤也是合法的皮肤）。 六个之外的动作名合法但不被引用，值仍要校验
licensestring第三方皮肤必须带。缺失时界面要显示警示 而不是默认当 MIT
providedBy · createdAt · updatedAt string · number · number 来源插件与时间戳。updatedAt 只在界面上显示， 不作为排序键 —— 换一张图就重排会让用户点着的那一行跳走（§6）
规范化的三处承诺（输入宽、输出窄，SkinEntry → SkinBrief）： assets 省掉 → {} · builtin 省掉 → true · enabled 省掉 → true · motions 只保留六个枚举内的键。 把它们混成一个类型，就得在类型上放宽输出、或在类型上禁止合法的输入。
「URL 前缀不进业务数据」这条要守住。 如果 skin.state 里放的是完整 URL （http://127.0.0.1:4317/plugins/skins/ui/assets/…）， 那么端口与前缀会从 Core 的路由层泄漏成一份要同步维护的数据： 改端口要改 skins.json，而 skins.json 是 用户数据 —— 用户数据被我们改坏了，是最难排查的那种坏。
所以前缀由两处各自固定一次：Vite 的 base（构建期）与 SkinRenderer 里的常量（运行期）， 清单里一个 URL 都不放。清单只给 skinId + assetId， 由渲染器自己拼。 同一条纪律在 models 那侧已经付过学费 —— plugin-ui.ts 里那段注释专门解释了为什么插件的 Vite base 必须写死前缀。 那是有意的重复，因为拼错前缀的症状是「两个插件互相换脸」，离原因很远。

它做的事，按顺序

#动作细节
1启动即读三处 ${dataDir}/skins.json（fs 直读，不是 plugins.readFile —— 那个 RPC 只服务插件自带数据） + 打包进来的 builtin-skins.json 与 builtin-assets/。三者合成一份（§6 的合并规则）。
读失败不崩：发一份空 skin.state + 一条 service.degraded 语义的日志，界面显示「清单读不到」。
不要给用户「重试」按钮 —— 重试一万次结果一样（是文件不在，不是网络抖）
2校验并规范化 用 shared 里的 parseSkinCatalog（与 parseVendorCatalog 同一套做法：校验规则只有一份）。 校验内容：id 唯一 · 路径不得以 / 开头或含 .. · skinId 与 assetId 都要过一遍（它会变成目录名，见 §8 第 2b 条）
3publish skin.state 重播整份。这是 owner 的义务，也是订阅方能只写一行订阅就拿到全量的原因
4收到 skin.list → 再 publish 一次 收集方上线时问一次。服务不记账、不记「谁问过」 —— 总线不提供返回值，重播整份让这个问题自然消失
5收到 skin.set → 改一处、答一次 三条路径：元数据（改 skins.json）· 资产（写文件 + 生成新 assetId）· 删除（删清单条目 + 删目录）。
每次都回一条 skin.set.result（带 requestId）。
先落盘再重播：顺序反了会出现「界面说有、文件没有」的一帧
它一共 260 行，其中没有一行在处理图片像素。 这是刻意的：服务只写字节与清单，显示由 Core 的静态路由送（§3 第 5 跳）。 所以这个进程不占内存、不做解码，而且「已显示的皮肤」不依赖它在位。
与 tools 服务对比会很直观：后者要转发执行、要管审批 pending 表、 要落审计 —— 因为它在一条数据通路上。皮肤不在。
写操作的失败路径比成功路径多，这是这一节真正要设计的东西。 资产写入至少会遇到这五种，每一种都要答得具体（§8 第 1 条）：
  • 格式 / 大小不合法 → 服务再验一遍（客户端验过也要验）
  • 磁盘写不了（满 / 只读）→ 这是环境问题，不该报成「图片有问题」
  • 清单写成功、文件写失败 → 最坏的一种：清单指向一个不存在的文件。 所以顺序是先写文件、成功后才写清单，而失败的文件要清掉（不然后面重试全是坏条目）
  • 删除被引用挡住 → 回 blockedBy，一个字都不改
  • 并发 patch 撞车 → 两个 skin.set 同时改同一套皮肤。 处置是「整份重写 + 按 requestId 排序回答」，不引乐观锁 —— 清单是 KB 级、单机、一个人编辑，引锁的成本高于它防的问题

路径穿越校验仍然不能省，但理由变了。 B 形态下 skins.json 可能来自第三方插件；A 形态下它只由服务自己写， 穿越风险降到很低。
但它变成了「防我自己写错」：skinId 会变成目录名， 用户可能起名叫 "../evil" 或 "C:\Windows" ——这不是攻击，是手滑，而手滑造成的后果与攻击一样。 所以 assertSafeSkinId 是用户接口的一部分，不是安全补丁。

6资产通路：Core 要加的那一条路由，以及六个边界

§2 选了用户数据，于是这一节从「怎么绕过 Core 的限制」变成 「Core 要加什么、加完之后边界在哪」。六条全部是仓库里核对过的事实， 出处标在表尾。

环节现状（已核对）本设计怎么办
服务写数据 ✅ 已有。握手的 dataDir 指向 pluginDataDir(dataDir, pluginId) （shared/src/paths.ts），那是可写的 直接用。skin 服务落 ${dataDir}/skins.json 与 ${dataDir}/<skinId>/assets/。 不需要 Core 参与这一步
服务读清单 plugins.readFile 只读自己插件目录（dist/ 侧）， utf8 · 2 MiB 上限 也不需要它：清单在 dataDir 里，服务直接 fs 读 —— 它本来就能写那个目录。plugins.readFile 那个 RPC 服务的是 插件自带数据（models 的 catalog.json），与这里无关
浏览器取资产
← 唯一的新增		 GET /plugins/<id>/ui/* → registry.uiDir(id) （= dist/ui）。userData 没有任何路由伺服 新增 GET /plugins/<id>/data/*，根 = pluginDataDir(cfg.dataDir, id)。 穿越检查沿用 plugin-ui.ts 那四行（同构，不是新写法）。 Core 仍不解析内容 —— 它不知道什么是 portrait
MIME contentTypeFor 的表里有 svg png jpg jpeg gif webp ico， mp4 / webm 不在表里 → 回落 application/octet-stream v1 只用 png / webp / gif —— 动画 webp 与 gif 在 <img> 里就能播（object-fit、 尺寸控制全都一样）。mp4 作为增量列入待决（§15 第 3 条）
缓存头 immutable 的判据是 /-[0-9a-zA-Z_-]{6,}\.[a-z0-9]+$；否则一律 no-cache 走 userData 之后这条路更顺：assetId 就是内容寻址的 （§4），换一张图 = 换一个 assetId = 新 URL， 缓存自动失效。不需要任何版本号或查询参数。 而它匹配不上 immutable 判据（a1b2c3d4.png 没有 - 前缀的哈希段）， 所以会走 no-cache —— 对 32px avatar 无所谓， 立绘与动作要走 no-cache 就要考虑流量（待决）
SPA fallback 插件 UI 路由的未知路径不返回 404，而是回 index.html（200 + HTML） 新路由不能有这个 fallback —— 它伺服的是数据不是页面， 回 index.html 会让「资产不存在」变成一段 HTML。
于是 SkinRenderer 仍然要靠 onerror： 拼错路径 → 404 → <img> 解码失败。 但「拿到的不是图片」这一层消失了，错误更好判（§7）
新路由必须比 static.ts 先判，且要过 Origin 白名单。 server.ts 里 /plugins/ 的判定已经在 static.ts 之前（注释写明「顺序反了，插件的 404 就永远说不出口了」）。 /data/ 要挂在同一个 /plugins/ 判定里， 否则会被 static.ts 兜底成 SPA。
Origin 白名单同样要过 —— 与 /plugins/*/ui/* 同一套判定， 不加就等于给 CSRF 开了个口子（能读用户皮肤目录）。
「一份数据，一个投递路径」——走 userData 之后这句话反而更简单了。 服务与浏览器读的是同一个文件：服务 fs 读 dataDir/skins.json， 浏览器经新路由读 /plugins/skins/data/skins.json。 没有副本、没有「构建时复制」那一步（那是 B 形态才需要的）。
校验规则仍然只有一份：shared/src/skin.ts 的 parseSkinCatalog，服务端与 widget.skins 都调它。 漂移的症状会是「界面上有的皮肤，资产 404」—— 而那离原因很远。

内置皮与用户皮：mergeCatalog

这是走用户数据之后唯一真正难的地方，因为 skins.json 是持久文件， 而内置皮随插件版本变化。三条规则各自对应一个方向的问题：

#规则不这么做会怎样
1内置皮以代码为准（fresh 覆盖 persisted 的同名内置条目） 用户改过内置皮的显示名，升级后被静默改回。 这是有意的：内置皮是产品的，用户对它没有所有权。 想让名字保持自己的，就 fork 一份（新建一条 builtin:false）
2用户皮以数据为准（persisted 里 builtin:false 的， fresh 覆盖不进去） 插件某天恰好也内置了一个叫 mine 的皮 → 用户的皮被产品皮覆盖 → 用户做的图全丢
3孤儿内置皮留痕（从版本里消失的不静默丢，进 orphanedBuiltin） 上游删掉某个内置皮 → 用户的清单里永远赖着一份， 界面上还显示着、点进去发现文件没了。留着 + 给删除按钮， 界面上标「已从插件中移除（数据保留）」
落盘顺序也必须是确定的。mergeCatalog 输出与落盘都按 「内置在前、再按 name 的码位」排。 为什么要钉住：顺序抖动会让 changed 永远为 true， 于是每次启动都重播整份 skin.state，而订阅方什么也没变。
按码位比意味着中文名的顺序不随直觉走（霓 U+9713 < 默 U+9ED8，所以「霓虹」排在「默认」前面）。 这不是 bug，是「用码位保证确定性」的必然结果。界面上要按语言习惯排的话得另给 localeCompare，那是界面的事，不影响落盘顺序。 单测里把这个结果写死了，好让「顺序偶然对」变成「顺序被钉住」。
唯一一处 Core 改动（可选，且是纯增量）。 若采纳 mp4：core/src/sse-bridge/util.ts 的 MIME 表 加 '.mp4': 'video/mp4' 与 '.webm': 'video/webm' 两行。 不动任何路由、不动穿越检查、不动 Core 的职责边界 —— 它只是「按扩展名给 Content-Type」 这个既有函数的查表项，而那份表的注释已经写着「两份 MIME 表意味着迟早有一份漏项」。
建议先不做：动画 webp 已经够用，而「为了一个格式去动 Core」在收益明确之前是坏交易。

8四条新纪律

#纪律为什么 / 怎么守住
0 删除与停用是两个动作，不是一个开关 停用让渲染侧不再用它、资产保留、随时开回来；删除连 assets/ 一起删、 不可逆。并成一个布尔，用户按错一次就永久丢图， 而「按错」的成本只是多点一次界面。
所以 SkinSetPatch 里 removed 与 enabled 是两个独立字段（§4）
1 皮肤的 motion 令牌与枚举共享来源，CSS 变量名不共享 枚举（idle/thinking/working/speaking/success/error）放进 shared，两边都 import。 变量名一律 --skin-motion-*， 不许进 sdk/ui/src/tokens.css。
理由：--motion-idle 已被会话列表重设计占用（那是颜色）， 而本设计要的是资源。共享枚举是对的做法（同一批运行态）， 共享变量名是错的（撞名会让「调个色」变成「换张图」）
2 assetId 内容寻址，一个内容一个 id 换一张图 = 生成一个新的 assetId，不是覆盖同一个文件。 于是「浏览器还在用缓存里的旧图」这件事结构上不会发生 —— 新内容 = 新 URL，不需要任何版本号、查询参数或缓存失效技巧。
代价：旧文件不会自动消失，要靠「删除皮肤时连目录一起删」与 「清理未被引用的皮肤」（§11）两条出口。孤儿文件无害，只是占磁盘
2b 路径校验两道闸，各管各的 ① shared/src/skin.ts 的 assertSafeAssetId / assertSafeSkinId —— 写入时 fail fast， 用户当场看到「这个路径不合法」
② Core 新路由的穿越检查 —— 读取时的最后一道
不是重复：① 的价值是「错误发生在用户看得见的那一步」， 而不是过五分钟某个 <img> 拿到 403， 那时候用户已经不知道刚才那一步是哪一步了。 这与工具侧「约束 + 审批」是同一条纪律
3 四级「拿不到」必须分开报，不能合成一句 ① 没绑（合法回落）② 已确认悬空（清单在，但没有这个 id —— 说得出是谁的，给解绑） ③ 无法校验（skin.state 没来 —— 不能说是谁没提供，给重试） ④ 资产加载失败（清单在、id 对，但文件取不到 —— 文件被删或磁盘出错，给重试）
合成一句的后果很具体：用户在场景 ② 会去重装插件，而真正要做的只是删掉那条绑定； 在场景 ③ 他会以为「某个插件坏了」，而真相是「插件没装」。
② 与 ③ 的分界正是 §6 那条「没收到 skin.state」—— 一份清单都没拿到，说出提供方就是猜
4 皮肤降级不影响任何能力 skin 服务挂、插件被卸、资产 404 —— 角色仍然完全可用： 提示词、技能、工具、模型偏好一项不少。
因为皮肤一个字节也不进模型（§1、§5）。这条要在界面上写出来， 否则「界面变丑了」会被当成「Agent 坏了」—— 而用户在皮肤失效时第一反应就是重开会话，白白丢掉上下文
第 4 条有一个反直觉的推论，值得单独说。 因为外观完全不参与装配，所以它没有「生效时机」问题 —— 提示词要写「下一轮生效」（因为每轮重算），而皮肤改一下立刻就变 （因为它只是换一个 <img src>，下一帧就重画）。
不要给皮肤加「下一轮生效」那种提示。那是照抄提示词那一条的结果， 而两条的时间尺度根本不同。界面文案要跟各自的机制走， 不是跟上一版界面走。

决定为什么

引用数写在卡片上，但不给「去改」入口 见 §9 最后那条。写清「被 3 个角色引用」是有决策价值的（决定能不能删）， 而跳转是另一个议题

不要按「最近更新」排 —— 走用户数据之后用户会频繁换图， 那一列一动，用户点着的那一行会跳走。 updatedAt 可以显示，但不作为排序键（§6）

「缺动作」这件事必须逐个可见，而且要能补

用户自建的皮肤常常只带 portrait 与 idle。 缺哪几个必须逐个画出来（虚线框 + 状态点），因为：
  • 隐藏缺失 → 用户以为这套皮肤「只有这些动作」，而回退是在会话里撞见的（§7 第 1 级是静默的）
  • 合并成一句「部分动作缺失」 → 用户不知道该期待哪几个，于是每个都用不对的预期去撞
状态点三色与工具面板的 pill 语义一致： 绿 = 有，灰 = 这个皮肤没声明（不是错），红 = 声明了但取不到（是问题）。
走用户数据之后，灰色的那几格要带一个「+ 补上」 —— 那是这个视图从「只读目录」变成 「编辑器」的具体体现，也是用户新建一套皮肤后最想做的事。
上传的四条约束（都要在界面上说清，不要让用户撞到）：
  • 格式白名单：png / jpg / jpeg / webp / gif / svg。 没有 mp4 —— Core 的 MIME 表里没有它，会回落成 octet-stream 而 <video> 放不出来（§6）。动画 webp / gif 在 <img> 里就能播
  • 大小上限：单文件与服务总量两个上限都要有，且上传前在客户端预检 （bytes 是上传真值，§4）。服务端要再验一遍 —— 客户端校验是为了体验，服务端校验是为了正确性
  • 每次上传生成新的 assetId，不覆盖旧文件。 于是「换图后浏览器还显示旧的」结构上不会发生（§8 第 2 条）
  • 失败要说清是哪一步：格式不对 / 超大 / 磁盘写不了 / 校验不过。 合成为一句「上传失败」的话，用户重试三次就走了

卸载语义

动作资产与清单characters.json 的 skinId界面
卸载 / 停用 skins 插件保留保留 角色页显示「无法校验」+ 解绑可用（§8 第 3 条）； widget.skins 整个视图不存在（它是插件产物）
重装 skins 插件原样回来保留 用户的皮肤一张不少 —— 这就是走用户数据换来的东西。 然后 mergeCatalog 把新的内置皮并进来
升级 skins（新内置皮上线）新增内置皮；用户皮一条不动保留 新皮不会自动绑到任何角色上 —— 绑定是一个显式的用户决定
删掉某个角色不受影响删那条 皮肤不随之删除：它可能被别的角色引用，也可能还没被引用
删除一套皮肤连资产目录一起删（不可逆） 被引用则拒绝 二次确认，且要填 confirmUnreferenced（§4）。 想保留就「停用」 —— 那个可逆
进程被 kill -9不受影响不受影响 正在显示的皮肤不受影响 —— 资产由 Core 的静态路由送，不经过这个进程
备份 / 迁移 dataDir一起搬一起搬 皮肤与引用关系同时恢复，不会出现「图在但引用丢了」
这一节与 tools 插件的卸载表完全一致，而且这正是应该的。 tools 的 approvals.json 走「数据保留、只是不再可用」， 因为那是用户的授权决定。皮肤走同一条，因为它也是用户的决定 （§2 的判据）。
对照一下 B 形态会是什么样：资产随插件走，卸载即消失， 于是「重装之后我的皮肤没了」—— 而用户装插件是为了用它。 那个形态下唯一说得通的皮肤是产品自带的那几张，用户一张也改不了。
走用户数据之后，多了一个 B 形态没有的问题：磁盘占用。 用户上传的立绘动辄几百 KB 一套，几十套就是几十 MB，而卸载插件不会清掉它们。 所以设置页要能回答「userData/plugin/skins/ 占着多少」， 并给一个「清掉未被任何角色引用的皮肤」的入口。
⚠️ 那个入口不能默认全选 —— 「未被引用」是一个推断 （读 agent.state，而那份可能没到，§4）。 所以列表要逐条列出来、让用户勾选，默认勾选为空。

12不变式与红线（本设计不得破坏）

不新增进程间协议：stdio JSON-RPC + shared 的 EventMap/CommandMap 仍是唯一入口。本设计的 4 个新 topic 全部是这张表上的四行，不是新机制。
Core 的全部改动：一条路由。 GET /plugins/<id>/data/*（§6）—— 它不做穿越判断以外的事，仍然是查白名单 + 搬字节。
而这一条路由本身也不是新机制：它与 /plugins/<id>/ui/* 是同一段代码换了个根目录（registry.uiDir(id) → pluginDataDir(dataDir, id)）。 唯一的行为差异是不做 SPA fallback，而那是因为它伺服的是数据。
不变式本设计如何满足
Core 不解析插件内容 皮肤清单是内容，经总线；资产是字节，经静态路由。 Core 只做穿越检查 + MIME + 缓存头 —— 它不知道什么是 portrait， 也不知道 userData 里哪个目录归哪个插件（那是注册表给的现成答案）
能力存在性必须有重播通路 skin.list（收集方上线问一次）+ skin.state（owner 重播整份）。 与 tools / models / skills 同一套。写操作同理： skin.set 带 requestId， skin.set.result 回同一个 id —— 总线不提供返回值， 所以「谁在等」必须由发起方自己记住，这一条对读是隐含的、对写必须显式
缺失是合法的 没装 skins 插件 / 角色没绑 skinId / 绑的 id 不存在 / 资产 404 —— 四者都不是错误，只是「少一层外观」。角色完全不受影响（§8 第 4 条）
顺序必须确定 目录排序内置在前、再按 name，不依赖文件系统的 readdir 顺序。 动作渲染顺序由枚举定义，不依赖对象键序
写只限自己 本插件只写 ${dataDir}/ —— 那是握手时 Core 指给它的、 本来就属于它的目录。它一个字都不写 characters.json。
读：清单走 fs，别的插件的数据经总线只读。
这条纪律的形态变了，但没松：B 形态是「零写路径」， A 形态是「写路径存在，但它的根是 Core 发给我的那个根」
绑引用不绑实现 skinId 与 tools:["read_file"] 同级。 agents 的产物里没有任何一行与像素有关； 皮肤被删了，agents 那份数据也仍然合法（它只是一个 id 字符串）
消息唯一写者 本插件不写任何消息，也不发 loop.run。 三个对话视图因此零改动
界面不做装饰性欺骗 没装插件则整个视图消失（它是插件产物）；角色侧显示「无法校验」而不是空白或写死的「默认」； 停用是真的生效（灰掉、引用变成无效），而不是点一下只改个本地变量
失败也要产结果 skin.state 在清单读失败时仍然发一份空清单而不是不发 —— 订阅方要能区分「清单是空的」与「清单还在路上」； skin.set 的每一次尝试（包括校验失败）都回一条 skin.set.result —— 不能只在成功时回， 否则发命令的界面永远在转圈
删除不可逆，所以要两问 删资产要 UI 二次确认 + confirmUnreferenced。 而确认框文案要写清「删了什么、能不能恢复」 —— 用户对「删掉一个皮肤」的直觉是「皮肤没了，素材还在」， 而实际上资产目录一起没了
Core 的全部职责，本设计之后仍然是两句话。 查白名单、搬字节（外加记生命周期）· 伺服静态产物。
本设计给它加的那条路由正是它已经在做的第二句，只是根从 dist/ui 换成了 dataDir。
刻意没给的第三条：Core不参与删除判定。 「这个皮肤有没有角色在用」只有 agents 知道， 而 Core 去查它意味着 Core 要理解 characters.json 的语义 —— 那就破了上面第一条不变式。所以判定在插件里，Core 只搬字节。

kill -9 skin 服务 已显示的皮肤不动（资产由 Core 送，不经过它）；新会话显示「无法校验」； 角色其余能力完全不受影响
卸掉再重装 skins 插件 用户的皮肤一张不少地回来（§11 的 A 形态核心收益）； 新的内置皮被并进来；用户皮一条不动（mergeCatalog 第 2 条）

① 皮肤是用户的决定，所以它在 userData，卸载时保留。 这是全篇唯一的地基。判据只有一句，与 approvals.json、 preferences.json 完全相同： 这是用户的决定还是产品的一部分？
代价是 Core 要加一条 GET /plugins/<id>/data/*（§6）， 而它仍然只是换了个根目录的搬字节 —— Core 不知道什么是 portrait， 也不知道 userData 里哪个目录归哪个插件。 收益是界面可写、重装不丢用户的图。
② 内置皮与用户皮共处一份 skins.json，靠 mergeCatalog 划界。 分成两个存储位置就要回答「同名怎么办」，而那正是第二个真源的起点。 三条规则：内置以代码为准 · 用户皮以数据为准 · 孤儿内置皮留痕并给删除按钮。
③ 角色侧只多一个字符串。 skinId 与 tools:["read_file"] 同级， owner 是 agents 服务，写它的界面是 widget.agents。 本插件一个字都不写那个文件；它只写自己的 dataDir。
④ 皮肤一个字节也不进模型。 不进 loop.run、不进 prompt、不进 tools 参数。 所以它不参与装配、没有「下一轮生效」问题、坏了不影响角色能力。 不要给它加与提示词相同的那套文案 —— 那两条的时间尺度根本不同。
⑤ 零跨插件通信是白捡的，不是绕出来的。 <img src="/plugins/skins/data/…"> 是一次同源静态 GET。 plugin-ui.ts 当初为「同源存储」做的那套论证， 让「chat-workbench 的 iframe 画 skins 插件的皮肤」不需要任何协议。
⑥ 四个「拿不到」必须分开说。 没绑（合法回落）· 已确认悬空（说得出提供方，给解绑）· 无法校验（说不出提供方，给重试） · 资产加载失败（清单在、文件不在）。 合成一句的代价很具体：用户在第二种情况会去重装插件，而真正该做的只是删掉那条绑定。
