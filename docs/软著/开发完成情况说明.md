## 二、开发目的与背景

### 2.1 开发目的

本项目旨在开发一款**运行于个人计算机本地的、以 AI 大模型为核心能力的通用智能体工作台**。用户无需
掌握编程技能，即可在一个桌面应用内完成「接入模型 → 与智能体对话 → 让智能体调用工具做事」的完整
闭环，且全部对话记录、角色设定、凭证与配置都保存在用户自己的机器上，不上传第三方服务器。

### 2.2 开发背景

现有同类产品存在三方面不足：

1. **云端优先，数据不可控**：多数 AI 助手把会话与文件上传至服务商云端，用户无法掌握数据边界，
   也无法在无外网或内网环境中使用。
2. **功能固化，不可裁剪**：界面与能力写死在主程序中，用户只能被动接受；想换一种交互形态或替换
   某一项能力，只能整体换软件。
3. **只对话、不办事**：仅提供聊天窗口，不能读取本地文件、不能执行命令、不能按目标自主规划多步
   任务，实际生产力有限。

本项目针对以上不足，确立三项设计目标：

- **本地优先**：数据目录由用户指定，会话、角色、配置、凭证全部落地在本地磁盘；模型可接入本机
  运行的推理服务，全程不依赖外部云。
- **一切皆插件**：软件内核（Core）只做「发现插件、拉起服务、转发事件」三件事，所有用户可见的
  功能——对话、角色、技能、工具、模型接入、界面组件——都以插件形式存在，可安装、停用、卸载、
  替换。
- **Agent 会做事**：以会话循环（Loop）为执行引擎，支持流式回复、思维链、工具调用与执行过程展示、
  Token 用量统计、子 Agent 与目标规划，并配套可逐工具设定的「自动放行 / 每次询问 / 直接拒绝」
  三档执行策略（未设定时按工具风险档取默认值）。

## 五、软件技术架构

软件采用「微内核 + 插件 + 服务进程 + 事件总线」的四层结构。

```
┌──────────────────────────────────────────────────────────────┐
│  Tauri 2 桌面外壳（Rust）                                     │
│  · 无边框窗口 1600×900（最小 900×600）· 托盘 · 文件对话框      │
└──────────────────────────────────────────────────────────────┘
                             │ 载入静态前端资源
┌──────────────────────────────────────────────────────────────┐
│  Vue 3 工作台客户端（TypeScript + Vite + Pinia）              │
│  · dockview 负责「面板（Panel）」外层布局（停靠/拖拽/分屏）    │
│  · vue-movable-box 负责「组件（Widget）」内层几何（百分比）    │
│  · 每个组件运行在独立 iframe 中，可为不同插件提供的界面         │
└──────────────────────────────────────────────────────────────┘
                             │ HTTP + SSE（本机回环地址）
┌──────────────────────────────────────────────────────────────┐
│  Core 微内核（Node.js + TypeScript）                          │
│  · 扫描插件 → 解析清单 → 按依赖拓扑拉起服务 → 转发事件         │
│  · 提供 SSE 事件流 / 命令接口 / 偏好与配置 / 静态资源          │
│  · 不解析插件业务内容，只搬字节、只做路由                      │
└──────────────────────────────────────────────────────────────┘
                             │ JSON-RPC（标准输入输出）
┌──────────────────────────────────────────────────────────────┐
│  插件与后台服务进程                                            │
│  会话 / 循环 / 模型接入 / 工具 / 技能 / 角色 / 可靠性 / 工作台  │
└──────────────────────────────────────────────────────────────┘
```

### 5.1 微内核（Core）

Core 是可执行的最小内核，职责被严格限定为四项：

1. **发现**：扫描插件目录，读取每个插件的清单文件 `plugin.json`（声明其服务、界面组件、能力与
   依赖），并对清单做一致性校验（清单引用的事件主题必须存在于事件契约中，否则拒绝启动并报错）。
2. **拉起**：按插件依赖关系做拓扑排序，以子进程方式启动各插件的后台服务，并完成握手、心跳、
   健康检查；服务异常退出时按策略重启，超过最大重启次数则标记失败并停止重试。
3. **转发**：维护事件总线，向所有连接的前端与服务广播事件；把前端的命令按主题路由到订阅该主题的
   服务。
4. **托管与供源**：提供偏好读写、配置读写、插件界面与数据的静态资源访问、健康检查等接口。

Core 不保存业务数据、不解释会话内容、不感知「会话」「消息」等业务概念，因此插件可以被整体替换
而不影响内核。

### 5.2 插件与服务

每个插件是一个目录，其清单文件 `plugin.json` 声明四类信息：

| 字段 | 含义 |
|---|---|
| `services[]` | 该插件随应用启动的后台服务 |
| `ui.views[]` | 该插件提供给工作台装配的界面组件（Widget） |
| `capabilities[]` | 该插件对外提供的能力位（例如 `session.list`、`loop.run`、`llm.request`） |
| `dependencies[]` | 该插件依赖的其他插件 |

截至开发完成日期，仓库随附并默认安装 **7 个插件、15 个后台服务、14 个界面组件**，应用启动后
全部服务均为就绪（ready）状态：

| 插件（中文名） | 版本 | 界面组件数 | 提供的服务 | 依赖 |
|---|---|---|---|---|
| 对话工作台 | 1.0.0 | 4 | `session`、`loop`、`llm` | 模型接入 |
| 模型接入 | 1.1.0 | 1 | `llm-provider-openai` | — |
| 智能体角色 | 1.0.0 | 1 | `agent` | — |
| 技能管理 | 1.0.0 | 1 | `skills` | — |
| 工具管理 | 1.0.0 | 1 | `workspace`、`tools`、`fs-tools`、`shell-tools`、`web-tools`、`misc-tools`、`skills-tools`、`mcp-tools` | — |

### 5.3 事件契约与通信

前端与服务之间不直接互相调用，全部通过 Core 的事件总线以「主题」解耦通信。事件契约集中定义在
`shared/src/events.ts`，并遵守**只增不改**的纪律（新增主题可以，改名或改语义不可以）。主题命名
遵循 `域.实体.动作` 的规则。当前契约包含：

- **事件主题 58 条**（服务已启动 `service.starting`、服务就绪 `service.ready`、模型请求开始
  `llm.request.started`、模型流式增量 `llm.token.streamed`、模型调用工具 `llm.request.tool_call`、
  会话已创建 `session.created`、消息已追加 `message.appended`、循环状态变化 `loop.state.changed`、
  工具已注册 `tool.registered`、主题已切换 `skin.state`、角色状态 `agent.state`、技能状态
  `skills.state`、工作区列表 `workspace.list.result` …）；
- **命令主题 48 条**（会话列表 `session.list`、会话详情 `session.get`、会话创建 `session.create`、
  会话重命名/删除/置顶/归档/导出、消息追加 `message.append`、运行循环 `loop.run`、取消运行
  `loop.cancel`、模型请求 `llm.request`、模型列表 `llm.models.list`、凭证读写

软件运行时提供主题清单校验、通配订阅（`*` / `**` / 前缀匹配）与心跳保活，断线自动重连。

## 六、技术特点

1. **微内核 + 事件解耦**。内核不含业务逻辑，新增或替换功能只需增删插件目录，不需改动内核代码，
   也不会影响其他插件。

2. **插件界面进程级隔离**。每个界面组件运行在独立 iframe 中，插件样式与脚本互不污染；插件之间
   的共享状态仅保留「当前会话」一个字节，通过浏览器同源存储同步，其余状态由各自订阅事件流重建，
   从结构上避免状态不一致。

3. **双层可拖拽布局**。外层由 dockview 管理面板的停靠、拖拽、分屏与标签页；内层由自定义的
   可移动盒子组件管理同一个面板内多个组件的几何位置（以百分比为单位，适配窗口缩放），布局偏好
   持久化保存，重启后原样恢复。

4. **编辑器 / 运行时双模式**。编辑模式下面板显示网格与虚线框，可新建面板、把组件拖入窗口、
   调整尺寸；运行模式下面板布局被锁定，只保留业务操作，避免误操作打乱界面。

5. **凭证与业务数据分离**。模型服务商的密钥独立存放于本地凭证文件，只在提供服务商接入能力的
   服务进程内读取，不经事件总线传输，日志与事件流中不出现密钥明文。

6. **端到端可验证的工程纪律**。全仓库共 20 个子包纳入自动化测试，集成测试会真实拉起 Core 与
   服务进程，覆盖握手超时、服务异常退出、清单损坏、依赖成环等异常路径。

## 十、尚未完成的功能与后续计划

以下内容在本次开发周期内未完成，**不影响软件现有功能的正常使用**，将纳入后续版本：

   `<服务器>__<工具>` 登记并逐次审批），但尚未提供「检测本机已安装的 MCP 服务」与
