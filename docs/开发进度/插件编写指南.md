# 插件编写指南 · 给下一个插件照着抄

> 目的：新增能力 = 加一个目录 + 五个文件，让 Core 自动认领。本指南把现有插件拆开给你看，
> 并列明每一步的验证方式。**唯一真源永远是 `plugins/<id>/plugin.json` + 各服务的 `service.json`**，
> 本文档若与代码冲突，以代码为准并回复本文档。
>
> 最后更新：2026-10-28（依据当前 7 个插件的实际形态整理；样例取自 `reliability` / `agents` / `workbench`）

---

## 1. 一个插件长什么样

```
plugins/<id>/
├── plugin.json              # 清单：身份 + 声明了什么（services / ui.views / dependencies）
├── package.json             # 插件根包：只有 pack 一个脚本（scripts/pack-plugin.mjs）
├── services/
│   └── <sid>/               # 一个目录 = 一个子进程（JSON-RPC 服务）
│       ├── package.json     # build 用 scripts/build-service.mjs；buildOutput 指向插件 dist
│       ├── service.json     # 进程契约：entry + publishes + subscribes
│       ├── src/index.ts     # new Service({ id: '<sid>' }) …
│       └── tests/           # vitest
├── ui/                      # 可选。多视图共用一个 bundle，hash 切视图
│   └── src/index.html
└── dist/                    # 构建产物，Core 只认它（gitignore）
    ├── server/<sid>/index.js + service.json
    └── ui/
```

- **代码与产物都在插件目录里**：分发 = 拷走 `plugin.json + 自带数据 + dist/`，`node scripts/pack-plugin.mjs` 只做「产物是否齐全」的核验，不做压缩。
- **Core 冷启动扫盘**，只启「已安装插件声明的服务」（`core/src/service-manager/plugin-registry.ts` → 白名单交 ServiceManager spawn）。
- 一个插件可以只有 UI 没有服务（`workbench`：6 个视图、0 服务）；也可以只有服务没有 UI（`reliability`）。

## 2. 最小插件：纯服务、无 UI（拿 reliability 当样例）

### 2.1 `plugin.json`

```jsonc
{
  "id": "reliability",              // 也是 userData/plugin/<id>/ 的键
  "name": "可靠性",
  "version": "1.0.0",
  "icon": "🟡",
  "author": "osteosome",
  "license": "Apache-2.0",
  "description": "一句人话：装它得到什么，卸它失去什么。",
  "services": ["llm-retry"],
  "components": [],
  "ui": { "views": [] },            // 无 UI 就留空数组
  "capabilities": [],               // 只给人看/给界面展示，不参与任何判定 —— 别往里写逻辑
  "dependencies": [],               // pluginId 列表；决定启动拓扑，依赖在前
  "autoStart": true
}
```

要点（来自架构约定，已由测试与事故背书）：

- `capabilities[]` **不参与任何判定**（一旦被依赖就变成第二真源）。
- `dependencies[]` = 已安装即满足（不判健康）；`installOrder` 由此计算，依赖环会被检出并不给启动顺序。
- `plugins/credentials/` 曾因「只剩 dist 没有 plugin.json」而完全不被认领——清单在，它才是插件。

### 2.2 `services/<sid>/service.json`

```jsonc
{
  "id": "llm-retry",
  "version": "1.0.0",
  "protocolVersion": "1.0.0",
  "entry": "node dist/index.js",
  "publishes": ["llm.metrics.usage", "llm.request"],   // 你会发出的全部 topic
  "subscribes": ["llm.request", "llm.request.failed"]  // 你会订阅的全部 topic
}
```

三个红线（都真实踩过）：

1. **publishes/subscribes 必须与代码一致**。`core/tests/service-manifest-sync.test.ts` 扫源码比对；
   漏声明 = 服务照常 ready、命令 202、总线上**零订阅者、零事件**，界面只是「没反应」。
2. **改过任何 `service.json` / `plugin.json` 必须重启 Core**（只在启动时读一次，4.1 #7）。
   验证：`GET http://127.0.0.1:1420/health` 看你的服务是否 `ready`、`reason` 是否有 initialize mismatch。
3. **`source` 是总线保留字**（ServiceManager 盖章为 serviceId，`manager.ts`），业务字段别叫 `source`。

### 2.3 `services/<sid>/src/index.ts`

```ts
import { Service, logger } from '@osteosome/service-sdk'
import { DEFAULT_RETRY_POLICY, type RetryPolicy } from '@osteosome/shared'

const service = new Service({ id: 'llm-retry', version: '1.0.0' })

// 订阅事件
service.subscribe('llm.request', (payload, topic) => {
  // payload 是 Record<string, unknown>；字段做窄化校验再信任
  const requestId = typeof payload.requestId === 'string' ? payload.requestId : ''
  if (!requestId) return
  // …处理…
  service.publish('llm.metrics.usage', { requestId, usage })
})

async function main(): Promise<void> {
  await service.start()   // 握手回填 service.dataDir
  const dir = service.dataDir
  if (!dir) {
    // 会话服务的姿势：拿不到 dataDir 就 fail fast，绝不退相对路径
    throw new Error('llm-retry: no dataDir from the handshake')
  }
  // start() 之后才能建 store / 发能力注册事件：
  // start() 之前 publish 会被静默丢弃（SDK 在 !started 时 warn 掉）
}

main().catch((err: unknown) => {
  logger.error(`llm-retry: failed to start: ${String(err)}`)
  process.exit(1)
})
```

`@osteosome/service-sdk` 的 API 面（`sdk/ts/src/service.ts`）：

| API | 语义 |
|---|---|
| `new Service({ id, version })` | 服务身份；id 与 `service.json` 的 `id` 一致 |
| `await service.start()` | 握手 + JSON-RPC 挂接；回填 `service.dataDir`；**之后的代码才合法** |
| `service.subscribe(topic, fn)` | 返回 disposer；首次订阅发 `bus.subscribe` |
| `service.publish(topic, payload)` | 未 start 时**静默丢弃并 warn**——能力注册一律放在 `start()` 后 |
| `service.call(method, params)` | **等响应**的 JSON-RPC（`credentials.*` 等点对点取数走这里；结果不回灌总线） |
| `service.dataDir` | 握手回填 = `userData/plugin/<插件id>/`；**start() 之前恒为 `''`，先校验再用** |
| 读插件自带数据 | `plugins.readFile` RPC（Core 点对点只读特权，只限自己插件目录；models 读 catalog.json 就是这姿势） |

### 2.4 `services/<sid>/package.json`

```jsonc
{
  "name": "@osteosome/llm-retry",       // workspace: plugins/*/services/* 会被 pnpm 认进去
  "private": true,
  "buildOutput": "../../dist/server/llm-retry/index.js",
  "scripts": {
    "build": "node ../../../../scripts/build-service.mjs",   // esbuild 单文件、零外部依赖
    "typecheck": "tsc --noEmit",
    "test": "vitest run --passWithNoTests"
  },
  "dependencies": {                     // 运行时依赖全部会被打进单文件
    "@osteosome/shared": "workspace:*",
    "@osteosome/service-sdk": "workspace:*"
  },
  "devDependencies": { "typescript": "^5.7.2", "vitest": "^3.1.1", "@types/node": "^24.0.0" }
}
```

为什么必须走 `build-service.mjs`：产物要能**拷到没装本仓库的机器上直接 `node dist/index.js`**，
所以打成单文件、全量内联（只留 Node 内置）。产物落 `plugins/<id>/dist/server/<sid>/`。

## 3. 带 UI 的插件（拿 workbench 当样例）

- `plugin.json` 的 `ui.views[]` 每条 = 界面上一个可停靠组件：

```jsonc
"ui": { "views": [
  { "id": "widget.service-status", "title": "服务状态", "entry": "index.html" },
  { "id": "widget.settings",       "title": "设置",     "entry": "index.html#settings" }  // 多视图共用 bundle，hash 切
]}
```

- 源码在 `plugins/<id>/ui/`（pnpm 认 `plugins/*/ui`），vite 打到 `dist/ui/`，Core 伺服在 `/plugins/<id>/ui/`。
- 每个视图是**独立 iframe**，靠同源 SSE 事件流派生状态（`sdk/core-client`），跨 iframe 只共享当前会话 id（sessionStorage）。
- 坑：SFC 说明注释必须写在 `<script>` **内部**——`<script>` 之前的内容按 HTML 解析，报错位置不指向真因。

## 4. 数据与磁盘规矩

- **每插件一个数据目录**：`userData/plugin/<pluginId>/`（`shared/src/paths.ts` 的 `pluginDataDir`）。
  同插件多服务共用（tools 的 8 个服务都在 `userData/plugin/tools/`），要分成子目录也在这里面做。
- **唯一读写者**自己管自己的文件；解析失败 → 逐条报错照常运行，不整份拒（agents/skills/session 都这个姿势）。
- **原子写**：临时文件（pid+uuid）+ rename；stores 的写路径无一例外（教训见 agents/store.ts 注释）。
- 直接写用户数据目录而不是 dist/——「487 条写进 dist/」的事故源于 dataDir 空串未校验。

## 5. 接进总线的姿势（契约纪律）

- 所有 topic 在 `shared/src/events.ts` **唯一真源**登记，**只增不改、不删**（旧事件有测试锁着）。
- 「状态靠事件推导」必须自带**主动对齐**：服务注册个 `xxx.reannounce`，前端订阅到对齐才有初始快照
  （纯事件驱动没有初始快照，是 10-03 抓到的坑）。
- 承认自己拥有什么：数据文件的 owner 注释写在文件头（谁读谁写、缺失语义）。

## 6. 做完自验（六条，照抄执行）

```powershell
pnpm install                                # 新 workspace 包要先进 lock
pnpm -r run build       ; echo "EXIT=$LASTEXITCODE"   # 期望 0（产物齐 = dist/server/*/index.js 都在）
pnpm -r run typecheck   ; echo "EXIT=$LASTEXITCODE"   # 期望 0
node scripts/smoke.mjs  ; echo "EXIT=$LASTEXITCODE"   # 期望 0 且 [smoke] PASS；日志应出现
                                                      # 「plugin layer: … <你的插件>: - -> ready」
# 清单同步防回归（改过 service.json 后）
pnpm --filter @osteosome/core exec vitest run tests/service-manifest-sync.test.ts

# 真进程检查（默认 7 插件）
node core/dist/main.js --help   # 或 start-p1b.cmd；GET http://127.0.0.1:1420/health 看服务 ready
```

- 只看 `$LASTEXITCODE`，**不要** grep 过滤测试输出后宣称通过（本项目有前科）。
- 判定绿灯后：更新 `docs/开发进度/阶段追踪.md`（如属里程碑）+ `README.md` 插件清单行。

## 7. 出问题去哪看

| 症状 | 先查 |
|---|---|
| 服务没起来 | `/health` 的 `reason`（initialize mismatch = 清单漂移 → 重启 Core） |
| 界面点了没反应 | 该服务的 `service.json` subscribes 是否含这条 topic；再查 `core/tests/service-manifest-sync.test.ts` |
| 插件「凭空消失」 | 它有没有合法 `plugin.json`（`/api/plugins` 的 problems 字段） |
| 事件收不到但有订阅 | SDK `started=false` 丢 publish（注册代码是否在 `start()` 后）；Bus 无订阅即不回放 |
| 数据文件丢内容 | 是否在 `start()` 前就用了 dataDir / 是否没走原子写 |
