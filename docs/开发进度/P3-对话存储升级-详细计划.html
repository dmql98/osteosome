JSONL → node:sqlite · 硬切分页 · 设计见 docs/插件demo/chat-workbench/对话工作台-优化计划.html §6
0 目标与范围 1 前置与基线 2 里程碑 3 工作分解 4 固定设计 5 测试矩阵 6 验收标准 7 风险台账 8 顺序与回滚
本计划只做一件事：把 chat-workbench 的会话存储从 JSONL 换成 Node 内置 node:sqlite， 并把「整份 messages 走 SSE」硬切成按游标分页（含对话时间线 UI 的「加载更早」）。
它解决 JSONL 解决不了的三件：① rename 全量重写（→ 单列 UPDATE）； ② cache 无界（→ 不再整会话常驻内存）；③ session.get 全量 SSE（→ 按页取）。
红线：只用 node:sqlite，永不 better-sqlite3；且不做旧兼容（§0.3）。

0目标与范围

0.1 一句话

plugins/chat-workbench/services/session/src/store.ts 的持久化实现由 JSONL 换成 SQLite； session.get 改为游标分页（不再支持整份返回）；时间线 UI 改为分页加载。

0.2 做什么

  • 底座：src/db.ts（node:sqlite 门面 + withTransaction）；不加任何依赖。
  • schema + 迁移引擎：src/migrator.ts，_migrations 版本表、每步 BEGIN IMMEDIATE、迁移前备份 sessions.db.pre-*。
  • 两张表 + 四索引：sessions / messages；索引见 §4.1。
  • store 换实现：root/list/ids/meta/create/rename/setPinned/setArchived/setWorkspace/remove/clear/appendMessage 全走 SQL；缓存归零。删除全部 JSONL 代码路径。
  • 游标分页（硬切）：session.get 恒返回 page{hasMore,nextCursor,total}；limit 缺省取服务端默认（50）。旧的全量行为移除。
  • UI：ChatTimelineView 首屏取一页 + 顶部「加载更早」，与流式事件去重、滚动位置保持。

0.3 不做的事（含「不做旧兼容」）

不做理由何时再议
旧 JSONL 数据迁移 已决定 不写 index.json/.jsonl → SQLite 的导入器；旧 sessions/ 不再被读取。用户历史会话不迁移、不保证可见 若之后必须找回旧数据 —— 另立一次性脚本，不属本阶段
旧 .json 单文件格式兼容 P1-6 早已迁到 JSONL，旧格式兼容代码随本次一并删除 不再
session.get 全量返回 已决定 分页是本次的目的之一；保留「不传 limit = 全量」等于把长会话死法留在原地 不再
回退到 JSONL 实现的路径 既然不迁移旧数据，回退只等于「删 DB + 换回旧代码」，旧 JSONL 目录已不再被任何代码读取 不再
better-sqlite3原生 ABI / 打包坑；node:sqlite 是同一件事的零依赖答案永不（红线）
全文检索（fts5）前端只搜标题，正文搜索是另一件事真需要搜正文时加一条 migration
36 列大表 / 多工作区分组本产品是 Agent 工具台；现有 ~10 字段足够字段真的不够时
服务端未读 / 多端同步 / 虚拟滚动未读走 sessionStorage；分页后单页有界各自触发条件出现时

4固定设计

4.0 驱动（红线）

  • import { DatabaseSync } from 'node:sqlite'，只此一个驱动。同一进程里不得存在「失败就回退 better-sqlite3」的双驱动分支。
  • services/session/package.json 不加任何依赖（内置模块无需声明）。
  • 门面刻意小：只暴露 exec / prepare().run|get|all / close / withTransaction。允许破坏性修改 store 调用点，不模仿 better-sqlite3 的完整 API。

4.1 schema（migration 1）

CREATE TABLE sessions (
  id           TEXT PRIMARY KEY,
  title        TEXT    NOT NULL,
  created_at   TEXT    NOT NULL,
  updated_at   TEXT    NOT NULL,
  pinned       INTEGER NOT NULL DEFAULT 0,   -- 0/1，对外 boolean
  archived     INTEGER NOT NULL DEFAULT 0,   -- 0/1，对外 boolean
  parent_id    TEXT,
  last_message TEXT,
  workspace    TEXT,
  workspaces   TEXT,                          -- JSON 数组文本
  corrupted    INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE messages (
  id                TEXT PRIMARY KEY,
  session_id        TEXT NOT NULL REFERENCES sessions(id) ON DELETE CASCADE,
  seq               INTEGER NOT NULL,          -- 单会话内单调递增（排序/游标键）
  role              TEXT NOT NULL,
  created_at        TEXT NOT NULL,
  content           TEXT NOT NULL,
  finish_reason     TEXT,
  prompt_tokens     INTEGER,
  completion_tokens INTEGER,
  reasoning         TEXT,
  tool_call_id      TEXT,
  tool_name         TEXT,
  tool_calls        TEXT                        -- JSON 数组文本
);

CREATE INDEX idx_sessions_updated_at ON sessions(updated_at DESC);
CREATE INDEX idx_sessions_pinned     ON sessions(pinned);
CREATE INDEX idx_sessions_archived   ON sessions(archived);
CREATE INDEX idx_messages_session_seq ON messages(session_id, seq);
与设计稿的一处必要偏差：设计稿写索引 messages(session_id, id)。 但 message id 是随机 m_<uuid>，不随写入单调，不能当游标。 故新增 seq 列并以其建索引 —— 游标分页与「取最新 N 条」都靠它。这是实现层决定，不改对外协议。
boolean 边界：node:sqlite 绑不了 JS boolean。 读写边界各一个 toDbFlags / normalizeFlags：写 0/1，对外 undefined（假）。

4.2 迁移引擎

_migrations(version INTEGER PRIMARY KEY, name TEXT NOT NULL, applied_at TEXT NOT NULL)

migrate(db):
  for m in MIGRATIONS where m.version > current:
    backup(dbFile)                     // sessions.db.pre-<version>-<ts>，不删
    withTransaction(() => { m.up(db); record(m) })   // BEGIN IMMEDIATE，失败整体回滚

新增列一律走幂等 addColumnIfMissing（查 PRAGMA table_info 后再 ALTER TABLE），方便后续 migration 复用。

4.3 冷启动与旧数据处置（不做迁移）

  1. 每次启动：openDb(<dataDir>/sessions.db) → migrate()（首次即建 schema）。
  2. 不读、不导入旧 sessions/ 目录；index.json / .jsonl / .json 的解析代码全部删除。
  3. 旧目录原样留着（不删）—— 不是因为要兼容，而是「删用户数据」应是显式动作；本阶段不管它。
  4. 新库与外层目录不同名（sessions.db vs sessions/），互不干扰。
  5. dataDir 缺失 → fail fast（复用 index.ts 的既有红线）。

4.4 对外 API 与分页线格式（硬切）

SessionStore：CRUD 方法名/语义不变；get（整份）保留为内部用（export/markdown），新增 getPage：

get(id): SessionFile | null                      // 内部：export / markdown
getPage(id, { limit, before? }): { file: SessionFile; page: { hasMore; nextCursor; total } } | null

命令与结果 —— session.get 恒分页：

// 请求（limit 可缺省 = 50；before 空 = 最新一页）
session.get { requestId, sessionId, limit?, before? }

// 结果（恒带 page；messages = 本页，升序）
session.get.result {
  requestId,
  session: { meta, messages },
  page: { hasMore: boolean, nextCursor: string | null, total: number }
}
  • limit 缺省 = 50（服务端常量，UI 可覆写）。
  • before 缺省 = 从最新往上取；before = nextCursor 取更早一页。
  • nextCursor = 本页最旧消息的 seq（字符串）；无更早消息时 null。
  • total = 该会话消息总数（COUNT(*)）。
  • 没有「不传 limit 就返回全量」这条分支 —— 那是被砍掉的旧兼容。

4.5 UI（M4）

  • 首屏：切会话时发 session.get{limit:50}；sessions.messages 存当前已加载历史。
  • 顶部「加载更早 N 条」：hasMore 为真时显示；点击发 before:nextCursor，将返回消息 prepend 并更新 cursor。
  • 去重：以 message id 为主键合并历史页与 message.appended/流式占位行（占位行无服务端 id，落库后按内容/id 换入，沿用现有逻辑）。
  • 滚动锚定：prepend 前后记录 scrollHeight 差，保持视口位置（不跳到顶部）。
  • 切会话重置分页状态；session.updated 只动 meta，不动已加载消息。

7风险台账

#风险触发条件缓解
R1用户 Node 落在 22.5~22.12只有 engines>=22.5.0 时 require('node:sqlite') 需标志M0 上调下限到 >=22.13.0；启动校验给明确版本号与下载地址，不静默降级
R2node:sqlite 仍打 ExperimentalWarningNode 官方标 experimental接受该行日志；不全局关闭 warnings（会盖住真问题）
R3不迁移 = 用户旧会话「消失」升级后旧 JSONL 不再被读，历史列表变空已接受（§0.3）。旧目录不删，给「另立脚本找回」留后路；发布说明须写明
R4M2/M3 不同批改导致 UI 读不到消息session.get 已恒分页但 UI 仍按全量解析（或反之）M3 与 F4a 同批；单测断言结果恒带 page

R6cursor 语义写死成 seq 后难改将来改用时间戳/复合键cursor 作为不透明字符串对外，解码只在 store 内；换键不改协议

R8并发写同一 DB两个 Core 实例共享 dataDirSQLite 自身串行化 + BEGIN IMMEDIATE；本阶段不引入进程内队列（现网单实例）

8顺序与回滚

8.1 落地顺序

  1. M0（db.ts + engines）：纯新增，先合。
  2. M1（schema + 引擎）：独立，合。
  3. M2（store 换实现，唯一破坏性 PR）：换 SQL + 删 JSONL 代码 + 重写 store 单测；合并前打 tag。
  4. M3 + F4a 同批（协议 + UI 首屏）：session.get 恒分页，UI 随之。否则界面空白。
  5. M4：UI「加载更早」+ 去重 + 滚动锚定。
  6. F5：文档 + 基线 + 冒烟。

8.2 回滚

阶段回滚动作数据影响
M0 / M1直接 revert（未产生业务数据）无
M2revert 代码；删 sessions.db*新库期间写入的会话丢失（旧 JSONL 本就不迁移）
M3 / M4同 M2 一并 revert（协议与 UI 同批）同上
