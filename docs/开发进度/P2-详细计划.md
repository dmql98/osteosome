# P2 详细计划 · 最小 LLM 对话（DSH 接缝三角 · 单 provider 实现）

> 修订：2026-09-23 评估定案。原 P2（写死单 provider 走中立流契约）不变，但按 **DSH 接缝三角**（`LlmAdapter` / `Registry` / `StreamChunk`）+ **两个声明式接缝**（凭证引用 resolver、retry 策略）提前落全部契约——再叠一个 deepseek 真实现。工作量 **+0.5~1 天，阶段总量约 1 周**。

---

## 0. 目标与范围

### 0.1 目标

- 跑通「前端 ChatPane → `/api/command` → LLM 服务 → deepseek → 流式 token 回前端」的整条链路。
- **接口先于实现**：把 DSH 的接缝三角（**LlmAdapter / Registry / StreamChunk**）+ 两个声明式接缝（**凭证引用 resolver、retry 策略**）在 P2 落地为**类型 + 目录 + 一个真实现**，P4 只做「更多 provider 实现 + 凭证存储 + retry 执行器 + 管理 Pane」，不重写骨架（满足 RFC §8 不变式之一）。

### 0.2 范围内（In Scope）

- `services/llm/` 服务：manifest + `index.ts`，订阅 `llm.request` → 组装 → 流式发布。
- 接缝契约文件（**四件**；`types.ts` 同时含 `LlmAdapter` 与 `StreamChunk` 两个类型，`stream.ts`/`chunk.ts` 翻译层另计非契约）：
  - `adapter/types.ts` —— `LlmAdapter` / `LlmAdapterContext` / `AdapterRoute` 类型；
  - `adapter/registry.ts` —— provider 路由（`routeKey` = provider id）+ 声明元数据；
  - `credentials/resolver.ts` —— **凭证引用解析**（v1：`env:<VAR>` 引用；预留 `core` kind，P4 接 core 凭证 store）；
  - `retry/policy.ts` —— 声明式 `RetryPolicy`（次数 / 退避 / 视为瞬态的错误码），P2 **只声明不执行**。
- `stream.ts` —— native SSE wire → `StreamChunk`（block-start / text delta / block-end / finish 终块）翻译层。
- `adapter/deepseek.ts` —— 唯一真实现（deepseek-chat，openai 兼容 wire 的 SSE）。
- 前端 `features/chat/chat-pane.vue`：输入 → 发送 `llm.request` → 订阅 `llm.token.streamed` 累积显示。
- 事件契约（**只增不改**，见 §3 事件表）：沿用 RFC 既有 `llm.request.started` / `llm.token.streamed` / `llm.request.finished`，新增 `llm.request.failed`。

### 0.3 范围外（Out of Scope）

- ❌ 多 provider（openai / anthropic / openrouter）与模型目录 `listModels()` —— P4。
- ❌ 凭证存储 / 加解密 / 设置 Pane —— P4（`core/src/credentials/`）。
- ❌ retry 执行器（真重试）—— P4。
- ❌ Session / Loop / 多轮历史 —— P3。
- ❌ 工具调用（tool-call 块）解析执行 —— P7；P2 只透传层**识别并降级** tool-call 块（跳过不渲染，不报错）。
- ❌ reasoning 块渲染 —— P4/P7 视需要新增 `llm.block.*` 事件（只增不改）。
- ❌ P2 之前无历史：每次请求带调用方拼的 messages（P3 起由 Loop 拼）。

## 1. 仓库改造

```
services/llm/
├── service.json                 # manifest：publishes/subscribes（见 §3 事件表）
└── src/
    ├── index.ts                 # 服务入口：订阅 llm.request → 组装 → 流式发布；错误兜底
    ├── adapter/
    │   ├── types.ts             # LlmAdapter / LlmAdapterContext / StreamChunk 类型归属
    │   ├── registry.ts          # register()/resolve()/list()；routeKey = provider
    │   └── deepseek.ts          # 唯一真实现（deepseek-chat）
    ├── credentials/
    │   └── resolver.ts          # resolveApiKey(ref)：env 引用；预留 core kind（P4）
    ├── retry/
    │   └── policy.ts            # RetryPolicy 类型 + deepseek 默认策略（声明，不执行）
    ├── stream.ts                # native SSE → StreamChunk 翻译（probing + 归一）
    └── chunk.ts                 # StreamChunk 判别函数（isFinishBlock 等）
```

依赖：`@osteosome/sdk`（总线/handshake）。provider 只用 Node 内置 + `fetch`（Node ≥ 18 原生），**不引入 axios/openai 官方 SDK**（bundle 最小、无鉴权魔法）。

## 3. 接口定案（P2 补齐）

### 3.1 StreamChunk —— 中立流协议（对齐 `ost-开发文档.md` §18）

块化三段式，服务内部契约；**前端继续收 `llm.token.streamed`**（RFC 不变），块结构不出 wire：

```ts
type StreamChunk =
  | { kind: 'block-start'; id: string; blockType: 'text' | 'reasoning' | 'tool_call'; index: number }
  | { kind: 'delta'; id: string; blockType: 'text' | 'reasoning'; text: string }
  | { kind: 'tool-arg-delta'; id: string; blockType: 'tool_call'; name: string | null; arguments: string } // 原始 JSON 透传
  | { kind: 'block-end'; id: string; blockType: 'text' | 'reasoning' | 'tool_call' }
  | { kind: 'finish'; finishReason: 'stop' | 'length' | 'content_filter' | 'tool_calls' | 'error'; usage?: { promptTokens; completionTokens }; error?: StreamError }
```

**→ `llm.token.streamed` 事件映射**（服务内部块 → 前端事件）：

- `{ kind: 'delta', blockType: 'text', text }` → `llm.token.streamed { requestId, token: text, index }`；`index` 为本次请求内文本 delta 的**服务侧递增序号**。
- `reasoning` / `tool_call` / `block-start` / `block-end` **不产生事件**。
- **tool-call 决策**：P2 收到 `tool-call` 块 → **静默丢弃，不发事件**（P7 才消费工具调用）；`reasoning` 块同理只进 adapter 层，P2 前端不渲染。
- `finish` 块 → `llm.request.finished`。

**`finishReason` 归一化**：统一枚举 `stop | length | content_filter | tool_calls | error`，**每个适配器负责把 provider 原生值映射到该枚举**（P2 deepseek 的 `stop_reason`；P4 anthropic 的 `end_turn`/`stop_sequence` → `stop` 等）。**`aborted` 不进枚举**：主动取消 = 成功路径，`llm.cancel` 后适配器以 `stop` 提前 yield finish（见 §3.4 取消语义）。

**`usage` 字段（disjoint 记账对齐「只增不改」）**：P2 只填总量：

```ts
usage?: {
  promptTokens: number          // P2：总量（含 cached 与 uncached）
  completionTokens: number
  // P4 起追加（可选，P2 union 中的块可缺省）：
  cachedPromptTokens?: number   // 命中上下文缓存的 prompt 部分
  uncachedPromptTokens?: number // 未命中部分
}
```

P2 各适配器只上报总量；P4 按 provider 能力补 `cached/uncached` 细分（disjoint 记账，总量 = cached + uncached 校验）。

### 3.2 LlmAdapter —— 接缝接口

```ts
interface LlmAdapter {
  readonly provider: string
  readonly defaultModel: string
  stream(req: LlmRequest, ctx: LlmAdapterContext): AsyncIterable<StreamChunk>
}

interface LlmAdapterContext {
  apiKey: string            // 由 credentials/resolver 解析后注入（进程外不落盘）
  retryPolicy: RetryPolicy  // 声明式；P2 不执行
  signal?: AbortSignal
}

interface LlmRequest {
  provider: string          // routeKey
  model?: string
  messages: { role: 'system' | 'user' | 'assistant'; content: string }[]
  temperature?: number
  meta?: Record<string, unknown>  // 调用方透传（含 requestId 溯源）
}
```

> **定案**：`provider` / routeKey 统一为供应商名——P2 用 **`deepseek`**（不必带 `-official` 等后缀）；P4 新增 `openai` / `anthropic` / `openrouter` 同理。ChatPane 直接拿 routeKey 下发，前端不展示 display name。

### 3.3 错误码（StreamErrorCode）

| 码 | 触发 | 是否瞬态（retryableCodes 覆盖） |
|---|---|---|
| `unauthorized` | 401/403 | 否 |
| `rate_limited` | 429 | 是 |
| `server_error` | 5xx | 是（503 起） |
| `network` | fetch 网络异常 / 超时 | 是 |
| `invalid_request` | 400 / wire 畸形 | 否 |
| `unsupported_provider` | registry 无此 provider | 否 |
| `missing_credential` | resolver 解析失败 | 否 |

> 对齐 §18④「字符串判 429 收敛为错误码」。P2 全链路不再出现供应商字符串匹配。

### 3.4 事件契约（只增不改）

**命令 topic**（bus 上订阅而非发布，注册进 manifest）：

| Topic | 语义 | Payload |
|---|---|---|
| `llm.request` | 发起流式对话 | `{ requestId, provider, model?, messages, temperature?, meta? }` |
| `llm.cancel` | **新增**：取消在途请求 | `{ requestId }` |

**事件 topic**（服务发布）：

| Topic | 语义 | Payload |
|---|---|---|
| `llm.request.started` | 已开始 | `{ requestId, provider, model }` |
| `llm.token.streamed` | 文本 delta（text 块累加） | `{ requestId, token, index }` |
| `llm.request.finished` | 正常结束 / 主动取消 | `{ requestId, finishReason, usage? }` |
| `llm.request.failed` | **新增**：硬错误（非瞬态或超限） | `{ requestId, error: { code, message } }` |

manifest：`subscribes: ["llm.request", "llm.cancel"]`；`publishes: ["llm.request.started", "llm.token.streamed", "llm.request.finished", "llm.request.failed"]`。

**`provider` 值定案落到示例**（§3.2 的 `deepseek` 具体怎么用）：

```ts
// services/llm/service.json —— 事件/命令里的 provider 字段一律 = routeKey
//   subscribes / publishes 载荷中的 provider: 'deepseek'

// ChatPane 发送 llm.request 的 payload：
{ requestId: 'c-42', provider: 'deepseek', model: 'deepseek-chat', messages: [
    { role: 'user', content: '你好' }
  ], temperature: 0.7 }
```

> **取消语义**：`llm.cancel { requestId }` → 路由到对应在途请求的 `AbortController.abort()`；适配器收到 aborted 信号 → 以 `finish{ finishReason:'stop' }` 提前结束（**成功取消不留痕，不发 failed**；`aborted` 不进 finishReason 枚举，见 §3.1）；已结束的 requestId → 静默忽略。**「1s 上限」含义**：abort 后等适配器 yield finish 最多 1s；**超时未收到** → 服务侧强制发 `llm.request.finished { finishReason:'stop' }` 并释放 in-flight 表（不等慢适配器，避免请求挂死）。

## 4. 测试矩阵

| 模块 | 用例要求（至少覆盖） |
|---|---|
| `chunk` | 各块构造、判别函数、finish 块缺 `finishReason` 拒绝、tool-arg 原始 JSON 透传不变形 |
| `registry` | 注册唯一性（重复 → 抛错）、resolve 命中 / 缺失抛错、list() 返回 provider + defaultModel |
| `deepseek` | 多行 SSE 解析、`[DONE]` → finish、`content` delta、`reasoning_content` → reasoning 块（不渲染路径）、error 段 → 错误码（429/5xx/非 JSON） |
| `stream` | 探测与归一：CRLF、行内多 `data:`、连续空行、截断行忽略、非 `data:` 前缀忽略 |
| `resolver` | `env:X` 命中、缺失 → `missing_credential`、`core:` kind 未接 → 明确 unimplemented 错 |
| `index.ts` | started → streamed（按序）→ finished；异常 → failed（码化）；缺 provider → `unsupported_provider`；finish 前 error → failed 且不重复发；**cancel → abort → finish{finishReason:'stop'}（不发 failed）；cancel 已结束 requestId → 静默忽略** |
| ChatPane | 发送 → 202；token 累积按 requestId 匹配；**failed → Spinner 收起 + 错误占位 + 错误码中文映射；cancel → 停止按钮出现/消失 + 不残留本地幽灵消息**；Spinner 生命周期 |

**Mock 策略**：`fetch` → `vi.stubGlobal`/msw 返回伪 SSE body（`ReadableStream`）；`EventSource` → FakeEventSource（沿用 P1b 模式）；SDK Service → 真连 Core 或 stub bus。

## 6. 风险与决策

| 主题 | 决策 / 规避 |
|---|---|
| **接缝过度设计** | 只落 P4 需要的最小接缝（adapter/registry/resolver/retry 声明）；不做多 provider 骨架抽象、不做插件热插拔；`tool-call` 块仅识别降级 |
| **SDK 依赖膨胀** | provider 只 `fetch` + 原生 API；不引 openai 官方 SDK；对速查 Table 的 baseURL/鉴权差异在 deepseek 适配器内部收敛 |
| **凭证裸奔** | v1 只认 `env:<VAR>`（如 `DEEPSEEK_API_KEY`），解析失败即 `missing_credential`，不写死默认 key；`core` kind 预留，P4 接 `core/src/credentials/` |
| **retry 空转** | retry 在 P2 **只声明不执行**，避免半吊子重试造成重复请求；执行器 P4 与凭证 seam 一并装备 |
| **崩溃恢复** | 重试交给 Core 进程管理（P1a）：kill llm → 拉起 → 事件恢复；请求级别的重试 P4 再做 |
| **事件 flood** | token 逐条发布 OK（RFC 既有契约）；若 P4 遇到吞吐瓶颈，再以 `llm.block.*` 增量降频（只增不改），P2 不预建 |
| **P2 阶段波动** | 接缝契约 + 单 provider + ChatPane 一次 PR 交付；如 deepseek wire 探测超时，切成 openai 兼容基类再换 baseURL，一周兜底 |

## 7. 开工顺序

```
P1a + P1b 全绿
  └► WS-1 llm 骨架 ──────────────┐
  └► WS-2 StreamChunk（纯类型）──┤
  └► WS-3 adapter+deepseek ──────┼─► WS-5 ChatPane
  └► WS-4 resolver+retry 声明 ───┘       │
```

- WS-2/3/4 都只依赖 SDK 与 chunk 类型，可与 WS-1 并行起步；WS-5 需要全部就位。
- 每个 WS 单独 commit；WS-6 收尾整个 P2 一个 PR（含 ChatPane 冒烟）。
