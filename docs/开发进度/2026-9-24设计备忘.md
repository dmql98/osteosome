## 1. 动机：问题不在「AI 能不能操控」，在「散落各处」

### 1.1 假问题与真问题

**假问题**：「AI 能否操控任意本地服务？」

——**已经解决了**。MCP / Skill / CLI 各自解决了一类能力暴露，生态成熟。Osteosome 不需要发明新协议。

**真问题**：「这些东西散落在各处，没有统一的地方能看到、管理、调用。」

—— 这才是缺口。

### 1.2 散落的三处

一台开发机上，可能同时存在：

**MCP server**
- Claude Desktop 的 `claude_desktop_config.json`
- Cursor 的 `.cursor/mcp.json`
- Cline / Continue / Windsurf 各自的配置文件
- 各项目内的 `mcp.json`
- 有些跑在 Docker、有些 `npx xxx`、有些本地二进制

**Skill**
- `~/.claude/skills/` 下的 SKILL.md
- 各项目 `skills/` 目录
- Obsidian / Notion 里的技能笔记
- Skill 市场下载的

**CLI**
- PATH 里的可执行文件（`gh` / `aws` / `kubectl` / …）
- 各语言包管理器装的 bin（venv / node_modules / cargo bin）
- 项目脚本（`./scripts/*.sh`）

### 1.3 散落的后果

每个 AI 工具**只看得见自己那部分**：

| 工具 | 看得见 |
|---|---|
| Claude Desktop | 只看得见它配置的 MCP |
| Cursor | 只看得见它配置的 MCP + 部分 CLI |
| 终端用户 | 只有 `which xxx` 能看一点 CLI |
| 谁 | 都看不到全局 |

**用户本机总共能做什么**——没人知道。**AI 也不该被期待知道**——它没渠道。

---

## 2. 定位：统一发现 + 统一注册 + 统一治理

> **Osteosome 不做新协议，做一个聚合层——让 AI 看到一张完整的工具清单，让用户管得住所有工具。**

```
┌─────────────────────────────────────────────────────────┐
│                    Osteosome                            │
│                                                          │
│  ┌──────────────────────────────────────────────────┐  │
│  │          统一 Tool Registry                        │  │
│  │  （AI 看到的唯一工具清单）                          │  │
│  └──────────────────────────────────────────────────┘  │
│         ▲              ▲              ▲                 │
│         │              │              │                 │
│  ┌──────┴───┐   ┌──────┴───┐   ┌──────┴───┐           │
│  │ MCP 发现  │   │ Skill 发现 │   │ CLI 发现  │           │
│  └──────┬───┘   └──────┬───┘   └──────┬───┘           │
└─────────┼──────────────┼──────────────┼─────────────────┘
          │              │              │
    ┌─────┴─────┐  ┌─────┴─────┐  ┌─────┴─────┐
    │ 各处的     │  │ 各处的     │  │ PATH 里   │
    │ MCP 配置   │  │ SKILL.md  │  │ 的 CLI    │
    └───────────┘  └───────────┘  └───────────┘
```

**三件事**：
1. **发现** —— 扫已知位置，找到所有 MCP / Skill / CLI
2. **注册** —— 归一化成统一 tool 定义，进 registry
3. **治理** —— 审批、凭证、命名空间、可见性，统一管

## 3. 三种来源的聚合方式

### 3.1 MCP server —— 有标准协议，做 client

MCP 已是事实标准（Anthropic 主导，Claude Desktop / Cursor / Cline 均支持）。Osteosome 做 **MCP client**。

**发现**：
1. 读已知配置位置（Claude Desktop / Cursor / Cline 的 `mcp.json`）
2. 读用户自定义位置（设置 Pane 里配置）
3. 读项目内 `mcp.json`

**连接**：
1. transport 支持 stdio / SSE / HTTP（MCP 多种 transport）
2. 握手：`initialize` → 拿 server capabilities
3. 列工具：`tools/list` → 工具清单
4. 订阅资源 / 提示：`resources/list` / `prompts/list`

**归一化**：

```ts
// MCP tool 定义
{
  "name": "read_file",
  "description": "...",
  "inputSchema": { ... }
}
// 归一化为 Osteosome tool
{
  name: 'mcp.filesystem.read_file',
  description: '...',
  parameters: { ... },
  execute: async (args) => mcpClient.call('tools/call', { name, arguments: args })
}
```

**生命周期**：
- Core 可以 spawn MCP server（本地 stdio 型），或用户已启动的连接（SSE / HTTP 型）
- 健康检查：MCP 无标准 ping，用 `tools/list` 周期性探测，或依赖进程存活

### 3.2 Skill —— 无标准协议，做解析器

Skill 无强规范，但 SKILL.md 有惯例（frontmatter + markdown body）。

**发现**：
1. 扫 `~/.claude/skills/`
2. 扫用户配置的目录
3. 扫各项目 `skills/` 目录

**解析**：

```markdown
---
name: pdf-processing
description: 处理 PDF 文件——拆分、合并、填表
---

# PDF Processing

## 能力
...
```

- 读 frontmatter（YAML）→ `name` / `description`
- 读 body → 提取结构化能力（或整体作为上下文）

**注册（两种形态）**：

| Skill 形态 | 处理 |
|---|---|
| **纯知识型**（只有 markdown） | 作为「上下文片段」注入 system prompt（**不是 tool**） |
| **工具型**（带 `scripts/` 子目录） | 脚本包装成 tool + 说明注入 |

**关键判断**：**Skill ≠ tool**。Skill 是「知识 + 可能带工具」。

### 3.3 CLI —— 有 `--help`，做探测

CLI 是最散的一环。PATH 里的可执行文件、各包的 bin、项目脚本。

**发现**：
1. 扫 PATH（**排除系统命令**：`ls` / `cat` / `grep` / …）
2. 扫用户配置的目录
3. 读 `package.json` / `pyproject.toml` 的 bin 声明

**探测**：
1. 对每个候选，尝试 `--help` / `-h`
2. 解析 help 文本 → 提取命令结构（或让 AI 解析）
3. 有些 CLI 有 `--json-help` / `--schema`（更好）

**注册**：
- 简单 CLI → 一个 tool，参数透传
- 复杂 CLI（子命令多）→ 每个子命令一个 tool
- 或者：让 AI 通过 `shell.run` 直接调（更灵活但没结构化）

**v1 边界**：**只做显式声明**（用户在设置里手动添加 CLI）。自动扫 PATH 太脏，远期再说。

**风险**：`--help` 输出格式千奇百怪——自动解析的可靠性远低于 MCP / Skill。

## 4. 统一 Tool Registry

不管来源是 MCP / Skill / CLI，最终都归一化到同一个结构。

```ts
interface UnifiedTool {
  name: string                      // 带命名空间：mcp.fs.read_file / skill.pdf.split / cli.gh.pr_list
  description: string               // AI 通过这个决定要不要调
  parameters: JSONSchema
  source: 'mcp' | 'skill' | 'cli' | 'internal'
  sourceId: string                  // 哪个 MCP server / 哪个 skill / 哪个 CLI
  dangerous?: boolean
  requiresApproval?: boolean
  exposed: boolean                  // 是否暴露给 AI（用户可关）
  cost?: { unit: string; amount: number }
}
```

**AI 视角**：一张统一的清单，它不知道也不关心背后是 MCP 还是 CLI。

**用户视角**：设置 Pane 里看到所有来源，可以：
- 启用 / 禁用某个工具
- 分组管理（按来源 / 按项目）
- 设置审批策略（哪些工具要确认）
- 看使用统计

---

## 5. 统一治理层

三个来源汇聚后，**统一治理**才是真正的价值：

| 治理维度 | MCP | Skill | CLI | **统一后** |
|---|---|---|---|---|
| **审批** | 各自的 UI | 无 | 无 | Osteosome 统一 `tools.pre-execute` |
| **凭证** | 各 config 里 | 无 | env / 各工具自己的 | Osteosome 统一 credentials seam |
| **命名空间** | 各 server 自己 | 无 | 全局 PATH | Osteosome 强制前缀 |
| **可见性** | 全暴露 | 全暴露 | 全暴露 | 用户可逐个开关 |
| **使用统计** | 无 | 无 | 无 | Osteosome 统一记账 |
| **审计** | 无 | 无 | 无 | Osteosome 落事件日志 |

**这是「聚合」比「散落」的核心收益**——不只是「看得到」，而是「管得住」。

## 6. 对 P7 的影响

**P7 从「MCP + 工具管线」扩展为「MCP + Skill + CLI 统一发现 + 工具管线」**。

### 6.1 原 P7

```
- 工具执行管线（pre / execute / post + 审批）
- MCP server 接入
- tools.executed 事件
```

### 6.2 修订 P7

```
- 工具执行管线（pre / execute / post + 审批）        ← 不变
- MCP client + 发现 + 归一化                        ← 扩展
- Skill 发现 + 解析 + 注册                          ← 新增
- CLI 发现（v1 只做显式声明）                       ← 新增
- 统一 Tool Registry                                ← 新增
- tools.executed 事件                               ← 不变
```

**工作量增加**：约 +3-5 天（Skill 发现 + CLI 显式注册 + 统一 registry）。

**为什么并入 P7 而不新开阶段**：核心是「工具管线」，三个来源只是「发现器」。管线做一次，三个发现器是并行的插件。

**可选拆分**：若担心 P7 过载，可拆 P7a（管线 + MCP）/ P7b（Skill + CLI）。**不推荐**——三个发现器共享同一 registry 和审批，拆开引入接口对齐成本。

## 8. 边界与非目标

**本期明确不做**：

- ❌ 新协议——只吃 MCP / Skill / CLI 现成的
- ❌ 自动扫 PATH 解析所有 CLI（v1 只做显式声明）
- ❌ AI 自动生成 tool 包装（可能有幻觉 / 过度暴露 / 静默错误；远期只做「AI 生成 → 用户审核」）
- ❌ 跨设备同步（本机聚合已足够）
- ❌ 团队共享 / 权限（单机场景）

**远期考虑**：

- CLI 自动发现（`--json-help` / `--schema` 规范化的 CLI 优先）
- AI 生成 tool 草稿（用户审核后落盘）
- 云端 MCP（远程 SSE / HTTP 的 MCP server）
- 跨设备 / 团队

## 9. 开放问题

1. **P7 是否扩展为「工具管线 + MCP + Skill + CLI」？**
   建议是，不加新阶段。若需拆分建议 P7a / P7b。

2. **CLI 发现 v1 是否只做显式声明？**
   建议是——自动扫 PATH 太脏。远期等 CLI 生态出现 `--schema` 规范再自动化。

3. **Skill 的两种形态（纯知识 vs 带脚本）是否分开处理？**
   建议分开——知识注入 system prompt，脚本变 tool。二者在 `UnifiedTool` 结构里表现不同（前者不进 registry）。

4. **统一 Tool Registry 是否落盘？**
   建议落盘——用于用户开关状态、使用统计、审批策略持久化。位置：`serviceDataDir(dataDir, 'tools')/registry.json`。

5. **MCP 配置的发现路径白名单？**
   建议先内置已知位置（Claude Desktop / Cursor / Cline），用户可扩展。不主动扫全盘。
