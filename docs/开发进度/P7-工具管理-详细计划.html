本计划覆盖两件事，且顺序不能反：
M0 工作区能力位（前置） —— 现在 loop 的沙箱根，以及设计稿里计划的 fs-tools 沙箱根，都是 userData/plugin/<id>/tool-root —— 一个空目录。模型读不到用户的项目，也写不进去。整条工具链缺一个输入：「用户在哪个项目上工作」。 没有它，后面 14 个 WS 全都跑在一个读不到任何东西的空目录上。
M1~M6 工具能力位 —— 把工具从 loop 进程里拆成 1 个闸门 + 7 个执行者，落审批、约束与目录视图。
参照：工作区照天枢 dev 的右栏与 web/server/src/routes/workspace.ts · agent/inner.ts； 三处刻意的差异见 §4.1。

0目标与范围

0.1 目标（一句话）

用户能选定一个工作目录，模型在那里读、写、跑命令；每一次越界与副作用都过一次可追溯的授权。

0.2 In Scope

#交付判据
①会话工作区：项目区 + 授权根，可增删；目录选择器（桌面原生 + 服务回退） 给会话绑目录后，模型能读到里面的真实文件
②工具能力位：1 闸门 + 7 执行者（workspace / fs / shell / web / misc / skills / mcp） widget.tools 列全 12 个静态工具 + 1 个动态族
③逐次审批：三档策略（ask/auto/deny）+ proc 二次确认 写 / 网络 / 进程类在执行前弹面板；只读不弹
④工作区审批：越界 → 「把此目录加入授权工作区」→ 批准后重派 同一轮内该调用被重派并成功
⑤约束：constraintFields + shared 单份规则引擎 空 allowed_commands 的 bash 必然失败
⑥三条纪律：超时 / 孤儿 / 残留注册（含 kill -9 集成测试） kill -9 一个执行者，目录只少它那一批
⑦界面：widget.tools 5 Tab + widget.session-workspace + 对话侧审批面板 真 Core + 真 SSE 下全部可点、状态由事件重建

0.3 Out of Scope

不做为什么
删除 / 编辑工具实现实现属于执行者插件；本插件只拥有「启用」与「策略」。给「删除」等于骗用户。
「检测本机 MCP」扫他人配置目录越界。plugins.readFile 只读自己插件目录，这条纪律不为导入方便而破。
并行执行同一轮的多个工具P3 起就是顺序执行。并行是独立议题。
审计日志 audit.log会话里的 role:'tool' + loop.tool.executed 已是可导出的流水；再存一份会变成第二个真源。
跨会话 / 全局工作区工作区是会话属性。全局会让「在 A 项目改文件却改到 B」成为可能。
兼容天枢的两值 dangerous它无法区分出网 / 写盘 / 起进程（webfetch 被标成 false）。四值 risk 是替代。

4固定设计（不可改的契约）

4.1 工作区：照天枢，但三处不同

#天枢（dev）OST为什么
1/api/workspace/{list,resolve,open} 是 Core 路由 服务命令 workspace.list|resolve|open，走总线 OST 的 Core 没有任意文件系统面（只有 /api/plugins 与 /plugins/*）。加一条「列任意目录」的路由，等于拆掉「Core 不碰用户文件」这条不变式。
2塞进「右栏」多合一面板（角色 / 工作区 / 助手 / 知识库 / 目标 / 统计） 独立 widget.session-workspace OST 是 dockview，组件可自由摆位。不需要一个塞满东西的右栏 —— 那是把布局权收回到插件里。
3越界审批由 agent 发起（agent/inner.ts 的 approval_kind:'workspace'） 由 执行者 发起；kind:'workspace' 的审批由 loop 应答（闸门不参与） 「谁执行谁负责」：只有执行者知道自己算出来的沙箱根。应答者必须是 loop —— 它要在批准后重派那次调用（见 §4.3）。闸门仍然只答「允许吗」。

4.3 越界审批与重派（M0 的关键语义）

1. 执行者：tool.execute{T, name, arguments, workspaces}
   └─ 路径越界 → 不执行，产 tool.execute.result{ok:false,
        escape:{ requestedPath, permissionRoot }}      // permissionRoot = 最小可授权目录
2. loop：看到 escape → 发 tool.approval.requested{ kind:'workspace',
        requestId:T, requestedPath, permissionRoot, sessionId }
3. 用户：批准 → tool.approval.resolved{ T, approved:true }
   └─ 闸门忽略 kind='workspace'（它只答 exec 类）
4. loop：发 session.set.workspace{ addRoot: permissionRoot }
        然后**重派** tool.execute{T, ..., workspaces:[…新增]}
5. 执行者：这次路径在根内 → 正常执行 → tool.execute.result{ok:true}

// 拒绝 / 超时 → 把越界失败回填给模型（正常路径），不重派
「可以重派」的前提只有一条：越界发生在任何副作用之前。 执行者的路径守卫在动手前跑 —— 所以重派同一个 toolCallId 是幂等的。 这条前提必须有一条测试守着（断言：重派前执行者未产生任何写/命令副作用）。 一旦将来有工具「先写一半再发现越界」，这条前提就破了，重派会变成执行两次。

4.4 沙箱 = 会话工作区 ∪ 授权根（执行者算，loop 不算）

谁持有说明
权威来源session 服务（<id>.json 的 meta） 唯一写者不变；session.set.workspace 是唯一入口
透传loop run 开始时从 session.get.result 拿；中途新增根靠 session.updated 更新本地副本
执行各执行者 用 shared 的 assertPathSafe 自己判断。loop 不持有任何路径。
空工作区— 任何路径都越界 → 第一次调用触发工作区审批。工具照常下发（不用「隐藏」：把「为什么不能用」变成一次可操作的授权）
workspace 服务能列任意目录，但它永不 readFile。 只 readdirSync + statSync（判 isDir），不读文件内容。
它不进 tool.registered —— 模型够不到它。它是 UI 支撑面，不是工具。 这两条都要在 service 头部注释与测试里写死：「只列目录、不读文件」是它的能力边界，不是实现细节。

4.6 八个服务，协议几乎逐字节相同

8 = 1 闸门 + 6 静态执行者 + mcp-tools + workspace。 六个静态执行者（fs / shell / web / misc / skills）的 service.json 逐字节相同； mcp-tools 多两条配置命令；workspace 只有 3 条 workspace.*；闸门只答审批、不执行。
「MCP 是动态的」这件事在协议层看不出来 —— 这正是关键： loop、闸门、界面对 MCP 与对 read 一视同仁，差异全关在 mcp-tools/src/ 里。

8.1 单一团队的一天推进顺序（建议）

  1. 先拍 §7.1 的 8 个 ★ —— 它们改一个，后面的代码就改一片。
  2. M0 全做完并演示一次「绑目录 → 读真实文件」。这是整个计划里唯一值得先给人看的东西。
  3. M1 + M2 并行度低（同一人），按 WS-1→2→3→4 串。
  4. M3 单独一天，只做这一件事。
  5. M4 可以并行（不同执行者目录互不依赖），但每次只上一个，上完验一次目录没少东西。
  6. M5 与 M4 后半可并行（界面只依赖 tools.state 的形状，不依赖有几个执行者）。
一句话纪律（贯穿全程）： 先让服务能各自工作，再切主线；每个执行者是一个目录（可独立删）； 越界与副作用各走各的闸（约束不弹窗、审批才放行）； loop 手里不留路径。
