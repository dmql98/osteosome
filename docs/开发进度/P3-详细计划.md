# P3 详细计划 · 会话存储 + 最小 Loop（会话编排）

> 修订：2026-09-23 评估定案。原 P3（最小 Loop · 会话编排）**扩展 +30~50%**：新增 `services/session`（dataDir JSON 持久化 + 4 事件）、会话列表 Pane、Loop 改为「读会话历史 + 多轮 + 流式回复」编排。SQLite 落库继续延后 P8。工作量 **+3~4 天，阶段总量约 2-3 周**。

---

## 0. 目标与范围

### 0.1 目标

- 会话成为一等公民：**会话 = 可持久的消息 log**（append-only），会话列表可新建 / 切换 / 重命名 / 删除，并跨窗口实时同步（SSE）。
- Loop 服务把「provider + system prompt + 会话历史 + 新消息」组装成一次 `llm.request`，流式回填；`loop.state.changed` 是 P5-P7 挂接的宿主状态。

### 0.2 范围内（In Scope）

- `services/session/` —— 会话 CRUD + 消息 append-only + **dataDir 下 JSON 文件持久化**（SQLite 延后 P8）。
- 事件契约（只增不改）：
  - `session.created` / `session.updated` / `session.deleted`
  - `message.appended`
- 命令/响应 IPC 模式（request/result 对，见 §3.3）：`session.list`、`session.get`、`session.create`、`session.rename`、`session.delete`、`session.clear`、`message.append`。
- `services/loop/` —— 订阅 `loop.run` → 读会话历史 → 组装 messages → 发 `llm.request` → 流式回填为 assistant 消息 → `loop.state.changed`（idle / running）。
- 前端：
  - `features/session/session-list-pane.vue` —— 会话列表（新建 / 切换 / 重命名 / 删除 / 当前高亮）；
  - ChatPane（P2）升级为**绑定当前会话**：历史加载、流式追加、发问走 `loop.run`。

### 0.3 范围外（Out of Scope）

- ❌ SQLite / 事件持久化 / 回放 —— P8。
- ❌ 多 provider / 凭证存储 / retry 执行器 —— P4。
- ❌ 角色（人设）服务化 —— P5（P3 的 system prompt 为常量）。
- ❌ 技能 / MCP 工具 —— P6 / P7。
- ❌ 会话搜索、消息编辑/删除、token 统计 —— 后续按需。
- ❌ 会话 pinned/user-only 标记 —— 仅预留字段可空。

## 1. 仓库改造

```

├── service.json                 # subscribes 命令 / publishes 事件（§3.4）
└── src/
    ├── index.ts                 # 服务入口：命令分发 + 事件发布
    ├── store.ts                 # serviceDataDir(dataDir,'session') JSON 持久化（幂等读写 + 并发保护）
    ├── session.ts               # 会话聚合逻辑（create/rename/delete/message.append）
    └── ids.ts                   # 会话/消息 id 生成 + 时间戳

services/loop/
├── service.json                 # subscribes: loop.run / loop.cancel / llm.token.streamed / llm.request.finished / llm.request.failed；publishes: loop.state.changed / loop.run.failed / loop.run.cancelled / loop.token.streamed
└── src/
    ├── index.ts                 # loop.run 主流程（状态机：idle → running → idle）
    ├── prompt.ts                # P3 常量 system prompt（P5 换角色服务）
    └── history.ts               # 从 session.get.result 组装多轮 messages（截断策略）

client/src/features/session/
└── session-list-pane.vue        # 会话列表（ui 组件库实现）

client/src/stores/
└── session.ts                   # Pinia：list + current + dirty（bind SSE 事件）
```

数据目录布局 —— **对齐 P1a §3.1 规范**：服务只写自己的 `serviceDataDir(dataDir, 'session')`（PowerShell/跨平台用 `paths.ts` 同款解析）：

```
serviceDataDir(dataDir, 'session')/        # = ${dataDir}/services/session/
sessions/
  index.json      → [{ id, title, createdAt, updatedAt, pinned?: boolean }]
  <sessionId>.json → { meta: {...}, messages: Message[] }   # messages 追加式
```

> 决策：单文件整写（会话消息量在 P3 规模内 < 数百条，整写可接受）；Session 服务是**唯一写者**，串行防并发（见 §6）。

## 2. 工作分解（WS-1 ~ WS-6）

### WS-1 · session 服务骨架 + store（2d）

- [ ] `service.json` + `src/ids.ts` + `src/store.ts` ——
  - `load()`：index.json + 各 `<id>.json` 懒加载；损坏 JSON → 该会话降级为 `corrupted` 标记（不崩服务、不吞其它会话）
  - `save()`：写临时文件 + rename 原子替换（防半写坏档）；`flush()`：变更防抖
  - indexes：`index.json` 与 `<id>.json` 双写一致
- [ ] `src/session.ts` —— create（生成 id/标题）/ rename / delete / `clear`（清空全部）/ `appendMessage`（消息 id + createdAt 由 ids 生成，**只增不删不改**）
- [ ] `src/index.ts` —— 命令分发（§3.3 表）→ 持久化 → 发布事件（§3.4）
- [ ] **子绿灯**：store 单测（CRUD、原子写、损坏档降级、双写一致）

### WS-2 · 命令/结果 IPC 模式（1d）

- [ ] 定义 RPC 约定（§3.3）：命令 topic + `<cmd>.result` 响应 topic，`requestId` 关联
- [ ] session 服务**七个命令**全部走通；`session.list.result` / `session.get.result` 可被前端与 loop 消费
- [ ] **子绿灯**：对伪 Core 的端到端单测（list/get/create/rename/delete/message.append 全链）

### WS-3 · loop 服务（2d）

- [ ] `src/prompt.ts` —— P3 常量 system prompt（OST 外壳定位；P5 接角色服务替换）
- [ ] `src/history.ts` —— 取 `session.get.result` 历史 → 拼多轮 `messages`；超长截断策略（保守：保留最近 N 组 + 首条 system/user 上下文，`maxMessages` 常量）
- [ ] `src/index.ts` —— **loop 是唯一写者**（消息只经 loop/session 落库）。收到 `loop.run { requestId: A, sessionId, text }`：
  1. **先把 user 消息落库**：`message.append(role:'user', text)` → 会话里立即可见（不等 llm 响应）
  2. `session.get` 取该会话历史 → 拼多轮 `messages`（prompt.ts 常量 system 置首）
  3. **loop 内部生成 `requestId: B`**（A≠B），发 `llm.request { requestId: B, ... }`；维护 A↔B 映射
  4. `loop.state.changed(running, requestId: A)`；消费 `llm.token.streamed { requestId: B }` → 查 A↔B 映射 → **发 `loop.token.streamed { requestId: A, sessionId, token, index }`**（把 B 换成 A 再回前端）；维护 in-flight 累积全文（**不落库，只驻 loop 内存**）
  5. 结束（按 B）：`message.append`（assistant 全文 + finishReason/usage）→ 释放 → `loop.state.changed(idle, requestId: A)`
  - 失败：`loop.run.failed { requestId: A, ... }`（错误码透传），不落 assistant 消息
  - **cancel**：`loop.cancel { requestId: A }`（见下）
- [ ] **requestId 分层定案**：**A** = `loop.run` 的，驱动 `loop.state.changed` / `loop.run.failed` / `loop.run.cancelled`（前端只看 A）；**B** = loop 发 `llm.request` 时生成的内部 id（llm 事件全带 B）；映射关系只活在 loop 进程内，不泄到前端
- [ ] **`loop.cancel` 传播链路**：`loop.cancel { requestId: A }` → loop 查 A→B 映射 → 发 `llm.cancel { requestId: B }` → 等 llm `finish{finishReason:'stop'}` → 不落半截 assistant → `loop.state.changed(idle, A)` + `loop.run.cancelled { requestId: A }`；未知 A → 静默忽略（与 llm.cancel 同语义）
- [ ] **子绿灯**：loop 对伪 llm + 伪 session 的全链单测（多轮、失败路径、state 机切换、防重入、cancel 全链路、A/B 不串号、**崩溃后 in-flight 清理**）

### WS-4 · 前端 session 状态 + 会话列表 Pane（2d）

- [ ] `stores/session.ts` —— Pinia，**state 全集**：
  - `list: SessionMeta[]`（全量会话索引）、`curId: string | null`、`loading: boolean`、`error: string | null`
  - `bootstrap()`：`session.list` → `session.list.result` → 写 `list`；**`curId` 为本地态**（不跨窗同步、不落 preferences，本窗刷新回「最近会话」）
  - SSE 订阅 `session.created/updated/deleted` / `message.appended` → 响应式更新 `list`（**会话列表跨窗实时**，curId 不同步）
  - 「最近会话」定义：`list` 里 **`updatedAt` 最大** 的一条
- [ ] `features/session/session-list-pane.vue` —— ui 组件库实现：
  - List + Card 渲染会话（标题/时间）；点击切换；当前高亮
  - 新建（Button）/ 重命名（Modal + Input）/ 删除（Confirm Drawer/Modal）
  - 空态 EmptyState
- [ ] **子绿灯**：mock bus 断言 list 渲染、curId 切换、create/rename/delete 事件驱动刷新、跨窗同步

### WS-5 · ChatPane 会话化（1.5d）

- [ ] ChatPane 升级：进入即 `session.get { sessionId: curId }` 当前会话 → 渲染历史消息（List）；发问 → `loop.run`（含当前会话）
  - **`session.get.result` 为 null（curId 空/已删）** → 回退 `list` 中 `updatedAt` 最大的最近会话；list 也为空 → 空态 + 「新建会话」引导
  - **发问前 curId 为空 → 前端先 `session.create`（title 默认「新会话」）→ 拿 `sessionId` → 再 `loop.run`**（会话创建是前端职责；loop 不接受空 sessionId，见 §3.4）
- [ ] 流式：订阅 **`loop.token.streamed`**（当前 `sessionId` + `requestId` = 当前 A）→ **累积到本地 in-flight 消息**（虚拟 id，如 `in-flight-<A>`，逐 token 追加可见）；`message.appended` 只做**最终落库确认**——收到时把本地 in-flight 换成服务端 `messageId`（视图 id 切换，不重放 content）；无 history 冲突（P2 的单条清空逻辑移除）
- [ ] loop 状态展示：`loop.state.changed(running)` → 输入禁用 + Spinner；**`loop.run.failed` → Spinner 收起、错误占位 + Toast、输入恢复可发**
- [ ] **停止按钮改 `loop.cancel`**：P2 ChatPane 的停止按钮原来发 `llm.cancel`；P3 起 loop 在中间，**前端只见 A** → 停止按钮发 `loop.cancel { requestId: A }`（消除 `llm.cancel` 双语义）；`loop.run.cancelled` → 本地收起 Spinner
- [ ] **loop 崩溃恢复**：订阅 `service.failed { serviceId: 'loop' }` → 清本地 in-flight（Spinner 收起、输入解禁）+ Toast「服务重连中」；等 Core 重启后 loop 回到 idle（它的 state 是进程内态，崩溃即归零，无需回放）
- [ ] **子绿灯**：ChatPane + sessionStore + loop 集成冒烟（见 §5）；断言 user 消息发送即落、`loop.run.failed` 走错误占位不残留

## 3. 接口定案（P3 补齐）

### 3.1 数据模型

```ts
interface SessionMeta {             // index.json 条目
  id: string; title: string; createdAt: string; updatedAt: string; pinned?: boolean
}
interface Message {                 // 追加式，不可变
  id: string; role: 'system' | 'user' | 'assistant';
  createdAt: string; content: string;
  finishReason?: 'stop' | 'length' | 'content_filter' | 'tool_calls' | 'error';
  usage?: { promptTokens: number; completionTokens: number };
}
```

### 3.2 Loop 状态

```ts
type LoopState = 'idle' | 'running'   // paused 预留（P5+P），P3 不实现
// 事件：loop.state.changed { requestId, sessionId, state: LoopState, model? }
```

### 3.3 命令/结果 IPC 约定（RPC over bus）

| 命令 topic（session 订阅） | 请求 payload | 响应 topic | 响应 payload |
|---|---|---|---|
| `session.list` | `{ requestId }` | `session.list.result` | `{ requestId, sessions: SessionMeta[] }` |
| `session.get` | `{ requestId, sessionId }` | `session.get.result` | `{ requestId, session: { meta, messages } \| null }`（**null → 调用方回退「updatedAt 最大」的最近会话**） |
| `session.create` | `{ requestId, title? }` | `session.create.result`（发布 `session.created`） | `{ requestId, sessionId, title }` |
| `session.rename` | `{ requestId, sessionId, title }` | `session.rename.result`（发布 `session.updated`） | `{ requestId, sessionId, title }` |
| `session.delete` | `{ requestId, sessionId }` | `session.delete.result`（发布 `session.deleted`） | `{ requestId, sessionId }` |
| `session.clear` | `{ requestId }` | `session.clear.result`（**逐个发布 `session.deleted`**，复用现有事件） | `{ requestId, deletedCount }` |
| `message.append` | `{ requestId, sessionId, message: { role, content } }` | `message.append.result`（发布 `message.appended`） | `{ requestId, sessionId, message: Message }` |

约定要点（写入 RFC 习惯）：
- 命令 = 总线上的「对象」（沿用 `/api/command` 注入语义）；**响应 = 独立事件**，靠 `requestId` 关联。
- 缺失的请求字段 / 不存在会话 → `*.result` 返回 `error: { code, message }`（码见 §6 统一表），不吞静默。

### 3.4 事件契约（只增不改）

| Topic | 语义 | Payload |
|---|---|---|
| `session.created` | 新会话 | `{ sessionId, title, createdAt }` |
| `session.updated` | 重命名 / pinned 等 | `{ sessionId, title?, updatedAt }` |
| `session.deleted` | 删除 | `{ sessionId }` |
| `message.appended` | 消息落库成功 | `{ sessionId, message: Message }` |
| `loop.run` | 命令（loop 订阅） | `{ requestId, sessionId, text }`（**sessionId 必填**；空 → `loop.run.failed{ code:'invalid_request' }`，loop 不自动建会话） |
| `loop.cancel` | 命令（loop 订阅）：取消在途 run；**无 `<cmd>.result`（fire-and-forget）**，结果由后续 `loop.run.cancelled`（成功）或 `loop.run.failed`（失败）体现 | `{ requestId }`（= loop.run 的 A） |
| `loop.state.changed` | 状态切换 | `{ requestId, sessionId, state: 'idle'\|'running' }` |
| `loop.run.failed` | 本次跑动失败（错误码透传） | `{ requestId, sessionId, error: { code, message } }` |
| `loop.run.cancelled` | **新增**：本次跑动被主动取消（成功路径不留半截消息） | `{ requestId, sessionId }` |
| `loop.token.streamed` | **新增**：loop 转发 llm 的 token（按 B 过滤、换发 A）；前端只看 A | `{ requestId: A, sessionId, token, index }` |

> `loop.token.streamed` 的 `index` **保留 llm 侧原值**（不重编）；`sessionId` 由 loop 从 `loop.run` 里带出。前端只用 `index` 做排序/去重判断，不要求从 0 连续。

## 6. 风险与决策

| 主题 | 决策 / 规避 |
|---|---|
| **持久化选型** | P3 用 dataDir JSON（依赖少、可读）；SQLite 延后 P8 一次性接管；迁移路径：session 服务换 store 实现即可，事件契约不动（P8 只换 store.ts） |
| **消息一致性** | session 服务是唯一写者，命令串行执行（进程内队列），防两处同时 append 丢写；`message.append.result` 回执保证前端知道落库 |
| **RPC 模式** | 不引 IPC 框架；沿用总线 request/result 对 + `requestId`；为 P4 凭证/设置 IPC 提供同一模式 |
| **loop 宿主耦合** | loop 不直读 session 文件，只吃 `session.get.result`（服务间唯一通道 = 总线），保持插件边界 |
| **流式回填竞态** | assistant 消息只由 loop（in-flight）写；`loop.token.streamed` 逐 token 累积本地 in-flight（虚拟 id `in-flight-<A>`）；`message.appended` 到达后**只切换虚拟 id → 服务端 messageId**（视图 id 变化，不重放 content）；前端无「去重追加」逻辑，只有「替换视图引用」 |
| **长历史** | P3 截断策略保守（最近 N 组）；Compaction 属 P7/P8 范围（对齐 RFC A组②） |
| **重入** | `loop.state.changed` 非 idle 时重复 `loop.run` → `loop.run.failed(code: "busy")` |

## 7. 开工顺序

```
P1a + P1b + P2 全绿
  └► WS-1 session store ────────┐
  └► WS-2 RPC 模式 ─────────────┼─► WS-4 会话列表 Pane ──┐
  └► WS-3 loop（依赖 WS-2）─────┘                         ├─► WS-6 收尾
                                              └► WS-5 ChatPane 会话化
```
