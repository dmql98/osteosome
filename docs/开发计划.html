踩到一个真实的依赖方向问题（第一版 provider 恒空）

第一版把 provider 下拉与模型目录也放进 store，结果 provider 永远为空。原因是 useLlmProviders / useModelCatalog 是每次调用新建 ref 的 composable（不是单例）， 且靠 onMounted 订阅 —— 只在组件 setup 上下文有效：

  • 在 store 的 getter 里调它们 → 拿到的是刚建的空实例，永远是空
  • 在 store 里订阅 → 订阅挂在随后被丢弃的实例上，等于没绑

处置：不把这两个 composable 改成单例（那会牵动 settings 等既有调用方），而是把依赖方向摆正 —— store 只管「这一轮对话」的 run 状态；provider 列表与模型目录这类展示派生数据留在 ③ 的 setup 里 （那里才是合法调用上下文），选中后写进 store。理由写进了 chat.store 的注释， 防止以后有人「顺手」把它挪回 store。

「flex」怎么在绝对定位下实现

会话列 240px 与输入区 120px 是计划定的固定值，对话区是 flex（占满剩余）。 绝对定位没有 flex，所以 flex 那部分在首次渲染时按当前画布尺寸换算成像素 —— 画布变宽，吃掉剩余的两栏跟着变宽，会话列不动。 量不到尺寸（jsdom / 隐藏容器）时用兜底值，否则盒子会全叠在左上角。

优先级：保存的 rect > 三盒预设 > 通用网格

用户拖过之后保存的 rect 说了算 —— 那是用户的选择，不该被预设覆盖；预设只负责「第一次打开时的样子」。 这正是「一键复位」能成立的前提：复位清掉保存的 rect，预设重新生效。

面板头加快捷复位入口
  • PanelHeaderActions 加「↺ 重置为对话布局」，走 layout.resetLayout() （高级设置里已有同一入口，这次是把它提到面板头）
  • 走全局复位而不是只复位当前面板：布局快照是全局的，只复位一个面板会造成 「一个面板是三盒、另一个还是乱的」
  • resetLayout() 顺手补了 updateLayout(api.toJSON())：原来只靠 api.clear() 触发的 onDidLayoutChange 异步回写，紧接着退出/刷新复位会丢， 重启后又看到拖乱的旧布局
写测试时抓到一个真 bug

第一版为「量到 0」加了宽度下限（Math.max(width, 540)），结果窄画布下右栏超出画布右边 （320px 画布算出 532px 宽的右栏）。被「窄画布不溢出」那条用例当场抓到。0 的情况本来就由 兜底值处理，下限守卫纯属多余 —— 已改为只防非正数，并在注释里写明为什么不能设下限。

验收
  • 测试 12 组：几何 9 组（固定宽占满高 / 吃掉剩余 / 紧贴下方 / 不溢出 / 画布变宽则②变宽而①不变 / 窄画布不为负不溢出 / 兜底值 / 用给定尺寸） + 优先级 3 组（拖过的不被覆盖 / 没拖过的用预设 / 复位后预设重新生效）
  • 优先级那三条用纯函数复刻同一顺序来守，而不是挂载整个 PanelContainer （要 mock dockview + movable-box 的指针交互，成本高于收益）
诚实说明
  • 本轮不做窄窗降级（§不做清单）。窄画布下只是「可用但不好看」：会话列按比例收窄、 输入区固定 120px 可能把对话区压得很矮。已断言「不溢出、不出负」这条底线
  • 「三个盒子可各自拖动」靠的是 MovableBox 本来的能力 + 优先级约定，没写组件级测试。 真正兜住的是「复位后预设重新生效」

为什么它还是「假的」—— 三处不实（2026-10-02 复核）
不实之处后果

归属原则（已定案）

协同才能工作的 → 聚合成插件；可独立取舍的 → 独立插件。 据此 6 个服务 + 9 个组件划成 5 个插件： 工作台基础（无服务，只碰 Core 的内置组件）／对话工作台（session+loop+llm + 3 组件）／ 模型接入（llm-provider-openai）／凭证（credentials）／ 可靠性（llm-retry）。

关键区分：归属是意图，状态是事实。 「哪些服务/组件属于哪个插件」是人写的设计决定，磁盘上读不出来 → 必须落盘（plugin.json）； 「这个插件现在几分健康」是它那些服务的真实 status 聚合 → 可派生。 所以不能靠「从服务派生一份清单」来消除硬编码 —— 那会得到一份服务列表的镜像，不是插件。

plugin.json 的形状（草案，S7-1 定案）
// plugins/chat-workbench/plugin.json —— 一件能用的东西：一组服务 + 一组组件 + 依赖
{
  "id": "chat-workbench",          // 同时是目录名
  "name": "对话工作台",
  "version": "1.0.0",
  "icon": "💬",                      // 可选
  "services":   ["session", "loop", "llm"],
  "components": ["widget.session-list", "widget.chat-timeline", "widget.chat-composer"],
  "capabilities": [{ "name": "chat.run", "detail": "发问 / 流式 / 工具循环" }],  // 可选
  "dependencies": [{ "pluginId": "models" },
                        { "pluginId": "credentials", "optional": true }]
}

// plugins/  —— 每个插件一个目录，可打包成一个 zip 分发（拷目录即装）
plugins/
  chat-workbench/plugin.json    // session + loop + llm + 3 组件
  models/plugin.json            // llm-provider-openai（12 家厂商实例在内）
  credentials/plugin.json       // 凭证服务
  reliability/plugin.json       // llm-retry
  workbench/plugin.json         // services: [] —— 只碰 Core 的内置组件

与 service.json 的分工：service.json 描述 「一个进程怎么被拉起来」（entry / protocolVersion / publishes / subscribes，Core 用它管生命周期）； plugin.json 描述「哪些进程与组件算一件东西」（归属与依赖，Core 不看它来启进程）。 两者不重叠 —— 所以加插件不需要改 service.json，加能力位不需要改 plugin.json。
