2P0 — 必须先修

F-01 P0 session 把会话写进构建产物目录

根因链（三段，缺一不可）：

  1. plugins/chat-workbench/services/session/src/index.ts:12-13 
    const service = new Service({ id: 'session', version: '1.0.0' })
const store = new SessionStore(service.dataDir || process.env.DS_DATA_DIR || '.data')
    这行在模块顶层执行 —— 此时 service.start() 还没跑。
  2. sdk/ts/src/service.ts:91 dataDir = '' 直到 :142 握手返回才赋值 → 第一个操作数恒为空串。 plugins/chat-workbench/services/session/src/index.ts:13 的 process.env.DS_DATA_DIR 全仓只有这一处引用、Core 从不设置 → 第二个操作数恒为空。 于是恒等于 '.data'。
  3. core/src/service-manager/manager.ts:351 spawnServiceProcess(manifest.entry, { cwd: svc.dir })，P2 起 svc.dir = plugins/<id>/dist/server/<sid> （core/src/service-manager/plugin-registry-runtime.ts:143） → 相对路径 .data 解析成 构建产物目录。

磁盘实证（2026-10-05 取证）：

plugins/chat-workbench/ ├── dist/server/session/.data/sessions/ ← 正在被写：364 文件 / 291 KB，index 364 条 │ 最后写入 2026-10-05 10:25（Core 还在跑） └── services/session/.data/sessions/ ← 遗留：822 文件 / 603 KB，index 768 条 目录 mtime 2026-09-30（P2 之前的 cwd） userData/plugin/ ← Test-Path = False，一条会话都没有 userData/core/preferences.json ← 偏好 / 密钥在这里，是对的

四个后果：

  • 改数据目录对会话无效：本周新增的 ost.config.json 换根之后，偏好跟着走， 会话仍留在插件的 dist/ 里 —— 一个功能在最大的那块数据上是空的。
  • 随时会消失：git clean -xdf、重新 clone、换机器、换分支重装， 会话全没；.gitignore 的 dist/（.gitignore:2） 让它们既不入库、也不在 git status 里出现。
  • 只读安装目录会直接写失败（Program Files / /Applications）。
  • 产品自相矛盾：shared/src/paths.ts:36-38 明确约定 <dataDir>/plugin/<pluginId>/，Core 也确实算好了这张表 （plugin-registry-runtime.ts:159-166）—— 唯一的消费者没用它。
已经是好的：打包没有泄露风险。scripts/pack-plugin.mjs:61-72 已把 .data 排除在交付物外，且 core/tests/pack-plugin.test.ts:122 有断言守住 （「是运行期数据，不该被发出」）。这条不用动。

怎么修（最小改动，见第 6 节清单第 1 步）：把 store 的构造推迟到 service.start() 之后 —— 例如 main() 里 await service.start() 拿到 service.dataDir 再建 store，或改成 lazy getter； 同时删掉 DS_DATA_DIR 这个死掉的兜底（要么删，要么让 Core 真的下发）， 否则它会继续给人「这里有逃生门」的错觉。

F-02 P0 1186 条会话被劈成两份，822 条是孤儿

两份错位数据不是同一份的两个副本，实测文件名零重叠：

  • core/src/config/paths.ts:251-259 migrateLegacyDataDir —— 只在 dataDir 为空目录时才动；现在 userData/ 非空 → 直接 return。

顺序不能反：必须先修 F-01 的代码，再搬数据。 先搬的话，服务下次启动又往 dist/ 里新建一份，等于白搬。

合并策略建议：以「文件名并集」为准（两份零重叠，无冲突）， index.json 取两份条目合并去重，54 个不在 index 里的文件按 「保留但不进 index」处理（它们本来就是游离的，别凭空造出 index 条目）。 具体命令见第 7 节附录，跑之前先停 Core。

3P1 — 这一轮该修

F-03 P1 SDK 的 dataDir 在 start 前是空串，且不 fail-fast

sdk/ts/src/service.ts:91-92 把 dataDir = '' 当成契约写在注释里。 问题在于 '' 是 falsy —— 调用方写 a || b || c 时不会报错，只会静默落到 c。 F-01 就是这么来的，而写这段代码的人看注释是发现不了的（注释只说「start 前为空」，没说「读了会怎样」）。

建议：改成未握手取值即抛 —— get dataDir() { if (!this.started) throw new Error('service.dataDir available only after start()') }； 测试要提前拿到值的话，给一条显式逃生口（如 ServiceOptions.prefillDataDir）， 而不是让生产代码靠 || 兜底。

改完这一条，F-01 的写法在编译期/启动期就活不下去 —— 这是治本的那一半。

F-04 P1 没有任何测试断言「服务把数据写进了给它的那个目录」

  • core/src/service-manager/plugin-registry-runtime.ts:159 serviceDataDirs() 由静态分析标注 no covering tests。
  • 现有端到端 core/tests/e2e.test.ts / plugin-ui-e2e.test.ts / scripts/smoke.mjs:236-298 全都在验 「命令有回执、进程被杀能重启」，没有一条看落盘位置 —— 这就是 F-01 能活到今天的原因：轴 1（数据落点）在测试里是空白。

建议：加一条最小回归 —— 起真 Core（临时 dataDir）→ 发 session.create → 断言文件出现在 <tmp>/plugin/chat-workbench/sessions/， 且 plugins/**/dist/** 下没有新增任何文件。两条断言合起来才堵得住 F-01。

F-05 P1 loop 的工具根默认等于构建产物目录

plugins/chat-workbench/services/loop/src/index.ts:31

const TOOL_ROOT = process.env.LLM_TOOL_ROOT?.trim() || process.cwd()

和 F-01 同一个机制：cwd = plugins/chat-workbench/dist/server/loop。 后果是 toolSpecs(TOOL_ROOT)（:40）在一个构建产物目录里扫工具定义， executeTool 的路径守卫基准也变成那个目录 —— 不显式设 LLM_TOOL_ROOT，工具能力实际上是死的，而且报错不会指向「根选错了」。

建议：默认值换成与 cwd 无关、且随部署形态确定的路径（开发期仓库根 / 安装期 dataDir 下的 workspace），并把最终值暴露到 /api/info， 让设置页能看见「模型能读哪个目录」。

$srcA = Join-Path $repo 'plugins\chat-workbench\dist\server\session\.data\sessions'   # 364，当前在用
$srcB = Join-Path $repo 'plugins\chat-workbench\services\session\.data\sessions'      # 822，孤儿

# 文件名并集（实测零重叠，不会互相覆盖）
foreach ($src in @($srcA, $srcB)) {
  Get-ChildItem $src -File -Filter *.json | Where-Object Name -ne 'index.json' |
    ForEach-Object { Copy-Item $_.FullName (Join-Path $dst $_.Name) -Force }
}

# index 取并集去重
# 注意用 .NET 读写：PS5.1 的 `Set-Content -Encoding UTF8` 会写 BOM，
# 而服务端是 JSON.parse(readFileSync(...)) —— BOM 会让它直接抛 Unexpected token。
$a = [System.IO.File]::ReadAllText((Join-Path $srcA 'index.json')) | ConvertFrom-Json
$b = [System.IO.File]::ReadAllText((Join-Path $srcB 'index.json')) | ConvertFrom-Json
$merged = @($a) + @($b) | Group-Object id | ForEach-Object { $_.Group[0] }
[System.IO.File]::WriteAllText((Join-Path $dst 'index.json'), ($merged | ConvertTo-Json -Depth 8))

# 2) 核对：文件数 = 并集 1186，且 index 条目 = 768+364 去重
(Get-ChildItem $dst -File -Filter *.json | Where-Object Name -ne 'index.json').Count
