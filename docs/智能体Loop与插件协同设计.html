智能体 Loop 与插件协同设计

2026-10-06 · 8 插件 / 10 服务 / 一次完整 agent loop 的协同设计
这份文档回答两件事：① 新增四个插件（技能管理 / 工具管理 / MCP 管理 / 智能体角色）之后， 8 个插件 10 个服务各自负责什么、怎么协同；② 一次完整的 agent loop（含工具轮与审批）是怎么走完的。
最重要的一条结论先给：这四个插件没有一个需要扩展插件标准。 它们全是普通插件 —— 一个 plugin.json + 若干 services/<sid>/ + 一个 dist/。 角色、技能、工具这三样东西不在 plugin.json 里，它们是运行期由服务注册出来的： 装一个插件 → 它的服务起来 → publish 自己的提示词片段与工具目录 → 装配器下一轮就多了一份。
不新增任何进程间协议：本文新增的 11 个 topic 全部是 shared/src/events.ts 那两张表上的新行，不是新机制；Core 一行都不用改（Core 不解析插件内容）。
配套： docs/插件标准.html（归属与接口标准）· docs/插件化架构优化.html（目录与分发形态）· docs/插件协作与AI能力装配.html（prompt / 技能 / 工具的契约种子）
开始之前先钉死五条会被反复引用的既有事实（下面每一节都靠它们，错了整篇就塌）：
① plugin.json 的 capabilities[] 永远只给人看，一旦有代码依赖它做判断， 它就变成第二个真源（真源是 service.json 的 topic 白名单）。所以「A 声明了某能力，B 就能调」不成立。
② dependencies[] 不产生运行时耦合，只影响启动顺序与状态聚合； 缺必需依赖是 degraded 而不是不启动。
③ 服务之间只经总线与 plugins.readFile。 plugins.readFile 的边界是全部内容：只读 · 只限自己插件目录 · 无根即拒 · ≤2 MiB。 所以没有任何服务能读别的插件目录 —— 下面「插件自带技能包」怎么处理，全靠这一条推出来。
④ 历史里的 system 消息一律丢弃（buildMessages 的既有性质）， 于是 prompt 每轮重新装配，装/卸插件立即生效且不需要迁移任何历史数据。这是整个设计最省事的一处地基。
⑤ 命令的应答一律走 <cmd>.result 事件，总线不提供返回值。 所以每一次「问模型某件事」都是「发一条命令 + 等一条结果事件」两跳，本文的时间估算都按这个来。

1四个新插件：诉求 → 形态

原始诉求是四句话。它们都能成立，但每句都要拆成「谁负责」才落得了地：

诉求落成什么谁负责不负责
技能管理插件
管理装了哪些技能		 plugins/skills/
1 服务 skills · 1 视图		 用户技能的主人（userData/plugin/skills/custom/）+ 全系统索引的持有者 不负责「读别的插件目录里的技能包」—— 结构上不可能（readFile 只限自己）。
插件自带技能由那个插件自己的服务读并注册。
工具管理插件
管理装了哪些工具		 plugins/tools/
2 服务：tools（目录 + 审批）+ fs-tools（只读文件工具执行体）		 工具目录的聚合视图 + 审批仲裁 + 一个真工具执行体当切片 不是「所有工具的宿主」。执行体归各自注册工具的服务； tools 服务自己也是一个执行者（它带 fs-tools）。
MCP 管理插件
管理 MCP 连接		 plugins/mcp/
1 服务 mcp · 1 视图		 服务器配置 + 协议桥：spawn 子进程、tools/list → 生成 tool.registered 零新增 topic。它就是 tool.registered 的一个生产者， 所以装配器（loop）对 MCP 零改动。
智能体角色插件
选角色 / 配提示词+技能+工具		 plugins/agents/
1 服务 agent · 1 视图		 角色档案 + 绑定解析（提示词片段 / 技能 id / 工具名 / 模型偏好） 不拥有技能与工具 —— 角色存引用。 绝不把工具代码打进角色插件自己的 dist/server/（见 §10 的失败模式）。
为什么这四个是「插件」而不是「Core 的四个功能」。 因为它们各自都满足插件标准的全部三条：身份（能独立启停、能被依赖、能升级覆盖安装）· 接口契约（service.json 的 publishes/subscribes 就是它们的能力声明）· 界面（ui.views[]，可独立摆位）。
而反过来说：「用户自己的技能放哪」这件事必须有一个主人（skills 插件）。 没有主人的 userData/ 子目录迟早出问题 —— 那是凭证插件已经退役过一次的教训。

依赖图（只影响启动顺序与状态，不产生运行时耦合）

models （无依赖） ▲ │ dependencies:[{pluginId:"models"}] chat-workbench session · loop · llm —— 装配器在这里 ▲ ▲ ▲ ▲ │ │ │ │ │ │ │ └── reliability llm-retry（旁路重发 llm.request） │ │ └── tools tools · fs-tools │ └── agents agent（角色档案） └── skills skills（技能索引） mcp （无插件依赖！） 它只依赖 chat-workbench 的 topic 存在，不依赖那个插件在位 workbench （无依赖 —— 只碰 Core：/health · /events · /api/command） ★ 注意 mcp 与 skills 都不在 dependencies 里。 它们是「可选能力」：没装 skills → 装配器没有技能索引这一层，模型少一批技能， 对话照常；没装 mcp → 工具目录里没有 MCP 来的工具。缺失必须是合法的。
「依赖」与「可选能力」的区别值得单独说。 dependencies[] 声明的是「我需要你才能正常工作」，缺了我是 degraded； 而 skills / mcp / tools 提供的是「有它我多一份能力」，缺了我只是少一点。
写成依赖的后果很具体：只装 chat-workbench 的用户会看到一堆 degraded 插件， 而 degraded 在 UI 上是橙色的、写着「缺依赖」—— 那是在对用户说谎，它什么都没缺。
反向的代价也要认：不写依赖就得不到启动顺序保证。缓解办法不是依赖，是 §9 的重播三段式—— 每个「能力存在性」都自带一条「现在都有谁」的查询通路，于是启动顺序不再是任何人的隐式依赖。 这条已在 llm 主位与 provider 两侧落地

这张图最重要的三个读法：
① 竖着看是「谁提供什么」，横着看是「一轮对话走过谁」。 竖着看第 ③ 层到 ④ 层那段：agent / skills / tools / mcp 四个服务都只往那条黄色装配线里 publish 一份东西， 而没有任何一条线是它们直接指向 loop 的代码调用。装配器不关心它们从哪来。
② loop 是唯一的编排者，也是唯一知道「这一轮」的服务。 它做四件事：装配、执行工具轮、换发 requestId（A/B）、管轮上限。 谁都不该能绕过它 —— 所以工具轮上限 MAX_TOOL_ROUNDS 留在 loop 手里， 而不是分给各个工具宿主。
③ 沙箱边界跟着执行者走。 今天 loop 用自己插件的 dataDir 算只读沙箱根； 工具分散到多个插件后每个执行者各自算自己的（它有 dataDir + plugins.readFile）， loop 手里不该再有路径。这是「拆开之后反而更简单」的一处。
8 插件 / 10 服务的账： models 1 服务 · chat-workbench 3 服务 · reliability 1 服务 · workbench 0 服务 · skills 1 · tools 2 · mcp 1 · agents 1 = 10。
10 个进程，崩溃隔离度换来的代价是10 次握手 + 10 条 stdio 管道。 而每增加一个能力位服务，那个能力就可以被独立启停、独立升级、独立授权 —— 这是这笔交换划算的判据。
顺带：plugins/credentials/ 在仓库里还留着一个空目录 （凭证插件退役后留下的）。扫盘期「目录在但零清单」按既定语义等于没装，不报错 —— 但它该被清掉， 否则读代码的人会以为凭证还在。

3逐个设计：四个新插件

3.1 skills 技能管理

plugins/skills/ ├── plugin.json │ services: ["skills"] · dependencies: [] · ui.views: [ widget.skills ] ├── services/skills/ │ └── service.json │ publishes : skill.registered · skill.unregistered · skills.state · skills.list · tool.registered · tool.unregistered │ subscribes: skills.list · tool.execute ├── ui/ → dist/ui/ widget.skills 技能库 └── （无自带数据：技能包是别人的东西）
// skills 服务的职责，只有两件： ① 持有全系统一份技能索引（name + description + 来源 + 启用态）→ publish 成一个提示词片段 ② 执行 skill_read —— 模型要全文时才给正文（懒加载 / 渐进披露） // 「插件自带的技能包」怎么办 —— readFile 只限自己插件目录，所以： 每个带技能包的插件自己用 plugins.readFile 读 plugins/<自己>/skills/<name>/SKILL.md， 解析 frontmatter，然后 publish skill.registered{ ownerPluginId:"<自己>", name, description, enabled }。 skills 服务只是收集方 —— 它从不读别人的目录（结构上不可能，也不该）。 // 用户自建技能住 skills 插件自己的数据目录： userData/plugin/skills/custom/<name>/SKILL.md ← skills 服务是它唯一的主人 userData/plugin/skills/skills.json ← 启用开关 + 插件技能的本地覆盖
这个分工是 readFile 的边界直接推出来的，不是设计偏好。 任何服务想读另一个插件目录里的技能包都做不到（唯一的通路是 HTTP 数据面，而那条面不存在且 dataReadableBy[] 那条不生效的授权声明建议直接删掉）。
于是「技能 = 跨插件可引用的一等公民」这个诉求只能靠 「每个插件 publish 自己那份，skills 服务聚合成全系统一份」来实现。 好处这恰好与「工具 = 可插拔能力位」完全同构 —— 一处收集器管两类东西。
技能的四条硬边界（否则「技能插件」就是一个装了就等于装了任意代码执行的后门）：
① scripts/ 的执行必须等审批位落地。 今天的内置工具是纯只读、路径锁在自己的沙箱根内、单文件 ≤64 KB、目录 ≤200 项， 而且源码注释里明确写了「没有写 / 删 / 网络 / 进程类工具，那些必须先有审批 listener 才允许存在」。 脚本执行直接违反这条：它就是进程执行。
② 同名冲突拒绝第二个（fail fast），不「后者覆盖前者」。 症状差别很大：后者覆盖的症状是「我改了技能却不生效」，而原因在另一个插件里，几乎无法排查。
③ description 是契约不是注释。 渐进披露意味着模型必须先决定「要不要读这个技能」。写得含糊 = 技能装了也不会被读，而 UI 上它明明是绿的。 所以 skills 管理视图要给「description 长度 / 是否含 when 触发条件」一个显式的体检提示。
④ 卸载不回溯历史。 历史里那条 role:'tool' 的技能正文还在（append-only，不改）。 数据保留、只是不再可用；重装即恢复。不要级联删。

3.2 tools 工具管理

plugins/tools/ ├── plugin.json │ services: ["tools", "fs-tools"] · dependencies: [] │ ui.views: [ widget.tools ] ├── services/tools/ │ └── service.json │ publishes : tool.registered · tool.unregistered · tools.state · tools.list · tool.approval.requested │ subscribes: tools.list · tool.execute · tool.approval.resolved · tool.execute.result（失败时兜底回执） │ ★ 它是「审批仲裁 + 目录聚合视图」，不是所有工具的宿主 ├── services/fs-tools/ │ └── service.json │ publishes : tool.registered · tool.unregistered · tool.execute.result │ subscribes: tools.list · tool.execute │ 执行体：read_file · list_dir（从 loop 迁出来的切片） └── ui/ → dist/ui/ widget.tools
// 工具目录的唯一真相源：注册事件的并集（不是某份 JSON） tool.registered{ serviceId, tools: ToolSpec[], risk?: 'read'|'net'|'proc'|'write' } ★ 关键设计：声明与执行同源。 模型看到的 name / description / parameters schema，是那个执行者顺手 publish 的， 和它 publish「我叫什么名字」是同一次动作 —— 不可能漂移。 把 ToolSpec 从执行体里剥出来单独放一个 JSON，会立刻产生「谁执行」的二义性，而答案是唯一的：执行体就是一个服务。
为什么把内置的 read_file/list_dir 从 loop 迁到 fs-tools。 三条理由，一条比一条重：
① 只有一条执行代码路径。 loop 里保留一个「宿主就是我自己」的单进程特例看着省事， 但那意味着两条执行路径要各自测、各自修 bug，跨进程那条出问题时会怀疑错对象。
② loop 手里不该再有路径。 今天 TOOL_ROOT 由 loop 用自己的 dataDir 算出来； 工具分散后沙箱边界必须随执行者走，否则「谁有权读哪个目录」就永远只有一个答案。
③ 它是 W4 的验收切片。 把一个已经在跑的工具搬过去，就能在不加任何新功能的前提下验证 tool.execute / tool.execute.result 这条新通路是否真的通。
loop 侧保留发布权不变（loop.tool.executed + message.append{role:'tool'}）， 所以对话界面一行都不用改 —— 变的只是「谁真正执行」。
// userData/plugin/tools/ approvals.json ← 审批策略：per-tool { mode:'auto'|'ask'|'deny', remember? } workspace/ ← fs-tools 的沙箱根（替代今天的 chat-workbench/tool-root/） ★ 策略放这里，不放 Core —— Core 不该知道有哪些工具，更不该知道哪些危险。

3.3 mcp MCP 管理

plugins/mcp/ ├── plugin.json services: ["mcp"] · dependencies: [] · ui.views: [ widget.mcp ] ├── services/mcp/service.json │ publishes : tool.registered · tool.unregistered · mcp.server.state │ subscribes: tools.list · tool.execute · service.failed（清理残骸） └── ui/ → dist/ui/ widget.mcp：服务器清单 / 连接态 / 工具数 / 手工试调 // 运行期行为 启动：读 servers.json → 对每个 enabled 的服务器 spawn 子进程 → MCP initialize → tools/list → publish tool.registered{ serviceId:"mcp", tools:[…该 server 的全部工具] } 调用：loop 发 tool.execute{ name:"mcp__fs__read_file", … } → mcp 服务认领这个名字 → tools/call → tool.execute.result 失联：子进程退出 / tools/list 超时 → publish tool.unregistered{ serviceId:"mcp" } → 目录里那一批消失 ★ 零新增 topic。mcp 就是 tool.registered 的第二个生产者，所以 loop 侧对 MCP 零改动。 这就是「把工具做成能力位而不是做进 loop」的全部回报。
MCP 引入的三个新问题（都和工具跨进程化是同一批，只是一起解决）：
① 命名空间不能由模型猜。 多台 MCP server 都有 read_file 时， 必须有一层确定的命名规则（推荐 mcp__<serverId>__<toolName>）。 让模型在两个同名工具里挑，是把「协议歧义」转成「模型随机选」，症状是「同样的问题两次结果不同」。
② 一个 server 崩了不能拖垮其他 server。 每个子进程独立超时、独立注销； tool.execute 要有超时兜底（失败结果，不是静默），否则用户看到的就是「模型一直转圈」。
③ 令牌 / 环境变量不能进总线。 很多 MCP server 要 API key。 正确做法是它们只存在 mcp 插件自己的 servers.json 与子进程环境里； 事件里只出现 serverId。与「凭证明文永不过总线」是同一条红线。

3.4 agents 智能体角色

plugins/agents/ ├── plugin.json services: ["agent"] · dependencies: [] · ui.views: [ widget.agents ] ├── services/agent/service.json │ publishes : agent.state（角色列表·重播整份） · prompt.fragment.registered · prompt.fragment.unregistered │ subscribes: prompt.fragments.list · agent.state（自身重播） ├── ui/ → dist/ui/ widget.agents：列表 / 编辑器 / 绑定选择器 └── （无自带数据：角色是用户数据，不进交付物目录）
// userData/plugin/agents/characters.json —— 角色 = 一组绑定 [ { "id": "reviewer", "name": "代码评审员", "prompt": "你是资深代码评审员。只指出会导致故障、丢数据或难以回退的问题，不评论风格。", "skills": ["git-diff"], // 引用 skills 服务的 name "tools": ["read_file","list_dir"], // 引用工具的 name；"*" = 全部 "provider": "deepseek", "model": "deepseek-chat", "thinking": "medium", "params": { "temperature": 0.2 } }, { "id": "bare", "name": "裸会话", "prompt": "", "skills": [], "tools": "*" } ] // 模型偏好可省略 —— 省略即「不覆盖」，回落链： loop.run 参数 → 角色偏好 → models 插件的 preferences.json 默认 → env → 硬编码
角色服务只做一件事：把「角色」这份用户数据解析成一组具体的绑定。 它不认识技能的实现，也不认识工具的执行体 —— 那是各自服务的事。 它回给 loop 的是一份纯数据的「配方」：fragments[] / skills[] / tools[] / provider / model / thinking。
所以 loop 侧零新增 topic：角色那份提示词片段是普通片段， 通过既有的 prompt.fragment.registered 进来，和 reliability 插件发的那条一模一样。
而这正是这条路线最好的结果：角色的「存在性」与「能力」统一了，而且没有为此扩展任何标准。 装一个角色插件 → 它的服务启动 → publish 它的片段 → 装配器下一轮拼进去； 卸掉 → 服务停 → 片段随之消失 → 模型不再假装拥有那些能力。
必须提前防的一个失败模式：如果角色插件把「绑了哪些工具」当成自己的实现 —— 把工具代码打包进自己的 dist/server/，那工具就退回到进程内注册表， 而那份注册表的文件头明确写着「这是最小工具循环的种子，不是终态」。
症状：装第二个角色时工具列表互相污染、无法共享、进程数不降反升。 守住边界：角色存引用，工具归服务。
同样地，角色也不该打包技能包 —— 技能包是 skills 服务与其他插件的自带数据， 角色只存 skill 的 name。

6★ 一次完整 agent loop：18 步

核心动效。按 ▶ 播放看一个数据包走完一轮含工具调用与审批的完整对话， 或点单步前进。⑤⑥⑦⑭⑮ 是本轮新增/改造的五格；每步都标了落在哪个面： 🌐 同源 HTTP/SSE · 🔌 服务与 Core 的 stdio 管道 · 🔁 总线 · 📖 只读特权 · 📁 本地文件。

1 / 18 实线 = 本轮主线 · 虚线回边 = 工具轮
⑤⑥ 与 ⑭⑮ 之间的那个空档，是这份设计里最容易做错的地方。 prompt 与 tools 必须由同一个装配点、同一时刻收集。
工具在位但提示词没说明它存在 → 模型不会去调一个它不知道存在的工具， 而症状是「工具明明装了却不生效」，看起来像工具坏了。
反过来，提示词提到了工具而它没注册 → 模型调一个不存在的名字 → 拿到失败结果 → 模型会自我纠正（这正是我们想要的），所以这个方向的错是可恢复的。 所以选择同源收集不是「整洁」，是让错误方向朝可恢复那边倒。
A / B / T 三个 id 的分工，与「每个前端状态只能按 A 认领一次」。
A = loop.run（前端只见 A）· B = llm.request 内部 id， 每个工具轮换一个（B→B′），映射只活在 loop 内存 · T = toolCallId， 同时用作 tool.execute 的 requestId（一对一，不需要新关联表）。
推论：三个 iframe 各自订阅 loop.state.changed{running}，谁先看到谁认领， 而它们认领到同一个 A，所以三个视图的「正在生成」必然一致。 所有 handler 第一件事都是 if (requestId !== activeA) return， 防上一轮迟到的 token 污染新一轮 —— 在有工具轮之后这条更关键，因为现在一条 A 会对应多个 B。

四层提示词：顺序必须确定

priority层来源约束
0身份层loop 内置常量 恒在、不可被覆盖、不可被卸。否则模型不知道自己是什么、不知道自己有哪些能力。 它也是 prompt 里唯一不该被用户编辑的一段 —— 可编辑的部分属于角色层。
5角色层agent 服务 publish 一条角色一个片段。角色不存在（没选 / 已删）→ 这一层为空，不是错误。 回落是「裸会话」，不是报错。
10技能索引层skills 服务 publish 一条 全系统一份，但按角色绑定过滤后再拼。 过滤器放在 skills 服务侧（它知道启用态），不在装配器侧。
30~90能力层各服务自愿 publish reliability 的「工具失败不得美化」、mcp 的「你有外部工具」之类。 缺失合法：没装 reliability 就没这条，订阅失败要忽略。
顺序必须确定，否则症状是「模型行为随机」。 规则：priority 数字小的在前；同 priority 按发布者 id 字典序、同发布者内按片段 id 字典序。
这不是洁癖 —— 一个系统两次启动得到两份不同的提示词，而唯一症状是「模型有时听指令有时不听」， 几乎无法排查。而且它会伪装成「模型问题」，于是你会去调温度、调模型、换厂商，浪费一整天。
同一条纪律也适用于工具目录：ToolSpec[] 的顺序同样要确定 （按 serviceId 字典序，serviceId 内按 name 字典序）。 为什么这条对工具尤其重要：部分厂商的 prompt 缓存按 tools 数组内容命中， 顺序抖动会让缓存全部失效 —— 症状是「同样的对话 token 费用翻了十倍」，而没有任何报错。
预算闸门为什么必须「整块丢弃 + 告警」，不能「静默截断」。 buildMessages 保留最近 20 条并把截断点对齐到 user 边界 （孤立 tool 消息会让上游 400）。 能力层片段变长时，20 条历史里真正的对话占比会变少，而症状是「插件装上之后模型变笨」—— 它看起来像模型问题，不像预算问题。
所以规则是：超字节上限（默认 8 KB）时按 priority 从低到高整块丢弃，每丢一条打一条 logger.warn；不要「截半条」—— 半条指令比没有更糟，模型会照着半条做。
整块丢弃也可能让一个必需片段消失（行为突变）。所以规则还配一条： 丢了就要在界面上看得见 —— 往 loop.run 的关联上下文里发一条 「本轮有 N 个提示词片段因超预算被丢弃」，让「能力」视图能列出被丢了哪些。

9五个必须一起解决的机制

9.1 重播三段式：每一种「能力存在性」都必须自带

这条是本文最重要的一条纪律，它的来源是一次真实事故： 插件化落地时服务遍历顺序从「平铺目录字母序」变成「按插件」， llm-provider-openai 于是先于 llm 启动 → 主位订阅时注册事件已经发完 → 路由表空 → 所有请求 unsupported_provider。 修法不是把顺序排回去，而是让 llm 启动后自己发一次 llm.provider.reannounce。

发布方重播 / 收集方问一次 / 前端等 connected 后再问
三条纪律，全部沿用已有机制，没有发明：
① 「重播整份」而不是发增量。 订阅方可能晚于发布方启动，那批增量事件早就发完了。拿到全量就不需要 diff、不需要补偿逻辑 —— 这条性质比省字节重要得多。
② 每个 *.list 命令空载荷。「现在都有谁」不需要参数。
③ 缺失合法，订阅失败要忽略。 一个不带片段 / 不带工具 / 不带技能的插件完全正常。让装饰性内容打死主链路是本末倒置。
已守住的三处 llm.provider.registered ↔ llm.provider.reannounce · models.prefs.state ↔ models.prefs.get · models.credentials.state ↔ models.credentials.list —— 新增的每一族照抄这个三段式。

9.2 工具执行与审批：一个显式状态机

按 ▶ 走一遍。注意四个状态上的三条纪律： ① timeout 与 failed 都必须产生一次失败结果，不许静默 —— 静默的等价物是用户看着「模型一直转圈」； ② orphaned（结果到达时这一轮已被取消）静默丢弃，不许补发， 与既有「nextRound 对未知 B 返回 null」同一处置； ③ rejected 也回填给模型 —— 告诉它「这个操作被用户拒绝了，请用别的办法」， 而不是直接失败整轮。

审批策略放哪、为什么。 放 宿主插件自己的 userData/plugin/tools/approvals.json， 不放 Core —— Core 不该知道有哪些工具、更不该知道哪些危险。
三级：auto（策略免审，只读类默认）· ask（逐次审，带「记住这次」）· deny（永久拒）。默认必须是 ask 而不是 auto： 一个新装的工具在第一次执行前就免审，等于「装了就等于装了」—— 而用户装它时并没有读它的代码。
「记住这次」要带作用域：记住 会话级 或 工具级， 不要记成全局 —— 否则第一次的「这次允许」会变成永久通行证。

9.3 沙箱边界随执行者走

今天：loop 用自己插件的 dataDir 算 TOOL_ROOT userData/plugin/chat-workbench/tool-root/ ← loop 手里有路径 终态：每个执行者各自算自己的 fs-tools → userData/plugin/tools/workspace/ mcp → 子进程自己的沙箱（协议/容器决定，我们管不着，只做超时与审批） skills → userData/plugin/skills/custom/<name>/ （skill_read 只能读这里） 角色 → 只存引用，永远不持有路径 ★ loop 手里不再有任何文件系统路径。 这不是洁癖：它让「新增一个工具执行者」这件事不需要改 loop 一行， 而 loop 是这条主链路上唯一被所有能力方依赖的服务。
为什么 loop 不该再有路径，这条要讲透。 今天 loop 同时是「编排者」和「工具宿主」，于是它需要知道「读文件能读到哪里」。 一旦工具分散到 5 个插件，loop 若还要做沙箱裁定，就得知道每种工具的边界规则 —— 那是一条必然会长歪的耦合：某个执行者改了边界规则，loop 不知道，于是它给出的判定是过时的。
正确形态是「谁执行谁负责」：执行者有 dataDir + plugins.readFile， 它自己算自己的根；loop 只需要知道「这个 toolCall 该发给谁」，而那是从 tool.registered 的并集里查出来的 —— 一份数据，不是一条规则。

9.4 超时、孤儿、残留：三件事必须同一批做

问题触发场景症状（不处理的话）处置
超时 执行者进程崩溃 / 卡死 / MCP 子进程不响应 用户看到「模型一直转圈」，无错误、无日志提示 每个 tool.execute 带一个硬超时（默认 30 s，MCP 按服务器配）。 超时产生一次失败结果（ok:false + 人话原因）回填给模型，让它换个办法。
孤儿结果 审批期间用户 loop.cancel；或这一轮已被取消而结果才到 补发一条 loop.tool.executed 到一个已结束的状态 → 界面出现「幽灵工具块」 静默丢弃。判据：结果到达时 A 已释放或轮次不匹配。 与既有「nextRound 对未知 B 返回 null」同一处置。
残留注册 宿主进程被强杀（崩溃 / 插件被停用）→ 它来不及发 tool.unregistered loop 内存里留着一个指向已经不在的进程的工具 → 每轮都 tool.execute 到空气， 然后超时。表现为「工具偶尔失灵」 订阅既有 service.failed / service.stopped， 按 serviceId 清掉它注册的一切。 这是本文新增的一条硬要求 ——「进程退了，内存里的注册表就空了」这个假设在正常退出时成立，在被强杀时不成立。
「残留注册」是最容易被漏掉的一条，而且它的症状最有欺骗性。 正常路径上服务会先 unregistered 再退出，所以开发者本地测试永远看不到它： 本地「停掉 tools 插件」走的是优雅停机。
出问题的是「用户在任务管理器里杀掉 core」「机器断电」「插件被自动更新替换」这些路径。 而症状是间歇性的：「工具偶尔失灵，重启一次就好了」—— 于是每个人都会去怀疑模型、去调温度、去换厂商，没有人会想到去查注册表。
所以这条必须有测试：kill -9 一个工具宿主服务，断言 loop 的工具目录在 X ms 内不再包含它。

9.5 模型偏好回落链：五层，逐层向后

provider / model / thinking 的取值顺序（第一个有值的赢） ① loop.run 的显式参数 前端用户当场选的 ② 角色偏好 agents/characters.json 的该角色字段 ③ models 插件的 preferences.json 默认 用户设置窗里的「默认」 ④ env（LLM_PROVIDER / *_MODEL） 部署者的显式意图 ⑤ 硬编码 今天 loop/src/index.ts:30 的 env.LLM_PROVIDER || 'deepseek' skills / tools 同理，各有自己的回落： 技能 = 角色绑定 ∩ 已启用（两者都为空就是不带技能，不报错） 工具 = 角色绑定 ∩ 已注册（"*" 表示全部已注册；未装的工具执行者不在并集里，天然消失） ★ 为什么不把 ⑤ 删掉。 它是唯一一层「零配置时也能跑」的兜底，而 ①~④ 全空意味着用户什么都没配。 但它必须排在最后 —— 今天它排在最前（只有 env 一条路），于是只接了 OpenAI 兼容端点的用户， 第一次发问就得到 unsupported_provider，而下拉里明明有模型。这是最伤用户的一类 bug。

10失败模式清单：会真的发生的那几种

失败模式怎么发生的用户看到的症状设计上的防线
角色把工具打包进自己
最严重		 角色插件作者把「我带的工具」理解成「我的工具」，代码打进自己的 dist/server/ 装第二个角色时工具列表互相污染、无法共享、进程数不降反升 守住边界：角色存引用，工具归服务。 这条要在插件作者文档里写成不变量，并用一条 CI 守卫： 角色的 dist/server/ 里不许出现 tool.execute 的执行实现 —— 它只能出现在 service.json 的 publishes 里（发命令，不是执行）。
技能 scripts 变成后门 有人把「工具型技能」（scripts/*.sh）先做出来，审批位还没落地 装一个技能 = 装一个任意代码执行 脚本执行必须等审批位。技能脚本产生的是 risk:'proc' 的工具， 而 risk:'proc' 在策略里默认 ask 且不可被插件自身改成 auto。
MCP 同名工具 两台 server 都有 read_file 同样的问题两次结果不同；模型随机挑 确定的命名规则 mcp__<serverId>__<toolName>。 冲突在注册时就拒绝并给出人话原因，不留到运行时。
提示词超预算被静默截断 装了 6 个大技能 + 3 个能力插件，片段总量越过上限 「装上插件之后模型变笨」—— 看起来像模型问题 整块丢弃 + logger.warn + 界面上列出被丢了哪些（§8）。
工具目录顺序抖动 实现时用了 Map 的插入序而非显式排序 同对话 token 费用翻十倍，无任何报错 显式排序规则（§8），并加一条测试：两次收集同一批注册，ToolSpec[] 逐字节相等。
同名技能后者覆盖 两个插件都带 git-diff 「我改了技能却不生效」，原因在另一个插件里 拒绝第二个（fail fast），并在 skills 视图里标出冲突的两个来源。
晚启动的收集方永远看不到目录 loop 启动晚于 tools 服务，注册事件早发完了 「工具有时有有时没有」—— 取决于进程启动顺序 §9.1 重播三段式。tools.list 是空载荷命令。
停插件留下半截历史 在途的一轮被直接 kill 会话历史里有一半截 assistant 消息，永远留在那里（append-only） 既有约定：停插件先发 loop.cancel 收尾，超时才强杀。
残留注册指向死进程 kill -9 一个工具宿主 「工具偶尔失灵，重启就好了」 §9.4 第三行：service.failed → 按 serviceId 清目录。
MCP 令牌进了总线 有人把 token 放进 tool.registered 的某个备注字段 令牌出现在 SSE 与日志里，无法撤回 与「凭证明文永不过总线」同一条红线。 加一条守卫：payload 里不允许出现 key/token/secret/password 命名的字段（大小写不敏感）。
清单里那一条标红的，值得单独强调它的性质。 前九个失败模式都是「有人写错了」，可以靠 review 与文档防住； 第十条（角色打包工具）不同 —— 它看起来完全合法：代码能跑、测试能过、演示很自然。
它唯一的不合法之处是抽象层次错了（把「引用」写成了「拥有」）， 而抽象层次错误不会被任何运行时检查发现。
所以对这类错误，唯一有效的防线是让正确写法比错误写法更省事： 角色插件只要订阅 agent.state + 发一条 agent.resolve 就能工作， 它根本不需要知道任何工具代码。等作者发现「不写那 50 行也能跑」， 错误的写法就没有生存空间了 —— 这比任何一条文档规定都管用。

11不变式与红线（本设计不得破坏）

  • 不新增进程间协议。 stdio JSON-RPC + shared 的 EventMap/CommandMap 仍是唯一入口。 本文新增的 15 个 topic 全部是这两张表上的新行，不是新机制。
  • Core 一行都不用改，而且 Core 不解析任何插件内容。 它的校验逻辑是「查表」，表变宽自动覆盖。 已核对 manifest.ts:41-56 就是查表；plugin-registry-runtime.ts 不 import 任何插件概念。
  • 提示词 / 技能 / 工具 / 角色都不进 plugin.json。 那张表是归属信息（哪些进程、哪些页面、哪些依赖），不是内容信息。 把内容写进去会让 plugin.json 变成大杂烩， 而且「提供了但是空的」与「不提供」将无法区分 —— 而目录存在性检查读不出这个区别（这两个的处置完全相反：前者是配置错误，后者正常）。
  • 凭证明文永不过总线、永不进 SSE、永不进日志。 新增的 MCP 令牌走同一条红线。凭证引用（file:<id> / env:NAME） 当不透明字符串透传，只有执行者解引用。
  • 存在性由服务决定，不由目录决定。 没装 provider 就等于没有那个模型；没有服务注册工具就等于模型不知道那个工具。 不存在「声明了但用不了」的第二种状态。
  • 每种「能力存在性」都必须自带重播通路。 每个 *.list 命令 + 收集方上线时主动问一次。 启动顺序不该是任何人的隐式依赖。
  • 缺失是合法的。 没装 skills / tools / mcp / agents 任何一个，对话照常工作，只是少一份能力。 订阅失败要忽略，不能让装饰性内容打死主链路。
  • 顺序必须确定。 提示词同优先级按发布者 id → 片段 id 字典序； 工具按 serviceId → name 字典序。同一个系统两次启动得到不同的装配结果， 症状是「模型行为随机」或「token 费用翻倍」，两者都几乎无法排查。
  • 有长度上限并告警。 静默截断是最坏的一种。
  • 只读工具可策略免审；写 / 网络 / 进程类必须逐次审，且默认是审。 这条是技能 scripts/ 的前置条件，不是可选项。
  • loop 是唯一的编排者。 工具轮上限、requestId 映射、消息落库、状态机 全在 loop。谁都不该能绕过它。
  • 角色存引用，技能与工具归服务。 角色插件的 dist/server/ 里 不许出现工具的执行实现。
  • 测试跟着被测物走。 装配器（composePrompt / 工具过滤 / 预算闸门）的测试留在 loop 包； 每个插件自带数据与协议符合性的校验留在那个插件包里 （照 service-distribution.test.ts 与 plugin-ui-e2e.test.ts 的做法： 真构建 → 真 Core → 真请求）。 而两个必须有的跨插件集成测试：① 装配结果逐字节可重现； ② kill -9 一个工具宿主后目录在 X ms 内清空。这两条只能在真 Core 上跑， 所以它们不属于任何一个包。

12实施顺序：每一步独立验收、独立可 revert

全部只动服务与事件表，不动插件标准。

W0补模型配置缺口零新协议

W2agent 服务（角色）第一个新插件
做什么

带一个真角色切片

同时把角色选择器接进 composer

做什么
索引 = 一个提示词片段（W1 已有）· 正文 = 一个工具（W4 才有通路）—— 所以顺序上它要么在 W4 之后，要么先只发布索引、skill_read 暂不可用。
建议：W3 与 W4 同批，否则「技能管理界面里显示已装但一调就不生效」比没有更糟。
知识型技能先行
它只需要「索引片段 + skill_read 工具」， 不需要脚本执行、不需要审批。这是本文唯一建议先开的一类技能。
W4工具跨进程化 + tools 插件唯一真正的新协议
做什么
tool.registered / .unregistered / tools.list / tool.execute / tool.execute.result + 新建 plugins/tools/（tools + fs-tools 两个服务）。 切片 = 把 loop 里已经在跑的 read_file/list_dir 搬过去： 不加任何新功能就验证了整条新通路。
同批做完（否则只是把问题挪了位置）
① tool.execute 硬超时 + 失败结果兜底； ② 孤儿结果静默丢弃； ③ service.failed → 按 serviceId 清目录； ④ 沙箱边界移到执行者自己的 workspace/，loop 手里不再有路径； ⑤ kill -9 集成测试。
验收
对话界面零改动（loop 保留 loop.tool.executed + message.append{role:'tool'}）； 工具目录在「能力」视图里可见且带来源服务；两条跨插件集成测试通过
W5审批位W6 的前置
做什么
tool.approval.requested / .resolved + 审批弹窗 + approvals.json 的三级策略。默认 ask，只读类可自动升到 auto（需用户显式改）。
纪律
「记住这次」带作用域（会话级 / 工具级），不记全局。 rejected 也回填给模型而不是失败整轮。 审批期间用户取消 → 结果成为孤儿 → 静默丢弃。
验收
装一个 risk:'proc' 的工具：第一次执行必弹审批；拒绝后模型收到「用户拒绝了」并自己换办法
W6mcp 服务loop 侧零改动
做什么
新建 plugins/mcp/：tools/list → tool.registered； tools/call → tool.execute.result。 零新增 topic —— 这是本文对「工具做成能力位」这个决定的最终验证： loop 对 MCP 一行都不改。
同批做完
确定的命名规则 + 冲突注册时拒绝；每 server 独立超时与独立注销； 令牌只在 servers.json 与子进程环境里（事件里只出现 serverId）。
W7脚本型技能（可选）依赖 W5
做什么
技能包里的 scripts/* 注册为 risk:'proc' 的工具。 这条可以永远不做 —— 知识型 + 工具型 + 工作流型三种形态已经够用。
若要做
必须有 W5 已落地，且 risk:'proc' 在策略上不可被插件自身改成 auto。 这一条是「技能不是后门」的技术保证，不是文档约定。
为什么 W3 建议与 W4 同批，而 W2 可以单独走。 W2（角色）只需要 W1 的提示词片段这条通路，而「角色绑技能」那部分可以先绑空列表 —— 角色照样能用，只是暂时不带技能。缺一份绑定是「少一点能力」，不是「坏了」。
而技能不一样：技能的全部内容都在 skill_read 这个工具里。 工具通路没通之前，「已装技能」在界面上是绿的、点下去读不出正文 —— 那是在对用户撒谎。所以技能宁可晚一点整体上线，也不能半上线。

#问题选项建议与理由
1装配器放哪 ① loop 进程内收集
② 新增一个「装配」服务
③ 提到 Core		 ①。loop 已经是工具目录的装配者，一处组装逻辑让 prompt 与 tools 同步增减； ② 多一跳总线往返与一个失败点；③ 违反「Core 不解析插件内容」。

2角色里存引用还是存快照 ① 存 name 引用
② 把当时的 prompt/tools 快照存进角色		 ①。② 会让「装/卸插件立即生效」这个最省事的性质消失 —— 快照必须跟着每次装卸做迁移，而历史是 append-only 的，迁移不了。

② 两个（全局装/启用 + 角色绑定）		 ②。一个开关会逼用户「要么给所有角色开，要么全关」—— 而技能管理插件的诉求正是「管理装了哪些技能」。
实现上很便宜：角色存 name 引用，全局开关在 skills 服务的 skills.json， 取交集。两条都要有，因为「装了就全局生效」是另一种失控。
4提示词片段的字节上限取多少 ① 不限
② 8 KB（建议）

② 只读 auto / 其余 ask
③ 全部 auto（信任已注册）		 ②，但新装的工具第一次仍要 ask。

② 现在删掉
③ 补上数据面		 ②。它只进了 schema，而能施加限制的 HTTP 面不存在。
本文所有跨插件读都走总线事件（agent.state / models.prefs.state / tools.state / skills.state）或 纯引用（角色存 name）。
留着一条不生效的授权声明比没有更糟 —— 它让读代码的人以为边界存在。
这份设计与既有三份文档的关系，一句话对齐：
插件标准.html 钉死了「这五样东西都不在插件标准里」（§2）， 本文是那条结论的落地施工图； 插件协作与AI能力装配.html 给了prompt / 技能 / 工具三条线的契约种子与六条待决问题， 本文把它们合进一个闭环，补上MCP 与角色两族，并给 W0–W7 的落地顺序。
