中栏：这一步过不过 Core、走哪条通路 —— 最容易搞混的一层，所以单独占一栏。
右栏：同一时刻用户屏幕上是什么样子。
走完整轮之后，那三条结论应该自己就成立了： ① 提示词、技能、工具、角色都不在任何插件清单里，它们是各服务注册出来的； ② Core 在所有「进程之间」的通路上，但不在任何一条「进程与外部世界」的通路上 —— 左图上，紫色线一律收进 Core，青色虚线一律从服务直接出框； ③ Core 从不解析内容 —— 它查白名单、转字节、记生命周期，仅此而已。

    1两种情况：接着旧会话聊，还是开一个全新会话

    一轮对话只有两种情况，区别只在一件事：这个会话里面有没有历史。 从「发消息」那格之后的所有步骤完全一样 —— 装配、请求、模型往返、工具轮、收尾，一格都不差。
    所以这不是「两条流程」，而是同一流程前面挂一段长度不同的前置： A 有 2 格前置（先选中，再各自把历史载入进来）；B 只有 1 格前置（建一个空会话）。
    B 内部不分情况。列表点「新建」和直接发第一句话，建出来的是同一个东西：一个没有历史的新会话， 跑的是同一条命令、同一段代码 —— 区别只在界面上那一下是谁点的。

    B 内部为什么不再分情况。
    列表点「新建」的下一件事通常就是首问 —— 所以这两步本来就是同一条链上的相邻两格， 没有必要当成两条路：建完之后要发的话，走的还是下面那一模一样的 16 格。
    它们跑的是同一段代码、同一对命令：session.create 一条、回执一条、 session.created 一条。所以做成一格前置就够了，界面上只是谁点了那一下不同。
    要留的只是两个把手：① 用户点「新建」；② 他干脆不点，直接敲第一句话 —— ② 才是常态，很多人从来不碰那个按钮，那时会话列表根本没参与。
    这也是为什么 Core 那一侧完全不用改：它只是又转发了一条已在白名单里的命令。

    三条最容易在实现里踩空的地方，全部集中在这两种情况的分叉上。
    ① session.create.result 必须【常驻订阅】。 它就是那条已经咬过两次的坑：不要为一次命令临时订阅 topic（换 SSE 连接会开一个「两条流都不在」的窗口， 回执和领域事件双双丢失）。
    症状对照：A 场景完全正常（因为没有这一跳），只有 B 会坏 —— 所以它躲过所有在 A 场景上做的测试。
    修法：session.create.result 进常驻订阅集合，在本地按 requestId 配对。
    ② curId 失效要有兜底。 另一个窗口删掉了当前会话、或会话文件损坏（列表里那个 ⚠ 标记），此时 session.get 返回 session: null。返回 null 不是抛错，调用方要回退到最近会话（recent()）， 而不是崩、也不是静默建一个空会话 —— 后者会让用户以为历史丢了。
    ③ 「空会话」不是一个状态，是「还没有消息」。 session.create 只建 meta（id / title / 时间戳），内容由 message.append 填。 所以不要给「空会话」写一套单独的渲染逻辑 —— 对话组件现有的空态（EmptyState）就够了。
    A 与 B 之所以能共用一套渲染，正是因为第三条：它们在服务端没有两种形状， 只有「消息条数不同」。

    2对话侧只有三个组件：会话列表 · 对话 · 输入框

    chat-workbench 插件的界面就是三个组件，不多不少。plugin.json 里声明了三个 ui.views[]，Core 把同一个 dist/ui/index.html 代伺服三次， 用 #hash 让同一个产物渲染三种形态 —— 所以界面上三个框是同源 iframe，可以自由拖拽摆位。

    三个组件彼此零通信 —— 没有 postMessage，没有 BroadcastChannel，一个都没用上。
    它们唯一共享的是一个字节：当前会话 id curId （同插件跨 iframe 用 sessionStorage + storage 事件共享， 正好是「一个窗口一份、三个 iframe 共享」的语义）。
    其余全部状态各自从同一条 SSE 事件流重建：每条事件自带 sessionId 与 requestId，按 curId 过滤即可。
    推论一：三个组件的「正在生成」必然一致 —— 它们认领到同一个 A。
    推论二：加第四个组件不需要任何后端改动 —— 因为它用的是同一个 HTTP 接口 + 同一条 topic 流， 差别只在 ?topics= 过滤与本地 curId 过滤。
    推论三：不需要传输层这件事，是拆开之后才看清的 —— 拆之前 pinia 单例看起来在解决「跨组件同步」， 实际上它只是把同一份数据做成了同一个对象，掩盖了「这些数据本来就有多个独立副本的来源」这个事实。
    两条只有这三个组件才会踩的坑。
    ① 不要为一次命令临时订阅一个 topic。 SSE 的订阅集建在 URL 里（协议没法给已建立的连接加 topic），所以每多一个 topic 就必须 重开一条连接；而新流 open 之前有一个「新旧两条都不在」的窗口 —— 落在这个窗口里的事件永远丢了：handler 还在，但那一刻没有任何一条流在传输。
    形态：create() 为一次命令临时订阅 session.create.result → 换流 → 紧接着的回执与 session.created 双双丢失 → 会话列表不刷新，还干等 10 秒兜底 （用户要切走再切回来才看见）。sdk/core-client/src/sse.ts:57-81
    规矩：要等回执就常驻订阅再在本地按 requestId 配对； 或把「问一次」挂在 state === 'connected' 上（连上就问、重连就再问，天然自愈）。 也不能改成「新流 open 之后再关旧流」兜住 —— 重叠期同一事件会投递两次， 而 loop.token.streamed 是直接追加、无去重，那会把刚修好的「事件只到一次」打回原形。
    ② 「对话」这个组件的 handler 第一件事必须是 if (requestId !== activeA) return。 现在一条 A 会陆续收到多个 B 的 token（第 ⑫ 步换 B），漏掉这条的症状是： 用户连发两轮，第二轮的答案里混进第一轮没说完的半句话，而且复现需要时序恰好。

    📖 stdio 点对点 RPC ＋ 🌍 外部直连

    接口调用方去向边界
    initializeCore每个服务 握手回 dataDir（服务唯一一次拿路径的机会）、coreVersion。
    plugins.readFile任一服务自己插件目录 只读 · 只限自己插件目录 · 无根即拒 · 禁 node_modules · ≤2 MiB。 所以没有服务能读别的插件目录 —— 技能包、工具声明各自自读。
    POST {baseUrl}/chat/completionsmodels/llm-provider-openai上游厂商 不过 Core。请求头里的 Authorization 明文只存在于这个进程的内存里。
    stdio JSON-RPC：tools/list · tools/callmcp/mcp用户机器上的子进程 不过 Core。这是唯一能把任意程序接进工具目录的路， 所以它必须走同一套审批（risk:'proc'）。
    把「过 Core」与「接口类型」两张维度叠起来，会得到三条很实用的结论。
    ① Core 的 HTTP 面这一轮只被用了三次：伺服界面、收命令、发事件。 插件之间的十几次交互一次都没碰它 —— 全走总线。
    ② 唯一需要 Core 新增能力的场景是「进程要出网」—— 而那个能力 Core 刻意没有。 所以 MCP 接进来时要新增的不是 Core 的功能，而是一个服务去管子进程。 这是「把能力做成能力位」的第二个回报（第一个是模型层零改动）。
    ③ 「多视图」这条能力成本几乎为零。 因为三个视图用的是同一个 HTTP 接口 + 同一条 topic 流， 差别只在 ?topics= 过滤与本地过滤 curId。 所以「加一个新视图」不需要任何后端改动 —— 加第四个、第五个也是免费的。

    4六条通路：哪些过 Core，哪些不过

    这一节要建立的唯一认知：Core 在「进程之间」的全部通路上，但一条都不在「进程与外部世界」的通路上。
    因为每个服务只有一条到 Core 的 stdio 管道（sdk/ts/src/service.ts:205 的 bus.publish → Core 的总线 → core/src/service-manager/manager.ts:646 再用 bus.event 通知推给订阅者）。 所以「插件之间没有直接调用」这句话，字面意义上是真的，而「所有字节都经过 Core」也是真的。
    但 Core 不解释任何 payload —— 它查一次 topic 白名单、搬一次字节、记一次生命周期。 「在数据通路上」与「在语义上」是两件事，这份设计只占前者。

    但旁路    		 握手回 dataDir；plugins.readFile 只读自己插件目录 （manager.ts:559-599）。不进总线、不进 SSE， 与 preferences.get 是同一套纪律。 ⑦（读 credentials.json）、每个服务启动时
    最后一行「不过 Core」值得停一下，因为它是反直觉的。 插件进程可以自由出网 —— Core 既不代理也不审查。
    好处是没有活动部件：不需要反向代理、不需要管上游端口生命周期、 上游的流式缓冲问题不会变成 OST 的问题（provider 直接从上游读 SSE，转成中立块再进总线）。
    代价是「插件装上就等于有出网能力」 —— 这与「插件装上就等于能读自己目录里的文件」是同一性质的事。 两者都靠用户装它这个动作作为授权，而不是靠 Core 把关。
    这也是为什么网络类工具必须逐次审批：审批弹窗问的是「现在要不要让这条通路真的被用掉」， 而不是在问 Core 能不能代理 —— Core 根本没这个能力。

    ② 唯一需要新增 Core 能力的场景是「进程要出网」—— 而那个能力 Core 刻意没有。 所以 MCP 接进来的时候，要新增的不是 Core 的功能，而是一个服务去管子进程。 这就是「把能力做成能力位」的第二个回报（第一个是模型层零改动）。

    6第 ④ 步为什么是最关键的一格

    右栏那张「装配摘要」卡是整轮里信息量最大的一屏，值得单独拆开讲。

    priority 0 身份层
    loop 内置常量。恒在、不可卸 —— 否则模型不知道自己是什么、不知道自己有哪些能力。
    priority 5 角色层
    agents · agent 服务 publish。角色不存在就是这一层为空，不是错误（回落成裸会话）。
    priority 10 技能索引
    skills · skills 服务 publish 一条，内容是每个技能一行「name + 什么时候该用它」。
    priority 30~90 能力层
    reliability · llm-retry 等各服务自愿 publish。缺失合法。
    「顺序必须确定」不是洁癖，是一条会伪装成别的东西的规则。 排序键 = priority → 发布者 id → 片段 id 字典序。
    不这么排的后果：同一个系统两次启动得到两份不同的提示词，唯一症状是「模型有时听指令有时不听」—— 你会去调温度、调模型、换厂商，因为没有任何报错指向真正的原因。
    工具目录同样要排序（serviceId → name），而那条更贵： 顺序抖动会让 prompt 缓存全部失效，症状是「同样的对话 token 费用翻了十倍」，同样零报错。

    工具目录 = 注册并集 ∩ 角色绑定

    • 并集来自所有服务 publish 的 tool.registered： tools · fs-tools 的 read_file/list_dir、 skills · skills 的 skill_read、 tools · tools 的 run_tests、mcp · mcp 那一批。
    • 取交集用 agents · characters.json 里那个角色的绑定清单。"*" 表示「全部已注册」。
    • 空集不是错误：角色没绑工具就是没绑。但「模型返回了目录外的工具名」必须是失败结果， 不是静默忽略 —— 静默会让模型永远不知道自己调错了。
    • 绑定指向未注册的工具（用户卸了那个插件）时忽略并标一条悬空引用，不报错： 缺一份绑定只是「少一点能力」。
    • 进的是 API tools 参数，不进 system 文本 —— 前缀缓存友好。
    • 预算闸门：片段总量 8 KB、历史 20 条（截断点对齐到 user 边界， 因为孤立的 tool 消息会让上游 400）。超了整块丢弃 + 每条一条 warn， 不要静默截断 —— 症状是「装上插件之后模型变笨」，而没人会想到去查字节数。
    这一格最省事的地方：prompt 每轮都重算，而且这一格不过 Core。 既有性质是「历史里的 system 消息一律丢弃」—— 于是装一个插件 → 它的服务起来 → publish 一条片段 → 下一轮就多了一份，不需要迁移任何历史数据， 也不需要 Core 知道这件事发生过。
    副作用也要认：改一个角色的提示词，对已有会话立刻生效，不会追溯。这既是特性也是意外来源， 所以角色编辑界面必须写明「下一轮生效」。

    7三个 id：为什么不能省

    id是什么谁看得见为什么需要它
    A loop.run 的 requestId 前端只认它
    Core 也只当字符串转发    		 它是对外的「这一轮」。所有 UI 状态都按 A 认领。 三个 iframe 各自订阅同一批事件、认领到同一个 A，所以三个视图的「正在生成」必然一致。
    本轮 A 贯穿两个工具轮 —— 第 ⑫ 步换的是 B，不是 A。而 Core 不知道 A 有多长。
    B → B′ llm.request 的内部 id 只活在 loop 内存 一次工具轮 = 一次新的 llm.request，所以一条 A 会对应多个 B。 B 让「哪一次上游请求」在模型层内部是清楚的，而回程事件必须换发成 A，B 永不泄前端。
    T₁ T₂ toolCallId，同时用作
    tool.execute 的 requestId    		 模型 · loop · 执行者
    Core 仍然只当字符串    		 模型返回的工具调用块 id 天然就是一次执行请求的 id —— 不需要任何额外的关联表，一对一配对是免费的。
    所以审批弹窗天然知道自己在等哪一次，而 Core 不需要参与这个关联。
    有工具轮之后，「防上一轮迟到 token 污染新一轮」这条从建议变成了必需。 现在一条 A 会陆续收到多个 B 的 token，handler 的第一件事必须是 if (requestId !== activeA) return。
    漏掉它的症状：用户连发两轮，第二轮的答案里混进第一轮没说完的半句话， 而且复现需要时序恰好 —— 又是一个几乎无法定位的问题。

    8三个必须一起解决的新问题

    第 ⑩ 步引入了唯一真正的新协议（跨进程执行 + 审批）， 而它带来的三个问题必须在同一批解决，否则只是把问题挪到了别处。 右栏第 ⑬–⑮ 步可以亲手验证「失败也要产结果」这条。

    问题触发不处理会看到什么处置
    超时 执行者崩溃 / 卡死 / MCP 子进程不响应 用户看到「模型一直转圈」，无错误、无提示 硬超时 → 产生一次失败结果（ok:false + 人话原因）回填给模型。 静默的等价物就是「一直转圈」。
    孤儿结果 审批期间用户按了停止；或这轮已结束而结果才到 界面上出现一个「幽灵工具块」，挂在已经结束的轮次下面 静默丢弃，不许补发。判据：结果到达时 A 已释放或轮次不匹配。
    规则来源：与既有「nextRound 对未知 B 返回 null」同一处置。
    残留注册 执行者被强杀（崩溃 / 插件被替换），来不及发注销事件 「工具偶尔失灵，重启一次就好了」 —— 间歇性、无报错、没人想到去查注册表 Core 早已发布 service.failed / service.stopped （manager.ts:776,787）—— loop 只要订阅它、按 serviceId 清目录即可。
    这条最容易被漏因为本地测试走的永远是优雅停机，永远看不到它。 必须有 kill -9 集成测试。
    顺带说明：这是 Core 少数「主动产出语义」的地方（它知道进程死了）， 但它仍然不判断「这意味着哪个工具没了」 —— 那是订阅方的事。
    为什么「沙箱边界随执行者走」是这三件事的自然解法。 今天 loop 用自己插件的 dataDir 算只读沙箱根，理由是它同时也是文件工具的宿主。 一旦工具分散到多个插件，loop 若还要裁定边界，就得知道每种工具的边界规则—— 那是一条必然会长歪的耦合：某个执行者改了规则，loop 不知道，于是它给出的判定是过时的。
    正确形态是「谁执行谁负责」：执行者有 dataDir 和 plugins.readFile， 自己算自己的根；loop 只需要知道「这个 toolCall 该发给谁」， 而那是从注册并集里查出来的一份数据，不是一条规则。

    9一页速查

    本轮的新协议
    tool.execute · tool.execute.result · tool.approval.requested · tool.approval.resolved
    （其余能力全部是「一个重播事件 + 一个 *.list 命令」，同构复刻已有的三处）
    新协议落在哪
    chat-workbench · loop（发）· tools · tools（审）· tools · fs-tools（执行）—— Core 一行都没改，它的校验逻辑就是查表。
    谁来装配
    chat-workbench · loop 进程内，不过 Core，与工具目录同一装配点、同一时刻
    轮上限在哪
    留在 loop（MAX_TOOL_ROUNDS，默认 5）—— 它是编排决策，谁都不该能绕过
    角色存什么
    userData/plugin/agents/characters.json → prompt · skills[] · tools[] · provider/model/thinking —— 全是引用
    输入框怎么拿到角色
    输入框 widget.chat-composer 订阅 agents · agent 的 agent.state（总线事件），不是读文件。没装 agents 插件时那个下拉要消失，不能留空的。
    dataReadableBy[] 至今没有生效点（server.ts 里只有 /api/plugins 与 /plugins/* 两条路由），建议删掉 —— 一条不生效的授权声明比没有更糟
    widget.tools 怎么拿到目录
    订阅 tools · tools 的 tools.state。能力目录一律走事件，前端不读插件文件 —— 因为它运行期才成形
    加一个新视图
    成本≈0：同一个 HTTP 接口 + 同一条 topic 流，只需在 ?topics= 与本地 curId 过滤上动手
    角色不存什么
    技能包、工具代码、沙箱路径。绑引用不绑实现
    MCP 的地位
    它就是 tool.registered 的第二个生产者 → loop 侧零改动； 它管子进程用的是自己的进程，不用 Core 代理 —— 所以 Core 不需要新增任何功能
    审批策略放哪
    userData/plugin/tools/approvals.json —— 不放 Core，Core 不该知道有哪些工具
    默认审批
    ask。只读类可被用户显式升到 auto；新装工具第一次仍然要问
    失败怎么处理
    回填给模型让它自我纠正（含被拒绝）。不自动重试有副作用的工具
    Core 的全部职责
    查白名单 · 搬字节 · 记生命周期（service.* / plugin.state.changed）· 伺服静态产物
    Core 不做的事
    不解析插件内容 · 不参与编排 · 不管插件 UI 内部路由 · 不代理外部网络
    如果只记三句：
    ① 「能力」住在服务里，不住在插件清单里。 装一个插件就是多起一个进程，它 publish 自己那份，下一轮装配器就多认得它一点； 卸掉就是模型不再假装拥有那些能力。这个效果不来自任何目录规则。
    ② 「进程之间」全部过 Core，「进程与外部世界」一条都不过。 所以 Core 必须可靠、必须轻；而出网能力属于插件，不属于 Core。
    ③ Core 在数据通路上，不在语义上。 它能搬 1 MB 的工具结果，但不知道那是一个工具结果。 这条边界一旦模糊，「插件化」就退化成了「一个大进程里塞了几个模块」。
