插件标准 · Plugin Standard

OST 实施稿 · 修订版：标准只管归属与接口，其余一律不管
一句话标准：插件 = 一个自带前后端的目录；plugin.json 是它唯一的身份， service.json 是它唯一的接口契约，dist/ 是 Core 唯一认的东西。 除了这三样，插件目录里放什么，标准一概不管。
本版修订：上一稿错误地把 prompts/、skills/<name>/、tools.json 写成了每个插件的标准槽位。那违反了 docs/插件化架构优化.html §7 的不变式 「目录约定只有「你有一个属于自己的目录」这一条；里面放什么是插件的事」。 正确说法见 §2 与 §9。
标注：已有 已落地并被测试守住 · 半有 形状在、机制缺 · 待建 本轮要实现

1标准定义：插件目录里只有三样是标准的

plugins/<plugin-id>/ ← 目录名必须等于 plugin.json 的 id │ ├── plugin.json ← 标准① 身份 + 归属 + 依赖 ├── services/<sid>/service.json ← 标准② 一个进程怎么起、说什么话 ├── dist/ ← 标准③ Core 只认产物 │ ├── server/<sid>/index.js 单文件 · 零外部依赖 │ └── ui/index.html + assets base 必须命名空间化 │ ├── services/<sid>/src/ ← 源码，不在标准内（Core 不读） ├── ui/ ← 源码，不在标准内 └── …任何别的文件… ← ★ 不在标准内。catalog.json 只是「恰好有一个」 userData/plugin/<plugin-id>/ ← 同样完全自由：里面有什么、什么格式，由插件自己定
「插件自带数据」是开放式的。 原文写的是 plugin.json 旁边「catalog.json 等」—— 那个「等」字就是标准的态度： 插件可以带任意数据文件，Core 只按「只读 · 只限本插件目录」授权，不校验名字、不校验形状。 catalog.json 是 models 插件自己的约定（它的 12 家厂商预设）， 不是所有插件都要有的槽位。
实现上这条落在 plugins.readFile：服务打成一个文件后没有任何 require 能解析到 plugins/<id>/xxx，于是 Core 授予「读自己插件目录里的只读文件」这条点对点特权。 路径由那个服务自己定，Core 不查。
「自带前后端」三个精确含义，每条都有代价：
① 后端 = 一个独立进程，stdio JSON-RPC 与 Core 说话，不开 HTTP 端口。 代价：进程数 = 服务数；收益：崩一个不拖垮全部。
② 前端 = 一个静态产物目录，Core 代伺服在 /plugins/<id>/ui/*，同源 iframe。 代价：base 必须命名空间化，否则两插件请求同一个全局 asset 路径（症状「A 的界面加载到 B 的代码」）。
③ 产物必须能脱离本仓库运行：esbuild bundle，产物里不允许出现任何非 Node 内置 require。 这条要有测试守（拷到空目录跑一次），因为它极易被无声破坏 —— 哪天 build 里加一个 external， 产出会退化成「仓库里能跑、拷出去不能跑」，CI 全绿、用户装上才发现。

2插件标准「不」规定什么 核心

以下四样不是插件标准的组成部分，任何插件都不必认识它们

  • 提示词 / system prompt —— 它是每轮重新装配的运行时值，不是交付物。
  • 技能 / SKILL.md —— 它是懒加载资源，索引是全系统一份，不是「每个插件各自的索引」。
  • 工具目录 / ToolSpec —— 工具是有副作用的执行体，在 OST 里执行体的容器是服务。
  • 角色 —— 角色是一组绑定（选哪些提示词 / 技能 / 工具 / 模型），是用户数据。
上一稿错在哪：把「运行时能力的来源」写成了「插件目录的标准槽位」。 这带来四个具体后果：
① 每个插件被迫理解它。 一个纯服务的可靠性插件凭什么要有 prompts/ 目录？
②「不提供」与「提供了但是空的」无法区分。 前者该静默，后者是配置错误 —— 而目录存在性检查读不出这个区别。
③ 把「来源」和「归属」绑死了。 插件化的原则是归属是数据、状态是事实； 而提示词片段可以有多种来源（插件自带文件、别的服务动态发布、用户自己编辑）， 一旦规定成目录，就等于宣布「插件自带文件」是唯一来源。
④ 用户编辑的那份没有位置。 它是用户数据，天然在 userData/plugin/<id>/， 不该也不可能塞进插件的交付物目录里。

那它们从哪来？—— 只有两条既有的面

来源通路边界适合
插件自带文件 plugins.readFile
（文件名与路径由那个服务自己定）		 只读 · 只限本插件目录 · 无根即拒 · ≤2 MiB 静态的东西：厂商预设、技能包、示例配置
总线（新 topic） 服务运行时 publish
→ 收集方组装		 topic 必须在共享事件表里；值不进 Core 依赖运行期事实的东西：当前可用工具、当前角色绑定的技能
两条面都已经是既有的。 第一条已由 models 插件读自己的 catalog.json 验证过； 第二条是所有服务之间唯一的通道。所以「让角色带提示词 / 技能 / 工具」这件事， 不需要扩展插件标准，只需要扩展服务与事件表。

3注册：插件如何进入 Core 的视野

注册没有 API、没有中心注册表 —— 它是拷一个目录。刻意如此： 分发物天然是一个文件夹，升级就是覆盖安装。

4 个真实插件 + 1 个反例 · 5 道闸门 · 任何一道不过只降级不抛错
为什么扫盘「不抛错」，而服务 manifest 校验「全成功或抛」。 性质不同：service.json 是代码，里面坏一个就是部署坏了，不该装作没事； 而插件清单是数据，拷目录进来就可能不合法 —— 而且一个插件坏掉不该让 Core 起不来。 所以每个问题收进 problems[]，其余插件照常加载。
症状对比：全抛 → 一个坏插件让整个应用打不开；收进 problems → 界面照常， 那个插件在详情页显示「装好了但用不了」并说明原因。
// plugins/<id>/plugin.json —— 契约（Zod；未声明字段会被剥掉，所以不写就没这个能力） { "id": "models", // 必须等于目录名 "name": "模型接入", "version": "1.1.0", "icon": "🧠", "services": ["llm-provider-openai"], // 归属：哪些进程算一件东西 "components": [], // 归属：哪些本地组件归我（迁移期字段） "ui": { "views": [ // 形态：可独立摆位的插件页面 { "id": "widget.llm-settings", "title": "模型设置", "entry": "index.html" } ] }, "capabilities": [ { "name": "…", "detail": "…" } ], // ⚠ 纯展示，不参与判定 "dependencies": [], // 只影响顺序与状态 "dataReadableBy": [], // 已声明，但需先有数据面才生效 "coreCompatibility": { "min": "0.1.0" }, // 不写 = 不限 "autoStart": true } ← 注意这里没有 prompts / skills / tools 字段。它们不在这张表里，因为它们不是归属信息。
两条容易被误读的细节：
① capabilities[] 永远只给人看。 一旦有代码依赖它做判断，它就变成第二个真源 —— 真源是 service.json 的 topic 白名单。所以「A 声明了某能力，B 就能调」不成立。
② 同一个 widget id 不许同时出现在 components[] 与 ui.views[]。 客户端不知道该用本地实现还是 iframe，而两者都能渲染出东西。

4发现：Core 如何知道插件列表

plugins/*/plugin.json → Zod 校验 + 环检测 + 拓扑排序 → problems[] → 喂进真实服务状态 → 派生 ready/degraded/failed/stopped → GET /api/plugins（manifest 原样透出 + 状态聚合） → 前端 usePlugins() 摊平成视图模型（不留第二份数据）

状态的定义顺序（有意的）

状态判据为什么不是别的
degraded缺必需依赖，或有服务未 ready 不是 failed：缺 provider 时对话工作台仍该显示、仍该让用户看见缺什么，只是发不出请求。
failed声明的服务里有 failed比「未就绪」更严重：进程在但死了。
stopped未安装 / 未启动 / autoStart:false 且一个都没起 不是 degraded —— 它没坏，是没开。混在一起，用户会去「修」一个没坏的东西。
ready依赖都在 + 声明的服务全 ready—
状态是派生的，所以事件只在变化时发。 它由「服务真实状态 + 依赖满足」算出来，没有自己的存储。Core 记住上次结果， 只在真的变了才 publish：一直发 → 每次心跳抖动都推一遍、前端得自己去重； 一次都不发 → 前端永远拿不到 starting → ready 的跃迁。
刷新时机挂在 service.* 生命周期事件上，不轮询。
环检测必须跑在拓扑排序之前。 顺序不能反：topoSort 对环只是「不死循环」的降级处理， 它不是检测手段。反过来跑，有环时会先排出一份看似正常的部分顺序，照着启就会互相等待直到一起超时。
环内成员：仍然出现在列表里（用户看得见「装了但起不来」），但不进启动顺序 —— 宁可少列，也不列一个假的顺序。

5启停：Core 如何管理生命周期

停之前先收尾；启停不重扫盘
allowedServiceIds(): ReadonlySet<serviceId> | undefined ├─ 插件层未配置 / 目录不存在 / 目录里零清单 → undefined = 不限制（照旧全启 + 告警） └─ 正常读到清单，四条「不 spawn」（或关系）： ① 已卸载（目录在，但用户说卸了） ② 显式停用（preferences.plugins.enabled[id] === false） ③ autoStart: false ④ 环内（不在启动顺序里，依赖无解） ⑤ coreCompatibility 不满足 → 不启动，但插件仍然可见 刻意【不】包含：依赖未满足【不】阻止 spawn。 只装 session 不装 models 时用户仍要看得到会话列表 —— 仅因缺 provider 就杀掉 session 是真实的功能回退。
四个真实踩过的坑：
① 停插件前必须先收尾。 若插件含 loop，先发一次 loop.cancel。 直接杀会留下半截 assistant 消息 —— 而会话历史是 append-only 的，那半截永远留在那里。
②「运行期生效」与「重启生效」必须共用同一份判定。 只在运行期处理停用、启动路径只看「已卸载」→ 症状是「禁用某插件，当天正常，重启后它自己回来了」。
③ 重扫盘不能把新插件的服务接进 ServiceManager —— 服务目录表是构造时定的。 rescan() 只更新清单与状态。症状：「插件显示 ready 但服务没起来」。
④ 一个服务停不下来不该让整条命令失败。 否则「停 reliability」会因为某服务卡住而连别的也不停。
「插件」不是进程，所以启停必须展开。 Core 没有插件的进程句柄，只有服务的。 规则：按启动顺序逐个启停它声明的服务；停之前先 loop.cancel 收尾；单个失败只告警不中断。
已知前提 当前四个插件的服务互不重叠，没有做引用计数。 将来一旦「同一个服务被多个插件声明」，必须改成只有声明它的插件都没装才真停。

6服务与接口：Core 如何知道插件能提供什么、能被调什么

这是整个标准里唯一真正有约束力的部分。两份清单，职责正交：

文件回答的问题谁读校验
plugin.json哪些进程与页面算一件东西（归属 / 依赖） Core 编排 + 前端展示Zod；id=目录名；服务目录存在；产物已构建
service.json一个进程怎么起、它说什么话（entry / protocolVersion / topics） Core 管生命周期时topic 必须在共享事件表里，否则进程起不来
直接收益：加一个插件不用改任何 service.json，加一种能力不用改任何 plugin.json。 两份清单各答一个正交问题，没有重叠。

可调用接口的唯一真相源：共享事件表

shared/src/events.ts ├── interface EventMap { … } // 事实：已经发生的事（过去式） ├── interface CommandMap { … } // 请求：要别人做事 ├── const EVENT_TOPICS = […] as const satisfies readonly EventKey[] └── const COMMAND_TOPICS = […] as const satisfies readonly CommandKey[] Core 启动每个服务前：拿 service.json 的 publishes/subscribes 去这两张表里查。 查不到 → 该服务不 spawn → 插件降级并说明「声明了不存在的话题」。
这张表「只增不改」，所以它是破坏性变更的防火墙。 加字段 ✅ ／ 改字段类型 ／ 改语义 ❌（升 topic 版本）。 理由：这些 topic 名已经进到已分发的插件产物里了 —— 悄悄改一个 payload 字段的含义， 症状是「升级之后老插件某个功能静默失效」，极难定位。
所以破坏性变更要配 coreCompatibility.min 抬版本号，而不是悄悄改。

三层声明，三种用途，互不越界

声明回答消费方能被代码用来判定吗
services[]归属：哪些进程属于我Core（编排）能 —— 决定 spawn 与数据根
ui.views[]形态：哪些可独立摆位的页面前端（iframe）能 —— 决定摆什么

dependencies[]顺序：谁先起、缺了会怎样Core（排序 + 状态）不能产生运行时耦合
（插件目录里的其它文件）它自己的事只有那个插件自己不能 —— Core 不解析

7环境依赖：plugin.json 的 requires 待建

为什么现在需要它。 一旦 OST 开源、分发物只有 dist/， plugin.json 就成了唯一的信息载体 —— package.json 不进交付物（所以用户看不到作者的 npm 依赖）、 node_modules 不进（所以任何 external 出去的依赖就是不存在）、 作者的 CI 也不在（所以 OST 仓库里那道「拷到空目录跑一次」的守卫保护不到第三方插件）。
今天的实测：pack-plugin.mjs 的 preflight 只查文件存在性， 完全不检查产物里有没有外部 require。所以一个带 accidental external 的第三方插件， 跑 pnpm pack 会产出一个「合法」的交付物，一路顺到用户手上才炸。

为什么没有 kind: "module"

「插件需要某个原生模块」这件事在 OST 的模型里是自相矛盾的：
· 能 bundle 的包 → 必须 bundle。service-distribution.test.ts 那条静态守卫已经在强制这件事 （产物里出现任何非 node: 前缀的 require 就红）。
· 不能 bundle 的（.node 二进制）→ 它不是插件的依赖，是运行环境的能力。
而「运行环境提供某种能力」在 OST 里已经有正确表达了：能力位 / 另一个插件。 所以它应该走 dependencies[] 或总线，而不是伪装成一条依赖声明 —— 否则这条声明永远只是「我需要 X」，却没有任何办法说明「谁提供 X」， 那是一条无法兑现的承诺，比不写更糟。

形状

// plugins/<id>/plugin.json "requires": [ { "kind": "node", "version": ">=22.5" }, { "kind": "executable", "name": "git", "why": "读写仓库快照" } ] // 不写 = 不限（与 coreCompatibility / dataReadableBy 同一条缺省纪律）
// shared/src/plugin-manifest.ts —— 沿用 PluginDependencySchema 的风格 const RequiresSchema = z.discriminatedUnion('kind', [ z.object({ kind: z.literal('node'), /** 版本区间。留空 = 只要「有 Node」*/ version: z.string().optional(), why: z.string().optional(), }), z.object({ kind: z.literal('executable'), name: z.string().min(1), /** 先只做存在性。版本区间要引入「输出怎么解析」，那是个 DSL —— 等真需要再加 */ version: z.string().optional(), why: z.string().optional(), optional: z.boolean().default(false), }), ]).array().default([])
为什么用「带 kind 判别符的扁平数组」而不是分组对象： 加一种新 kind 是往 union 里加一个值，结构不变；而分组对象加一种就得改顶层形状。 且 optional 在每个 entry 上语义统一，前端渲染也能走一条分支。

不能从 package.json 推导，但可以和产物对账

做法评价
读 package.json 的 dependencies 自动填 不可行：package.json 不进 dist → 用户读不到；pnpm workspace 依赖指向 仓库内的工作区包 → 推导出来是噪声；devDependencies 与分发完全无关。
扫产物里的 require(...) 与 requires 对账 这才是真相：产物是 esbuild 打完之后的实际状态，而 package.json 里大部分依赖 已经被打进去了。
规则：产物里出现非 node: 前缀的 require，但没有在 requires 里声明它 → 报错。
这条能自动抓住 95% 的真实事故（作者忘了 bundle、或误加了 external）， 而且不需要作者自觉。

检查放在哪：扫盘期只做零成本的

最要小心的一点：scanPlugins 是同步的、在 Core 构造期调用。 如果在里面 spawn 子进程探测 PATH，四个插件 × 2 个 CLI × 1.5s ≈ Core 启动卡 12 秒。
而且某些 Windows 环境的 CLI 会弹 GUI 框（凭据管理器之类）然后卡死 30 秒。
时机手段成本会不会崩
扫盘期
同步		 node 版本字符串比较近零不崩
扫盘期
同步		 PATH 目录扫描判 executable 存在
existsSync(dir/name) + Windows 再试 .exe/.cmd/.bat		 近零不崩
doctor
异步 · 一次性		 真跑 --version、真加载模块慢一点，可接受有超时保护
「PATH 扫描代替 spawn」是这里的关键。 纯 fs 操作、零子进程，所以放在扫盘期同步做也安全 —— 而且比 spawn 更准（不会碰到「某个 CLI 在无 TTY 下弹窗卡死」这类问题）。

三态可信度：不要用一盏灯骗人

声明得再细，检查也永远只是近似：文件在 ≠ 能加载（原生模块装错平台/ABI 时文件在但 dlopen 会失败）； 声明了 version 但不真跑，就无法知道真实版本。 所以 UI 上要区分三态，而不是用一盏绿的灯宣称「依赖满足」。

扫盘期（零成本同步）→ doctor（真跑一次）

三态各自意味着什么：
detected —— 静态推断：文件存在 / 版本号可解析。它不能证明「能用」， 但足以把「缺」与「有」分开，而这已经能回答用户绝大多数问题。
verified —— 真的跑了 / 真的加载了。只有 doctor 给得起。
unknown —— 没检：超时、崩溃、非致命错误。 关键 绝不能把 unknown 显示成绿色 —— 那等于对用户撒了一个关于他自己机器的谎。

不满足时映射到 degraded，不发明第五种状态

环境不满足该映射到哪个？答案是 degraded，理由和「缺必需插件依赖」完全一致： 它没坏（不是 failed），它装了也在跑（不是 stopped）， 就是「装好了、缺 X、用不了」。
发明第五种状态的下游全部要改：前端渲染、图标、筛选、状态聚合、plugin.state.changed 契约 —— 而语义上它就是 degraded。

呈现三层（缺的时候报，满足的时候也要报）

层次作用为什么必须有
插件详情页体检报告（✓ / ✗ + 人话原因） 已有 PluginDetailWindow，missingDependencies 字段现成
服务状态面板「这个服务为什么没起来」 用户遇到症状时第一个看的地方
启动日志一行 warn排障的最后一道
要双向显示。 不只缺的时候报，满足时也要显示 ✓ —— 用户会去详情页确认「我装的东西是全的」。只报缺，用户无法区分「全绿」和「没检查过」。
reason 要是人话：「缺少可执行程序 git（用于：读写仓库快照）」而不是 env_check_failed。

诚实的保证边界

能保证的：B 的机器满足全部 requires + Core 版本 → 服务一定能起、握手能完成。
不能保证的：网络不通、磁盘满、能力位被别人抢、用户自己停用了插件。
所以准确的说法是：requires + 自检把「不可发现的问题」变成「可发现的问题」，而不是消灭问题。
这个措辞很重要。一旦对外承诺「保证能用」，某天做不到时用户会当成 bug 报， 而真实原因是环境 —— 然后整套声明机制会被当成不可信。过度承诺是这类设计最常见的失败方式。

兼容性

plugin.json 里所有新字段都必须有缺省值 —— 理由和 coreCompatibility / dataReadableBy 一样：不写 = 不限， 现有四个插件零改动就能过，而「没声明」永远是安全的缺省。
同时 Zod 默认会剥掉未声明字段，所以不写进 schema 就等于丢了 —— 加上 requires 之前，别指望有人手写这个字段能生效。

8Agent Loop 闭环：一轮对话怎么穿过几个插件

核心动效。按 ▶ 播放 看一个数据包走完 10 步，或点单步前进。 每步标了落在哪个面：🌐 同源 HTTP/SSE · 🔌 服务与 Core 的 stdio 管道 · 🔁 总线 · 📁 本地文件 · 📖 只读特权。

1 / 10
黄色那格「能力来源」是本版的关键修正。 它不在 plugin.json 里、不在插件目录标准里。它是各服务自愿通过两条既有的面 （📖 自己插件目录里的只读文件 ／ 🔁 总线 publish）交给装配器的。
装配器不关心它们从哪来，只按 { id, priority, content } 这样的统一形状收集。 所以「装一个能力位 → 提示词与工具同时增减」是自然结果，而不是某条目录规则的效果。
A / B 两层 requestId 是闭环的关键设计。 A = loop.run（前端只见 A），B = llm.request 内部 id，映射只活在 loop 内存 —— 所以回程事件必须换发成 A，B 永不泄前端。
推论：每个前端状态只能按 A 认领一次。三个 iframe 各自订阅 loop.state.changed{running}， 谁先看到谁认领 —— 它们认领到同一个 A，所以三个视图的「正在生成」必然一致。 所有 handler 第一件事都是 if (requestId !== activeA) return，防上一轮迟到 token 污染新一轮。

9提示词 / 技能 / 工具 / 角色 各自归谁

四样东西都不在插件标准里。那它们是什么？各有一条归属线：

东西本质宿主容器 怎么进上下文谁决定它存不存在
提示词 每轮重算的
运行时值		 装配器（在 loop 内） 拼进 system 首位
历史里的 system 一律丢弃 → 下一轮即生效，历史不用迁移		 有没有服务 publish 片段
技能 懒加载资源
索引全系统一份		 一个服务管
扫描 / 校验 / 索引 / 按需读		 只有 name+description 进提示词
正文经一个读工具按需回填		 那个技能服务在位且扫到了
工具 有副作用的
执行体		 一个服务（跨进程能力位） 走 API tools 参数
不进 system 文本（前缀缓存）		 那个工具服务注册了
「注册」= 经总线声明自己
角色 一组绑定
用户数据		 一个服务管档案 切角色 = 换一组绑定
→ 装配器下一轮用新的		 角色服务在位 + 用户创建了角色

为什么工具不能是一份声明文件

工具最要紧的信息不在 ToolSpec 里：会不会写文件？要不要审批？会不会调网络？沙箱边界在哪？超时多久？
这些只有执行者知道。把它们从执行体里剥出来单独放一个 JSON，会立刻产生「谁执行」的二义性 —— 而答案是唯一的：执行体就是一个服务。
模型看到的声明（名称 / 描述 / 参数 schema）是那个服务顺手发布的， 和它发布「我叫什么名字」是同一次动作 —— 声明与执行同源，不可能漂移。
这正是 P7 WS-2 写的终态「工具 = 可插拔能力位（跨进程）」。

为什么技能不能挂在插件目录上

技能是懒加载的：启动时全系统只有一份索引（每个技能一行），正文按需读。 参与选择的是「当前角色绑了哪些技能」，不是「装了哪些插件」。
同一个技能要被多个角色、多个插件引用 —— 它需要独立的命名空间与独立的选择机制； 一旦放进某个插件目录，它就变成那个插件的私有物，而角色绑定别人的技能就变成了跨插件耦合。
而且索引的形状由「谁在用」决定（模型的上下文预算），不由「谁分发」决定。

契约提案：全部只是共享事件表上的新行

// 提示词片段 —— 发布方重播整份，收集方上线时问一次 'prompt.fragment.registered' { pluginId, id, priority, text } // 事件 'prompt.fragment.unregistered' { pluginId, id } // 事件 'prompt.fragments.list' Record<string, never> // 命令 // 工具 —— 声明与执行同源 'tool.registered' { serviceId, tools: ToolSpec[] } // 事件（发布者 = 执行者） 'tool.unregistered' { serviceId } // 事件 'tools.list' Record<string, never> // 命令 'tool.execute' { requestId /*=toolCallId*/, sessionId, name, arguments } // 命令 'tool.execute.result' { requestId, ok, content, summary } // 事件 'tool.approval.requested' { requestId, toolName, summary, risk } // 事件 'tool.approval.resolved' { requestId, approved, reason? } // 命令 // 技能不需要新 topic：索引 = 一个提示词片段（name+description） // 正文 = 一个工具（读某个服务自己目录下它自己定的路径）
五条纪律，全部沿用已有机制：
① 重播整份而不是发增量。 订阅方可能晚于发布方启动，那批增量早发完了。拿到全量就不需要补偿逻辑。
② 缺失是合法的。 没有片段 / 没有工具 / 没有技能的插件完全正常 —— 订阅失败要忽略， 不能让装饰性内容打死主链路。
③ 顺序必须确定。 同优先级按发布者 id 字典序。同一个系统两次启动得到不同提示词， 症状是「模型行为随机」，几乎无法排查。
④ 有长度上限并告警。 提示词片段变长会挤占历史预算，症状是「能力装上之后模型变笨」—— 它看起来像模型问题，不像预算问题。静默截断是最坏的一种。
⑤ 每个新能力都要自带重播命令。 插件化落地时 provider 早于主位启动导致路由表空、 所有请求 unsupported_provider，修法是让主位自己上线时问一次。 启动顺序不该是任何人的隐式依赖。
工具跨进程化会引入三个新问题，必须同一批解决，否则只是把问题挪了位置：
① 超时与孤儿。 执行者崩溃 → 结果永远不来 → loop 卡在 running → 用户看到「一直转圈」。 必须有超时兜底（失败结果，不是静默）。
② 审批期间用户停掉了这一轮。 结果到达时若 A 已释放 → 静默丢弃，不许补发。
③ 沙箱边界随执行者走。 今天 loop 用自己插件的 dataDir 算只读沙箱根； 工具分散后每个执行者各自算自己的（它有 dataDir + 只读特权），loop 手里不该再有路径。

10不变式（实施时不得破坏）

  • Core 不解析插件数据的内容与格式 —— 它只给插件一个目录、并在 HTTP 层搬字节。 目录约定只有「你有一个属于自己的目录」这一条；里面放什么是插件的事。 本版新增为第一条
  • 不新增进程间协议：stdio JSON-RPC + 共享事件表仍是唯一入口。新增能力一律是表上新行。
  • requires 只能是数据，不能是可执行逻辑 新。 如果清单能写检查逻辑（如 "check": "git --version && test -d /foo"）， 那就等于给插件在 Core 进程里执行任意命令的能力 —— 既打破「Core 不解析插件内容」， 也是个洞。所以声明是结构化的值，执行逻辑由 Core 提供有限几种类型，插件只能填值。
    同理永远不新增第五种插件状态：环境不满足映射到 degraded。
  • 凭证明文永不过总线、永不进 SSE、永不进日志：主位只转发不透明引用，只有执行者解引用。
  • Core 不知道插件存在：ServiceManager 只收一张「服务 id → 数据根」查表与一个「允许启动集合」， 不 import 任何插件概念。
  • 插件数据写权限只属自己：服务握手只拿到自己插件那一份路径，跨插件写在结构上不可能。
  • 一个插件坏掉不能让 Core 起不来：清单是数据，问题收进 problems[]。
  • 存在性由服务决定，不由目录决定：没装 provider 就等于没有那个模型； 没有服务 publish 片段就等于那段提示词不存在。能力存在性 = 谁注册了，不 = 谁的目录里有个文件。
  • 测试跟着被测物走：装配器测试留在 loop 包；每个插件自带数据的校验留在那个插件包里 （真构建 → 真 Core → 真请求）。

11实施顺序

每一步独立验收、独立可 revert。全部只动服务与事件表，不动插件标准。 W0 · 补三个配置缺口 零新协议。默认 provider/model/thinking 落 models 服务自己的用户数据， 回落链 = loop.run 参数 → 该默认 → env。消掉「配置了却发不出去」。 今天 loop 硬编码 env||'deepseek'，只接 OpenAI 兼容端点的用户第一次发问就失败。 W0.5 · requires 两条 见 §7。① plugin.json 加 requires 字段 + Zod schema + 单测； ② 产物对账守卫：扫产物里非 node: 前缀的 require，与 requires 比对。 这条【保护生态】—— 第三方作者不会跑 OST 的测试文件。 两件都不含任何探测逻辑，可独立落地。 W1 · 提示词片段装配 3 个 topic + 一个装配函数。片段来源 = 各服务经总线 publish（或自己带文件）， 装配器不关心来源。它顺带验证「装配器放 loop」这个决定对不对， 并且是 W2/W3 的地基。 W2 · 角色服务 档案 + 绑定（人设 / 模型 / 工具 / 技能）+ character.changed。 它是一个服务（可属于任意插件），不是一个插件标准槽位。 W3 · 技能服务 扫描 + 校验 + 全系统索引（进提示词片段）+ 一个读正文的工具。 零新机制：索引是片段、正文是工具。 W4 · 工具跨进程化 执行者 = 服务；声明与执行同源；聚合复用 W1 的收集器。 带一个真插件当切片：把内置只读工具抽成独立工具插件。 W5 · 审批位 + MCP W5 之后才开脚本型技能（那等于进程执行）。MCP 服务是 「运行时从协议生成 tool.registered 的执行者」，走同一条路，装配器零改动。
为什么 W0 排在最前：零新协议、改一个文件、消掉一个用户可见故障。 而 W1 之后每一步都会让提示词与工具面同时变化 —— 如果没有一个稳定的默认模型回落， 你分不清「模型变笨了」是提示词改动还是模型选错了。先把地基修平再改上层。

A附录 · 「角色作为插件」的正确形态

你最初的想法是「把角色做成插件，能编辑提示词、带技能、带工具」。 按本标准，这句话可以成立，但要分清哪部分由标准负责、哪部分由那个插件自己负责：

诉求由谁负责说明
角色能分发、能独立启停、能自带界面标准：做成一个普通插件 plugin.json 声明 id / 依赖 / ui.views[]；一份 dist/。 它和 models 插件享有完全同等的待遇，没有任何特殊之处。
角色的提示词可编辑那个插件自己：一份自带数据文件 + 一个服务读它 标准只提供 📖 只读特权（读自己目录）与 🔁 总线（发片段）。 文件名与形状由它自己定 —— 就像 catalog.json 是 models 插件自己的约定。
用户的编辑存哪约定：用户数据 userData/plugin/<id>/ 与插件交付物物理隔离，升级覆盖安装不会冲掉用户编辑。这是三层归属的用武之地。
角色带技能技能服务 + 角色服务里的绑定 技能包是技能服务管的事；角色只存「绑了哪些技能」。引用，不是拥有。
角色带工具工具服务 + 角色服务里的绑定 工具是独立的能力位服务；角色只存「绑了哪些工具」。这样工具可被多个角色共享。
这条路线最好的结果：角色的「存在性」与「能力」统一了，而且没有为此扩展标准。 装一个角色插件 → 它的服务启动 → publish 它的提示词片段 → 装配器下一轮拼进去； 它的界面可摆位；它绑定的技能与工具因为对应服务在位而可用。 卸掉 → 服务停 → 片段随之消失 → 模型不再假装拥有那些能力。
而这个效果不来自任何目录规则，来自「服务注册了什么」—— 也就是插件化最初那条原则：存在性由能力提供者决定。
一个必须提前防的失败模式：如果角色插件把「绑了哪些工具」当成自己的实现 （比如把工具代码打包进自己的 dist/server/），那么工具就退回到「进程内注册表」， 而那份注册表是今天的现状 —— 它的文件头明确写着「这是最小工具循环的种子，不是终态」。 症状会是：装第二个角色时工具列表互相污染，且无法共享。守住边界：角色存引用，工具归服务。
