01 一句话摘要

Osteosome 的终局形态不是「插件化单体」，而是 微内核 + 全外部插件 + 消息总线：

  • Core（TS / Node，极薄、很少更新）：只管三件事——服务进程管理、消息总线、SSE 桥。不做业务逻辑。
  • 服务（独立进程，语言自由，外部插件）：LLM / Loop / 角色 / 统计，全部走 .ostpkg 安装流程，可单独重启，Core 不重启。
  • 前端 Shell（Vue 3 + dockview-vue，骨架）：PaneHost + 布局引擎 + SSE 单例。所有 Pane 是外部插件，运行时动态加载。

核心通信模式：总线上发事件（request / response 配对靠 ID），前端用 SSE 订阅、HTTP POST 发命令。统计服务等旁路消费者零侵入——LLM 服务不需要知道统计服务存在。

已确定的决策（不再讨论）：

① Core 用 TS / Node（薄骨架 + 与前端类型共享 + Electron 同语言）。
② 前端用 Vue 3 + dockview-vue（团队熟 Vue，dockview-vue 官方支持与 React 版功能对齐）。
③ 通信走总线事件 + SSE/HTTP POST，不用 WebSocket。
④ 服务必须进程外（否则无法做到「重启服务不重启 Core」）。
⑤ 全外部插件：没有内置服务/Pane，唯一加载路径是运行时加载。

03 微内核模型：Core 极薄，全外部插件

v3 的核心判断：「Core 稳定、服务频繁更新、重启服务不重启程序、所有插件一律平等」这个需求，直接决定服务必须是进程外，且没有任何内置服务。

▲ 骨架只有两样（不可插件化）

① Core（后端骨架）

  • 进程管理（spawn / kill / 健康检查 / 重启）
  • 消息总线（publish / subscribe / replay）
  • SSE 桥（/events + /api/command + 静态资源）

Core 是加载器本身，不能是插件。

② 前端 Shell（前端骨架）

  • PaneHost + dockview-vue 集成
  • Layout 引擎（序列化 / 持久化）
  • SSE 单例 + core-sdk
  • 通用 UI 组件（Button / Input / Icon）

Shell 是 Pane 的宿主，不能是 Pane。

▲ 其余全是外部插件

服务插件（.ostpkg）

  • LLM 服务 / Loop 服务 / 角色服务 / 统计服务
  • 第三方服务（用户自写）
  • 全部走 <dataDir>/plugins/<id>/service/

Pane 插件（.ostpkg）

  • 聊天 Pane / 统计 Pane / 角色 Pane / 服务商 Pane
  • 第三方 Pane（用户自写）
  • 全部走 <dataDir>/plugins/<id>/pane/

官方插件 = 随安装包预置

官方插件不是「内置」，而是随安装包预置在 seed/，首次启动自动安装到 plugins/。之后用户可卸载、更新、替换——和第三方插件完全平等。

一句话：骨架只有 Core + 前端 Shell，其余全是外部插件。

代码路径唯一，官方与第三方一视同仁。用户感知是「开箱即用」（seed 预置），架构上是「一切都是插件」。

05 Core 契约细节：三个模块的接口

Core 极薄，但薄不等于模糊。三个模块的接口先写清楚，服务开发者和前端 SDK 才能并行开工。Core 用 TS 实现，接口即契约，编译期检查。

Core = Bus + ServiceManager + SseBridge。

三者职责不重叠：Bus 管事件分发，ServiceManager 管进程生命周期，SseBridge 管前后端桥。Core 不 import 任何业务模块。

模块 1 Bus —— 消息总线

interface Bus {
  // ── 发布 ─────────────────────────────────────────
  publish<T extends EventKey>(
    topic: T,
    payload: EventPayload<T>,
    options?: { persist?: boolean }
  ): void

  // ── 订阅（返回 disposer） ─────────────────────────
  subscribe<T extends EventKey>(
    topic: T | Pattern,
    handler: (payload: EventPayload<T>) => void | Promise<void>,
    options?: { once?: boolean; priority?: number; filter?: (p) => boolean }
  ): () => void

  // ── 回放 ─────────────────────────────────────────
  replay(from: number, to: number, topics?: EventKey[]): AsyncIterable<Event>

  // ── 元信息 ───────────────────────────────────────
  stats(): { published: number; delivered: number; dropped: number }
}
特性说明
背压慢订阅者不阻塞总线。内存队列上限 N，超限丢弃最旧并计 stats.dropped。
通配符llm.* 匹配 llm.request / llm.token / llm.done；* 匹配所有。
持久化白名单persist: true 或 topic 前缀白名单才落库。
跨进程服务通过 stdio 发的 publish 请求，Core 接收后投递到本地 Bus，再 fan-out。
错误隔离handler 抛错 → 捕获 → 打日志 → 继续投递。

模块 2 ServiceManager —— 进程生命周期

interface ServiceManager {
  start(): Promise<void>                     // 扫 plugins/*/service.json，按 inject 拓扑排序启动
  stop(timeoutMs?: number): Promise<void>    // 逆序停止，超时强杀
  restart(serviceId: string): Promise<void>  // 热插拔：单个服务重启，Core 不动

  status(serviceId: string): ServiceStatus
  list(): ServiceInfo[]
}

type ServiceStatus = 'starting' | 'ready' | 'restarting' | 'failed' | 'stopped'
机制说明
发现扫 <dataDir>/plugins/*/service/service.json，无内置路径。
依赖拓扑manifest 的 inject 声明依赖，Core 推导启动顺序。
健康检查按 healthCheck.interval 发心跳；超时 N 次判定 failed。
重启策略maxRestarts + backoff: exponential。
优雅停止SIGTERM → 等待 timeoutMs → SIGKILL。
stdio 分帧JSON-RPC 消息用 Content-Length 头分帧（LSP 同款）。

设计点说明
每个连接独立订阅前端传 ?topics=llm.*，Core 为这个连接创建过滤后的 Bus 订阅。连接关闭自动 dispose。
统一包成 event: messagetopic 在 JSON body 里，前端单监听器按 topic 分发。这样 topic 可以动态扩展。

多窗支持每个 Pane 独立开一个 SSE 连接。弹窗连上即收流。

三个模块如何组装

// core/src/main.ts
import { Bus } from './bus'
import { ServiceManager } from './service-manager'
import { SseBridge } from './sse-bridge'
import { PluginInstaller } from './plugin-installer'

const bus = new Bus({ persist: { adapter: sqliteAdapter } })
const services = new ServiceManager({ bus, pluginsDir: './plugins' })
const bridge = new SseBridge({ bus, port: 1420, staticDir: './dist/client' })
const installer = new PluginInstaller({ services, pluginsDir: './plugins', bus })

// 启动顺序：
// 1. Bus 就绪
// 2. SseBridge 起 HTTP 服务（前端可连）
// 3. 首次启动检测：plugins/ 为空 → 从 seed/ 安装官方插件
// 4. ServiceManager 扫 plugins/*/service.json → spawn 所有服务
await bus.ready()
await bridge.listen()
await installer.seedIfEmpty('./seed')
await services.start()

06 事件契约规范：服务开发者的合同

总线是公开的，事件是公开的。没有规范，事件类型会失控——几百个事件、命名混乱、版本冲突。这一节是服务开发者必须遵守的合同。

三条铁律：

① 只增不改——事件字段只加不删不改，破坏性变更必须升版本。
② payload 可序列化——JSON 能过，不带函数、Symbol、循环引用。
③ 类型共享——事件类型定义在 shared/events.ts，Core、服务、前端共用同一份。

规范 1 命名：domain.entity.action

格式：<domain>.<entity>.<action>

✅ 好例子：
  llm.request.started       // llm 领域，request 实体，started 动作
  llm.token.streamed
  llm.request.finished
  loop.state.changed
  character.changed
  tools.executed
  service.ready
  plugin.installed

❌ 坏例子：
  llmRequestStarted          // 没有分隔符，无法通配符匹配
  llm_req_start              // 下划线风格不一致
  LLM.REQUEST.STARTED        // 大写，阅读负担
  update                     // 太泛，没有 domain 前缀
段约定已有域
domain服务归属llm loop character tools storage session service plugin ui
entity被操作的对象request token message state call event
action过去式动词started streamed finished changed failed executed ready installed

规范 2 版本：只增不改

变更类型做法
加字段 ✅直接加，不改 topic
加可选字段 ✅直接加，标注 optional
删字段 ❌标记 deprecated，两个版本周期后删
改字段类型 ❌升版本：llm.token.v2
改语义 ❌升版本，或换新 topic

规范 3 Payload：必填字段与约束

interface EventBase {
  ts: number          // 时间戳（毫秒）
  source: string      // 发布者 serviceId
  requestId?: string  // 一对一请求-响应配对
  traceId?: string    // 关联链
  sessionId?: string  // 会话上下文
}
约束值理由
payload 大小≤ 256KB（建议）超过则存 blob，事件里带引用 ID
高频事件速率≤ 1000/s（建议）超过则批量合并
必填字段ts source审计、排序、溯源
禁止字段函数 / Symbol / 循环引用 / BigIntJSON 序列化会失败
敏感数据不落库，或脱敏后落库API key / 用户隐私

07 服务 SDK 细节：TS / Python 双语言

服务开发者不该手写 JSON-RPC 分帧、握手、心跳、重连。SDK 是「服务开发者与 Core 的合同」的可执行版本——每种语言一个包，接口一致。

SDK 的三件职责：

① 与 Core 握手、注册、心跳；② 把 bus.publish / bus.subscribe 封装成语言惯用 API；③ 进程退出时优雅清理。服务开发者只写业务逻辑。

握手协议 stdio JSON-RPC，LSP 风格分帧

// ── 分帧格式 ─────────────────────────────────────
Content-Length: 123\r\n
\r\n
{"jsonrpc":"2.0","id":1,"method":"initialize","params":{...}}

// ── 握手时序 ─────────────────────────────────────
1. Core → 服务：spawn 进程
2. 服务 → Core：request 'initialize'
3. Core → 服务：response { sessionId, heartbeatInterval }
4. 服务 → Core：notification 'initialized'
5. 双向进入运行态：publish / subscribe / heartbeat
6. 服务退出前：notification 'shutdown'，Core 回 'exit'

// 插件服务入口（如 plugins/com.osteosome.llm/service/src/index.ts）
import { Service, bus, logger } from '@osteosome/service-sdk'

const service = new Service({ id: 'llm', version: '1.0.0' })

service.subscribe('llm.request', async (req) => {
  const { requestId, provider, model, messages } = req

  bus.publish('llm.request.started', {
    ts: Date.now(), source: 'llm', requestId, provider, model,
  })

  try {
    for await (const token of callProvider(provider, model, messages)) {
      bus.publish('llm.token.streamed', {
        ts: Date.now(), source: 'llm', requestId, token: token.text, index: token.index,
      })
    }
    bus.publish('llm.request.finished', {
      ts: Date.now(), source: 'llm', requestId, usage: {...}, finishReason: 'stop',
    })
  } catch (err) {
    bus.publish('llm.request.finished', {
      ts: Date.now(), source: 'llm', requestId, usage: null, finishReason: 'error',
    })
  }
})

Python SDK 的额外工作：必须处理 stdin / stdout 的二进制模式，必须避免 print() 污染协议流（日志走 stderr），必须注意 asyncio 与同步 HTTP 库的混用。这些 SDK 都封装好了。

Manifest 校验 SDK 启动时做三件事

  1. schema 校验：manifest 是否符合规范。
  2. 版本校验：protocolVersion 是否与 Core 兼容。
  3. 事件一致性：publishes / subscribes 的 topic 必须在 shared/events.ts 声明。不一致直接拒绝启动（fail fast）。

没有内置插件。骨架只有 Core + 前端 Shell，其余全是外部插件。本节定义插件包格式、安装流程、前端动态加载机制、首次启动预置。

统一加载路径：全部运行时加载。

删掉两条编译期路径（services/*/service.json 扫目录、import.meta.glob 扫 Pane）。官方插件与第三方插件完全平等——前者随安装包预置在 seed/，首次启动自动安装；后者由用户手动安装。代码路径完全相同。

一、骨架与插件的边界

骨架（不可插件化）

  • Core：Bus + ServiceManager + SseBridge + PluginInstaller
  • 前端 Shell：PaneHost + Layout 引擎 + SSE 单例 + 通用 UI 组件

这两样是加载器本身，随安装包发布，不走插件流程。

插件（全外部）

  • 服务插件：LLM / Loop / 角色 / 统计 / 第三方
  • Pane 插件：聊天 / 统计 / 角色 / 服务商 / 第三方

全部走 .ostpkg 安装流程，放 <dataDir>/plugins/。

二、.ostpkg 包格式

一个插件 = 一个 .ostpkg（tar.gz），目录结构：

顶层 manifest.json：

{
  "id": "com.example.my-plugin",
  "name": "我的插件",
  "version": "1.0.0",
  "protocolVersion": "1.0.0",
  "author": "someone",
  "license": "MIT",
  "service": {

五、前端 Pane 的动态加载

前端 Shell 构建产物里没有任何业务 Pane。所有 Pane 在运行时动态加载：

// panes/registry.ts —— 运行时加载
const registry = new Map<string, PaneDefinition>()

export function definePane(def: PaneDefinition): PaneDefinition {
  registry.set(def.id, def)
  return def
}

// 不再 import.meta.glob
// 改为：收到 plugin.installed / service.ready 事件后，动态加载该插件的 Pane
export async function loadPanesFromPlugin(
  pluginId: string,
  paneEntries: { id: string; url: string; version: string }[]
) {
  for (const entry of paneEntries) {
    // 加 cache-bust，避免更新后浏览器命中旧缓存
    const mod = await import(
      /* @vite-ignore */ `${entry.url}?v=${entry.version}`
    )
    registry.set(mod.default.id, mod.default)
  }
}

六、卸载与更新

场景行为
同 id 覆盖安装装到临时目录 → 校验 → 替换旧目录 → 重启该服务 → 广播 plugin.installed
服务重启用 Core 不重启ServiceManager 的 restart(id) 直接 kill + spawn
前端 Pane 更新前端 import() 有缓存，需加 cache-bust：import(url + '?v=' + version)
卸载插件停止服务 → 删目录 → 广播 plugin.uninstalled → 前端移除 Pane（布局保留占位「插件未安装」）
版本不兼容manifest 的 protocolVersion 不满足 → 拒绝安装，提示用户升级 Core
降级允许，但需用户显式确认（旧版可能不兼容新事件类型）
事件版本升级：如果新服务发 llm.token.v2 而旧前端还在订阅 llm.token，服务需同时发两个 topic 过渡（见 §6 规范 2）。过渡期结束（比如两个版本周期）后停发旧的。

机制说明落地阶段

前端 Pane 的导入 = 动态 ESM（import()）+ Import Maps（共享 Vue）+ Shadow DOM（样式隔离）。
官方插件 = 随安装包预置在 seed/，首次启动自动安装；之后与第三方插件完全平等。

10 消息总线：服务对等，通信公开可观察

核心设计：服务之间不直连，全部经过总线。

服务 A 要调服务 B：A 发请求事件 → B 订阅并处理 → B 发响应事件 → A 订阅。配对靠 requestId。这样 N 个服务不需要 N(N-1) 个通道，只需要一张总线。

「Loop 调 LLM」的完整走线

// ① Loop 服务发请求事件（带 requestId）
bus.publish('llm.request', {
  requestId: 'req-001', provider: 'deepseek', model: 'deepseek-chat',
  messages: [{ role: 'user', content: '你好' }],
})

// ② LLM 服务订阅，处理后发响应事件
bus.subscribe('llm.request', async (e) => {
  for await (const token of callProvider(e)) {
    bus.publish('llm.token.streamed', { requestId: e.requestId, token, index })
  }
  bus.publish('llm.request.finished', { requestId: e.requestId, usage: {...} })
})

// ③ Loop 服务订阅响应（匹配自己的请求）
bus.subscribe('llm.token.streamed', (e) => {
  if (e.requestId === 'req-001') handleToken(e.token)
})

// ④ 统计服务旁路订阅（零侵入）
bus.subscribe('llm.request', (e) => stats.providers[e.provider]++)

好处 旁路观察是免费的

  • 统计服务订阅 llm.*，LLM 服务不需要为它改任何代码。
  • 新增日志 / 审计 / 分析服务，同样零侵入。
  • 调试时在总线上打日志，所有服务间通信一览无余。
  • 事件天然适合事件溯源：落库、回放、审计都免费。

注意 总线的工程约束

  • 背压：慢订阅者不能阻塞总线，需要队列 / 丢弃策略。
  • 事件契约治理：事件类型多了会失控，需要命名规范、版本管理。
  • 跨进程开销：JSON 序列化 + IPC，高频事件要注意批量与缓冲。
  • 事件类型共享：TS 定义的事件类型，Core 与 Vue 前端共享，编译期检查。

11 单向通信：语义单向，控制流反向

流式消息、状态推送这些语义上单向的通信，用 WebSocket 这种全双工协议是浪费。但要区分两层。

语义层单向

逻辑上只有一个方向有意义：

  • 事件流：Loop 服务发 llm.token，聊天框只接收
  • 状态推送：角色服务发 character.changed，前端只更新 UI
  • 日志流：任何服务发日志，观察者只收

传输层经常还是双向

即使语义上单向，传输层经常需要反向：

  • 建连握手（client → server）
  • 心跳保活（双向）
  • 断线重连（client → server）
  • 取消订阅 / 背压反馈

所以「用单向协议」通常意味着「主数据流单向 + 控制流反向」。

为什么「两个单向接口 ≠ 手工开两个 pipe」

「双向服务 = 开发两个单向接口」思路对，但不要手工开两个 pipe，因为：

  • 配对问题：多个服务同时调 LLM 服务，两个 pipe 怎么知道哪个响应配哪个请求？
  • 生死同步：两个 pipe 要同时管理，一个挂了另一个成僵尸。
  • 组合爆炸：N 个服务两两通信需要 N² 个通道。

正确形态：请求事件 + 响应事件，配对靠 ID，通道管理归总线。见 §10 的代码示例。

前端协议选择：SSE + HTTP POST

方向协议理由
后端 → 前端（事件流）SSE语义单向，浏览器原生 EventSource，自带重连，纯 HTTP，穿透代理友好
前端 → 后端（命令）HTTP POST「发完就不管」的短请求，无需长连接
进程间控制面JSON-RPC over stdio语言无关，进程隔离
服务 ↔ 服务总线（不直连）一对多 / 多对多天然，旁路可观察

前端 Pane 订阅事件（Vue 3）

<script setup lang="ts">
import { ref } from 'vue'
import { useEventBus } from '@osteosome/client/core-sdk'

const messages = ref<{ role: string; content: string }[]>([])
let currentMsg = ''

// 只订阅自己关心的事件类型
useEventBus('llm.token.streamed', (e) => {
  currentMsg += e.token
})
useEventBus('llm.request.finished', (e) => {
  messages.value.push({ role: 'assistant', content: currentMsg })
  currentMsg = ''
})
</script>

<template>
  <div v-for="m in messages">{{ m.content }}</div>
</template>
为什么不用 WebSocket：

接收是单向的，SSE 天生为此；发送是「发完就不管」，POST 足够。WebSocket 的复杂度（握手、心跳、状态机）在这里换不来任何收益。

12 服务热插拔：Core 不重启，单个服务更新

「Core 很少更新，之后只更新单个服务，重启服务就行，程序本身不需要重启」——这个需求把架构钉死了：服务必须是进程外。

服务 manifest（在 <dataDir>/plugins/<id>/service/service.json）

{
  "id": "com.osteosome.llm",
  "version": "1.0.0",
  "protocolVersion": "1.0.0",
  "entry": "python -m llm_service",        // 语言自由
  "inject": ["com.osteosome.storage"],     // 依赖声明 → Core 拓扑排序
  "publishes": ["llm.request.started", "llm.token.streamed", "llm.request.finished"],
  "subscribes": ["llm.request"],
  "panes": [
    { "id": "pane.llm.providers", "component": "ProvidersPane" },
    { "id": "pane.llm.config", "component": "LlmConfigPane" }
  ],
  "healthCheck": { "interval": 5000, "timeout": 2000 },
  "restartPolicy": { "maxRestarts": 3, "backoff": "exponential" }
}
注意 inject 用的是插件 id（如 com.osteosome.storage），不是服务名。Core 通过插件 id 找对应服务的启动完成状态。

热插拔带来的五个必须解决的问题

1 事件版本管理

服务 v1 发 llm.token { token }，v2 升级成 { token, confidence }。旧版前端 Pane 怎么办？

  • 事件 schema 带版本号：llm.token.v2
  • 或 payload 向后兼容（只加字段，不改字段）

2 Pane 与服务生命周期解耦

服务重启时正在显示的 Pane 怎么办？

  • Core 广播 service.restarting / service.ready 事件
  • Pane 订阅这些事件，显示「服务重连中」状态

3 服务重启后的状态恢复

服务重启后之前的状态没了，正在进行的 LLM 调用怎么办？

  • 事件溯源：所有状态变更都是事件，落库。服务重启后回放。
  • 或：重启时把未完成的任务标记为失败，让用户重试。

4 事件持久化与回放

如果事件不落库，统计服务重启后计数清零。

  • 关键事件落 SQLite
  • 统计服务订阅时，先回放历史事件，再接收实时
  • Core 提供 bus.replay(from, to) API

5 服务依赖关系

Loop 服务依赖 LLM 服务。LLM 服务重启时，Loop 服务怎么办？

  • 服务 manifest 声明 inject 依赖
  • Core 按拓扑排序启动 / 恢复
  • 依赖服务不可用时，Loop 服务收到 service.unavailable 事件，决定等待还是报错
热插拔的最终形态：

更新 LLM 服务 = 替换 plugins/com.osteosome.llm/service/ + Core kill 旧进程 + 启动新进程。Core 不动，其他服务不动，前端 Pane 通过 service.status 事件感知并更新 UI。这就是 VS Code 的语言服务器模型。

Pane 组件开发合同（三条硬性约定）

① SSE 单例 + topic 分发

禁止每个 Pane 各开一个 EventSource（浏览器对同源 EventSource 数量有限制，Chrome 是 6 个）。整个应用一个 SSE 连接，由 Shell 的 sse.ts 单例管理，useEventBus 订阅 topic。

② Pane 组件不直接 fetch

禁止 Pane 里直接 fetch('/api/xxx')。所有命令走 useCommand，所有数据走 useEventBus。这样：命令和事件统一走 Core，旁路可观察；Pane 不持有数据，只订阅事件；服务重启时 Pane 通过 service.status 事件感知。

③ 共享依赖必须 external

插件构建时 vue / dockview-vue / @osteosome/client/core-sdk 必须标为 external，由 Import Map 解析到 Shell 的实例。插件 bundle 里不允许打包自己的 Vue。

15 迁移期不变式（"don't make it worse"）

1
Model-visible means logged —— 写入模型上下文的任何新内容，必须先有 durable 事件 + 落库，不准只写内存。
2

3
旁路消费者零侵入 —— 统计 / 日志 / 审计服务只订阅不发布，不要求现有服务改代码。
4
Core 不跑业务逻辑 —— Core 只管进程管理、总线、SSE 桥、插件安装；任何业务模块必须下沉为插件。
5
任一注册必带 disposer —— ctx.on/effect / bus.subscribe 都返回回卷函数，禁止"只塞 Map 不提供卸载"。
6

8

12
每阶段一个 PR + 全绿 + 可单独 revert —— 不允许跨阶段大爆炸提交。

16 非目标与边界

❌ 不引入 Cordis 本体

初期用约 200 行自研 ctx 对齐接口，预留替换点。

❌ 不引入外部消息中间件

NATS / Redis / ZeroMQ 都不引。总线自研，桌面应用不跑 broker。

❌ 不重写 store/db

只加接口皮，零行为变更。storage 服务独立进程是阶段 3。

❌ 不做无进程重启的热替换

本期只做「重启单个服务不重启 Core」；「不重启服务也能热替换」是远期。

❌ 不一次支持所有语言

先 TS，再 Python，后 Rust / Go。SDK 是最大的工作量。

❌ 不做签名/沙箱（本期）

阶段 4 才做。本期只允许本地文件和可信 URL 安装。

❌ 跨窗拖拽

把一个窗拖进另一窗的网格：远期。v1 只做「同窗内换位 + 拉出独立窗」。

❌ 复制窗 / 一窗一会话

同一 pane 开多个实例看不同会话：远期。v1 全局单上下文。

❌ 操作类对话框窗化

❌ 服务直连旁路

服务 A 不能绕过总线直接调服务 B，否则旁路观察失效。

❌ 进程内跑非 TS 服务

进程内只跑 TS 模块；非 TS 服务一律进程外。

❌ 内置任何业务插件

骨架只有 Core + 前端 Shell。所有业务都是外部插件，官方与第三方完全平等。

① 会话模型 → event-sourced log

  • 契约：会话 = 仅追加类型化事件日志；Model-visible means logged 从条文变结构保证。
  • 落点：run_events 已半成形，目标把 messages/sessions 收敛为「写事件 → 派生表」。
  • 边界：数据模型层改动，独立成步，只事件化不斩旧表。

② Compaction → dsh 形状 seam

  • 词汇：compaction/start|summary|end 锁包围「测长→选区→摘要→落面」，崩溃 = 孤儿锁。
  • 落点：run.before-compact 扩展为这套词汇 + 触发词。
  • 验收：全程可重放可审计；孤儿锁由 LifecyclePlugin 回收。

③ 工具执行管线 → policy 监听

  • 形状：tools.pre-execute / post-execute 两个 waterfall 点。
  • 落点：审批/只读判定从 if/else 变 listener。
  • 验收：审批与执行解耦；策略挂载可逆；新增策略不碰 loop。

④ LLM 适配器 → 中立流契约

  • 契约：带 block 边界的类型化流（文本/推理/tool-call 显式块）+ finish 终块携带稳定错误码与 Retry-After。
  • 落点：llm/client.ts 的 LLMChunk 块化；format 兑现或删除；字符串判 429 收敛为错误码。
  • 验收：新增供应商不再手改单函数；错误告别字符串匹配。
落地顺序与边界（四项）。

④ LLM 适配器契约对齐（最小、纯行为侧，先做）→ ③ 工具管线（接阶段 3）→ ① 会话事件化（数据层大改，独立小步）→ ② Compaction（依赖事件化土壤，最后）。全程不引入 dsh 依赖。

20 总结

Osteosome v3 的架构本质：微内核 + 全外部插件 + 可观察总线。

骨架只有两样：Core（进程管理 + 总线 + SSE 桥 + 插件安装）和前端 Shell（PaneHost + Layout + SSE 单例 + 通用 UI）。

其余全是外部插件：LLM / Loop / 角色 / 统计 / 聊天 / 服务商 / 第三方，统一走 .ostpkg 安装流程，统一放 <dataDir>/plugins/，统一运行时加载。

前端（Vue 3 + dockview-vue）：Pane 订阅 SSE，POST 发命令，布局可序列化，可拉出独立窗，Shadow DOM 隔离样式。

插件 = 独立进程或独立 ESM bundle + manifest + 事件契约。新增一个插件 = 新增一个 .ostpkg。官方插件与第三方插件完全平等——前者随安装包预置在 seed/，首次启动自动安装。

最低可交付 = 阶段 1-2

Core 骨架 + PluginInstaller + seed 预置 + LLM 插件跑通 + 前端 SSE 收到流。约 3 周。

完整工作台 = 阶段 3

全部插件拆分、统计旁路验证、Vue 工作台化、插件管理 UI。约 6 周。

远期愿景 = 阶段 4

事件持久化 + 回放、多语言 SDK、签名 + 沙箱、服务市场。

下一步建议：
  1. 先落 阶段 1：进程内 ctx + 总线雏形 + LifecyclePlugin 化。
  2. 再落 阶段 2：Core 骨架 + PluginInstaller + seed 预置 + 第一个外部插件（LLM）+ 前端动态加载，验证端到端流。
  3. 阶段 3 之前先做 Vue 前端 Shell 骨架（1-2 天）：用 dockview-vue + Import Map + Shadow DOM 跑通「动态加载一个 pane」。
  4. 阶段 4（签名、沙箱、服务市场）独立成 RFC 细化。
