插件协作与 AI 能力装配

2026-10-05 · 逐个确认稿：core → 4 个插件 → prompt / 技能 / 工具
这份文档回答四个问题，全部以当前仓库的真实代码为依据，不是设想： ① 几个插件之间怎么交互（以及哪些说法其实不成立）；② 模型怎么配（一条五步链路 + 三处数据落点 + 优先级）； ③ prompt 怎么带入；④ 技能怎么加载、工具怎么调用。
现状定性：①②已落地且有测试守住；③④只有种子 —— prompt 是一个常量字符串、工具是 loop 进程内的注册表、技能还不存在。 这份稿子要做的是把③④的扩展点钉死，而不是重写①②。
配套：docs/插件化架构优化.html（目录与分发形态的定案）· docs/开发进度/阶段追踪.md（P5 角色 / P6 技能 / P7 工具管线的里程碑）
先说三条最容易误判的事实（它们决定了后面所有设计的天花板）：
① plugin.json 的 capabilities[] 不参与任何判定。 schema 的注释写得很直白：「纯展示，一旦有代码依赖它做判断，它就会变成第二个真源」 （shared/src/plugin-manifest.ts:107-110）。 所以「A 插件声明了 llm.request，B 插件就能调它」这句话今天不成立 —— 真正被校验的是 service.json 的 publishes/subscribes， 而那是对共享事件表的校验（core/src/service-manager/manifest.ts:41-56）。
② dependencies[] 不产生运行时耦合，只影响启动顺序与状态聚合。 缺必需依赖 → 插件 degraded 而不是不启动；依赖未满足刻意不阻止 spawn （plugin-registry-runtime.ts:408-414：只装 session 不装 models 时， 用户仍要看得到会话列表）。
③ 跨插件读数据今天没有通路。 dataReadableBy[] 只进了 schema，而能施加限制的 HTTP 面 （/api/plugins/<id>/data/*）不存在。 现网唯一的跨插件读是 ChatComposerView.vue 订阅 models.prefs.state —— 走的是总线事件而不是文件，所以那条声明目前没有生效点。

为什么这条依赖链没有变成隐式启动契约 —— 一个值得记住的实证： 插件化落地时服务遍历顺序从「平铺目录字母序」变成「按插件」， llm-provider-openai 于是先于 llm 启动 → 主位订阅时注册事件已经发完 → 路由表空 → 所有请求 unsupported_provider。 修法不是把顺序排回去，而是让 llm 启动后自己发一次 llm.provider.reannounce （chat-workbench/services/llm/src/index.ts:229-233）。
结论：启动顺序不该是任何人的隐式依赖；每个「能力存在性」都要有一条 「重播当前状态」的自查通路。这条已经在 llm 与 provider 两侧落地， ③④ 要新增的每一种能力（prompt 片段 / 技能 / 工具目录）都必须自带这一条。

模型配置的完整链路是一条五步，落点是三处文件。核心结论： models 插件的用户数据全部由它自己的 provider 服务持有，Core 与前端都只是通路。

优先级：三个来源冲突时听谁的

凭证来源（env 优先） ├─ 1. env:<ID_UPPER>_API_KEY ← 部署者的显式意图（脚本 / CI / 自建端点） ├─ 2. file:<credId> ← 用户在设置窗存的（userData/plugin/models/credentials.json） └─ 3. 都没有 → 不注册（前端下拉里不出现，等价于「没装」） 端点 / 默认模型的 env 覆盖 ├─ <ID_UPPER>_BASE_URL 改端点 （如 DEEPSEEK_BASE_URL=http://127.0.0.1:1234/v1） ├─ <ID_UPPER>_MODEL 改默认模型 └─ LLM_VENDORS_EXTRA 自填端点（JSON 数组）；优先级低于 settings 窗写的
为什么 env 优先：env 是部署者的显式意图，用户填的密钥是用户的偏好。冲突时听部署者的。 这条也解释了为什么集成冒烟可以指假上游跑全链路而不用改任何代码。
三处现在就要确认的缺口（都会让「配置了模型」这件事半残）：
① 默认 provider 是硬编码的。 loop/src/index.ts:30： DEFAULT_PROVIDER = env.LLM_PROVIDER || 'deepseek'。 副作用很具体：只接了 OpenAI 兼容端点的用户，第一次发问会得到 unsupported_provider —— 而下拉里明明有模型。
② 用户选的 provider/model 不持久化。 ChatComposerView.vue 里 provider 是本地 ref，首个 provider 注册后自动选 list[0]。 刷新页面 / 换窗口就回到第一项。
③ 逐轮参数与「默认配置」没有分层。 loop.run 每次带参， 但「这个会话/这个用户默认用哪家」没有任何落点。
建议：三者一起解 —— 在 preferences.json 里加一段 { defaultProvider, defaultModel, defaultThinking }（归 models 插件所有， 与 enabledModels 并列），loop.run 缺省时回落它，再缺省才回落 env。 不新增 topic（复用 models.prefs.set 的合并 patch），不改 Core。

4prompt 怎么带入

现状（plugins/chat-workbench/services/loop/src/prompt.ts，9 行） export const DEFAULT_SYSTEM_PROMPT = [ '你是一个本地桌面 AI 助手的对话后端，运行在 Osteosome 客户端里。', '用简体中文回答，语气自然、简洁，不啰嗦。', '如果用户的问题超出你的能力或需要外部信息，直接说明，不要编造。', ].join('\n') → buildMessages() 把它置首，历史里的 system 一律丢弃 （history.ts:37「system 统一由 prompt 参数提供，避免重复注入」）

这个常量不是 bug，它是「没有扩展点」的样子。要变成可装配的 prompt， 需要回答三个问题 —— 而且每个问题的答案都已经被现有机制框死了：

问题候选结论与理由
① prompt 分几层？ ① 身份层（loop 内置）
② 能力层（插件片段）
③ 会话层（每个会话）		 三层，全都要。 身份层不可卸（否则模型不知道自己是什么）； 能力层随插件装卸增减；会话层是角色 / 项目约定（P5 角色插件的落点）。
关键性质：历史里的 system 被丢弃 → prompt 每轮重新装配，不进 messages。 这条性质让「装/卸插件立即生效」免费 —— 不需要迁移任何历史数据。
② 片段从哪来？ A. plugin.json 声明（静态字符串）
B. 插件自带 prompts/*.md（plugins.readFile）
C. 服务经总线动态发布		 B 为主，A 与 C 为辅。
A 适合一行短提示，但 plugin.json 会变成大杂烩 —— 它现在是「归属」文件，不是内容文件。
B 让长 prompt 有语法高亮与可 diff，且随插件走（不占用户数据目录）。
C 是必须的补充：有的片段依赖运行期事实（当前 provider 列表、当前工具清单、技能索引）。
所以三种都要，但形状要统一 —— 都归一成 { id, priority, text }。
③ 谁装配？ ① loop 自己收集
② 新增 prompt 服务
③ 提到 Core 侧		 ① loop 自己收集。
loop 已经同时是 tool 目录的装配者（TOOL_SPECS）。 让 prompt 走同一个收集器，装一个插件 → prompt 与 tool 同时增减，一处组装逻辑。
② 会多一跳总线往返与一个失败点，而 prompt 没有独立的生命周期需求。
③ 违反不变式「Core 不解析插件内容」—— prompt 是内容。

契约提案（往 shared 加，只增不改）

// ── shared/src/events.ts 新增 ────────────────────────────── 'prompt.fragment.registered': { pluginId, id, priority, text } // 事件 'prompt.fragment.unregistered': { pluginId, id } // 事件 'prompt.fragments.list': Record<string, never> // 命令（reannounce 同款） // 装配结果由 loop 持有，不进总线 —— 没有别的进程需要知道最终 prompt 是什么
三条设计纪律，直接沿用现有机制：
① 「重播整份」而不是发增量。 同 llm.provider.reannounce / models.prefs.state： 订阅方可能晚于发布方启动，增量事件早发完了。拿到全量就不需要补偿逻辑，这条性质比省字节重要得多。
② 缺失是合法的。 一个不带 prompt 片段的插件完全正常（就像不带 catalog.json 一样）。 所以 loop 侧订阅失败要忽略而不是抛 —— 否则一个装饰性片段能打死对话。
③ 顺序要显式。 priority 数字越小越靠前，身份层恒为 0（不可被覆盖）。 拼接顺序必须稳定：pluginId 相同优先级时按 id 字典序 —— 否则同一个系统两次启动得到不同 prompt， 而症状是「模型行为随机」，几乎无法排查。
必须一起解决的一件事：prompt 与历史截断的相互作用。 buildMessages 保留最近 DEFAULT_MAX_MESSAGES = 20 条，并把截断点对齐到 user 边界 （history.ts:58-63，因为孤立 tool 消息会让上游 400）。 能力层片段变长时，20 条历史里真正的对话占比会变少，而症状是「插件装上之后模型变笨」—— 它看起来像模型问题，不像预算问题。
建议：prompt 片段有总字节上限（比如 8 KB），超了按 priority 从低到高丢弃并发一条 loop.run.failed 或至少一条 logger.warn。 静默截断是最坏的一种：模型表现退化，没人知道是因为 prompt 被砍了。

5技能怎么加载

今天没有技能。 docs/开发进度/阶段追踪.md 的 P6「技能」是 ⬜ 未开始， 交付物两条：「技能包（SKILL.md），按需懒加载」+「技能注入 loop」。 下面是把这两条落到现有机制上的形状 —— 不新增一种插件交互方式。

核心判断：技能 = prompt 片段 + tool，不是第三种东西

「懒加载」这个词容易让人以为要造一套新的加载器。实际拆开看，一个技能包只需要两件事：

形态包形态怎么进上下文什么时候用
知识型SKILL.md
frontmatter:
name / description / when		 启动时只注入 name + description（一行索引） 模型判断相关时，通过 skill_read(name) 读全文，正文作为 tool 结果回填。
工具型SKILL.md + scripts/* scripts/ 里的脚本注册为 tool；SKILL.md 只做说明注入 模型调那个 tool。说明与实现在同一个包里，所以模型看到的描述和实际能做的事不会漂。
工作流型SKILL.md + 若干 tool 组合 同知识型（索引注入）+ 该流程需要的 tools 一起进目录 先 skill_read 拿到步骤，再逐步调 tool。它不是一个新类别，只是前两者的组合。
「渐进披露」是这套设计里唯一真正的新东西，也是它必须被认真对待的原因： 启动时只注入索引（每个技能一行），全文只在模型要的时候读。
这不是优化，是可行性问题：20 个技能 × 平均 2 KB 全文 = 40 KB ≈ 10k token， 在 system prompt 里就把大部分预算吃掉了，而用户可能一个都用不上。
代价：模型必须先决定「要不要读这个技能」—— 所以 description 字段是契约不是注释， 写得含糊 = 技能装了也不会被读。这条要写进插件作者文档。

契约提案：复用已有的两条通路，只加两个 tool

// ① 索引 = prompt 片段（复用 §4 的契约，零新增 topic） 'prompt.fragment.registered' { pluginId:"skills", id:"skill-index", priority:10, text: "- pdf-extract: 把 PDF 抽成 markdown。用户提到 PDF/扫描件时先读它。\n- ..." } // ② 全文 = 一个 tool（工具目录走 llm.request.tools，今天已通） name: "skill_read" description: "读取一个已安装技能的完整说明。索引里列出的技能才可读。" parameters: { type:"object", properties:{ name:{type:"string"} }, required:["name"] } // ③ 工具型技能的 scripts/ → 同一批 tool（复用现有工具目录通路） name: "pdf_extract" ← scripts/pdf_extract.(py|js|sh)
为什么这样就够：ToolSpec 已经是中立契约（shared/src/llm/types.ts:47）， 主位透传、provider 各翻自家 wire、llm.request.tool_call 块闭合即发 —— 整条工具通路今天就能跑，只差「谁来填 TOOL_SPECS」这一个口子。
所以技能没有引入任何新的进程间协议，只是给已有的两条通路接了新的生产者。 这与「插件化零新增协议」是同一条纪律的延续。
四个必须现在定下来的边界，否则技能会变成安全洞：
① 技能从哪读？ 插件自带的走 plugins.readFile（只读、只限自己插件目录）； 用户自己的呢？建议 userData/plugin/<某个 skills 插件>/skills/<name>/SKILL.md —— 注意这需要一个「skills 插件」来当这个目录的主人，否则 userData/ 下会长出一个 谁都不认领的目录（这正是凭证插件退休的原因：没有主人的数据目录迟早出问题）。
② scripts/ 的执行边界。 今天的内置工具是纯只读、路径锁在 userData/plugin/chat-workbench/tool-root/ 内、单文件 ≤64 KB、目录 ≤200 项 —— 而且注释里明确写了「没有写 / 删 / 网络 / 进程类工具，那些必须先有审批 listener 才允许存在」。 脚本执行直接违反这条：它就是进程执行。所以脚本型技能必须先有审批位（§6）才能开， 否则技能插件就是一个「装了就等于装了任意代码执行」。
③ 技能之间的顺序与覆盖。 同一 name 两个技能都有 → 拒绝第二个（fail fast）， 不要「后者覆盖前者」：症状是「我改了技能却不生效」，而原因在另一个插件里。
④ 卸载时已读过的技能怎么办。 历史里那条 tool 结果还在（append-only，不改）。 建议照附件能力备忘的处置 A：数据保留、只是不再可用；重装即恢复。不要级联删。

6工具怎么调用

现状（plugins/chat-workbench/services/loop/src/tools.ts，152 行） ├── toolSpecs(root) ← 只声明 name/description/parameters，下发给模型 ├── executeTool(root, …) ← 副作用边界；未知工具返回失败结果而不抛（让模型自我纠正） ├── readTool → read_file 路径锁在 root 内 · ≤64 KB └── listTool → list_dir ≤200 项 root = userData/plugin/chat-workbench/tool-root/（默认空，用户想让它读什么就放什么） 组装点：loop/src/index.ts:381-382，握手之后才算（dataDir 那时才到货） 工具轮上限：MAX_TOOL_ROUNDS = env.LLM_MAX_TOOL_ROUNDS ?? 5

这份注册表文件头自己写着：「这是 P7『最小工具循环』的种子，不是终态。 终态是『工具 = 可插拔能力位 + 审批 listener + MCP』」。所以下面只说从种子到终态要动哪一处。

'tool.registered': { pluginId, tools: ToolSpec[] } // 事件（重播整份，不发增量） 'tool.unregistered': { pluginId } // 事件 'tools.list': Record<string, never> // 命令（reannounce 同款） 'tool.execute': { requestId /* = toolCallId */, sessionId, name, arguments } // 命令 loop→宿主 'tool.execute.result': { requestId, ok, content, summary } // 事件 宿主→loop 'tool.approval.requested': { requestId, toolName, summary, risk } // 事件 loop→前端 'tool.approval.resolved': { requestId, approved, reason? } // 命令 前端→loop
③ 会引入三个新问题，必须在这一步一起解决，否则只是把问题挪了位置：
① 超时与孤儿。 宿主服务崩溃 → tool.execute 永远没有 result → loop 卡在 running。 必须给 tool.execute.result 一个超时兜底（失败结果，不是静默）， 否则用户看到的就是「模型一直转圈」—— 与 10-04 崩溃自愈 里修的那个 provider 崩溃是同一种病。
② 审批期间用户停掉这一轮。 用户点了「允许」但这一轮已被 loop.cancel 取消 → 审批结果成孤儿。规则：结果到达时若 A 已释放，静默丢弃（与 nextRound 对未知 B 返回 null 同一处置）。
③ 谁决定 TOOL_ROOT。 今天 loop 用自己插件的 dataDir 算沙箱根。 工具分散到多个插件后，每个宿主服务各自算自己的（它有 dataDir + plugins.readFile）—— loop 手里不该再有路径。这是「拆开之后反而更简单」的一处：沙箱边界随工具的主人走。
④ 之后接 MCP 的位置也就清楚了：MCP server 是一个「宿主服务」， 它的 tools.json 是运行时从 MCP 协议生成的而不是文件里的 —— 所以它走的是同一条 tool.registered 通路，loop 侧零改动。 这就是把工具做成能力位而不是做进 loop 的全部回报。

8不变式与红线（本稿不得破坏）

  • 不新增进程间协议：stdio JSON-RPC + shared 的 EventMap/CommandMap 仍是唯一入口。 本稿新增的 9 个 topic 全部是这张表上的新行，不是新机制。
  • Core 不解析插件内容：prompt 片段 / 技能正文 / 工具 schema 全是内容， 一律经总线与 plugins.readFile，Core 一行都不碰。
  • 凭证值永不过总线、永不进 SSE、永不进日志：新增的任何路径都不得让明文出现在事件里。
  • 「能力存在性」必须有一条重播通路：prompt 片段 / 工具目录 / 技能索引 每一个都要有 *.list 类的重播命令 + 收集方上线时主动问一次。 这是本稿从「provider 启动顺序事故」里学到的最重要一条。
  • 缺失是合法的：不带 prompt 片段 / 不带工具 / 不带技能的插件完全正常。 订阅失败要忽略，不能让装饰性内容打死主链路。
  • 顺序必须确定：同优先级按 id 字典序。同一个系统两次启动得到不同 prompt， 症状是「模型行为随机」，几乎无法排查。
  • 只读工具不需要审批，写 / 网络 / 进程类必须审批 —— 这条今天写在 tools.ts 的注释里，它是技能里 scripts/ 的前置条件，不是可选项。
  • 测试跟着被测物走：loop 的工具 / prompt 测试留在 loop 包； 每个插件自带文件的校验留在该插件包里（照 service-distribution.test.ts 与 plugin-ui-e2e.test.ts 的做法：真构建 → 真 Core → 真请求）。
