对话界面架构

三组件 · 功能拆分服务 · Core 作为总线与桥 · 插件=聚合
一句话：界面 3 个组件（会话列表 / 对话 / 输入）；后端按功能拆成 session、agent、models 三个必需服务 + 若干能力位；Core 是进程管理 + 总线 + HTTP/SSE 桥，且零业务知识。 前端与服务之间只有两条通道：POST /api/command 发命令、GET /events 收事件。

3按功能拆分的服务

参照 pi 的架构文档： pi-ai 不跑工具循环也不存会话，pi-agent-core 不认识 Provider， TUI 不了解 Agent 业务 —— 「循环不知道 API key，TUI 不知道 Provider」。同样的关注点分离：

服务优先级职责（只做这一件）明确不做
session必需 会话 CRUD、消息读写、历史查询、按时间分组、落库不跑对话循环
agent必需 一轮对话的状态机：收输入 → 拉历史 → 调模型 → 工具循环 → 落库 → 取消/停止 不认识 provider、不知道 API key
models必需 provider 路由、wire 翻译、流归一、模型目录、思考强度翻译不跑循环、不存会话
provider:*能力位 各家 wire（openai 兼容 / anthropic / …），独立进程—
credentials能力位 凭证解析（值永不过总线）—
tools能力位 工具注册与执行、审批—
retry / usage旁路 重试、记账（不在成功路径上）—

3.2 对最初三个判断的纠正

最初判断结论理由
会话列表需要「管理会话的服务」对 pi 里 session 文件是唯一真相源，UI 直接读 transcript + 监听 entry_appended，不维护第二份状态
对话框要「接收流式输出 + 输入」半对 流是对的，但它不是一个服务，是 agent 发的事件投影；「接收输入」反了 —— ③ 才是命令来源（写），② 是投影（读），UI 上相邻只是布局
输入框「发送给 llm」错 pi 主路径是 AgentSession → Agent → runAgentLoop → streamFn：输入先进 agent，models 是最末端
（漏掉的）缺 agent 服务 —— 持有「这一轮对话」的全部状态：轮次、in-flight、工具轮数、取消句柄

如果 ③ 直发 models，后果都是具体的：

后果现象
工具调用哑掉收到 finishReason:'tool_calls' 没人执行、没人发第二轮
退化成单轮问答没人拉历史、没人拼多轮 messages
停止按钮无状态源不知道该禁用输入还是该发 cancel
渲染组件被塞进写职责每条消息都要 ② 或 ③ 自己 append 一次
②③ 长得一样重模型 / 思考 / 工具目录每个入口都要实现一遍

4Core：进程 + 总线 + 桥

前端组件
① 会话列表 ② 对话 ③ 输入
↓ POST /api/command（发命令）　　↑ GET /events（收事件）
进程管理拉起 / 健康检查 / 重启 / 崩溃恢复
总线 Bus事件路由 + pattern 匹配
HTTP / SSE 桥前端唯一入口
凭证 store值永不过总线
↓ bus.publish　　↑ bus.subscribe
业务服务（零业务知识的是 Core，反之）
session agent models provider:* credentials tools retry
纪律：Core 零业务知识
Core 里不许出现任何业务词汇 —— 不能有 sessionId、不能有 message、不能知道什么是 provider。 业务全在服务里，Core 只提供「进程 + 路由 + 桥」。有了这条，Core 就足够薄。
Core 不只是「拉起服务的服务」
按字面只做拉起会更复杂：服务之间要各自一套传输、前端要知道每个服务地址、一个服务重启上游引用全失效、事件回放无从谈起。 这四件事（进程 / 总线 / 桥 / 凭证）是一套东西，拆开反而多。

4.2 HTTP 接口（前端唯一能碰到 Core 的地方）

方法路径请求Core 内部谁在用
GET/events?topics=a,b.** query：topics（逗号分隔 pattern，缺省=不过滤） 建 SSE 连接 → 订阅总线 → 按 pattern 过滤后 data: {topic,payload} 逐条推 所有组件（② 订 agent.**,message.**；① 订 session.**）
POST/api/command {topic, payload}，topic 必须在 COMMAND_TOPICS bus.publish(topic, payload) → 订阅该命令的服务 ① 建/改名/删会话；③ agent.run；② session.get
GET/api/preferences—读 dataDir 的 preferences.json设置窗（主题 / 语言 / 插件启用状态）
PUT/api/preferences任意键值 patch合并写盘同上
GET/api/credentials?id= 可选返回掩码列表（sk-…），无明文设置窗 · 凭证区

GET/health—{ok, uptime, services:[{id,status}]}服务状态组件 · 集成冒烟

4.3 服务侧接口：JSON-RPC over stdio

组件看不到这一层 —— 它是 Core 与每个服务进程之间的私有通道。

方向方法用途
服务 → Coreinitialize握手。Core 下发 dataDir、heartbeatInterval、writableDirs；服务回 panes。握手完成前服务 publish 的消息会被丢弃（P2 WS-9 踩过：provider 注册能力必须在握手后）
服务 → Coreevent（通知）服务发事件/命令到总线（bus.publish 的出口）
服务 → Coreheartbeat健康检查（healthCheck.interval）
Core → 服务credentials.getcore:<id> kind 的凭证解析（P4 通道定案）

4.5 一次 publish，多方订阅（不存在「发两份」）

// session 服务里只有这一句：
service.publish('message.appended', { sessionId, message })

// Core 的总线自动扇出给：
//   ① 前端所有订阅了 message.** 的组件（经 SSE 桥）
//   ② 任何 service.json 里 declares subscribes 含 message.appended 的服务

没有「复制一份给 Core」这个动作 —— 服务发布的就是进 Core 的总线，Core 扇出。 若做成「发两份」（一份给列表、一份给 Core 转发），就会出现两个真相源，那才叫复杂度高。

4.6 命令 vs 订阅：判断标准

你要什么用什麼例子
拿数据（要一份当前状态）发命令 + 等 <cmd>.result（请求/应答，requestId 关联） agent 要历史 → session.get → session.get.result
关心变化（状态变了要知道）订阅事件（广播） 会话列表跨窗同步 → 订阅 session.created/updated/deleted

这两条不要混。agent 不需要「订阅所有 session 事件来攒历史」—— 它要历史就发一次 session.get； 会话列表也不需要轮询 —— 变化是广播过来的。agent 只在一个边缘场景订阅 session 事件：会话在它跑动途中被删（session.deleted）→ 提前收尾。

4.7 归属：谁的能力谁存

数据归谁为什么
会话与消息session 服务谁的能力谁存。Core 存 = session 服务变多余，且 Core 重启会丢
「这一轮对话」的进度agent 服务进程内态，重启归零（崩溃恢复 = 发 agent.run.failed）
provider 路由表models 服务能力位注册驱动
凭证Core 的 credentials store值永不过总线；这是 Core 唯一碰业务数据的地方

5插件 = 聚合（一件能用的东西）

插件不是「一个进程」，而是一件能用的东西：一组协同的服务 + 一组协同的组件 + 明确的依赖。 装它 = 拉起 N 个进程 + 出现 M 个组件；卸它 = 全部消失。这与 pi 的形态一致 —— pi-coding-agent 正是把 pi-agent-core + pi-ai + pi-tui 聚合成产品。

5.3 什么该聚合、什么该保持独立

能力归属理由
session + agent + models + 3 组件同一个插件 缺任何一个这个插件都没意义，拆开装没有价值
每家 provider:*各自独立插件 用户可能只要 openai 不要 claude；塞进主插件会导致「卸插件连带卸掉所有 provider」
credentials独立插件（可选依赖） 免凭证的本地端点不该被强塞
tools / 工具包每包一个独立插件 工具生态本身可插拔，一个工具集一个插件

规律：协同才能工作的 → 聚合成插件；可独立取舍的 → 独立插件。 这样既保证「装一件能用的东西」，又不牺牲「存在性由插件决定」。

5.6 代价与风险

风险严重度处置
停插件要停多个进程，其中一个正在跑工具中 停前先发 agent.cancel 走正常收尾，超时才强杀
一个服务挂了，插件状态怎么算低 定义为 degraded，插件详情窗列出哪个服务异常
依赖缺失（装了对话插件但没 provider）中 degraded + 明确提示「缺 provider:X」，不启动失败
现有 6 个插件条目 + 10 个服务要重写为 plugin.json低 机械工作，顺手修掉插件表硬编码

工作量：Core 插件发现 + 拓扑启停 + 状态聚合 + /api/plugins ≈ 1 天； 前端清单改拉 ≈ 0.5 天；迁移重写 plugin.json ≈ 0.5 天。值得做 —— 让插件名副其实，且让依赖在用户层面可见。

思考流（必修）：当前实现里主位的 isDelta(chunk) 不看 blockType， 于是 reasoning 块也被当成正文 token 发 —— 用 deepseek-reasoner 一类模型，思维链会混进回答正文。 修法：给流事件加可选字段 blockType?: 'text' | 'reasoning'（契约纪律「只增不改」允许加可选字段）， 由 models 层标注、agent 转发、前端分流 → ② 的折叠思考块才有数据。不加服务、不加 topic。

待定选项倾向
models 要不要把 provider 拆成独立进程？进程内注册表（pi 的做法）／独立进程 独立进程 —— 「存在性由插件决定」是 ost 相对 pi 的差异，别丢
credentials 内含进 models 还是独立？内含（pi）／独立能力位 独立 —— 「凭证值不过总线」是威胁模型红线
tools 独立服务还是 agent 进程内？进程内 execute（pi）／独立能力位 独立，但最贵（跨进程调用 + 审批流），可后置
