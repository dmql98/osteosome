2TASK-1 · 在 plugin.json 加 requires

T1 manifest 加 requires 字段与 Zod schema 约 30 行零新协议

目标

让一个插件能声明「我需要用户的机器上有什么」，且不写 = 不限。 本任务只加声明，不加任何探测逻辑 —— 探测是 §7 里说的后续工作。

为什么不能从 package.json 自动推导

  • package.json 不进交付物（pack-plugin.mjs 明确排掉）→ 用户根本读不到。
  • pnpm workspace 依赖指向仓库内的工作区包 → 推导出来是噪声，不是运行时依赖。
  • devDependencies 与分发完全无关。
所以它是 manifest 的一等字段，只有真需要的才写。 真正用来「自动发现漏声明」的不是 package.json，而是产物 —— 见 TASK-2。

触点

文件改什么说明
shared/src/plugin-manifest.ts加 schema
加字段		 紧挨 PluginDependencySchema（第 30 行附近）与 PluginManifestSchema（第 86 行起）。 风格照抄 PluginDependencySchema：带文件头的「为什么」注释。
shared/src/index.ts导出与 PluginDependencySchema 一并导出，供测试与 Core 复用。
shared/tests/（或既有 schema 测试处）加用例 见下方判据。

交付物

+ // shared/src/plugin-manifest.ts + /** + * 「我需要用户的机器上有什么」—— 只有 Core 判不了的那部分属于这里。 + * + * ## 为什么不从 package.json 推导 + * package.json 不进交付物（pack-plugin.mjs 排掉），用户读不到；pnpm workspace 的 + * 依赖指向仓库内的工作区包，推导出来是噪声。真正的对账对象是**产物**里的 require， + * 见 pack-plugin.mjs。 + * + * ## 为什么只有这两种 kind + * 「需要某个原生模块」不是依赖、是**运行环境的能力** —— 能 bundle 的必须 bundle + * （service-distribution 那条守卫在强制），不能 bundle 的应该走 dependencies[] 或总线。 + * 否则这条声明只是「我需要 X」而没法说明「谁提供 X」，是一条无法兑现的承诺。 + * + * ## 缺省纪律 + * 不写 = 不限。理由与 coreCompatibility / dataReadableBy 相同： + * 「没声明」永远是安全的缺省，现有插件零改动就能过。 + * + * ## 它只能是数据 + * 一旦允许写检查逻辑（如 "check": "git --version && ..."），就是给插件在 + * Core 进程里执行任意命令的能力 —— 既打破「Core 不解析插件内容」，也是个洞。 + */ + export const RequiresSchema = z.discriminatedUnion('kind', [ + z.object({ + kind: z.literal('node'), + /** 版本区间。留空 = 只要「有 Node」 */ + version: z.string().optional(), + why: z.string().optional(), + }), + z.object({ + kind: z.literal('executable'), + name: z.string().min(1), + /** 先只做存在性。版本区间要引入「输出怎么解析」，那是个 DSL —— 等真需要再加 */ + version: z.string().optional(), + /** 人话原因，直接显示给用户：「缺少可执行程序 git（用于：读写仓库快照）」 */ + why: z.string().optional(), + optional: z.boolean().default(false), + }), + ]) + // PluginManifestSchema 里加（紧挨 coreCompatibility） + requires: RequiresSchema.array().default([]),

判据

  • 缺省即不限：{ id, name, version } 三个字段的最小清单能过 schema，且 parsed.requires === []
  • 两种 kind 都能解析，且 optional 缺省为 false
  • requires: [] 与「字段完全缺失」结果一致（两条都过）
  • 缺 name 的 executable 被拒；未知 kind 被拒
  • 关键 未声明字段会被 Zod 剥掉：手写一个 requires 但 schema 没加时，解析结果里查不到这个键 —— 补一条断言守住这条
  • 现有四个 plugin.json（models / chat-workbench / reliability / workbench）全部仍能解析，且解析结果与改动前逐字段相等（零改动）
  • pnpm -r run typecheck 零错 · pnpm -r run test 全绿 · node scripts/smoke.mjs PASS

明确不做

  • 任何探测逻辑（不 spawn、不查 PATH、不读 process.versions）—— 那是后续任务
  • 不映射成新的插件状态：不满足时将来映射到 degraded，本任务只加字段
  • 不加 kind: "module"（理由见上方注释与 §7）
  • 不解析 version 区间做判定：字段先留着，语义留到真需要时再定
  • 不给现有插件补写 requires：先证明零插件也能过

风险

主要风险是「加了一个没人用的字段」。 缓解：判据里那条「四个插件逐字段相等」保证它不改变任何现有行为， 而 TASK-2 会立刻给它一个消费者。
次要风险：Zod 剥字段那条容易漏 —— 它与 ui / coreCompatibility 当初踩的坑是同一个， 所以补了断言。

3TASK-2 · 产物对账守卫

T2 打包时检查产物里的外部 require 阶段 A 可立刻做保护生态

目标

让 pnpm pack 在产物不合法时当场失败并说清哪里不对， 而不是产出一个「看起来合法」的目录。

为什么这条最该先做

「拷走就能跑」这条性质极易被无声破坏。 哪天有人在 build 脚本里加一个 external，或者某个依赖改成了动态 require， 产物会安静地退化成「在仓库里能跑、拷出去不能跑」—— 因为 Node 会向上逐级找 node_modules， 在仓库里一路找到 pnpm 的那份；拷到用户机器上没有 node_modules，于是 Cannot find module。
而报错发生在用户点发送的那一刻，不是构建的那一刻。
现有守卫（service-distribution.test.ts 第 3 条）能抓住，但它在 OST 的 CI 里 —— 第三方插件作者不跑你的测试文件。所以要把规则挪到所有人都跑得到的地方：打包流程。

触点

文件改什么说明
core/tests/service-distribution.test.ts抽出函数 把第 3 条（line 69-76）里那段正则抽成可复用函数， 测试与打包流程共用同一个，不要各写一遍。
scripts/pack-plugin.mjs加一条 preflight preflight()（line 158 起）里加一项「扫每个 dist/server/<sid>/index.js」。
顺手：它现在只查文件存在性，注释已经写明「不管清单的语义校验」—— 这条不属于语义校验，属于「拷走能不能跑」的机械前提，所以不违反那条纪律 （该纪律针对的是 schema / protocolVersion / topic 白名单那类）。
core/tests/pack-plugin.test.ts加用例 见下方判据。

两阶段的判定规则

// 阶段 A —— 不依赖 TASK-1，立刻可做 产物里有任何非 node: 前缀的 require → 报错 // 阶段 B —— TASK-1 之后，把「一律禁止」放宽成「没声明才禁止」 产物里有非 node: 前缀的 require 且 它不在 manifest.requires 里 → 报错 （为将来的 external / 原生模块场景留出口） // 实测基线（四个插件 / 五个服务的产物，应当全部通过） llm 220 KB require 3 条 非 node: 前缀 0 条 loop 236 KB require 8 条 非 node: 前缀 0 条 session 225 KB require 6 条 非 node: 前缀 0 条 llm-provider-openai 240 KB require 6 条 非 node: 前缀 0 条 llm-retry 222 KB require 3 条 非 node: 前缀 0 条
白名单的有效范围只有 node: 前缀这一条。 现有测试里那个 && r !== 'node:util' 分支是死代码 （'node:util'.startsWith('node:') 本来就为真）。抽函数时可以顺手清掉， 但注意副作用：若将来某个依赖吐一个裸 require('path')， 它会被判成外部依赖 → 假红。方向是安全的（烦人而不危险），但要在注释里写明。

判据

  • 阶段 A：四个内置插件的 pnpm run pack:plugins 全绿（实测基线：五个产物 220–240 KB，外部 require 均为 0 条）
  • 反向用例：造一个含 require('lodash') 的假产物 → preflight 必须红，且错误信息指出哪个插件的哪个服务缺了什么
  • 反向用例 2：改成动态 require(v) → 阶段 A 抓不到（静态扫不出来），用例要如实体现这一点，不许假装能抓
  • 打包失败时逐条列出全部问题（沿用现有 preflight 的行为：打包失败通常不止一处，逐条改比逐次重跑快）
  • verifyOutput() 复用同一函数（它现在也调 preflight，所以自动覆盖输出目录）
  • 阶段 B：requires 里声明了那个包 → 放行；没声明 → 红
  • pnpm -r run typecheck 零错 · pnpm -r run test 全绿 · node scripts/smoke.mjs PASS

明确不做

  • 不引入新的依赖：检查用手写正则（与现有守卫一致），不为了这件事加 eslint 插件或 depcheck
  • 不做真正的 load() 验证：那属于 ost doctor 的范围（见 §4）
  • 不检查 index.js.map：打包已经排掉 *.map，产物里不会有
  • 不把规则复制进 Core：Core 装不上时靠 scanPlugins 报，这一条只管发布前

风险

风险缓解
抽函数时动了现有测试，导致 service-distribution 那四条的行为悄悄变了 抽完先单独跑那一个测试文件，确认四条全绿再动 pack-plugin.mjs
误报打断别人的正常发布 阶段 A 只在真有外部 require 时才红；实测基线是 0 条。 若将来某个依赖升级导致误报，阶段 B 就是那个出口（声明即放行）。
「打包时过了但拷走还是不能跑」 本规则不是那个问题的充分条件 —— 静态扫抓不到动态 require。 真正端到端的证明是 service-distribution 第 4 条（拷到空目录真跑一次）， 而它只对内置插件生效。这就是 §4 里 ost doctor 存在的理由。

4相关但不在本文件（避免重复开工 / 重复设计）

项为什么不做要点（已设计，位置见 §7）
Core 级 Node 版本检查范围不同 插件化架构优化.html §5 P8 明写「要求用户机器上有 Node ≥ 24」， 而实测 engines、.node-version、.nvmrc 全都不存在， 且零检查。那是应用级前置条件，应该由 Core 判一次，而不是让每个插件各写一遍。 改一个文件，消掉「用户装完根本起不来但不知道为什么」的最坏故障。优先级高于这两项。
ost doctor <plugin-dir>依赖探测 七步自检器（清单 → 产物 → Core 版本 → 插件依赖 → requires → 真的 spawn 一次 → 人话报告）。 要复用 scanPlugins 与同一个 preflight，不另写一套 —— 否则会出现「doctor 说能装、Core 装不上」，那比没有 doctor 更糟。
requires 的实际探测后续 扫盘期只做零成本检查：node 版本字符串比较 + PATH 目录扫描（existsSync）代替 spawn —— scanPlugins 是同步的、在 Core 构造期调用， 在里面 spawn 4 个插件 × 2 个 CLI × 1.5s ≈ Core 启动卡 12 秒， 而某些 Windows 环境的 CLI 会弹 GUI 框卡死 30 秒。
能力位冲突检测生态成熟后 llm.provider.registered 的 provider 字段是全局命名空间， 而 routes.set 是幂等覆盖 —— 两个插件都注册 deepseek 会互相覆盖， 用户看到的现象是「我装了个插件，结果模型行为变了」。 今天只有一个插件会注册 provider，先不做，但要记下来。
一句话串起来：这两项只解决「怎么声明」和「怎么发现漏声明」， 不解决「怎么在别人的机器上验证真的能用」—— 后者是 doctor 的活。
而准确的目标表述始终是：把「不可发现的问题」变成「可发现的问题」，而不是消灭问题。
