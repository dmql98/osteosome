三条职责边界

Core 做什么
扫盘、起服务、搬运静态产物、把命令路由到总线、持有偏好与凭证。
Core 不做什么
不解析插件内容（不认识 catalog.json 里哪一家是哪家）；不新增进程间协议；不管理插件 UI 的内部路由。
插件 UI 做什么
在自己的 iframe 里渲染界面，通过 Core 的四条通路拿数据、发命令、订阅事件。

widget 与插件 UI 的关系：形态 1（一个插件多个视图）

widget = iframe(插件 UI 的一个命名视图)。一个插件的 UI 是一个应用，内部按 hash 切视图， plugin.json 声明它有哪些视图。这样现有「多个组件在同一面板自由拖动摆位」的体验完整保留：

"ui": { "views": [ { "id": "widget.session-list", "title": "会话", "entry": "index.html#session-list" }, { "id": "widget.chat-timeline", "title": "对话", "entry": "index.html#chat-timeline" }, { "id": "widget.chat-composer", "title": "输入", "entry": "index.html#chat-composer" } ]}
代价：同一插件的多个 iframe 之间看起来要共享状态。P6 收尾时的结论是：不需要。
先问「哪些状态真的需要跨？」—— 答案只有 curId，用 sessionStorage + storage 事件共享（按 origin + 顶层浏览上下文隔离，正好是「一个窗口一份、三个 iframe 共享」）。 其余状态（会话索引 / 历史 / 在途行 / sending / failed）每个 iframe 各自从 Core 的 SSE 事件流重建 —— 每个事件自带 sessionId + requestId， 按 curId 过滤即可。所以 BroadcastChannel / postMessage 一个都没用上， Core 也不知道 curId 这个概念。

P6 验证过的两件事：workbench 的六个视图一个都没碰这条 —— 它们要的信息全部来自 Core （/health、/events、preferences），而 iframe 与宿主同源，直接调就行； chat-workbench 的三盒确实是「共享客户端状态」那一类（② ③ 原本零直接通信、靠 pinia 单例同步）， 而拆开之后才看清 pinia 单例只是把「同一份数据」做成了「同一个对象」， 掩盖了「这些数据本来就有多个独立副本的来源」。
「需要通信」不是多视图的必然，是多视图之间共享客户端状态才需要；而即便共享，也先看看能不能各自重建。

services/、ui/（源码）；package.json、tsconfig*.json、pnpm-lock.yaml（构建元数据）； node_modules/；.data/（运行期数据，不随包走）； *.map —— Core 用 node index.js 启动、没开 --enable-source-maps，运行期读不到， 却占交付物约七成体积，还把源码原文带出去。
开发 vs 分发
差别只有一处 —— --plugins 指向哪：
开发 node core/dist/main.js --plugins ./plugins ／ 分发 node core/dist/main.js（全缺省）
打包
pnpm run pack:plugins（全部）／pnpm --filter '@osteosome/plugin-models' run pack（单个）
→ scripts/pack-plugin.mjs 装配上面那个目录（跨平台，不依赖 shell）。 先不做 tar/zip，目录本身就是交付物。
注意 必须带 run：少写 run 时 pnpm --filter … pack 命中 pnpm 内置的 pack，在仓库根生成一个 osteosome-plugin-<id>-1.0.0.tgz —— 里面是全部源码，跟交付物没关系，别误用。
安装
拷贝 + 五条校验，难的不是拷贝而是「装坏了要说清哪里坏了」。这五条全部已在 Core 扫盘期 scanPlugins 里实现，各有测试；pack-plugin.mjs 不复制这套规则，只做 装配前「产物齐不齐」预检 + 装配后对输出再跑一遍同一套（失败即删除重来）， 真正的验收证据仍是把产物交给 scanPlugins 跑一遍：
① plugin.json 过 schema（含 ui 与 coreCompatibility）
② 产物存在性：services[] 每项都要有 dist/server/<sid>/index.js； 声明了 ui.views 却没 dist/ui/index.html → degraded「未构建」
③ service.json 的 protocolVersion 兼容（manifest.ts 已有校验）
④ coreCompatibility 满足（见 P2）
⑤ publishes/subscribes 必须在 Core 侧 EventMap/CommandMap 里（已有校验）
这一轮真正修掉的
三个只有真去打包才会暴露的问题：
① shippable 一度把 dist/ 整个排进黑名单（只想排源码），于是 preflight 全绿、 输出零产物 —— 「检查通过」和「东西在」被写成了两套规则；
② services/session/.data/sessions/ 下 234 个会话文件混进交付物，根因是 services/session/src/index.ts:13 的 service.dataDir || process.env.DS_DATA_DIR || '.data' —— 相对路径回退，构建时落进 dist/。.data/ 已在过滤器里挡掉， 但这个回退本身仍应改成绝对路径或启动即失败（未动，另行处理）；
③ scanPlugins 对发行版必然报「services 在插件内没有对应目录」—— 源码侧检查没区分「有 services/ 源码树」与「只有 dist/ 的交付物」。 已修：源码侧检查只在源码树存在时跑（plugin-registry.ts）。 装好了却报错，比装坏了更难查，因为没人会去查一个正常的东西。
升级 / 回滚
覆盖安装前把旧目录改名 <id>.bak-<旧版本>，装完不删；新版本起不来就改回去。 不做同 id 多版本共存 —— preferences.plugins.uninstalled[id] 这类状态全按 id 存，多版本会打架。 <id>.bak-* 不带 plugin.json，不会被扫盘当成第二个插件。
后置（明确不做）
zip 解包 + plugin.install 命令（解包时的路径校验沿用 static.ts 那套 zip-slip 防护）； 远端源 / 签名校验。等真有人要装第三方插件时再说。
仍需说清的限制
高 这套分发仍要求用户机器上有 Node ≥ 24（Core 自己就是 Node 跑的）。 要免掉 Node，就得把 Core 也打成单文件二进制、或塞进 Tauri sidecar —— 那是另一个题，不在这份计划里。

6风险与代价台账

项代价缓解
开发体验掉档现在 pnpm dev 一下全热更新；之后改一个插件 UI 要单独 build + 起那个 dev server各插件 UI 的 dev 走 watch 模式；Core 已有 rescan() 可在插件产物变化后重扫
bundle 体积重复每个带 UI 的插件一份 vue（models / workbench / chat-workbench 各一份）P6 已做，且比预案便宜：组件与令牌进 @osteosome/ui， 各插件从源码引 —— 产物里仍有各自的 vue（这是 iframe 共享不了内存的必然）， 但「组件与样式只有一份源码」这件事被守住了。
踩过的坑：组件库一旦做 vite lib build，就等于给每个消费者塞一份 vue（94 KB 产物 vs 44 KB 源码）。 症状是双份 vue 实例 → Cannot read properties of null (reading 'ce')。 处置：组件库不产运行时产物。
跨 iframe 状态单例 store 失效；② ③ 零直接通信的架构要换传输层。workbench 六个视图不碰（信息全来自 Core），这条只在 chat-workbench 三盒兑现P6 已解决，且解法是「不引入传输层」：唯一需要跨的 curId 用 sessionStorage + storage 事件（按 origin + 顶层浏览上下文隔离，正好是「一窗一份、三 iframe 共享」）； 其余状态每个 iframe 各自从 SSE 事件重建（事件自带 sessionId + requestId）。
当初担心的「多一层通信就多一处『消息丢了页面不报错』的排障地」因此没有发生 —— 因为根本没有新增通信：三个 iframe 各自跟 Core 说话，而 Core 本来就在广播。
坑：storage 事件不在写入方触发，写入方必须本地先赋值再写盘
构建 / 分发流程缺失源码与产物混放，dist/ 被 gitignore；发行物此前根本不存在已解决：P2 定了「Core 只认 dist/」，P8 给出 pnpm run pack:plugins → pack/<id>/，并由 scanPlugins 复验。
仍开放 升级 / 回滚只有一条手工规程（改名 <id>.bak-<版本>），没有工具；zip 与安装器明确后置
theme / i18n 跨 bundleCSS 变量与文案要各自保持一致；Core 的 i18n 机制对插件 UI 无效theme 已解决：令牌在 @osteosome/ui，各插件引同一份源码（同源 iframe 读同一份 preferences.json 的 ui.theme）。
i18n 各带一份是必然 —— 跨 iframe 拿不到实例。但宿主那份必须摘干净： P6 把 settings.* 从 client 的 i18n 里删掉，插件那侧留自己的。 留着就是一份没人读的第二份文案，且没人会发现它已经过时
迁移期双份代码client 与插件各一份 UI直接替换而非并行；每个组件搬完即删 client 侧。 P6 结算：搬 workbench 时真的差点留下双份 UI —— 因为 Button 等组件宿主自己也在用。 靠「宿主注册表里不再有这六个 id」与 registry.test.ts 的反向对账守住； 组件本体则收进共享包，从根上消除「两份」这个选项
分发仍要 NodeCore 是 Node 进程，插件服务也是 node index.js —— 用户机器上必须装 Node ≥ 24接受（与现在同要求）；要免 Node 就是另一个题（Core 也打成单文件 / 塞进 Tauri sidecar）
安全面插件 UI 在 iframe 里同源调用 Core 全套 API不退步：现在整个 client 也是这个权限。Core 的 Origin 白名单已允许自身 origin
Core 契约变更改 /api/command 的 topic 名、/api/preferences 的键、/events 的 payload 形状，对已分发的插件都是破坏性变更这些名字都在 shared 的事件表里；破坏性变更要配 coreCompatibility.min 抬版本号，而不是悄悄改

7不变式（重构中必须守住）

  • 不新增进程间协议：stdio JSON-RPC + shared 的 EventMap/CommandMap 白名单校验仍是唯一入口（service-manifest-sync.test.ts 继续拦漏声明）。
  • 凭证值永不过总线、永不进 SSE：插件 UI 也只能通过 /api/credentials 写，读走 Core 内部。
  • 偏好写入仍要单一所有者：usePreferences.patch 是浅合并，写 llm 就是整层替换 —— llm.vendorOverrides / enabledModels / connectedVendors 三个字段必须一起写、且只有一个写入点（LlmSettingsView.vue:474）。搬到插件 UI 后这条纪律照旧。
  • 模型清单只有一份：plugins/models/catalog.json，服务与 UI 读同一份；shared 不再持有它。
  • UI 组件与设计令牌各只有一份源码（P6）：在 @osteosome/ui。宿主与所有插件 UI 从源码引， 由各自的打包器处理 SFC —— 于是 vue 运行时在每个 bundle 里只有一份， 而「改一次按钮样式要记得改两处」这件事不存在。
    产物形态：组件库不产出运行时产物（exports 指向 src/*.vue）。 这不是省事，是必需的 —— 一份 lib bundle 会把 vue 也打进去，每个消费者各得一份实例。
  • 共享 UI 组件是纯展示的：props 进、事件出，不 import store、不 import core-client、不自己 fetch。 这条边界是它能被插件直接用的前提；需要取数的部分属于插件视图。
  • 一个 widget id 不能同时出现在 components[] 与 ui.views[]： 客户端不知道该用本地实现还是 iframe，而两者都能渲染出东西。
  • Core 不解析插件内容：只搬运字节，不认识 catalog.json 里哪一家是哪一家。
  • 服务只写自己插件的数据根 userData/plugin/<pluginId>/（Core 算好传下去，见 §4）；Core 自己的在 userData/core/。
  • Core 不解析插件数据的内容与格式 —— 它只给插件一个目录、并在 HTTP 层搬字节。目录约定只有「你有一个属于自己的目录」这一条；里面放什么是插件的事。这是「Core 不解析插件内容」那条不变式的直接延伸。
  • 插件数据的写权限只属自己；读别人的要在 plugin.json 的 dataReadableBy[] 里声明。权限边界靠机制而不是约定。
  • 「Core 不知道插件存在」这条要守住：ServiceManager 只收一张 serviceDataDirs 查表与 allowedServiceIds，不 import 任何插件概念。

8待决问题

问题选项与影响
同插件多视图的状态共享用什么
← P6 已决：什么都没用上		最终答案：不引入任何消息层。先问「哪些状态真的需要跨 iframe？」， 答案是只有 curId —— 其余（会话索引 / 历史 / 在途行 / sending / failed） 每个 iframe 都能各自从 Core 的 SSE 事件流重建，因为每个事件自带 sessionId + requestId，按 curId 过滤即可。 服务端事件流本来就是那个共享层，只是它一直在那里而没人注意到。
curId 用 sessionStorage + storage 事件： 按 origin + 顶层浏览上下文隔离，正好对上「一个窗口一份、三个 iframe 共享」的语义， 刷新后还在，且零新增协议。
已排除的选项：BroadcastChannel 是全应用广播，Tauri 多窗口下会互相抢 curId （curId 语义是「各窗独立」，P3 §3.4）；postMessage 要维护引用与握手； 「共享状态提到 Core 侧」会让 Core 知道「会话」这个概念，与 §7 冲突。
注意：storage 事件不在写入方自己触发，所以写入方必须 本地先赋值再写盘，否则那一下点击没反应。
components 字段的归宿
← P6 已定		P6 的实践给出了答案：不删，也不派生，而是把两个字段的职责分开 —— components[] 声明归属（插件停用时把这个本地组件一起藏起来）， ui.views[] 声明形态（它是插件页面，走 iframe）。 两者互斥。
为什么不是「Core 派生」：派生意味着 Core 要知道「哪些组件是本地的」—— 而 Core 对前端组件一无所知（§7「Core 不解析插件内容」的直接延伸）。 写清单的那一方才知道这件事。
旧 widget.* id 的迁移窗口
← P4 已决：不需要映射表		最终答案：两种方案都没用上。 因为 P4 决定 id 不加命名空间 —— 插件视图仍叫 widget.llm-settings， 和它顶替的本地组件同名。id 是 params.widgets[] 与 layout[id] 的持久化主键， 改名 = 用户拖好的位置全丢；同名 = 组件在原地换了实现，零迁移。
真正需要的不是映射表而是退役表（RETIRED_WIDGETS，记标题与 replacedBy）： 删掉一个组件等于让用户的布局悄悄少一个框，占位要说清它叫什么、为什么没了。widget.llm-providers 是第一个进表的。
插件 UI 的开发模式怎么起构建期已定（P5 / P6）：每个插件一个独立 vite 包，base 命名空间化 /plugins/<id>/ui/，产物落 dist/ui/ 由 Core 伺服。 仍未定的是热更新那半：每个插件一个 vite dev server + Core 反代（改动最小）／ 一个 vite 多入口（统一端口，但要处理模块重复与 HMR 边界）。 建议前者 —— 见 §6「开发体验掉档」，这是那份代价里唯一还没兑现缓解的部分。
plugins/credentials 插件的定位
← P1 没定，仍然开放		凭证归使用方插件之后，这个「凭证能力位」插件还剩什么。 退休（服务已有 dataDir，自己读文件）／ 转型成「帮用户管理各插件凭证文件格式」的库。 前者更干净，后者保留一个跨插件统一的凭证视图（但那又回到 Core 集中管密钥，与 §4 冲突）。 现状：既没退休也没转型 —— 它还在，纯服务无 UI，/api/credentials 与 credentials.resolve 都在服役（§3、§7 仍依赖）。 建议退休，但那是独立的一刀，不该塞进任何已完成阶段的收尾里。
发行方式还没定§4 已标「待确认」，指的是 OST 这个应用怎么发。 P8 只解决了其中一半：插件这一层的交付物已经是确定的（一个目录，pnpm run pack:plugins）。 剩下的仍是「应用怎么装」：免安装 zip（可写、升级不覆盖数据、用户能找到）／ 安装器（能写 Program Files， 但数据要么退回用户目录、要么给安装器分配权限）。建议免安装 zip， 并把「发行版判据」（exe 同级的标记文件）一起定下来，否则开发期与发行期数据会分叉。
Core 版本号怎么定已在 P2 定：Core 用 0.1.0，从自己的 package.json 读（不 import —— import 会把版本冻在打包那一刻）；读不到退 0.0.0 并告警。插件声明 coreCompatibility: { min, max }，不写 = 不限。剩下的政策问题：将来破坏性变更时，是抬 Core 的 minor 还是 major —— 建议抬 minor 并同步抬依赖它的插件的 min。
